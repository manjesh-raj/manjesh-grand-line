- **The console** (`main.swift` -> `ConsoleController`) hosts a **dynamic tab collection**, not a fixed two-tab enum. Tabs are `[TabModel]` (`TabModel.swift`), each owning a `CockpitTerminalView` + a `TabLaunch` (re)start recipe, rendered as `TabChipView` chips in a growing tab bar. Supports **new** (the "+" button), **duplicate** (right-click a chip; re-runs the same argv), **rename** (double-click / right-click; name is per-tab and never touches the process), **close** (a chip's own "×", or right-click; closing the last tab opens a fresh shell so the window is never empty), and **reconnect** (right-click; restarts the tab's process from its launch spec). All of this used to also be reachable via a top-level **Tab** menu (`⌘T`/`⌘D`/`⇧⌘R`/`⌘W`/`⌘R`/`⌘1`…`⌘9`) and zoom/theme via a top-level **View** menu - both are gone now (`fm/grandline-console-tabs-restore-tabmenu-fix`, see "## Menu bar"): every capability above is still reachable from the tab strip itself, and zoom lives on the Console toolbar / Settings' font-size presets, but none of those keyboard shortcuts work anymore. `ConsoleController.openFirstmateHost()` opens the built-in Shell + Mirror pair; `loadView` calls it at startup so the app still lands there by default, and it is also the pinned Hosts-sidebar entry's connect action (see below). This is Phase 0 of the connection-manager work (design: `data/cockpit-ssh-manager-research/report.md`, Section A4/A5 + D Phase 0). Later phases add the dashboard + embedded backend (P3) and packaging/signing (P4); the console stays backend-free.

- **`fm/grandline-remove-session-logging` deleted the session-logging ("record") feature outright** - the captain's call; it is gone, not hidden or defaulted off, so nothing below should be re-added without a fresh decision. What went: the Console toolbar's `record.circle` button and its `⌘⇧L` / Tab-menu "Toggle Session Logging" item, `ConsoleController`'s `toggleLoggingForActiveTab`/`startLogging`/`updateLogButton` and the `defaultLoggingEnabled` auto-start, `CockpitTerminalView`'s `startLogging(to:)`/`stopLogging()`/`isLogging` **and its whole `dataReceived(slice:)` override** (session logging was that override's only reason to exist - anything wanting a host-bytes choke point again has to re-add it, see `LocalProcessTerminalView.dataReceived` in the vendored SwiftTerm), `AppSettings.sessionLoggingDefault` plus its `fm.sessionLoggingDefault` `UserDefaults` key and the `FM_LOG_SESSIONS_DEFAULT` env var, Settings > Terminal's "Log sessions by default" row, and `BackupSettings.sessionLoggingDefault`. Two things worth keeping:
  - **Dropping an optional field from the `.glbackup` bundle needs no `formatVersion` bump, in the same way adding one already didn't** - `JSONDecoder` ignores a key the struct no longer declares, so a bundle a captain exported from an earlier build still imports with its now-unknown `sessionLoggingDefault` simply discarded. That direction is now pinned by a permanent `BackupSelfTest` case (`FM_RUN_BACKUP_TESTS=1`) that injects the removed key into a real encoded bundle's JSON and asserts the decode succeeds *and* that the injected bytes genuinely carried the key, so it cannot pass vacuously.
  - **The Console toolbar has no leftover hole**, measured rather than eyeballed: the record button was the *last* item in `HelmPageToolbar`'s trailing group, so the remaining controls just shift right and the group still ends flush at the same trailing inset (real off-screen renders across all 12 themes, plus a before/after geometry sweep - trailing-most control at maxX 1390.5 both before and after, every inter-button gap 4.0pt). Two probe readings that look like defects and are **not**: one gap measures 3.5pt rather than 4.0 (the labelled "Compose" button resolves to a non-integral 90.5pt width - sub-pixel rounding, identical on the pre-change build), and `SRELeadStatusPill` is 24pt tall next to the 28pt icon squares (by design, also identical pre-change). Settings' Terminal card genuinely collapsed: the gap under its last row went 104pt -> 22pt, i.e. the card no longer reserves the removed row's height.
- Every tab is a `CockpitTerminalView` (the P1 paste-hardening `LocalProcessTerminalView` subclass - do not touch its paste override; it is what makes screenshot-paste-into-Claude work). Terminals fork their child **in-process** via `startProcess`, so there is no websocket byte-pump and no per-keystroke round trip.
- **Scrolling:** SwiftTerm 1.15's `scrollWheel` already scrolls normal-screen buffers smoothly and content-wise (accumulates precise trackpad deltas -> whole lines 1:1, no page-jumps; `scrollSensitivity` default 1.0), so shell tabs feel like WezTerm with no extra code. Each terminal gets a **10,000-line scrollback** via `term.terminal?.changeScrollback(...)` (SwiftTerm default is 500).
- **The Console's firstmate host has exactly one tab now - a plain login shell - and the whole embedded-herdr concept is gone (`fm/grand-line-remove-firstmate-mirror`), superseding everything below about a "Mirror"/"Herdr" tab.** History, in order: PR #291's E1 (`fm/grand-line-audit-fixes`) had already collapsed a much larger tmux/herdr "Mirror" abstraction (`TmuxMirror`, `HerdrMirror`, `FirstmateBackend`'s resolution machinery, `mirrorTarget()`, `MirrorSession`, `TabLaunch.mirror(kind:target:)` - all deleted then) down to `HerdrSession.swift`: a bare `herdr` client (no args) opened as a second tab named "Herdr" alongside the Shell tab, plus a real-pixel display-gating fix (`CockpitTerminalView`'s "Display gating" section, still present and unrelated to this bullet - it suspends/throttles *redraw* for any tab that isn't on screen, and stays fully intact) meant to fix the resulting battery drain. It didn't fully fix it: the captain reported that even with that fix live, manually killing the herdr session process himself still measurably dropped the app's Energy Impact - meaning the live herdr-attach process and/or its continuous stream-parsing kept costing something regardless of redraw visibility. Rather than chase that further, the captain decided to remove the whole embedded-herdr capability outright: he watches/drives firstmate's own herdr session in his own terminal (WezTerm/iTerm) now, never inside this app. **Gone, do not reinstate without a fresh captain decision**: `HerdrSession.swift` entirely, `TabLaunch.herdr(executable:cwd:)`, `ConsoleController.connectHerdr`, the herdr-tab creation half of `openFirstmateHost()` (now opens only the Shell tab), `sendToFirstmateMirror(_:)`/`FirstmateMirrorSendResult` (F7's unaddressed "Message first mate" composer, which only ever existed to type into that tab - the header button, `AppShellController.sendToFirstmate`/`messageFirstMateFromMenu`, `FleetGeneralMessageOutcome`, and `⌘K`'s "Message First Mate" action all went with it; F7's *per-task* Reply, which shells out to `bin/fm-send.sh` and was never Mirror-dependent, is untouched), Console's "Claude usage" toolbar popover (`utilizationButton`/`ConsoleController`'s own `QuotaUsageController` instance - it was gated to the herdr tab only and had no other trigger; `QuotaUsagePopover.swift`/`QuotaData.swift` themselves survive, since `FleetController`'s Morning Briefing card has its own independent `QuotaUsageController` instance for the `.quota` deep link), and the herdr-tab-only mouse-selection-routing mechanism `CockpitTerminalView.prefersLocalSelection` drove (`fm/grandline-console-selection-contrast-followup`'s whole `mouseDown`/`mouseDragged`/`mouseUp` override block, plus its dedicated `TerminalSelectionRenderSelfTest.swift`) - dead code once nothing ever sets `prefersLocalSelection = true`, deleted rather than left inert. **Both of those last two came back, deliberately and re-scoped - see the `fm/grand-line-shell-tab-local-selection` bullet below**: the routing was never herdr-specific in substance (only in which tab kind opted in), and the captain's own decision put it on `.shell` tabs instead. Nothing else in this list has returned. `childEnvironmentDict()` still strips the `HERDR_*` env vars from every child process this app forks (Shell, ssh) - that's defensive hygiene against a captain running `herdr` *inside* one of those tabs, not something tied to an embedded herdr client, so it stays. `herdr` itself is still a real CLI this app knows about in one place: the Updates page's software checklist (`UpdatesData.swift`'s `.herdr` case) still checks/updates it via Homebrew, since the captain still runs it by hand.

- **Text selection is a *pair*, it is drawn by two independent mechanisms, and `FM_RUN_CONTRAST_TESTS`' `checkTextSelectionContrast` sweeps both across all 14 themes (`fm/grandline-text-selection-contrast-audit`).** The captain reported selected text in the Console rendering as a muted dark red on a dark blue block in light mode. Three things worth carrying forward:
  - **The two mechanisms do not share code and a fix to one covers nothing of the other.** The terminal pairs SwiftTerm's `selectedTextBackgroundColor`/`selectedTextForegroundColor`, filled from each theme's `selectionHex`/`selectionTextHex` by `HelmTheme.apply(to:)`; everything else goes through `HelmSelection` (`HelmInput.swift`). The terminal's own pairing is only real while the *vendored* `AppleTerminalView.buildAttributedString` still overrides a selected run's `.foregroundColor` - a SwiftTerm re-sync dropping that line would leave every selected run in its own ANSI colour on the selection fill, which is exactly the reported shape and which no colour value in this app could detect, so it is guarded as **source** by `checkVendoredTerminalPairsSelection`.
  - **`HelmSelection`'s fill is opaque now, and the measurement is why.** It shipped as `accent.withAlphaComponent(0.35)`, and a translucent fill's *effective* colour - therefore the contrast of the ink drawn on it - depends on whatever surface happens to be underneath. Measured: on Daylight that composites to `#B3C0E3` over a field and to a near-navy over §6.13's dark terminal card, and **no single foreground clears 4.5:1 on both** (the best available lands at 1.94:1 on one of them). Flattening it to an opaque colour is the same reasoning `HelmTheme.apply(to:)` already records for the terminal's own `selectionHex`. `HelmSelection.alphaLadder` then steps the wash up only where the flattened fill would not separate from the surfaces it sits on (`minimumSurfaceSeparation`, 1.35 - a visibility floor, deliberately *not* a WCAG number; only `solarized-light` needed a rung, at 0.42).
  - **The real defect was coverage, not the recipe.** Only 3 of ~13 app-owned `NSTextView`s ever called `HelmSelection.apply` - the rest were left on AppKit's own selection, which paints `NSColor.selectedTextBackgroundColor` behind the run **and sets no `.foregroundColor` at all**, so the text keeps whatever colour it already had (a severity red, a tinted token, a link) on a system highlight that knows nothing about the active theme. That pairing is unbounded by construction. All of them are wired now, and `checkEveryTextViewIsThemed` fails the build on a file that creates an `NSTextView` without reaching `HelmSelection`. A *selectable* `NSTextField` needs no per-site work: AppKit lends it the window's shared field editor, which `HelmFocusSensing.refresh()` already repaints on every first-responder change.
  - **`HelmContrast.legible`'s endpoint choice was wrong and its own doc comment said so.** It claimed to evaluate both endpoints and actually picked one from `relativeLuminance(surface) > 0.35`; the real crossover where black and white score equally is **0.179**, so any surface in `(0.179, 0.35]` was corrected toward white when black had the headroom, and could terminate at pure white still below the floor with nothing reporting it. Fixed to compare both. `HelmContrast.legibleOn(fill:preferring:)` is the new *guaranteed* variant for an opaque fill this app chose (max(black, white) against any colour is never worse than 4.58:1, so the search always terminates at or above the floor) - `legible` cannot promise that for an arbitrary caller, which is the documented `legible(.white, over:)` no-op.
  - **One theme's normal text genuinely failed and was corrected**: `solarized-light`'s `base00`/`base3` body pairing measured **4.13:1** and had been carried as an accepted limitation because the sourcing report's contrast pass only covered the ANSI/accent/chrome slots. It is `base01` (`586e75`, **4.99:1**) now - one step up Solarized's own monotone ramp, a canonical family value the spec itself lists for emphasized content on a light background, so there is no hue drift. Every other theme's normal and selected pairs already cleared the floor; the measured table is in that branch's PR description.
- **A selection the app never draws cannot be recoloured: a mirror tab's drag used to go to the multiplexer, not to SwiftTerm (`fm/grandline-console-selection-contrast-followup`).** `fm/grandline-text-selection-contrast-audit` (the bullet above) measured all 14 themes' terminal pairs clear of the floor and the captain's Console selection was *still* illegible afterwards - on the **Herdr tab specifically**, while the Shell tab beside it, same window and same theme, was fine. The reason no colour value could have caught it: **a `herdr session attach` client enables mouse capture** (`?1002h` / `?1006h`, both literals present in the herdr binary; herdr also ships `mouse_capture` and `copy_on_select` config keys), and SwiftTerm's `mouseDown`/`mouseDragged` hand every drag straight to the child whenever `allowMouseReporting && terminal.mouseMode != .off`, building **no selection of their own** - so `selectedTextBackgroundColor`/`selectedTextForegroundColor` were simply never read in that tab. What the captain saw highlighted was herdr's own selection, painted from herdr's own fixed dark theme (documented default `selection_bg = "#313244"`, a dark navy) with no knowledge of which of this app's themes is active. A plain Shell tab enables no mouse mode, so the identical drag there goes down SwiftTerm's selection path and comes out in the theme's colours. **Reproduced with real rendered pixels before anything was changed**, and that is the only way it was ever going to be visible: same content, same theme, same synthesized click-drag, `mouseMode = .off` paints `selectionHex` behind `selectionTextHex` and `mouseMode = .buttonEventTracking` paints nothing at all.
  - **The fix is a routing fix, in this app's own subclass, not a fourth vendored SwiftTerm patch and not a colour change.** `CockpitTerminalView.prefersLocalSelection` (set by `ConsoleController.addTab` for `case .mirror` only) makes an *unmodified* left-button **drag** build SwiftTerm's own, theme-coloured selection even while the child has mouse reporting on - which is what puts the Herdr tab on the exact mapping the Shell tab already used correctly, rather than inventing a second one. Nothing herdr can do with the mouse is lost: the press is **deferred** rather than swallowed, so a gesture that turns out to be a plain *click* is replayed to the child (herdr's sidebar/tab-bar clicks keep working, and it never sees a press whose release it will not also see), the scroll wheel is untouched, and **Shift+drag forwards the drag** - the inverse of SwiftTerm's own `shiftBypassesMouseReporting` default, so every herdr drag gesture stays reachable behind one modifier. Deliberately scoped to `.mirror`: an `.ssh` tab may be running vim or the captain's own tmux, where a plain drag reaching the remote program is what is expected.
  - **This mechanism was deleted by `fm/grand-line-remove-firstmate-mirror` and then restored, re-scoped to `.shell`, by `fm/grand-line-shell-tab-local-selection` - the AppKit lesson above is live code again, just opted into by a different tab kind.** The removal's reasoning was that nothing set `prefersLocalSelection = true` once the herdr tab was gone, which was true; what it missed is that the *substance* of the fix was never herdr-specific (a mouse-reporting child swallows a plain SwiftTerm selection whatever program it is), only the opt-in was. See the dedicated bullet below for the current scope and behaviour.
  - **`TerminalSelectionRenderSelfTest.swift` is back, Shell-only (`fm/grand-line-shell-selection-investigate-fix`) - deleting it whole took more than the routing fix with it.** Three of its five cases were genuinely herdr-specific and stay deleted; its first case never was. That case drives a real `CockpitTerminalView` in a real ordered-front window, feeds it real bytes, synthesizes a real click-drag, `cacheDisplay`s it and reads the pixels back, over every one of `HelmTheme.allThemes` - **the only pixel-level guard in this codebase that a theme's `selectionHex`/`selectionTextHex` pair actually reaches the screen rather than merely existing in the palette.** `FM_RUN_CONTRAST_TESTS`' own two selection checks are a palette measurement plus a source grep, so neither can see a render that stopped consulting those values (which is exactly the class of bug that made the herdr tab illegible while every palette number measured fine). Window-backed, so it is in `run-all-tests.sh`'s `NEEDS_SESSION` list. **Confirmed to catch two real injected regressions, not merely to pass**: removing the vendored `mutable[.foregroundColor] = selectedTextForegroundColor` line fails every theme by name (`glyphs only travel 0.00 of the way to selectionTextHex`), and pointing `HelmTheme.apply(to:)`'s `selectedTextBackgroundColor` at a literal fails by name.
  - **`FM_RUN_TERMINAL_SELECTION_RENDER_TESTS` is the permanent guard, and it asserts pixels rather than constants** - a real `CockpitTerminalView` in a real ordered-front window, real bytes fed in, a real synthesized click-drag, `cacheDisplay`, then read the colours back. **Confirmed to catch the regression by name**: reverting the routing reproduces "mirror painted 0 selected row(s)" against a shell that painted the theme fill, and removing the `.mirror` opt-in fails the source guard. It also pins that a click and a Shift-drag are still reported to the child while a plain drag is not.
  - **Two measurement lessons from writing it, both of which cost real time.** (1) **An absolute WCAG number derived from captured pixels is not trustworthy here**: inside a real window `bitmapImageRepForCachingDisplay` returns a rep in the *display's* profile, and that conversion is not losslessly invertible - `helm-light`'s `007194` fill comes back through `usingColorSpace(.sRGB)` as `3C82A2`, dragging a genuinely 5.38:1 pair down to a false 4.13:1. A **tolerant identity check in the rep's own space** is reliable (AGENTS.md's existing probe rule); the contrast floor stays measured from the palette, where `FM_RUN_CONTRAST_TESTS` already enforces it. (2) **Text is antialiased, so almost no pixel ever reaches the nominal ink colour** - "the second most common colour on a selected row" is a fringe blend and reads as far better contrast than the captain sees. The honest assertion is that the glyph pixels lie *on the segment* between the drawn fill and the declared ink, and how far along it the furthest one travels.
- **A plain drag only builds a SwiftTerm selection when the child process has mouse reporting OFF, and there is no longer any mitigation for that anywhere in the app - `fm/grand-line-shell-selection-investigate-fix` measured this rather than reasoning about it.** A captain report that Console Shell tab selection was "messed up again" after the Mirror removal was investigated first, and the Shell tab's own selection turned out to be **fine**: a real `ConsoleController` with a real Firstmate Shell tab (real login-shell child, real output, real `ConsoleCardChrome` inset, real E1 display gating) painted ~110k pixels of the exact `selectionHex` behind legible `selectionTextHex` ink in every theme swept, and the restored pixel suite passes all 14. The full evidence, screenshots included, is `data/grand-line-shell-selection-investigate-fix/report.md`. What the same harness *did* find is the mechanism that produces the reported symptom, measured in the same run: `MacTerminalView.mouseDragged` returns early whenever `allowMouseReporting && !shiftBypassesMouseReporting(event) && terminal.mouseMode != .off`, so a child that enables mouse capture (**Claude Code, vim, `less`, tmux, or `herdr` run by hand**) swallows the drag and the theme's selection pair is never consulted at all - plain drag selects **nothing**, Shift+drag selects correctly in the theme's colours. What is highlighted in that state is the child program's own selection, painted from its own fixed palette (herdr's documented default is `selection_bg = "#313244"`, a dark navy), which is precisely the original "dark navy block, illegible text in light mode" report. **This is not new and not a `#293` defect** - a Shell tab was never opted into local selection, deliberately, because an `.ssh` tab may be running vim where a plain drag reaching the remote program is what is expected. What changed is that the herdr session moved *out* of the one tab kind that had the mitigation. Whether to generalise the deleted routing (unmodified drag builds the app's own selection, Shift forwards it) to `.shell` tabs, to every tab, or not at all is a **registered open captain decision**, not something to implement on a hunch - and note the deleted mechanism was a *routing* fix, not a herdr-specific one, so option 2 is a re-scoping rather than a reinstatement.
- **A `.shell` tab keeps an unmodified drag for the app's own themed selection even when the program inside it has enabled mouse capture; Shift+drag forwards the gesture to that program instead (`fm/grand-line-shell-tab-local-selection`, the captain's chosen fix for what `fm/grand-line-shell-selection-investigate-fix` measured).** `CockpitTerminalView.prefersLocalSelection` and its `mouseDown`/`mouseDragged`/`mouseUp` overrides are back - implemented fresh, opted into by `if case .shell = launch` in `ConsoleController.addTab`, and **not** a reinstatement of the Mirror tab (nothing herdr-specific returned, and `TabLaunch` has no `.herdr` case left to opt in). Read `CockpitTerminalView.prefersLocalSelection`'s own doc comment before changing any of it; the report with every transcript is `data/grand-line-shell-tab-local-selection/report.md`.
  - **The scope is the decision, not an implementation detail.** A `.shell` tab is a local login shell: whatever mouse-reporting program the captain starts inside it (Claude Code, vim, `less`, tmux, `herdr` run by hand) is also reachable through its own keyboard interface, and *reading* that output is the tab's main job - so an unmodified drag is worth more as a selection than as a mouse report. An `.ssh` tab is deliberately untouched: it may be running vim or the captain's own tmux on a remote host, where a plain drag reaching that program is expected and the keyboard alternative is someone else's machine away. **An `.ssh` tab opted in by mistake would paint byte-identical pixels** while silently changing what a drag does inside a remote editor, so `TerminalSelectionRenderSelfTest`'s case 5 is a *source* guard asserting `.shell` opts in and that `addTab` contains **exactly one** `prefersLocalSelection = true` - confirmed to catch both the removed opt-in and an added `.ssh` one, by name.
  - **The press is deferred, never forwarded-then-stolen.** A left-button press on an opted-in view is held until the gesture reveals itself: motion means keep it (anchor SwiftTerm's own selection at the *press* point, since `mouseDragged` seeds `setSoftStart` from the event it is handed), no motion means replay press+release to the child. That is what keeps the child's own button state consistent - it never sees a press whose release it will not also see. Shift-modified events handed to `super` have the Shift flag *stripped*, because SwiftTerm's own `shiftBypassesMouseReporting` would otherwise route them to its selection - the exact default this opt-in inverts.
  - **Verified against real vim, not a synthesized mouse mode**: a real `ConsoleController`, its real Shell tab, `vim -c 'set mouse=a'` on a real file, `mouseMode` confirmed `buttonEventTracking`, then real gestures - plain drag sent **0** bytes to vim and painted ~76k pixels of the theme's fill; Shift+drag sent 55 bytes and painted none, with vim's own status line reading `-- VISUAL --` in the captured render; a plain click sent 18 bytes. Both registers, screenshots in that report's `evidence/`. `FM_RUN_TERMINAL_SELECTION_RENDER_TESTS` grew to five cases, and its case 3 asserts the *pre-fix* behaviour too (with the opt-in off, mouse capture swallows the drag and nothing is selected) specifically so the suite can still tell the fix from its absence.
  - **`fm/grandline-console-selection-overlay-sidebar` closed a real gap left by the deferred-press mechanism above: it had no minimum-movement threshold before treating a held click as a genuine drag.** AppKit calls `mouseDragged` for essentially *any* movement while the button is held - even a fraction of a point, no built-in click-vs-drag hysteresis - so an ordinary click on a mouse-reporting child (a captain running `herdr`'s own interactive session by hand in a `.shell` tab was the reported case) could jitter by a sub-pixel amount and immediately (1) flip `localSelectionDragActive` true with zero distance check, which meant `mouseUp` no longer saw "no motion happened" and never replayed the press+release to the child - silently eating the click, reported as "I have to click twice on the agent for it to work" - and (2) seed SwiftTerm's own selection at the press point and extend it to wherever that one jittered event landed (`MacTerminalView.mouseDragged`'s `selection.dragExtend`), which for a jitter crossing even one row highlights the *entire width* of every row in between (ordinary stream-selection semantics) - read by the captain as the app's own themed selection colour "bleeding" across whatever TUI panes the child program drew, since SwiftTerm has no notion of that program's own column layout. **Fix**: `CockpitTerminalView.localSelectionDragThreshold` (4pt, `locationInWindow` units) - `mouseDragged` now holds the press until movement from the original press exceeds it, rather than committing to a local-selection drag on the first delivered event regardless of distance. Real deliberate drag-to-select is unaffected (a threshold this small is crossed within one or two events of any intentional drag); a click's own hand/trackpad jitter now correctly stays a click. Confirmed to catch the exact regression, not just to pass: `TerminalSelectionRenderSelfTest`'s case 6 synthesizes the identical sub-threshold jitter gesture, asserts the fixed behaviour (click still reaches the child, nothing painted locally), then flips a test-only `CockpitTerminalView.localSelectionDragThresholdOverrideForTests` to `0` (the pre-fix behaviour) on the same gesture and confirms it reproduces at least one of the two symptoms.
  - **`fm/grandline-terminal-selection-sidebar-bleed` gave a `.shell` tab a per-tab, sticky way to invert the drag/Shift-drag mapping above - deliberately NOT a global default change, and the reason why is worth reading before touching this area again.** Captain report: dragging to select text in the right-hand content pane of a Console `.shell` tab running `herdr` (a terminal agent-multiplexer TUI that draws its own left sidebar of spaces/agents plus a right-hand content pane) also highlighted and copied characters from herdr's own sidebar. **First hypothesis, wrong and corrected by the captain with concrete counter-evidence before any code was written**: this was not the "full-row selection for every intermediate row" limitation `getSelectedLines`'s stream semantics genuinely have (SwiftTerm's `SelectionService` has no rectangular/block/column selection mode at all - confirmed by reading `SelectionService.swift`/`Terminal.swift`, and that fact is real, but it isn't what fires here). The captain tested the identical herdr session in WezTerm (a different terminal, no Grand Line code involved) and found: **a plain drag there already selects only the right-hand content and never touches the sidebar.** **Actual root cause, traced end to end through `CockpitTerminalView.mouseDown`/`mouseDragged`/`mouseUp` and vendored `MacTerminalView.swift`/`Terminal.swift`'s `?1002h`/`.buttonEventTracking` handling**: WezTerm forwards the drag to herdr, and herdr - the one program that actually knows where its own sidebar/content boundary is - renders a correct, pane-aware selection of its own when its real SGR mouse reporting receives the drag; Grand Line's `.shell` tab, by contrast, deliberately hijacks the identical plain drag away from herdr and into SwiftTerm's own pane-blind stream selection (`prefersLocalSelection`, above) - the bleed is the direct, expected consequence of hijacking a drag away from the one program that could have handled it correctly. **The mechanism the captain wanted already existed, gated behind Shift**: since `prefersLocalSelection`'s own escape hatch is "Shift+drag forwards the whole gesture to the child instead," a Shift-held drag in a herdr `.shell` tab was already, mechanically, reproducing WezTerm's plain-drag behaviour - traced with no ambiguity, not live-verified in that investigation's own sandbox (see `data/grandline-terminal-selection-sidebar-bleed/report.md`).
    - **Why the default was not simply inverted for every `.shell` tab (the captain's first instinct, Option B) - verified empirically, not assumed.** A real `claude` (Claude Code CLI) session was run in a disposable pty (`pty.fork()`, a fully separate child process, no query ever submitted to the assistant) and its raw output captured: `claude`'s interactive TUI enables `?1000h`/`?1002h`/`?1003h`/`?1006h` - full SGR mouse reporting - as **baseline startup behaviour of its own main chat prompt**, before any menu or scroll interaction. Since Grand Line's mouse routing only asks "is mouse reporting on," not which program enabled it, inverting the `.shell` default globally would apply identically to a tab running `claude`/firstmate crewmate sessions as to one running herdr - and `.shell` tabs running those sessions are the captain's own stated primary, routine workflow, not the theoretical vim/tmux edge case the original `prefersLocalSelection` decision already accepted losing. ### `NSSplitView`, and the trap inside choosing it

- **The deciding argument for `NSSplitView` over a hand-built layout is this file's own gotcha catalogue.** A hand-rolled two-pane layout means a constraint web per split, per nesting level, rebuilt at runtime - the exact shape of gotchas (10), (12) and above all (13), the window-width floor this codebase has shipped five times. `NSSplitView` sizes by **frame** and participates in no constraint graph, so that class is structurally unreachable here rather than merely avoided, and dividers/drag come free. `TerminalSplitContainer` is frame-driven for the same reason: one `layout()` setting one frame.
- **`NSSplitView`'s `arrangedSubviews` API is Auto Layout based; its plain `subviews` API is the frame-based one.** Measured, not read: building the tree with `addArrangedSubview` gave every pane a `.zero` frame - the split view installs constraints of its own against children with no intrinsic size, and it overwrote the manual halving. Use `addSubview` / `adjustSubviews()` / `setPosition(_:ofDividerAt:)`.
- **A freshly built split needs explicit halving.** `adjustSubviews()` preserves the proportions it finds, and a brand-new pane's are zero - so both children get the split view's own frame first, then `setPosition` puts the divider in the middle.
- **Auto Layout still owns everything outside that file**: the container carries exactly the four `terminalInset` constraints the tab's single terminal used to have, so from `content`'s point of view nothing about a tab changed. `DaylightDrillPageSlice2SelfTest`'s terminal-frame invariant passes unchanged.

### What follows the focused pane, and what deliberately does not

- **`TabModel.terminal` is still a `let` and still the tab's primary pane**, because ~50 call sites read it as "the tab's terminal" and every one of them means *this tab's session*: SRE Lead's bridge, the kube context badge, the block tracker, the Log Analyzer capture, the window title, drag forwarding. Only the actions about what the captain is **typing into right now** follow the focused pane - Compose, a snippet, a sent command, find, copy.
- **A split pane always runs a login shell, even on an `.ssh` tab, and that is the one decision worth revisiting.** `connectSSH` is tab-scoped by construction (the materialised key's temp file and the `awaitingKeyUnlock` guard both live on `TabModel`), and a per-pane ssh would be a second real connection plus a second Touch ID prompt per split - which is exactly what `SessionRestore` already refuses for a host page's duplicated tabs. A host page's split says so in one dim line; ⌘D remains the way to ask for a second session.
- **Splits are not persisted.** `SessionRestore` restores a tab's *name* and builds a fresh launch; restoring a pane tree would fork N shells at launch for a layout the captain may not want back.
- **A split pane's exit is never auto-reconnected**, whatever "Reconnect automatically" says: that setting is about a tab's session dropping, and re-forking a pane the captain closed by typing `exit` would make `exit` impossible to mean.
- **Focus is observed, never intercepted.** Each pane registers with `HelmFocusSensing` (`includesDescendants: true`), so clicking a terminal focuses its pane with no mouse handling - which matters, because this controller family has twice learned that overriding mouse events around a live `TerminalView` breaks something else.
- **`ConsoleController.focusTerminal(of:)` is still the *only* place this family hands a PTY the keyboard** (audit #2 §5.1(c)). `focusPane` records the move and delegates; it does not get to be a second gate. `Audit2SecurityFixesSelfTest.test_focusChokePoint` counts the sites and now sweeps `ConsoleController+Splits.swift` too - note it greps for a lowercase `terminal` on the same line, so a rewrite to `makeFirstResponder(focusedTerminal(of: tab))` silently drops the count to zero.

### Three findings from the self-test worth not re-deriving

- **`window.contentViewController = controller` leaves the view at `.zero` in a headless process** - every geometry case then passes vacuously. `window.contentView = controller.view` plus an explicit frame (`DaylightDrillPageSlice2SelfTest.mount`'s shape) is what gives real frames, and it also means `viewDidAppear` never fires, so no tab or pane forks a real shell.
- **`layoutSubtreeIfNeeded()` is a no-op unless something already marked the view dirty, and must be called on the view that owns the change.** Measured again here: a freshly mounted pane container reported a `.zero` frame with its four constraints active and satisfied until `content.needsLayout = true` preceded the call. Only a test needs this; a real window runs its own display cycle.
- **A pane *count* is not a split.** A split that stopped halving still builds two panes, and `adjustSubviews` still gives both a real size - just a lopsided one. Assert frames, and assert that the keyboard moved (`window.firstResponder`) rather than only that the container recorded a focus change: those are two different things, and only the second is what the captain feels.

It now requires `stableReadsRequired` (5) consecutive identical reads within a larger budget. **That fixed the Y drift and was not the whole story**, which is the part worth carrying: with the settle strengthened, CI's Y values came back stable and consistent and a **7pt difference in the runner's own clip view** remained, making every card 3pt narrower in one theme while column assignment, ordering, card count and grid density all matched exactly. **Measured rather than assumed: locally both themes get a byte-identical clip width under *both* scroller regimes (overlay 1500/1500, legacy 1483/1483)** - which rules out the scrollbar mechanism this file's own header suggests, and shows the differing clip width is not a property of the theme at all. So the comparison stopped asserting raw pixels, which had additionally been asserting that two independent mounts happened to get the same clip width, and now asserts the layout facts the suite exists to protect, each still exact: one column vs two, each card's column **index**, each card's width as a **ratio to the widest on the page** (the half-versus-full-width signal the original defect actually produced), the Appearance grid's density, and ordering within each column - plus a bounded 2% absolute-width tolerance. **Verified rather than argued: re-injecting the original captain-reported bug (theme-gated two columns) still fails it loudly, reporting "12 of 13 other themes disagree with daylight's layout".** That defect is a 2x difference; the runner noise is 1%. **The general lesson: when a parity check fails on a runner and not locally, ask what the check is asserting *beyond* the property it exists for - here, an environment fact about the clip view - rather than reaching for a tolerance on the property itself.** **Check `main`'s own window-backed lane before deciding a failure there is yours**: that lane is `continue-on-error`, so a suite failing on your branch while `main` is green is a real signal, and one passing on both is the known environment noise.
