- **`HelmDesignSystem.swift` is the app's design system: `HelmMetrics` / `HelmType` tokens plus `HelmCard`, the one card container (`fm/grandline-design-system-phase1`, Phase 1 of the full-app UI audit - read §3.2, §6.2 and §6.3 component 1 of `data/grandline-full-ui-audit/report.md` before touching any of it).** Before this there were **five** card recipes visible side by side (radius 10 / 12 / 13 / 14, two fill opacities), `card(icon:title:content:)` copied byte-for-byte into four controllers, its theming loop copied verbatim into six, three page gutters (18 / 20 / 28pt), and 18 distinct `systemFont` sizes with three of them all doing "card title". None of that encoded a product decision. What to know now:
  - **`HelmCard` is `ShiftPanelView` renamed and widened - that class no longer exists.** Its chrome is recipe C's (opaque `chromeBackgroundHex`, `chromeLineHex @ 0.6` border, radius `HelmMetrics.rCard`, a real 1pt header divider at `@ 0.5`), the model the audit chose, plus `SettingsController.card`'s icon-tile + title + subtitle header. **A `HelmCard` themes itself** - its own icon tile, title and subtitle included - so a page's `ThemeManager.shared.observe` closure calls `card.applyTheme(theme)` and nothing else. Do not add another `cardBackgrounds`-style registry, and do not hand-roll a rounded background view for a page section.
  - **Two ways to give it a header.** `setHeader(symbol:tint:title:subtitle:actions:)` is the structured one (`actions` land at the card's trailing edge - that is where Bootstrap's "Run full setup" progress track and button live); `setHeader(symbol:tint:titleLabel:subtitleLabel:actions:)` is the same thing reusing **caller-owned** labels, for text the page rewrites live ("GitHub (3)", "In flight (2)"); `setHeader(_ view:insets:)` is the arbitrary-view escape hatch for a header carrying its own count badge / filter row / buttons (Shift, Vault, Dictation use it). `setBody(_:insets:)` defaults to **flush**, which is what a scroll view or a list stack whose rows carry their own inset wants; real content passes `HelmCard.contentInsets`.
  - **`HelmCard.applyCardSurface(to:theme:cornerRadius:)` is the single definition of the card fill/border.** A surface that genuinely shares that chrome without being a card yet - `HelmStatTile` (Phase 4), which is where Updates' own stat tiles ended up - calls it rather than re-deriving the colours, so a page still has exactly one fill opacity. **The border carries real load, it is not decoration:** `chromeBackgroundHex == backgroundHex` in `gruvbox-light` / `tokyo-night-dark` / `tokyo-night-light`, so in those three the border is the only thing separating a card from the page (unchanged from before - the old `surface @ 0.6` fill composited to the same colour in exactly those themes).
  - **`HelmMetrics`** holds the spacing scale (`s1`-`s6`), radii by role (`rChip` / `rControl` / `rCard` / `rPanel`), the one `pageGutter` (24pt - every card-bearing destination now measures exactly this), and the three icon-tile sizes. **`HelmType`** holds the type scale by role - `pageTitle(_:)` / `sectionTitle()` / `rowTitle()` / `body()` / `caption()` / `kicker()` / `metric(_:)`. Reach for a token, not a literal. `HelmType.Voice` exists so the registered captain decision `grandline-full-ui-audit-decision-page-title-voice` (promote `ShiftFont.serif` app-wide, or retire it) has somewhere to land - it is **not** settled, and Shift's own serif headers were deliberately left alone.
  - **Out of scope when Phase 1 shipped, each its own later phase:** `HelmAccentRow` (component 2, shipped in Phase 3), `HelmStatTile` / `HelmEmptyState` / `HelmSegmentedTabs` (components 4-6, shipped in Phase 4), and recipe E - Bootstrap/Automation's `line @ 0.08` step-content boxes, which belong with the stepper component. Verified live for all 12 `HelmTheme.allThemes` with a temporary env-gated probe (reverted before commit, per the "Verifying native UI bugs" convention below) that walked each destination's real view tree after a real layout pass: 39 cards across 11 destinations, one radius / one fill / one border / one 1pt border width / one 24pt gutter per theme, plus real off-screen PNG renders of all 14 destinations confirming every page's content still renders inside its new card.
- **`HelmButton` is the app's one button, and the stock `NSButton` bezel is now a self-test failure (`fm/grandline-design-system-phase2`, Phase 2 of the full-app UI audit - read §3.2's "Buttons" section and §6.3 component 3 of `data/grandline-full-ui-audit/report.md` before touching it).** Before this the app had **124 stock `bezelStyle` buttons across 29 files** and **18 `keyEquivalent = "\r"` default buttons across 15** (both counts re-verified against `main`, not taken from the report), plus 13 `NSPopUpButton`s - all of which paint macOS's own grey bezel and system blue (`#0a84ff`) regardless of which of the 12 Helm accents is active. That is what made a fully-themed app still read as generic macOS. Now: **1** `bezelStyle` site remains and it is not a button (`TabChipView`'s inline-rename `NSTextField`), 128 call sites are `HelmButton`, and 13 are `HelmPopUpButton`. What to know:
  - **Four variants, picked per site from what the button already did**, not assigned mechanically: `.primary` (opaque `accentHex` fill + `selectionTextHex` label - at most one per sheet footer / card header), `.secondary` (bordered, theme-derived - the default that replaced the stock bezel), `.quiet` (borderless, muted, hover-only background - toolbar and link weight), `.destructive` (a contrast-corrected wash of the theme's own red). The recipe is `UpdatesController`'s Refresh pill - the one correctly-themed action that already existed - promoted into a real control.
  - **How it stops being a bezel:** `isBordered = false` means AppKit draws no bezel *at all* (verified by rendering a real default button both ways - the stock one composites its bezel material, the unbordered one captures fully transparent), so `keyEquivalent = "\r"` keeps the Return shortcut while the blue look has nothing left to paint. Confirmed against the strongest form of the old behaviour: with `window.defaultButtonCell` explicitly set, the button still pixel-samples as the theme accent. Chrome comes from the view's own layer; the label comes from `attributedTitle`, because **`contentTintColor` does not colour a string title, only an image** - three pages had each hand-rolled that workaround before it was shared (`UpdatesController`'s "Install in Bootstrap", `CommandLibraryViews`' Copy and Favorite; all three are now just a variant plus an optional `tint`).
  - **It themes itself** (like `HelmCard`): its own `ThemeManager.observe`, unregistered in `deinit`. Deliberately not a per-page button registry - that is exactly the shape of `ThemeManager.swift`'s checklist item 4, this codebase's most-repeated bug class. **Consequence: a page must not set `font` / `attributedTitle` / `contentTintColor` / `isBordered` on a `HelmButton`** - `restyle()` owns all four and will overwrite them on the next theme change.
  - **Migrating a site is a type change only.** `title`, `target`, `action`, `keyEquivalent`, `isEnabled`, `isHidden`, `identifier`, `tag` and `setButtonType(.pushOnPushOff)`'s `state` all keep working, and `controlSize` is overridden to map onto `Size` so an existing `controlSize = .small` line needs no edit. One real gotcha it exposes: **a control that signalled selection through `NSButton.state` was relying on the stock bezel's on-state, which no longer exists** - Settings' font-size presets and Hosts' tag chips now carry that state as `variant = selected ? .primary : .secondary` instead.
  - **`NSPopUpButton` needed no reimplementation** (§6.5 put that out of scope): it *is* an `NSButton` subclass, so `HelmPopUpButton` de-bezels it the same way and keeps the menu, `selectItem…`, `titleOfSelectedItem` and `indexOfSelectedItem` intact - verified live before it was written. Its label and chevron do follow `contentTintColor` (unlike `HelmButton`'s string title), since a popup draws its title from the selected menu item.
  - **`NSSwitch` is the one control that genuinely cannot be themed** - measured, not assumed: its header declares only `state`, and it answers `false` to `setTintColor:`/`setContentTintColor:`/`setAccentColor:`/`setFillColor:`/`setBezelColor:`. Its runtime property list does expose a `trackColor`, but that is private API and deliberately unused here. So the 6 switches still render in system chrome; whether to build a bespoke toggle is registered as a captain decision (`grandline-full-ui-audit-decision-nsswitch-theming`), not silently built.
  - **Deliberately untouched, with reasons:** Console's and Tools' tab-bar toolbar glyphs (already borderless, never part of the bezel count, and their per-state tinting - Block View's accent while showing - would need per-site rework; the report files that restyle under §6.4's "notable rework", and `HelmButton`'s `tint` is the seam it will use), and `LockScreenController`'s unlock pill (already a hand-rolled bespoke filled button, and §6.4 assigns the lock screen only `HelmType`/`HelmField`).
  - **Later phases:** `HelmStatTile` / `HelmEmptyState` / `HelmSegmentedTabs` (components 4-6, shipped in Phase 4) and `HelmField` (Phase 6, still open) - which is why a migrated page's `NSTextField`s, `NSSearchField`s and `NSProgressIndicator`s still read as system chrome next to its now-themed buttons.
- **`HelmAccentRow` is the app's one accent-carrying row, and the checklist row's status column is now a real column (`fm/grandline-design-system-phase3`, Phase 3 of the full-app UI audit - read §3.2's "Accent-bar card with an uppercase kicker" table, §4.14, §5.4 and §6.3 component 2 of `data/grandline-full-ui-audit/report.md` before touching it).** Before this, one idea had **four independent implementations** plus a fifth surface that had half of it: all agreed on a 3pt bar at radius 1.5 and a radius-10 card, and disagreed on everything else - three separate kicker constructions at three kern values (0.9 / 0.7 / 0.6), two badge treatments, and one outlier (`SRELeadChatView.accentCard`) with no border at all whose kicker was coloured from the raw tint hue. Row-rendering code across the five surfaces went from 530 lines to 171 (thin data->`Content` adapters), against a 378-line shared component of which 217 are code. What to know:
  - **`HelmAccentRow` is `NotificationRowView` promoted, not a redesign.** That class is gone; the notification panel is now a caller (`NotificationPanelViewController.makeRow`) of the component it donated, which is exactly what the audit asked for (§6.4: "becomes a *caller* of the component it donated"). Its geometry, `HoverHighlightView` card, `tint @ 0.4` border, 26pt circular `IconTileView` badge and `ToolRowLayout.pill` chip are unchanged.
  - **The rule that matters when extending it: the kicker is `HelmTheme.mutedInk`, never the tint hue.** A `HelmTint` is safe as a fill or a bar and is *not* automatically safe as text (`HelmContrast`'s doc comment, audit §5.7). The tint reaches the bar, the badge and the chip and never the kicker. `HelmContrastSelfTest.checkAccentRowRecipe` asserts that plus one bar weight / badge size / radius / kicker font+kern across all 12 themes, and `checkNoHandRolledKickers` fails the build on any `.kern:` outside `HelmType` - **both confirmed to catch a real regression, not just to pass** (colouring the kicker with `tintColor` and planting one hand-rolled `.kern: 0.7` each reproduced the exact failure).
  - **Structure is fixed at `init`, content at `configure`** - so a reused `NSTableView` cell just gets re-pointed. `chipPlacement` is `.trailing` for a wide list row and `.belowBody` for the 340pt notification panel; `leadingControl` swaps the badge for a caller-owned control (Shift's `ShiftTaskCheckBadge`, so click-to-toggle is unchanged); `contentView` swaps the title/meta labels for a caller-owned body (SRE Lead's rendered-markdown stack) while keeping the kicker, bar, badge and card. `hover: false` for a row that is not interactive - a hover highlight on something that does nothing is a lie (SRE Lead's transcript cards and Overview's read-only rows pass it).
  - **§5.4's status-column jitter is fixed in `ToolRowLayout`, which affects all five of its callers** (Updates, Bootstrap's software checklist + drift card, Automation, GitHub Sync, Vault). The row is now a real three-column table: a fixed name column, the status column (`statusViews` - the pill by default, plus the spinner/label that replaces it while a check runs), flexible space, then the actions (`trailingViews`) and the chevron pinned trailing. Measured live: 64pt of pill-x spread across five real rows (50pt across the real page's thirteen) -> **0pt**, with the chevron still pinned. **This bullet used to claim "a fixed name column is the only formulation that works, because measuring back from the trailing edge cannot pin the pill when one row's actions are 'Check' and another's are 'Check' + 'Install in Bootstrap ->'". That is only true of measuring back from the actions themselves, and the fixed leading column caused two live defects of its own** - see `fm/grandline-visual-polish-round2` below, which replaced it with a reserved trailing slot. `build`'s `trailingViews` now means *actions only*; a caller that just wants a pill passes neither argument.
  - **Why `HelmAccentRow` and `ToolRowLayout` were deliberately *not* merged**, despite both now being "a row with a tint": one is an alert/task card (bar, badge, kicker, body, chip) and the other a dense checklist row (fixed columns, action buttons, a disclosure chevron and an expandable log). They share the primitives that carry the visual language - `ToolRowLayout.pill`, `IconTileView`, the accent-bar idiom, `HelmType` - and nothing else, because their layouts genuinely differ. Merging them would have produced one type with two disjoint halves.
  - **Two real defects the migration surfaced, both fixed here:** `FleetController`'s own `pillLabelView` was a *second* copy of the §5.7 "hue as its own label" bug (Overview's rows now go through the contrast-corrected `ToolRowLayout.pill`), and the two Shift lists' 74pt `rowHeight` clipped the meta line's descenders once the rows moved onto the shared type scale - now 78pt, set from a measured 75pt fitting height plus the row view's 2pt insets rather than a guess.
  - **Verified** with real off-screen renders (`bitmapImageRepForCachingDisplay`/`cacheDisplay`, this repo's screenshot substitute) of all five surfaces across `helm-dark`/`helm-light`/`catppuccin-mocha`/`gruvbox-light`/`tokyo-night-dark`/`solarized-light`, driving the **real** `NotificationPanelViewController`, the **real** `ShiftController` page (seeded through a real `ShiftStore` against a scratch `FM_SHIFT_DIR`), the real `SRELeadChatView` with a real Finding + Recommendation exchange, and `FleetController`'s own row builder - plus the geometry probe above against the real `UpdatesController`. A lesson from that pass worth keeping: **a hand-hosted `NSTableView` in a probe sizes its rows to their own content, not the column**, so ragged card widths in a probe render are the probe's artefact - mount the real page before believing a width bug.
- **`HelmStatTile`, `HelmEmptyState` and `HelmSegmentedTabs` are the app's one stat tile, one empty state and one sub-navigation control (`fm/grandline-design-system-phase4`, Phase 4 of the full-app UI audit - read §3.2's "Stat tile", "Empty state" and "Sub-navigation" tables, §5.5, §6.3 components 4/5/6 and §6.4's adoption map of `data/grandline-full-ui-audit/report.md` before touching any of them).** Three independent components shipped together because each is small; they are separable and were built as three separate concerns. Call-site code across 15 files went from 1219 lines to 830 (**-389**), against 610 lines of shared component of which **363 are code**, plus 172 lines of new self-test. What to know:
  - **`HelmStatTile`** replaced **four** copies, not the three the audit counted: Overview (mono 15 semibold, 10/8 padding, 50pt), Shift (`ShiftFont.mono(19)`, 12/10, 56pt), Updates (mono 19 **bold**, 15/13, `surface @ 0.60`, 67pt), and `ShiftController.reviewStatTile` - a byte-identical duplicate of Shift's own `statTile` whose doc comment said it existed *only* because the two rows shared one theming array, so "whichever rebuilds last wins the next `applyTheme()` pass for both". A tile that themes itself deletes that reason. Shift's proportions won (§6.3's named model); the fill is `HelmCard.applyCardSurface`, which Phase 1 made public for exactly this, so a page can no longer have a tile surface and a card surface that disagree. Click support is Overview's, now a closure rather than a `Selector`.
  - **`HelmEmptyState` supersedes `ShiftEmptyStateView` - that class no longer exists**, the same rename-not-wrap call Phase 1 made for `ShiftPanelView`->`HelmCard`. Its `.compact` size *is* `ShiftEmptyStateView` (22pt glyph, body copy, the `preferredMaxLayoutWidth` fix that stopped "No saved secrets yet…" rendering as "No / sa"); `.standard` is `DocsController`'s Playbook state (40pt glyph, real title, room for an action), which §3.2 called the most complete one. `boxed: true` adds `HelmCard`'s fill/border for a state sitting straight on the page background (Overview, Review). **The action slot is a caller-owned `accessory: NSView?`, deliberately not a `(title, closure)` pair** - the app's one empty state with an action already owns a `HelmButton` *and* a spinner it enables/disables around its own async sync, so a component-owned button would have taken behaviour away rather than shared it. Four bare-label sites (Docs' runbook grid + postmortems, the rail's hosts flyout, Block View's table, the notification panel) gained the full treatment; each judged individually, and none was left a bare label, because every one of them is the whole content area of its container rather than a caption beside something else.
  - **`HelmSegmentedTabs`** is `ShiftController.buildTabRow` promoted. The audit's real finding here was that Shift's capsule and Docs' bare pills were **already byte-identical code** for the pill itself (12pt medium label, radius 7, 10/6 insets, accent wash) and differed only in the wrapper, so one recipe rendered as two different-looking controls a rail click apart; Updates' filter was a third near-copy at radius 6 in a radius-8 container. Docs' pills gained the capsule (§6.4's own recommended direction) and Updates' filter uses the new `.compact` size, for a control that sits in a toolbar beside a search field rather than under a page title. It deals in **caller-owned string ids**, not indices, so each page keeps its own enum (`ShiftTopLevelView`, `DocsTab`, `ToolFilterMode` all gained `String` raw values) and its own switch logic - the component switches nothing itself. `select(_:)` moves the pill without firing `onSelect`, which is what keeps it right when a view is reached from a menu item or the ⌘K palette rather than a click.
  - **`TabChipView` was deliberately left alone.** Console's and Tools' strips are closable, user-created, dynamic chips - "manage a set of tabs", not "switch between a fixed few views". Per the audit's own framing those are different concepts, and folding them together would have produced one type with two disjoint halves (the same reason §6.3 keeps `HelmAccentRow` and `ToolRowLayout` apart).
  - **A real §5.7 defect fixed in all three, and it is the reason `HelmContrast.legibleTintedText` now exists.** Two of the stat-tile copies painted a tinted metric with `HelmTheme.nsColor(tint.hex(in: theme))` directly, and *both* segmented-tab copies painted the active pill's label `= accent` - a hue used as text with no correction. Measured: the tinted metric reached **2.12:1** (gruvbox-dark red) and the active tab label **2.27:1** (solarized-light). `legibleTintedText` (promoted out of `HelmButton`'s own private copy, `HelmUIComponents.swift`) blends the hue toward the theme's own ink by the smallest step that clears 4.5, and has an `overAnyOf:` form for a component that cannot know which fill its label lands on. **The tabs case needed one more thing worth remembering: composite with `HelmContrast.mix`, not `NSColor.blended(withFraction:of:)`.** `blended` converts both operands into a *calibrated* RGB space before mixing, so its result drifts from the straight-sRGB composite alpha blending actually performs and `HelmContrast.ratio` then measures - small but real, and it left the active label at 4.39 in gruvbox-light while the correction believed it had cleared the floor.
  - **`FM_RUN_CONTRAST_TESTS` gained three checks** (one recipe per component per theme, plus both hue-as-text floors and §5.5's collapsed-empty-state shape), and **all three were confirmed to catch a real regression, not just to pass**: reintroducing the raw-hue metric, the raw-accent tab label, the `surface @ 0.6` tile fill and the removed `preferredMaxLayoutWidth` fix each reproduced the exact original failure by theme and by measured ratio.
  - **Verified** with real off-screen PNG renders (`bitmapImageRepForCachingDisplay`/`cacheDisplay`) of the **real** mounted `FleetController`, `ReviewController`, `UpdatesController`, `DocsController`, `VaultController`, `ShiftController`, `IconRailController`, `BlockContainerView` and the real `NotificationCenterController`'s real popover, across `helm-dark`/`helm-light`/`catppuccin-mocha`/`gruvbox-light`/`tokyo-night-dark`/`solarized-light` - plus real handler drives: the one clickable Overview tile fired `onNavigateToReview` (and a plain tile fired nothing), each page's tabs were switched through their **real `NSClickGestureRecognizer` target/action** rather than by calling `onSelect`, and Docs' "Sync Now" was `performClick`ed and confirmed to disable itself and show its spinner. Overview's, Review's and Vault's empty states only exist when their data is genuinely empty (this machine has real PRs, tasks and Vault secrets), so their own real factories were called directly and rendered - each measuring a real non-zero height and body width, which is §5.5's `bodyH=0` failure checked rather than eyeballed. **Two probe artefacts worth knowing before writing the next one:** a bare `wantsLayer` probe root paints *nothing*, so a standalone component grid renders on white and every muted/translucent colour looks wrong; and a standalone component has no page observer, so it needs the same `applyTheme` call a real page makes from its `observe` closure or it keeps the previous theme's colours through a switch. Both looked exactly like real theming bugs.
- **`HostsController` is the Hosts destination, and it owns SSH Keys and Snippets as segmented tabs - the two floating windows they used to live in no longer exist (`fm/grandline-design-system-phase5`, Phase 5 of the full-app UI audit - read §4.4, §4.5, §5.2, §6.3 components 1/2/3/5/6 and §6.4's Hosts and "SSH Keys / Snippets" rows of `data/grandline-full-ui-audit/report.md` before touching any of it).** The one phase of the rollout with a real *structural* change, correctly sequenced last because it depends on components 1, 2, 3, 5 and 6 all existing; the captain approved the navigation change (registered decision `grandline-full-ui-audit-decision-hosts-keys-snippets-merge`). `HostsSidebarController.swift`, `KeysSidebarController.swift` and `SnippetsController.swift` are **gone**, replaced by `HostsController.swift` + `HostsListSection.swift`. Nothing about connecting changed: the rail entry, the pinned Firstmate row's connect, per-host dedicated pages, quick-connect, the host editor window, and both editor sheets all behave exactly as before. What to know:
  - **What was actually wrong.** Hosts was still laid out as the 220-260pt Termius sidebar it had been before `fm/cockpit-native-ui-fixes2` promoted it to a full-size destination: at 1136pt it rendered Connect / Edit / Delete as three ~370pt `.fillEqually` buttons pinned to the bottom edge, with one 78pt row above ~800pt of dead space. Keys and Snippets were "near-identical twins" (same `footerButton` helper, same table setup, same `selectedX`/`clickedX`/`updateButtons` plumbing) in two floating windows. None of the three row views had an `applyTheme` at all.
  - **The page.** A `HelmSegmentedTabs` row over a **capped, centred content column** - an `NSLayoutGuide` with `leading >=` / `trailing <=` / `centerX ==` / `width <= 940` plus a **`.defaultHigh`** `width == 940`, never a required `==` tie (AGENTS.md's host-editor gotcha (3)). One `HelmCard` per tab, whose header carries the count, the explanatory subtitle (Keys' and Snippets' old page captions) and that tab's **add** action. The in-page "Hosts" title is gone - it duplicated the top bar's, which is what §4.4 flagged.
  - **`HostsListSection` is the one list behind all three tabs**, fed a `[Item]` array: an `NSTableView` (never an `NSStackView` of permanent rows - `DiffResultView.swift`'s header has the measured reason) whose `.record` rows are `HelmAccentRow` cards, with group headers and a `HelmEmptyState` rendered as rows of the same table. The empty row grows to fill whatever the other rows leave, so "nothing here yet" is centred in the card body rather than pinned to its top 180pt.
  - **The footer strip is gone; actions live in the row.** Each row's primary action (Connect / Edit / Run) plus a `⋯` overflow menu sit in `HelmAccentRow`'s new `trailingAccessory` slot, and the same array builds both that menu and the row's right-click `menu`, so the two cannot drift apart. **The pinned Firstmate row keeps an invisible `overflowSpacer` in that stack** rather than hiding the `⋯` button, because an `NSStackView` drops a hidden arranged subview out of layout entirely and the action column would go ragged - measured: 112pt wide starting at one x for every row.
  - **Three additions to `HelmAccentRow`**, each mirroring a slot it already had: `trailingAccessory` (caller-owned trailing controls, like `leadingControl`), `Content.tintHex` (a literal hue for a record carrying a **user-chosen** colour - a saved `Host`'s own `accentHex`; everything else still passes a `HelmTint`), and `isRowSelected` (see the selection bullet above). Plus `Content.metaIsCode` / `HelmType.code()` for a meta line that is literally a command or a fingerprint. Its click recognizer now sets `delaysPrimaryMouseButtonEvents = false`, without which the recognizer swallows the mouse-down and an enclosing `NSTableView` never sees the click that should select the row.
  - **`SSHKeyType.accentHex` became `SSHKeyType.tint`.** Those were four fixed hexes lifted from `HostCatalog.accents`, so they were picked against `helm-dark` and knew nothing about the other eleven palettes; once Phase 5 put that hue on a real accent bar the Ed25519 cyan measurably washed out against Gruvbox Light's cream page, seen in a real render. A `HelmTint` resolves per theme and keeps the per-algorithm differentiation.
  - **Menu items are unchanged in title and shortcut** - "Manage Keys…" (⌘⇧K), "New Key…" (⌘⇧N), "Manage Snippets…" (⌘⌥P), "New Snippet…" (⌘⌥N) - but now target `AppShellController.selectKeys` / `newKeyFromMenu` / `selectSnippets` / `newSnippetFromMenu`, which select the Hosts destination and the right tab instead of opening a window.
  - **Two real defects the migration surfaced, both found in a render rather than by reading the code**, and both the same AGENTS.md gotcha (12): a 90pt "Connect" button rendering ~900pt wide, because `setContentHuggingPriority` is a **no-op on an `NSStackView`** (the stack-level `setHuggingPriority` is the one that bites) *and* because the `HelmButton`s inside it needed `.required` content hugging of their own; and the `alphaValue = 0` first attempt at reserving the overflow slot, which `cacheDisplay` renders **visibly** (this repo's screenshot substitute ignores `alphaValue`), hence the real spacer view.
  - **Line-count delta** (code lines, excluding comments/blanks): the three list surfaces 945 -> 815 (**-130**, and 3 files -> 2), `main.swift` 502 -> 454 (**-48**, the two window methods gone), `HelmUIComponents.swift` 482 -> 462 (**-20**, `HelmTableRowView` deleted), against `HelmDesignSystem.swift` +44, `AppShellController.swift` +21 and `KeyEditorController.swift` +8 - **net -125**.

  - **The one non-obvious trap this uncovered, worth remembering before touching any theme's `backgroundHex`/`foregroundHex` pair again: a theme's default terminal text colour is sometimes tuned specifically against the OLD `backgroundHex` value, not against `chromeBackgroundHex` - moving the background can silently drop that pairing below the WCAG floor.** `FM_RUN_CONTRAST_TESTS`' text-selection check caught exactly this for `solarized-dark` (foreground `839496`/Solarized `base0`, tuned to 4.75:1 against the old `002b36`/`base03`, only 4.11:1 against the new `073642`/`base02`) and `solarized-light` (foreground `586e75`/`base01`, tuned to 4.99:1 against the old `fdf6e3`/`base3`, only 4.39:1 against the new `eee8d5`/`base2`) - the other 7 changed legacy palettes needed no correction. Fixed by moving each theme's `foregroundHex` one step further along Solarized's own monotone ramp (`base1`/`base03` respectively) - not a hand-mixed colour - which happens to land exactly on that theme's own `chromeInkHex` in both cases (not a coincidence: once a terminal's background literally equals the chrome's background, the terminal's own default text matching the chrome's own ink token is the natural, zero-hue-drift consequence). **Always re-run `FM_RUN_CONTRAST_TESTS` after touching any theme's `backgroundHex`/`chromeBackgroundHex` and read every `FAIL` line in the full log, not just the first one** - it is the one self-test that actually measures foreground-vs-background legibility per theme, and this class of regression produces no compile error and no other test failure.
  - **A second downstream break, in a totally different subsystem: `HerdrThemeSyncSelfTest.swift` had a "spot-check" (`panel_bg and sidebar_bg should be distinct tokens`) hardcoding the assumption that `HerdrThemeColors.derive(from:)`'s `panelBg` (`backgroundHex`) and `sidebarBg` (`chromeBackgroundHex`) must differ for `.dark`/`.light`.** They now correctly resolve to the same value for those two (and every other legacy theme) - `HerdrThemeSync.swift`'s own mapping comment already frames these as "Grand Line's own established 'content vs. chrome' pair", so a herdr panel that now shows one flat colour instead of two is herdr's sync **faithfully mirroring** what Grand Line itself displays, not a regression. Fixed by re-pointing that spot-check at a cross-theme comparison (`.dark`'s `panelBg` vs `.light`'s) instead, which proves the derivation is genuinely theme-sensitive without assuming panel/sidebar must differ within one theme - `daylight`/`dusk` still genuinely differ (their `paper`/`card` tokens are a separate, untouched distinction), but this test file never exercises those two ids.
  - **A third, narrower break in `CodePreviewSelfTest.swift`: a hardcoded "already-legible, must pass through the `legibleOn` correction uncorrected" example used `helm-dark`'s ANSI slot 8** (`747c86`, historically tuned to 4.68:1 against the old, darker `backgroundHex`) - it now measures 4.23:1 against the new, lighter one and correctly receives a small, working auto-correction (`#79818B`, 4.53:1). The self-test's *intent* (prove the correction mechanism is a no-op where nothing needs correcting) is still true and still worth asserting - just needed a different, still-genuinely-uncorrected example theme (`helm-light`'s own slot 8, `4e5661`, still 7.34:1 with no documented tuning history of its own).
  - **How this was verified visually without ever using `screencapture` or any physical-display interaction: this sandbox's display is NOT isolated from the captain's real desktop** (confirmed the hard way - a test `screencapture -x` call captured the captain's actual live Slack window with real private conversation content, immediately deleted). - **`fm/grandline-topnav-clicked-state-visibility-fix` closed the "reasonable next step" #281 flagged above, and found a related-but-distinct mechanism: `HoverHighlightView` had a real state-transition gap even for a caller that always correctly set `normalColor`/`hoverColor` (never bypassing them onto the raw layer).** Captain-reported: clicking a top-nav space pill (`DaylightBarController`, Overview/Command/Operations/Stores/Engineering) and leaving the cursor in place left that pill's label nearly invisible, blended into a stale background - moving the mouse away restored it, in both light and dark mode, on every real `HelmTheme`. **Root cause**: `normalColor`'s own `didSet` already knew to repaint immediately when it changes while the view is *not* currently hovering (`if !isHovering { setBackground(...) }`); `hoverColor` had no `didSet` at all. `DaylightBarController.applyTheme()` recomputes every pill's colors on every selection change: a newly-selected pill gets both `normalColor` **and** `hoverColor` set to the same opaque `selectedFill`, and its label's `textColor` set to `selectedInk` (chosen for legibility against `selectedFill`) - all correct, individually. But a click only ever happens while the cursor is already resting on the pill (`isHovering == true`, since `mouseEntered` fired before the click could register), so the `hoverColor` reassignment landed on a property with no repaint path, and the layer kept showing whichever color a *prior* `mouseEntered` had painted it with - the stale, pre-selection `hoverFill` (a faint muted wash). The label's `textColor`, having no such gate, updated immediately to `selectedInk` - legible against the *intended* `selectedFill`, not against the stale `hoverFill` still actually on screen. Two independently-correct colors, computed for the same end state, painted one hover-cycle apart. This is why it only ever showed up transiently (a captain's very next `mouseExited` repaints unconditionally from the by-then-settled `normalColor`/`hoverColor`, "fixing" it) and why it was theme-mode-independent (the mechanism never inspects a color's value, only whether it changed while `isHovering`). **Fix**: `hoverColor` (`HelmUIComponents.swift`) gained the mirror-image `didSet` - `if isHovering { setBackground(hoverColor, animated: false) } }` - closing the one asymmetry between the two properties. This is a shared-component fix, not a `DaylightBarController`-only patch: any other `HoverHighlightView` caller that reassigns `hoverColor` in response to a state change (a click, a keyboard activation, an external selection change) while the cursor may already be resting on the view was exposed to the identical latent defect - this task fixed the mechanism and confirmed it closes the one reported symptom, but did not attempt a second codebase-wide caller audit. **`TopNavPillPressedStateSelfTest.swift`** (`FM_RUN_TOPNAV_PILL_PRESSED_STATE_TESTS=1`) is the permanent regression guard: drives a real `mouseEntered` then a real click-recognizer dispatch (the literal repro sequence) across every pill x every real `HelmTheme` (light and dark) and asserts the label's `textColor` against the layer's *actually-painted* background (never the `normalColor`/`hoverColor` properties, since the whole bug is that those can disagree with what's painted) clears the WCAG AA text floor; a second case drives the same sequence through arrow-key pill navigation (`DaylightBarController.handleArrowKeyForTests`, a new test-only accessor mirroring `debugPills()`'s convention); a third confirms `mouseExited` still restores the settled fill correctly, unchanged. **Confirmed to catch the regression by name across all 14 themes** (not just the one dark-mode screenshot that first surfaced it) by reverting the `hoverColor` `didSet` and re-running - every theme failed with either a sub-4.5:1 ratio or an outright non-opaque stale background, then passed cleanly again once restored. (See "Never `git stash` in a task worktree" above for the cross-worktree stash collision hit while verifying this - no data was lost from either task.)

- **A real pre-existing defect in the app's one sunken field, found by measuring this screen rather than eyeballing it: `NSTextFieldCell` does not vertically centre its text in a frame taller than its own line height - it sits flush with the top.** A `HelmField` well is `controlHeight` (32) around a ~15pt line, so **every** sunken field in the app - all six editor sheets included - rendered its text and placeholder hard against the top edge. Measured on a real render: in a well spanning rows 711-770 (centre 740.5) the placeholder glyphs occupied 715-732 (centre 723.5) - **8.5pt high**, with the whole lower half empty; after the fix, **0.5pt**. `HelmFieldCentering` + `HelmCenteredTextFieldCell`/`HelmCenteredSecureTextFieldCell` (`HelmForm.swift`) is the fix, applied inside `makeSunkenTextField` so every well gets it at once. **Two near-identical cell subclasses rather than one on purpose**: a secure field needs an `NSSecureTextFieldCell`, and swapping in a plain `NSTextFieldCell` silently stops it masking what is typed - which on the lock screen would be a real disclosure, not a layout nit. `LockScreenSelfTest.checkPasswordWellCentringAndMasking` asserts both, and the masking half was confirmed to catch exactly that regression. This file's own predecessor hit the same AppKit behaviour and worked around it by letting the field keep its natural height inside a taller pill; a well pins its own height, so it needed the real fix.

- **`fm/grandline-settings-layout-theme-dependent-fix` fixed a real, captain-reported structural bug: Settings' whole page LAYOUT - not just its colours - changed depending on which of the 14 themes was selected.** Two screenshots at the same window size, "Daylight" selected vs. "Helm Light" selected, showed a materially different page: Daylight rendered a two-column layout (Connection/Terminal/Security left, Appearance/Morning briefing/Backup & Restore right) with the Appearance card's own theme-picker grid at roughly half page width (small swatches, a partial third row); Helm Light rendered Appearance as a full-width card directly under Connection, with the same 14 themes laid out as a much larger 4-wide grid, and Morning briefing/Backup & Restore reflowed elsewhere. **Root cause**: `SettingsController.rebuildCardLayout()`'s two-column decision was `theme.isDaylight && contentColumnWidth() >= twoColumnMinWidth` - gated on the active theme's *family*, not on width alone (a self-inflicted instance of this file's own repeatedly-documented "is this theme Daylight-family or legacy" pattern). That one condition drove both halves of the symptom: the column count itself, and - downstream of it - `rebuildAppearanceGrid()`'s own grid density, since `HelmResponsiveGrid.columns(containerWidth:...)` derives its column count from `appearanceContainer.frame.width`, which is half the page in two-column mode and the whole page in one. The gate dated to the original Daylight migration (Phase 4 slice 6) on the reasoning that a "half-migrated" look on a legacy palette would be worse than none at all - reasoning that does not survive a captain comparing the two side by side at the same window size, since a page that restructures when only the colour scheme changes reads as broken. **Fix**: the `theme.isDaylight` condition was dropped entirely from `rebuildCardLayout()` - the two-column threshold is now a pure function of the container's real width, applied identically to all 14 themes; the Appearance grid needed no code change, since its density was already purely width-derived and just inherited the fix once that width stopped depending on the active theme. **A second, genuinely separate, and deliberately UNCHANGED source of a few points of vertical noise was found and diagnosed while building the regression test**: `HelmCard.applyTheme` (`HelmDesignSystem.swift`) sets `headerTitle?.font = theme.isDaylight ? HelmType.cardTitle() : HelmType.sectionTitle()` (13.5pt vs. 15pt) - a pre-existing, deliberate, app-wide typographic decision from the original Daylight migration, applied to every `HelmCard` in the entire app, not something this bug introduced or something specific to Settings. It nudges a card's header row height by a point or two, which can shift a card's Y-origin within its column by up to ~2pt once accumulated down a column - confirmed by swapping the order two `SettingsController` instances were constructed in and seeing the exact same per-theme offset reproduce regardless of order, ruling out an AppKit warm-up/race artifact. That is not what either screenshot showed and fixing it would mean re-deriving `HelmCard`'s shared typography across dozens of unrelated pages - correctly left alone as out of scope for a "pure layout-consistency fix". **`SettingsThemeLayoutParitySelfTest.swift`** (`FM_RUN_SETTINGS_THEME_LAYOUT_PARITY_TESTS=1`) is the permanent regression guard: it builds a `SettingsController` per theme and compares a structural "layout fingerprint" (card count, one-vs-two-column state, every card's exact width and X-position/column assignment, and the Appearance grid's own per-row column counts) for exact equality, while tolerating up to 10pt of Y drift for the one sanctioned, measured, and documented `HelmCard` header-font difference above - at a width above the two-column threshold, one below it, and swept across all 14 themes. Confirmed live that reverting the fix reproduces the reported bug exactly (Daylight two-column/5-wide-grid vs. legacy one-column/wider-grid) and fails the new suite; reapplying it passes. **`DaylightDrillPageSlice6SelfTest.checkSettingsTwoColumnLayout` was also updated in the same task**, since its old assertion ("the twelve [legacy palettes] must be untouched [by two columns]") *encoded the bug itself* as expected behaviour - it now asserts the opposite, that a legacy theme crosses to two columns at the same width a Daylight theme does. **Any future per-theme "is this Daylight or legacy" branch that decides card count, column placement, or a shared grid's column density (as opposed to a colour, corner radius, or border weight) should be treated as a likely repeat of this exact bug class** - this codebase has an established, sanctioned convention of branching colour/corner-radius/shadow recipes on `theme.isDaylight` throughout the whole design system, and that convention is fine; branching *structure* (what exists, how many columns, how dense a grid is) on it is not, per this captain-confirmed correction.

## The canvas, the lists and the controls (UI modernization audit C, D, E)

**`fm/grandline-canvas-lists-controls-modernization` implemented C1-C3, D1-D5 and E1-E7 of the same audit (`data/grandline-ui-modernization-audit/report.md` §3C/§3D/§3E), the third and largest rollout batch after A1-A3 (#374) and B1-B5 (#375).** Fifteen findings; D2 was gated on a fresh captain decision and he chose option (2), "cap rows, not pages". Read §3C/§3D/§3E and §6 before extending any of it, and the captain-approved visual (`grand-line-modern-pass.html`) for the numbers - it is more specific than the report on several of them ("120ms eased state changes, a 2% press compression", "two curves total - one spring, one ease-out").

- **`HelmMotion` gained the batch's two shared primitives, and `fade` exists because of a real bug.** `spring()`/`springDuration` are the audit's own curve (`cubic-bezier(.3, 1.4, .45, 1)`, overshooting on purpose). `fade(_:to:duration:animated:)` is the one definition of "fade a view", and its header carries the finding that cost the most time here: **`view.animator().alphaValue` outside an animation context does not apply immediately.** D1's first draft used the proxy on both branches of its fade; it passed every component-level test and did **nothing at all** in a real list. Only the branch that genuinely animates may touch the proxy.
  - **The lesson generalises past that one bug: a component test whose view never had a window can pass while every real page fails.** The `HelmAccentRow` cases flipped the reveal before the row was in a window, and the proxy resolves differently there. Two cases were added specifically to close it - one drives the *real* `ReviewPRListView` and reads its rows' alphas, one asserts the mechanism on its own - and only those two reproduce the shipped bug. **Prefer driving the real page when a finding is about behaviour rather than about a colour.**

- **C1 - the canvas composes its space.** (Its *vertical* half was overturned by the captain after live use - see "The canvas is top-anchored" below - so the centring this paragraph describes is history; everything else here still stands.) The hero renders `FleetGreeting.Answer` (the same three-state decision and copy Overview's own banner computes - never a second one), and the content column centres both ways: vertically by inequality plus a 499 tie, horizontally by using only as many columns as a space has cards to fill (`HomeCanvasController.composedContentWidth`, derived from the grid's own arithmetic, never a literal). **The captain's uniform card height is untouched, as the finding requires** - what changed is the layout around it. A space with no verdict to report gets a `.neutral` badge, deliberately not a domain hue's `fallbackTint` (which resolves rose to `.critical` and would paint an alert on a page that measured nothing).
- **C2 - `HoverHighlightView.pressScale`/`baseTransform`.** The press composes with `HelmModuleCard`'s 3pt hover lift instead of fighting it: that card hands its lift to `baseTransform` rather than writing `layer.transform` directly, so there is **one owner** of that property. Opt-in per call site, because this class backs ~40 controls and a compression is right for a card you activate and wrong for a pill that is only a highlight.
  - **The mechanism matters more than the effect, and this shipped wrong twice: `HoverHighlightView` must NOT override `mouseDown` or `mouseUp`.** Either override - *even one that dutifully calls `super`* - stops a real `NSButton` nested inside the view from firing its action. The session strip's per-pill ✕ went dead, and `SessionSwitcherSelfTest` did not merely fail, it **hung** (which is what a "timed out" line for that suite in a full run means - do not write it off as the known CI flake). Bisected to `mouseDown` over three clean runs each way. The press is driven by a **local `NSEvent` monitor** instead, installed on `mouseEntered` and removed on `mouseExited`, which observes the stream and returns every event untouched - it cannot change which view AppKit delivers to. `CanvasListsControlsSelfTest.test_c2NestedButtonStillFires` is the cheap local guard so the next person to reach for a responder override here finds out at once.
- **C3 - the ribbon rests at 2pt/55% and blooms on hover.** The hue is untouched, so the domain-hue identity still reads. **The finding's own carve-out is kept and is asserted**: a card whose chip is `.bad` keeps its full edge, because quieting the ribbons is about stopping seven equal hues competing, not about hiding the one card that needs the captain.

A sidebar is always visible and carries each collection's live count, which is the thing a dropdown could not say. `StatusFilter` is deliberately a separate type from `Group`: `.active` spans two groups, and collapsing them would make "Active" mean "healthy".

- **Verified** by real off-screen renders of the real mounted page at 1180/1512/1900 and on `dusk`/`helm-light`, driving each filter through its **real** row click. **Five injected regressions each reproduced by name** (scripted file copies, never `git stash`): the row re-capped (which reported the captain's own symptom - 377pt stranded at 1512, 765pt at 1900), the filter made a no-op, Run History latching as a filter, an inert Preferences row, and counts read from the store rather than the search.
- **A probe that calls `ThemeManager.setTheme` must save and restore `fm.themeID`** - this one did not on its first run and left the self-test domain on `helm-light`, the exact poisoning this file already documents. The captain's real domain is `com.firstmate.cockpit.native`; the self-test domain is `FirstmateCockpit`.

## Forms, feedback, overlays, icons and type (UI modernization audit F, G, H, I, J)

**Fifteen findings of `data/grandline-ui-modernization-audit/report.md` §3F-§3J, shipped as five stacked PRs** (#377 F, #378 G1/G2/G4, #379 G3, #380 H, plus this one for I and J) - the fourth rollout batch after A1-A3 (#374), B1-B5 (#375) and C/D/E (#376). Read §3F-§3J and §6 before extending any of it. What is worth carrying forward:

- **G3's keep/migrate line is a rule, not a list, and the rule is where the safety lives.** Thirty `NSAlert` sites; **22 became `HelmConfirm`, 8 kept the system alert** - the four `CommandRiskConfirmation` gates, the herdr restart, the app self-update, and the two `beginSheetModal` sites. The test is "a command or a binary is about to execute outside this app's control, where the app cannot undo the consequence" - those keep the OS's own voice, because a themed dialog is this app *speaking*, and for those it is the OS that is about to act. Every migrated site keeps its exact Return/Escape mapping through `confirmIsDefault`. **A pre-existing cross-site inconsistency was found and deliberately not fixed**: ten sites let Return complete an irreversible action. Changing that is a captain decision about risk posture, not something to slip into a restyle.
  - **An `NSButton` holds exactly one `keyEquivalent`, and that broke Escape.** Giving Cancel the Return key on a `confirmIsDefault: false` dialog silently overwrote its Escape, so the whole class of "the safe answer is the default" dialogs could not be dismissed. `HelmConfirmView` carries a hidden zero-sized escape button instead. Caught by the new suite before shipping, which is the entire reason a migration this size needed one.
  - **`_ = HelmConfirm.confirm(…)` defeats a "the result is consumed" guard**, because it contains `" = "`. The guard rejects a `_ =` prefix explicitly.
  - Behavioural coverage is split honestly: `.cancel` is driven at every reachable site; `.confirm` only where the effect is safe headlessly (a `DestructiveConfirm`, a schedule delete, a runbook delete, a logout). Never for a real git push, a PR merge, a 547MB deletion or a store overwrite.
- **A view's `animator()` proxy does not apply immediately outside an animation context.** `HelmMotion.fade`'s header records it; G1's toast stacking hit it again - `restack` used `entry.bottom.animator().constant` on *both* branches, so the un-animated branch silently did nothing and toasts piled on one spot. Only the branch that genuinely animates may touch the proxy. The same shape broke `UnifiedSearchLayoutSelfTest` (a deferred `window.animator().setFrame` read back as the old height), fixed by tracking the pending frame - which also stopped the palette creeping down the screen on successive keystrokes.
- **I1 and H1 genuinely contradict, and the policy wins.** H1 asks for "destinations use their real artwork/hue" in the ⌘K palette; I1 - the report's own statement of *where each icon language lives* - says "raster app-icons only as page identity ... palette rows use symbol + hue". Both cannot be implemented literally. A palette row is not page identity, and a list of full-colour app squares beside tinted symbol rows is the "five apps" mix I1 exists to end, so the palette takes the hue and not the raster. H1's actual complaint (every action row wearing the same square) is fixed either way. `OverlaysModernizationSelfTest`'s assertion was inverted deliberately.
- **The raster policy is guarded by *use shape*, never by a list of allowed files.** `RailDestination.drillHeaderArtwork` is the one door to the raster set, so the rule is what a reader may do with it: hand it to a component as `artwork:` (the drill header, the canvas card's gradient tile, D4's empty-state watermark - the page's own identity filling its own empty area). Handing it straight to an `NSButton` or a row's image view is the violation, and it is the one that actually happened twice. A filename allowlist would need editing every time a page adds an empty state, and every edit is a chance to wave a real violation through.
- **I2: there are three equally valid ways to state a symbol's weight** - build it with a `SymbolConfiguration`, chain `withSymbolConfiguration`, or set `NSImageView.symbolConfiguration` on the view. The guard accepts all three and fails only on a symbol that states none, because that one renders at the view's default and looks like a deliberate light glyph rather than an oversight. `HelmSymbol.weight(for:)` caps at `.bold` - SF Symbols has no `.heavy`.
- **J1 retires the Georgia serif outright.** `HelmType.Voice.serif` is `.display` on the rounded face (same 22pt, so no call site reflows), Fleet's greeting moved to `heroTitle()` - the finding's own named site, and the literal "same words, two voices" defect against the canvas greeting one click away - and **`ShiftFont.serif` is deleted rather than left unreferenced**. `checkPageTitleVoice` was inverted: it used to assert the serif was reachable *only* through `pageTitle(.serif)` and now asserts it is reachable from nowhere at all. The lock screen, the one place the finding would have kept a serif, never had one.
- **J2's row-height sweep needed the fit check widened, because its scope was narrower than the finding's blast radius.** `TextScaleRowHeightSelfTest` measured one maximal `HelmAccentRow` shape and asserted it only against the four lists that share a 78pt base - so a Review PR row (64, no meta line), a Fleet log row (60, no chip) and a board card (81, chip *below* the body) had no fit coverage at all. Each is measured in its own shape now; asserting all seven against one number would be either vacuous or wrong.
  - **Measure a row in the shape its list actually renders, read off the cell's own `configure`.** The first Fleet-log fixture handed it a `meta:` line it never renders and reported the list 17pt short - a fixture bug wearing a layout bug's clothes. Checking against the pre-bump tokens is what exposed it (76 vs 60 *before* J2, so the "regression" pre-dated the change).
  - **A board card now needs exactly 81.0pt and is given exactly 81.0** - one point of shrinkage trips the check. J2 consumed that row's headroom; a further type bump clips it.
  - `LogErrorGroupListView`'s documented pre-existing shortfall went 18pt -> 19pt at Default. Still NOTE'd, still not fixable by a constant (its sibling correlation row wraps).
- **Four failures on CI's window-backed lane that every developer machine passes, and each has a transferable cause.** `main`'s windowed lane was 61/0, so all four were this rollout's - but only two were app defects.
  - **A GitHub runner has Reduce Motion ON.** H4's parallax check read `driftDurations` off the two wave layers with the setting untouched, so on a runner it measured GL-16 *working* - `startAnimationsIfNeeded` deliberately attaches neither drift there - and called it "no parallax". Any check that measures an animation must pin `HelmMotion.reducedOverrideForTests` rather than inherit the host's setting; pinning it also makes the *reduced* half assertable, which is coverage such a check usually lacks.
  - **Bucketing a coordinate has edges; cluster instead.** F3's swatch-grid check rounded each y centre into a 4pt bucket and reported "3 row(s), want 2" for a real two-row grid - two swatches on one row split whenever they straddle a bucket edge, and `NSButton.alignmentRectInsets` guarantees they sit a fraction apart. No bucket size fixes it. Group centres that are *near each other*, which has no edge and is what "distinct rows" means.
  - **`Expression N unable to find variable … in engine 0x0` means you forced layout on a view with no window.** `ConsoleController.setSRELeadPaneOpen` ran `NSAnimationContext.runAnimationGroup { view.layoutSubtreeIfNeeded() }` unconditionally, and it is reached from `applyTheme` via `ThemeManager.observe`'s **synchronous fire at registration** - i.e. inside `loadView`, before the view is in a window. It crashed a whole suite (SIGABRT) on a slower host and never reproduced locally. **Guard a forced layout pass on `view.window != nil`**: with no window the constraint constant alone reaches the same geometry, and an animation nobody can see is not worth a crash. This generalises to every `layoutSubtreeIfNeeded` reachable from a theme observer.
  - **A frame already scheduled when visibility flips still runs.** The Whiteboard's display-gating check demanded exactly 0 frames while hidden; that feature's own notes record 1 as correct. `<= 1` keeps the assertion real (an ungated page ticks ~30fps).
- **`grep -c` exits 1 when the count is zero**, which short-circuits a `cmd | grep -c error: && run-the-test` harness and reports an injected regression as "did not reproduce". Use `grep -q error: ||`. One R8 injection was written off as slack before this was spotted; the check was actually pinning the value to the point.

## UX15 - the two theme families: measured, and deliberately not closed

Full review #3's UX15: "Segmented tabs, module cards, icon rows and hover
states differ between the Daylight family and the 12 legacy palettes (UI13,
B7). A captain who switches between `catppuccin-latte` and `dusk` gets two
apps. Either finish extending the Daylight recipes to the legacy palettes (the
§3K option not taken) or retire the legacy palettes to a 'classic' setting."

The `fm/grandline-audit3-ux-fixes` batch (UX1-UX15) **measured this and did not
attempt it**, on the brief's own instruction not to leave the app in a third,
inconsistent state. This section is the measurement, so the follow-up does not
have to re-derive it.

### The size of the gap

`theme.isDaylight` is the branch. Every occurrence is a place where the two
Daylight palettes get one recipe and the twelve legacy palettes get another.

**143 branches across 36 files.** By file:

| Branches | File |
|---|---|
| 25 | `HelmDesignSystem.swift` |
| 15 | `HelmForm.swift` |
| 11 | `UnifiedSearch.swift` |
| 10 | `DaylightBarController.swift` |
| 8 | `HelmDaylight.swift` |
| 7 | `SettingsController.swift` |

### The two options, priced

**Extending the Daylight recipes to the legacy palettes** is not 143 edits. It
is 143 *design decisions*, each of which then has to hold across twelve
palettes in both light and dark registers, and each of which
`FM_RUN_CONTRAST_TESTS` will sweep. The Daylight recipes are built on
`DaylightTokens` - a token layer the twelve palettes do not have - so most of
these are not "apply the same colour", they are "decide what this token means
for a palette that was never designed around it".

It is, however, **strongly front-loaded**, which is the useful finding here:
the top five files are 69 of the 143 branches (48%), and four of those five are
shared components rather than pages. Closing `HelmDesignSystem`, `HelmForm`,
`UnifiedSearch` and `HelmDaylight` would close roughly half the gap and would
do it in the components every page already renders through - which is where a
captain would *notice* it. That is a plausible first slice for a dedicated
task, and it is a much better shape than working down the list by page.

**Retiring the twelve to a "classic" setting** is cheaper in code and is not
this task's call to make. It removes twelve themes the captain may be using,
and the selection is persisted per-captain (`fm.themeID`) - so it is a product
decision about what the app offers, not a refactor. It also interacts with
`FM_RUN_CONTRAST_TESTS`, which currently sweeps every theme × every tint and is
one of this repo's better guards; shrinking the theme set shrinks what that
sweep proves.

### The recommendation

**A dedicated task, taking the extend option, in component-first slices** -
starting with the five files above rather than with any page. The retire option
should not be taken without the captain saying so, because it is a decision
about the product rather than about the code.

Two things that are *not* blockers and are worth knowing:

- Nothing here is broken. Both families render, both clear the contrast floor,
  and `FM_RUN_CONTRAST_TESTS` sweeps both. The finding is about coherence, not
  correctness - which is exactly why it is safe to defer and wrong to rush.
- The branch count is a fair proxy for the gap but not a perfect one. Some of
  the 143 are a single colour; a few (`DaylightBarController`'s, `HelmForm`'s)
  are whole alternate layouts. A slice should be scoped by reading the
  branches, not by counting them.
