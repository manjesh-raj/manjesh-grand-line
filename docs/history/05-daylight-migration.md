- **`HelmDaylight.swift` is the Daylight token layer, and `daylight` is a real, selectable 13th `HelmTheme` (`fm/grandline-daylight-migration-phase1`, Phase 1 of the 7-phase Daylight UI migration - the spec is `data/grandline-ui-modernization-review/daylight-ui-design.md` §2/§3/§6.2/§8; read §2 in full before touching any value here).** Phase 1 is **tokens only** and deliberately changes nothing visible: no page is restyled, `ThemeManager`'s default is still `helm-dark`, and Daylight simply appears in the theme picker and Settings' Appearance grid (both derive from `HelmTheme.allThemes`, so neither needed a code change). **Phase 2 - `DaylightBarController` + `HomeCanvasController` replacing the rail and top bar - has since shipped; see the next bullet.** What to know:
  - **Every colour is either a §2.1-§2.3 token, one of §2.4's six measured corrections, or a minimal darkening of one that this file derives and states.** Nothing was invented to fill a gap, and `HelmContrastSelfTest.checkDaylightPalette` re-measures all of it against the codebase's own WCAG formula rather than trusting the table - **including the raw values the corrections replaced**, asserting those genuinely *fail* the floor, so a reverted correction is reported as such instead of quietly passing for an unrelated reason. All 16 ANSI slots are built from §2.4's own text-corrected values (an ANSI slot's job here is precisely "this hue as text on the theme's own background"); only cyan and the two greys needed a value §2.4 does not list, each a measured minimal darkening.
  - **Two deviations from the spec, both deliberate and both asserted by the self-test rather than only commented.** (1) §2.1's dark terminal card (`termBg`/`termInk`) is **not** this theme's `backgroundHex`: in this codebase that one token is simultaneously SwiftTerm's background *and* every destination's page ground *and* one of the two surfaces `HelmContrast`/`mutedInk` score every chrome colour against, so pointing it at `#23242B` turns every page dark. `backgroundHex` is `paper`, the term tokens are recorded on `DaylightPalette` for the phase that owns the Console page (§6.13, Phase 4 - which will also need its own contrast-verified ANSI set for a dark card), and `HelmTheme.apply(to:)` is untouched, as the migration's own "must NOT change" list requires. (2) `HelmType.body()` stays at 12 and `pageTitle(.serif)` stays Georgia even though §3 retunes both - each is a visible app-wide restyle, which Phase 1 is explicitly not allowed to make; the serif retires naturally when Phase 2/4 moves its callers onto the new `heroTitle()`/`drillTitle()`. `checkDaylightTypeRoles` fails if either is "fixed", so the next agent has to read why first.
  - **`HelmDomainHue` is the one genuinely new colour concept, and its per-theme fallback is the load-bearing half** (§2.8). On Daylight it returns §2.2's seven gradient pairs verbatim; on any of the 12 pre-existing palettes it borrows that palette's own `HelmTint` slot (1:1 in both directions - seven hues, seven cases, mapped by role: `teal`→`.accent` because the theme's own accent is its identity hue and is literally cyan in `helm-dark`, `rose`→`.critical`, `slate`→`.neutral`) and derives the lighter end by blending **0.32 white**, a fraction *measured off Daylight's own seven pairs* rather than picked. That fallback is what lets a Phase 2/4 component ask for "the Hosts hue" unconditionally, so `RailDestination.domainHue` (§2.2's "Owns" column; the four Setup sub-pages share amber, since §2.2 gives the hue to the area not the page) is safe to call on any theme. It is deliberately separate from the pre-Daylight `flyoutTint` - that answers "what does this row's `IconTileView` wash", this answers "what hue does this area of the app own" - so changing one must not silently change the other.
  - **A real bug this phase found in an existing helper, worth not re-discovering: `HelmContrast.legible` cannot correct a base that already *is* the endpoint it would blend toward.** It picks that endpoint from the *surface's* luminance, so `legible(.white, over: <mid-luminance hue>)` returns white unchanged - a silent no-op that left five of the twelve fallback palettes' gradient tiles at 2.64-2.91:1 while reporting success. `HelmContrast.legibleGlyph(over:target:)` is the fix and the one a coloured fill's glyph should use. Its rule is **directional on purpose**: white is preferred and kept whenever it clears the 3:1 icon floor, and only a fill white genuinely cannot carry steps toward whichever endpoint has headroom (yielding a grey glyph, the smallest correction). Deliberately *not* "pick whichever of white/black scores higher" - black beats white on several of Daylight's own hues (amber measures 6.42 black against 3.27 white), so that rule would put a black glyph on the amber tile and abandon the approved design for a floor white already clears.
  - **A measured caveat on `HelmGradientTile`, recorded rather than hidden.** §2.4 claims all seven tile hues pass 3:1 with a white glyph (lowest amber 3.27) - true, and re-verified, **against `h1`**, the gradient's darker end. Against the 135° midpoint the glyph actually sits on it does not hold: blue 3.54, violet 3.68, rose 2.99, teal 2.91, green 2.74, slate 2.74, amber 2.53. Both fixes were measured and both were rejected: correcting the glyph greys it on five of seven hues, and pulling `h2` back toward `h1` until the midpoint clears costs most of the gradient (amber survives with 32% of its spread, i.e. a flat tile). Neither is worth it, because the floor's own exemption applies - every tile in §4's table sits beside a visible text label carrying the same information, so the glyph is redundant decoration rather than the sole carrier of meaning. **An icon-only Daylight tile would need one of those two corrections and must not be added without re-opening this.**
  - **`HelmMetrics`' nine `d*` radii are §2.6's complete set, and `daylightRadii` is enforced**: `checkDaylightRadiiScale` asserts the set equals the spec's nine literals *and* that every named token is a member (which is what catches a tenth token added without extending the set). They sit alongside the pre-Daylight `rChip`/`rControl`/`rCard`/`rPanel`/`rRow` rather than replacing them - re-pointing those would restyle every existing card and chip in every theme - and the overlap (`rCard` 12 == `dTileLarge`, `rRow` 10 == `dTileSmall`) is intended, converging as Phase 4/5 migrates each page. `dCapsule` (999) is a **sentinel**: pass it through `HelmMetrics.capsuleRadius(forHeight:)`, never straight to a layer.
  - **`HelmCard.elevation(for:level:)` carries §2.5's two levels and only two** - the spec states the depth system as "exactly two", and a third would be a new definition rather than a use of this one. Daylight's are §2.5's measured values, ink-tinted (`#2A2B33`, not black - a black shadow over warm paper reads grey-green); **every other palette's `.resting` is byte-identical to what this method always returned**, asserted per theme, so `ConsoleCardChrome` renders exactly as before, and `.raised` scales that definition by the same ratios §2.5 uses between its own two (alpha x1.5, blur x1.87, offset x2.33).
  - **`HelmField.fill` now returns Daylight's own `inset` token**, and what that revealed is the part worth keeping: Daylight is the first palette whose card and page differ in a direction that puts the old 8%-toward-ink derivation almost exactly on the page's luminance (1.01:1 against `paper`), which `checkFieldRecipe` caught. Switching tokens is *not* what resolves it - `inset` is no further from `paper` (1.02:1); on this palette a well on the bare page is separated by its 1px `hair` border by design, and a well on a card (where every form in this app actually lives) reads at 1.14:1. So that check now **proves the border carries the boundary wherever the fill cannot**, rather than exempting a theme; a well that fails both is still a failure, and no pre-existing palette takes that branch.
  - **`pairId` is `helm-dark`, deliberately one-way.** No Dusk exists (§2.8), so ⌘⌥T from Daylight lands on a real dark palette rather than nowhere; `helm-dark` keeps pairing back to `helm-light`, because re-pointing it would change ⌘⌥T for a captain who has never selected Daylight. Revisit when Dusk lands - which §2.8 states as required debt before the dark options can be dropped.
  - **Verified by `swift build` (clean debug and release, zero warnings in this app's sources), the release binary carrying no `FM_RUN_*` strings, and all 65 runnable suites - deliberately without launching the app**, per the README's worktree rule. **Seven injected regressions each reproduced by name**: the prototype `muted` value (7 failures across three checks), the `legible(.white, …)` no-op glyph correction (the exact five fallback palettes), a tenth radius, §3's `body()` bump, a drifted Daylight shadow, `daylight` dropped out of `allThemes`, and a tile reading the §2.2 table unconditionally instead of resolving per theme.
- **The icon rail and the old top bar are gone: `DaylightBarController` (a floating bar) plus `HomeCanvasController` (a widget hub) are the app's whole navigation now (`fm/grandline-daylight-migration-phase2`, Phase 2 of the 7-phase Daylight UI migration - the spec is `data/grandline-ui-modernization-review/daylight-ui-design.md` §5 in full, plus §6.1/§6.2/§6.3/§6.4; read §5.1's "what dies, what survives" list before touching any of it).** This is the migration's one structural phase. `IconRailController.swift` and `TopBarController.swift` are **deleted**, not disabled. Everything *below* the chrome is deliberately untouched: `AppShellController` is still the window's root and still owns `bodyContainer`, `DestinationRegistry`'s permanent-mount/`isHidden`-toggle model is unchanged, and a "drill page" IS a mounted destination shown full-body exactly as before - it just sat `HelmDrillHeader.height` further down (**not any more - A2 removed that strip; see "## Window chrome fusion" below**). **Phase 3 (live data into every module) is next; §6.1's own instruction to wire real sources during this phase means most of it already landed here - see the "what Phase 3 still owes" bullet at the end.**
  - **The new shell, in three parts.** `root` holds `DaylightBarController.view` (pinned 14pt below the top, 22pt from each side, height 50, radius 18) and `bodyContainer` (full window width, starting `DaylightBarController.reservedTopHeight` down). Inside `bodyContainer`: `HelmDrillHeader` across the top, then every destination pinned below it - **both halves of that sentence are historical now; the UI modernization audit's A2 merged the drill header into the bar and a destination is pinned to `bodyContainer`'s own top, see "## Window chrome fusion" below.** `bodyContainer` no longer starts at the rail's trailing edge - it spans the full width, which is the one thing `AppShellBodyWidthSelfTest` had to be re-pointed at (its expectation went from `window width - 84` to `window width`; every case is otherwise unchanged, and the bug it guards - a stale `bodyContainer` frame - is unaffected by which width is correct).
  - **`RailDestination` survives un-renamed, and one thing about it changed meaning.** §5.1 names it as the routing enum, and ~20 files switch on it; renaming would have been a large purely-cosmetic diff. But **its case order is no longer load-bearing** - it used to be the rail's top-to-bottom order via `allCases`, and nothing iterates it for layout any more (the canvas's order is `DaylightModule.canvasOrder`). `isDailyUse` and `flyoutTint` likewise have no remaining consumer; they are kept so the rail's decision history stays greppable. New case: `.homeCanvas`, with its own `DestinationSlotID` and an **eager** mount, because it is the launch landing and every back button's target. `.overview`'s title changed from "Overview" to "Fleet" (§7: Overview *becomes* the canvas; the old page is the Fleet drill page).
  - **Spaces are presentation state and live in exactly two places** (§5.3). `DaylightSpace.swift` holds the five-case enum, the module→space table and §5.4's copy; `HomeCanvasController` holds the current selection. The bar draws pills and reports clicks, `AppShellController.selectSpace` does the navigate-then-filter two-step, and **no store, poller, registry or notification source knows spaces exist**. The membership is a **locked captain decision** (the spec's own decisions block) and `DaylightModuleSelfTest.checkSpaceTable` restates it as literal data rather than deriving it from the enum - a test that reads the table it is checking asserts nothing.
  - **`⌘1`…`⌘5` resolved by menu order, and that was the design rather than an accident, for as long as both the View and Tab menus existed.** The spec asked for `⌘1`…`⌘5` on the spaces *and* for Console/Tools `⌘1`…`⌘9` tab selection to be unchanged - which collide. AppKit picks the first *enabled* match scanning the main menu in order, and the Tab menu's items were `nil`-target (responder-chain routed). So with a terminal or Tools tab focused, `ConsoleController`/`ToolsController` was in the chain, the Tab item was enabled, and `⌘1` selected tab 1 exactly as before; anywhere else - including the canvas, where a captain reaching for a space actually is - nothing answered `selectTabByShortcut`, AppKit disabled that item, **a disabled item does not consume its key equivalent**, and `⌘1` fell through to the space item. The space items lived in the **View** menu (which came after Tab) and targeted `AppShellController` explicitly. **This whole mechanism is now historical** - `fm/grandline-console-tabs-restore-tabmenu-fix` removed both the View and Tab top-level menus outright (see "## Menu bar"), so there is nothing left for `⌘1`…`⌘5`/`⌘1`…`⌘9` to collide over; a space is selected by clicking its pill, a tab by clicking its chip.
  - **`HelmModuleCard` is the canvas widget** (§6.1): a 6pt gradient ribbon, a header row (30pt `HelmGradientTile` + title/subtitle + trailing chip), and one of five body kinds - `metric`, `peekRows`, `ring`, `progress`, `note` - plus `paragraph` for the wide briefing. Two layers, not one, and it is load-bearing: a shadowed layer must not clip and a rounded fill must, so the outer view carries the shadow (`masksToBounds = false`, explicit `shadowPath`) and an inner `HoverHighlightView` carries the fill, border and clip - the arrangement `HelmComposerCard` already proved here. The inner view is a `HoverHighlightView` specifically so §6.1's "the card is a `.button`" comes from the component (role, label, focus ring, keyboard press) rather than four overrides. **`maxPeekRows` (3) is enforced, not advisory**: a module handing over more rows is putting a table on the canvas, which is what §1's third rule forbids. `HelmRingGauge` and `HelmProgressBar` (§6.8) ship in the same file.
  - **`HelmResponsiveGrid.spanningRows`/`packRows` is the span-2 extension** (§6.1), sitting beside the existing `rows(_:)` rather than replacing it. It cannot use `.fillEqually` - a span-2 card is two columns plus the gap between them - so each card carries an explicit width constraint and a short row is padded to the full column count with spacers. **Every one of those width constraints is `HelmDaylightPriority.contentTie` (499), never required**, because the chain runs up through the canvas's document view to `bodyContainer` and therefore to the window (gotcha (13)). `packRows` is pure arithmetic, split out so the packing can be asserted without building a view - the failure it guards (a wide card rendering one column wide, a row overflowing) is a *math* bug. Packing is greedy rather than best-fit on purpose: the module order is captain-visible, and a packer that reorders to fill rows tighter would shuffle cards around on every resize.
  - **`HelmDrillHeader` is a *shell* header, not a per-page one**, and that is what made this phase's diff reviewable. One view owned by `AppShellController` gives all seventeen destinations a back button, a domain-hued tile and a live title without editing a single destination controller - restyling each page's own header chrome is Phase 4, in §7's table order. On the canvas it collapses - **which used to mean `isHidden` *and* a zero height constraint** (gotcha (11)), and no longer does: the audit's A2 made it an arranged subview of a stack inside the bar, where that gotcha's own `NSStackView` exemption applies and `isHidden` alone is enough. See "## Window chrome fusion" below.
  - **The canvas never constructs a store and never fires a fetch**, and `DaylightModuleSelfTest.checkCanvasConstructsNoStores` is a source guard on exactly that. It is not tidiness: the canvas is the launch landing and re-renders on every return from a drill page, so one `FleetDataSource.snapshot()` or `OpenPRsSource.fetchDetailed()` in there would make every back-navigation a multi-second stall *and* double the fleet's real workload. Instead: `FleetController.onSnapshotChanged` pushes its **own** refresh result here (that refresh already runs at launch, on every Overview visit, on the manual button and after a merge), `ServiceHealthRegistry`/`BackgroundSignalsPoller.lastCounts` are read as already-published state, five stores are injected, and the one on-disk read is a small runbook directory scan. The Refresh button calls the two pages' existing `refreshIfNeeded()`, not anything new.
  - **`FleetGreeting` (in `FleetData.swift`) is the extraction §5.4 asked for**: the time-of-day greeting *and* the answer-banner decision (which of three states, and the exact copy for each), as pure functions. `FleetController.render`/`renderBanner` call them, so the hub's one-line summary and Overview's banner are one computation - a hub whose summary disagreed with the page it links to would be worse than no summary. GL-14's rule rides along: with a failed PR scan the "all clear" branch reports the PR half as *unknown* rather than a confident zero, and the suite asserts the canvas never renders "0 PRs ready" in that state.
  - **`BackgroundSignalsPoller.SignalCounts` gained `vaultSecrets`**, recorded off the snapshot `checkVault` already loads. §6.1 is explicit that the Vault module "renders the LAST snapshot, it does not shell out on canvas load", and this costs no new `av` invocation anywhere.
  - **The bell and avatar moved, and nothing about them changed.** `NotificationCenterController` (store, adapters, dedup, badge) is unchanged and now lives on the bar; `AvatarLogoutPopoverController` and `HoverTrackingButton` moved verbatim out of the deleted rail file into `DaylightBarController.swift`. The notification panel took §6.12's two Daylight touches only: 340 -> 360 wide, and its header reads "Waiting for you" rather than "Notifications". The rail badge is gone with the rail - the same already-computed counts still reach the captain through the bell and through the Fleet/Merge-queue module chips, and no new signal was invented for either.
  - **No `NSVisualEffectView` anywhere in the bar**, asserted structurally. §6.3 calls gotcha (8) out by name for this exact surface, and the suite walks the bar's real subtree rather than trusting the reasoning.
  - **A finding worth not re-discovering: `autoreleasepool` is mandatory in any headless AppKit self-test that measures deallocation.** The suite's observer-leak check (fifteen self-theming cards are torn down on every space switch, so a card that failed to deallocate would leak a `ThemeManager` closure per rebuild) first reported 224 leaked observers over 20 switches and a live-card count climbing 69 -> 181 - which reads exactly like a retain cycle. It is not one: a headless suite never turns the run loop, so nothing drains the pool that removed views are autoreleased into. Draining per switch reports a flat 69 -> 69. The check is real and was confirmed to catch a genuine leak (removing `HelmModuleCard.deinit`'s `unobserve` reproduced 112 extras), but it would have sent the next agent chasing a cycle that does not exist.
  - **Verified by `swift build` (clean debug and release, zero warnings in this app's sources), the release binary carrying no `FM_RUN_*` strings, and all 66 runnable suites - deliberately without launching the app**, per the README's worktree rule. `FM_RUN_DAYLIGHT_MODULE_TESTS` is window-backed, so it sits in `run-all-tests.sh`'s `NEEDS_SESSION` list beside `AppShellBodyWidthSelfTest`. **Six injected regressions each reproduced by name**: a module moved into the wrong space, grid width constraints raised to required, an `NSVisualEffectView` added to the bar, the canvas constructing its own `DocsRunbookStore`, a drill header that never collapses on the hub, and the card's missing `unobserve`.
  - **What Phase 3 still owes.** §6.1's table is wired end to end - all fifteen modules read their real source today - so Phase 3's remaining scope is narrower than its name suggests: the two modules whose numbers come from `BackgroundSignalsPoller.lastCounts` (Setup, Vault) render an honest "hasn't been checked yet this session" for the ~10s before that poller's first pass, and the Tools and Settings modules are deliberately static text (§6.1's table says "static" for both). Everything else is live.
- **Phase 3 (`fm/grandline-daylight-migration-phase3`) verified §6.1's table module by module and found Phase 2's own "all fifteen read their real source" claim was accurate about the *reads* and wrong about two *pushes* - a live module needs both, and only a behavioural check can tell them apart.** Thirteen of fifteen modules needed no change (the bullet above's inventory holds); the two defects were both invisible in the source, because in each case the reading code was already correct and nothing called the thing that fed it.
  - **The Setup and Vault modules never left their loading state.** Both read `BackgroundSignalsPoller.lastCounts`, whose first pass lands ~10s after launch - and the canvas is the *launch landing*, so no `viewWillAppear` fires afterwards and nothing else it observed changed when a pass completed. Both cards said "hasn't been checked yet this session" for the rest of the session, however long the app stayed open. Fixed with `BackgroundSignalsPoller.observeCounts`/`unobserveCounts` - a token-based fan-out fired from `lastCounts`' own `didSet`, on the main thread it was already written on (enforced with a `dispatchPrecondition`, not just claimed). **This adds no poll**: the poller's cadence, passes and subprocesses are untouched, and `notifyCountsObservers` can only hand out numbers that already exist. `checkVault`'s two-field write was coalesced into one assignment so a single pass fans out once rather than twice.
  - **The tempting fix - riding `GrandLineNotificationCenter.observe`, which the poller already publishes into on the very same main-thread hop - is wrong, and wrong in the worse direction.** `NotificationSources.set*` collapses a zero count into `set(nil, id:)`, and that is a *silent no-op* when nothing was there to remove (`GrandLineNotificationCenter.set`'s own `if changed` guard). So a clean machine - no updates, no drift, no vault attention, the common case - would notify nobody and stay stuck on "unknown", while only a machine with a real problem updated. Verified by reading that guard, not assumed. Any future "the hub should react to X" wiring needs the same check: does the source actually publish when the answer is *nothing*?
  - **The canvas's counts observer is deliberately NOT gated on visibility**, unlike its `ServiceHealthRegistry` one. A first pass landing while the captain is on a drill page still has to reach these cards, or returning to the hub shows a stale "not checked yet" until something else forces a render. The cost is one coalesced rebuild per pass, i.e. at most one per 15 minutes.
  - **`HomeCanvasController.applyDictationStatus` was dead code.** It existed, was correct, and nothing ever called it - so the Dictation module's chip showed its initial value forever: "Ready" mid-recording, and "Ready" on a machine that had never granted microphone access. `AppShellController.setDictationEngineStatus` forwards to it now (a third subscriber to a signal the engine already fanned out twice, not a new signal). The module's initial value is also no longer a hardcoded `.ready`: `pushedDictationStatus` is `nil` until the engine pushes, and the module falls back to `DictationPermissions.currentStatus()` - three synchronous authorization-status reads, no subprocess, the same seed `DictationController` uses.
  - **The honest loading state is two states, not one.** `nil` counts plus "no pass has completed" (`lastCompletedPassAt == nil`) is genuinely "checking", and renders a `Checking…` chip plus copy saying the card fills itself in. `nil` counts *after* a pass completed is a real fault, and keeps the flatter "hasn't been checked yet" wording. Neither ever renders a fabricated number or an "all current" verdict - GL-14's rule, one more signal.
  - **`FM_RUN_DAYLIGHT_MODULE_TESTS` gained two cases**, and **all three failure modes were confirmed to reproduce by name**, not merely to pass: removing the subscription (failed both the behavioural observer-count assertion and the source guard), removing the dictation forward (named the wrong chip for two statuses), and reverting the loading copy. `checkLiveModuleWiring` also pins that an *unchanged* publish fans out zero times. `checkNoNewPolling` is Phase 3's one-line rule as a source guard - no `Timer`/`asyncAfter`/`DispatchQueue.global` in the canvas, the subscription present, and unregistered.
  - **A self-test honesty note worth keeping**: the behavioural "the cards changed after a real publish" half proves the *content* is right, and deliberately does not claim the render was attributable to the counts observer - a window-resize notification arriving during the drained main-queue turn would relayout the grid too. The wiring proof is the observer-count assertion and the fan-out count, which is exactly what failed when the subscription was removed. A headless suite never turns the run loop, so the canvas's render-coalescing `DispatchQueue.main.async` hop has to be drained explicitly (`drainMainQueue`); a `sleep` would not run it at all.
  - **Two spec deviations left alone on purpose, flagged rather than "fixed".** §6.1 wants the Fleet module's peek rows to carry each crew member's *elapsed* time - `FleetTask` has no such field, so producing one would be new collection, which this phase forbids; the rows carry the real status instead. And §6.1's Merge queue chip/subtitle split ("N open" / "N ready") is correct as built: `FleetDataSource.mergedPRs` is every open PR deduped, not a pre-filtered ready list, and the module filters it through `FleetDataSource.canMerge` itself.
  - **Phase 4 (per-destination drill-page restyles, in §7's table order - Tasks and Review first) is next.** Nothing in this phase touched a drill page's content.
- **`fm/grandline-daylight-canvas-refinements` is the captain's own override of two Phase 2 decisions, taken after seeing the hub running: every module card is now the same size, and the aggregate "Setup" card is four separate cards.** Read `DaylightSpace.swift`'s own enum comment before changing either - it is where both overrides are recorded.
  - **Uniform sizing.** §6.1's "wide variant" (the Morning briefing spanning two grid columns) is gone: `DaylightModule.span` and `HelmModuleCard.Content.isWide` no longer exist, and `HomeCanvasController.rebuildGrid` uses `HelmResponsiveGrid.rows(_:)` - the plain `.fillEqually` grid every other card grid in this app already uses - instead of `spanningRows(_:)`. **`spanningRows`/`packRows` are deliberately kept as uncalled infrastructure** rather than deleted: a concurrent crewmate was actively investigating them as a suspect in a live width bug at the time, the spec still describes span-2 as a grid capability, and `DaylightModuleSelfTest` still exercises `packRows` directly with literal spans so it cannot rot unnoticed. Note the difference if it is ever reinstated - `spanningRows` creates explicit per-card width constraints (at priority 499, gotcha (13)); `rows(_:)` creates none at all.
  - **The briefing paragraph is capped at `HelmModuleCard.maxBriefingClauses` (3)**, for the same reason `maxPeekRows` exists: unbounded, it would make its whole grid row as tall as the longest briefing of the day. It stays a `.paragraph` rather than becoming peek rows because each clause carries a real `BriefingTarget` and peek rows would throw the deep links away. The overflow is *stated* (a trailing plain `.none`-target clause, "+N more on Overview.") rather than silently dropped - the "no silent caps" rule.
  - **A real, non-obvious width regression this uncovered, and the reason the fix is where it is: an `NSStackView` resists clipping below its arranged subviews' minimums at `.defaultHigh` (750) by default, which is above `NSLayoutPriorityWindowSizeStayPut` (500) - so any stack inside a grid cell is a *window* floor unless told to yield.** In a `.fillEqually` row that floor is multiplied by the column count, so one card holding a long note capped `AppShellController.bodyContainer` at exactly **1135.5pt on every destination at once** (`.homeCanvas` is eagerly mounted, so its constraints are live whatever page is showing - gotcha (11)). This is a **fifth** distinct route to that recurring symptom, and it was invisible until the briefing card narrowed to one column: the double-width cell had been hiding it. Fixed with `HelmModuleCard.compressibleStack` - `setClippingResistancePriority(.defaultLow, for: .horizontal)` on the header row and every body row (gotcha (12): the *stack*-level API, since the content-priority ones are no-ops on a view with no intrinsic size). **Measured, not assumed, and worth not re-deriving: a leaf's own compression resistance does NOT propagate through a stack that has already agreed to clip** - dropping the paragraph `NSTextView`'s own 750 priority changed nothing once the stacks yielded, so that speculative change was reverted rather than shipped.
