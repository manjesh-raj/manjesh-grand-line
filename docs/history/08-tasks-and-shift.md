## Shift

- **`.shift` (`fm/cockpit-shift-foundation`, phase 1 of a multi-phase, captain-approved build) is a rail destination pinned in `navStack` right after `.hosts` and before `.review`** (`fm/cockpit-shift-rail-position` moved it there from right after `.overview`, per a captain correction) - deliberately NOT part of the bottom-anchored Tools/Docs/Updates/Bootstrap/Settings group, since this is a daily-use destination, not a utility. `IconRailController.RailDestination`'s case order is `overview, console, hosts, shift, review, ...`, which is what puts `.shift` there in `navStack`'s loop for free (see the enum's doc comment). Shift is a personal task/follow-up/project tracker backed by local YAML files instead of a database - the plan is multi-phase; this phase is foundation only.
- **The core distinction the captain was explicit about, and that no future phase should blur: a task is something to do, a follow-up is something to check on later.** They are modeled as two separate types (`ShiftTask` vs `ShiftFollowUp` in `ShiftModels.swift`) with different fields, never a shared "item" type with a kind flag. A follow-up is not "a task with a reminder."
- **Data layer (`ShiftStore.swift` + `ShiftYaml.swift` + `ShiftModels.swift`)** lives under a captain-configurable root, overridable via `FM_SHIFT_DIR` - the same convention `HostStore`/`SSHKeyStore`/`SnippetStore` already established with their own `FM_*_FILE` env vars. **As of phase 4 (`fm/cockpit-shift-git-sync`), the default root (when `FM_SHIFT_DIR` is unset) is `personal-tasks/` inside a local git clone of the captain's real `manjesh-config` GitHub repo, not the bare non-git folder phases 1-3 used** - see the "Git sync (phase 4)" bullet below for the clone/commit/push/pull mechanics. Directory layout under that root (batched files, not one file per task or follow-up, per the captain's explicit decision) is unchanged from phase 1:
  ```
  personal-tasks/                    (was a bare `shift/` folder in phases 1-3, see above)
  ├── tasks/
  │   ├── active.yaml
  │   └── completed/<YYYY-MM>.yaml   (one file per month a task was completed in)
  ├── follow-ups/follow-ups.yaml
  ├── projects/projects.yaml
  ├── notes/notes.yaml
  ├── activity/<YYYY-MM>.yaml        (history log, split by month like completed/)
  └── settings.yaml
  ```
  `ShiftStore.setTaskCompleted(id:completed:)` is the one place that moves a task: marking it done removes it from `active.yaml` entirely and appends it to that month's `completed/<YYYY-MM>.yaml` (never just a status flag flipped in place); un-marking it does the reverse lookup across every completed month file and moves it back. `ShiftStore.reloadAll()` re-reads every file from disk - it's what `ShiftController.viewWillAppear()` calls, so the page always reflects real on-disk state, not a stale in-memory copy.
- **YAML I/O reuses the Tools page's vendored library end to end, not a second YAML layer.** `ShiftYaml.swift` converts between the typed models above and `Yaml` trees, then serializes via `YamlBeautify.dump` (the exact function the Tools page's Beautify button uses) - so Shift's files automatically inherit `Vendor/YamlSwift`'s local order-preservation (`YAMLOrderedMap.swift`) and quote-preservation (`YAMLQuoteStyle.swift`) patches for free. One deliberate difference from the Tools page's passthrough Beautify: Shift always decodes a file into its typed Swift struct and re-encodes from a fixed field order (the order listed in the brief: `id, title, description, status, priority, due_date, ...`), rather than preserving whatever arbitrary key order a hand-edited file might have - since Shift owns its own schema end to end, this is a deliberate, simpler contract, not a lost capability. Every string field is written double-quoted (`.string(_, quoted: .double)`) so a value that looks like a YAML reserved word (a task titled `"true"`, a tag `"123"`) round-trips as a real string, not a coerced bool/int - checked directly in `ShiftStoreSelfTest.swift`, not assumed to transfer from the Tools page's own equivalent check.
- **List rendering (`ShiftListViews.swift`) is `NSTableView`-based for both the task list and the follow-up list**, following `DiffResultView.swift`'s pattern verbatim rather than a plain `NSStackView` of permanent rows - see this file's Diff-tool history above for the ~13.6-second layout blowup that pattern hit once a list grew into the hundreds. Measured live at 350 rows here: `setTasks` + `reloadData` ~0.4ms, a bounded-height enclosing `NSScrollView`'s `layoutSubtreeIfNeeded` ~70ms - no repeat of that pathology, because the table only builds row views for what's actually visible.
- **`ShiftController.swift` ("My Tasks") mirrors `FleetController.swift`'s page shape** (greeting header, stat tiles, `FlippedView`-backed scroll area) rather than three separate Today/My Tasks/Follow-ups pages - the captain explicitly rejected that split as redundant. Stat tiles: tasks due today, pending follow-ups, overdue tasks. The task list's checkboxes call `ShiftStore.setTaskCompleted` directly (the same move-not-flip behavior above) and the view re-renders from a fresh `store.activeTasks` read afterward.
- **Subtasks (`ShiftSubtask`, nested on `ShiftTask`) are only ever rendered in a project-scoped context, never as flat rows in the main task list** - this is a hard rule, verified directly (not just assumed) across all three phases so far - see the phase-specific Verification bullets below.

- **Git sync (phase 4, `fm/cockpit-shift-git-sync`) replaced phase 1-3's bare local folder with a real git-backed root, reusing `DotfilesData.swift`'s local-clone-plus-shell-`git` shape and `DocsSyncSource.ghAuthToken()` for auth - not a second git-sync mechanism.** `ShiftGitSync.swift` is the whole implementation: `ShiftGitSync.shared` (the one production instance) clones/pulls/commits/pushes a local working tree at `~/Library/Application Support/FirstmateCockpit/shift-repo/` (override `FM_SHIFT_GIT_CLONE_PATH`) against `DotfilesSource.cloneURL` (override `FM_SHIFT_REMOTE_URL` - how this phase's own verification pointed a real launched instance of the app at a disposable local bare repo instead of the captain's real `manjesh-config`, see below); `ShiftStore.resolveRoot()` returns `<that clone>/personal-tasks` unless `FM_SHIFT_DIR` is set, in which case it bypasses git sync entirely (used by every self-test, and available to any captain who wants a plain local-only folder with no git backing - `ShiftStore.gitSync` is `nil` in that case and `notify()` never calls `markDirty()`). **The speed contract**: every task/follow-up/project mutation already wrote its YAML file synchronously before this phase (see phases 1-3 above) - `ShiftGitSync` only owns what happens *after* that write. `ShiftStore.notify()` calls `gitSync?.markDirty()`, which flips the sync-status pill to "Local changes" immediately (no I/O) and (re)schedules a debounced commit+push on a private serial background queue (3s default) - several rapid edits collapse into one commit, never one per edit, and the UI never waits on git or network. A commit that succeeds locally but fails to push (offline, bad auth, diverged remote) leaves the pill at "Failed" with the local commit - and therefore the edit - fully intact; nothing here ever force-pushes, rebases, or discards local state. `ShiftGitSync.pullNow()` (`git fetch` + `merge --ff-only`, called on `start()` for a pre-existing checkout and on a 300s timer) fast-forwards silently when safe and reports `.diverged` without touching anything when local and remote history have genuinely diverged - real conflict-resolution UI is `cockpit-shift-conflict-handling`, the next queued phase, not this one. The sync-status pill lives in `ShiftController`'s header (`applySyncPill`, reusing `ToolRowLayout.pill`), driven by `ShiftGitSync.observeStatus` - real state from the queue, never a timer or fake cycle, hidden entirely when `store.gitSync` is `nil`. **Legacy-data migration**: the first time `.shared` successfully reaches a working tree whose remote is genuinely `DotfilesSource.cloneURL` (`migratesLegacyData`, gated on that exact match - see below for why), it moves any real content still sitting at the old phase 1-3 path into the new `personal-tasks/` root and renames the old folder aside (`shift.migrated-<timestamp>`, never deleted) rather than silently orphaning it.
  - **A real, live-verification-caught bug, not hypothetical: migration must never fire just because code is running through `.shared`.** `FM_SHIFT_REMOTE_URL` lets a real launched instance of this app point at a disposable test remote while still going through the `.shared` singleton (exactly what this phase's own verification does, and what any future manual testing should keep doing) - gating migration on "is this `.shared`" migrated the captain's real local phase 1-3 Shift data into a throwaway test clone the first time a test run's clone happened to succeed, live, during this phase's own work. Fixed by gating `migratesLegacyData` on the resolved remote genuinely equaling `DotfilesSource.cloneURL`, not on singleton identity.
  - **A second real bug, also live-verification-caught: a narrow but genuine race between this class's own initial clone and `ShiftStore.init()`'s synchronous first-run `settings.yaml` write.** `ShiftStore.init()` calls `ShiftGitSync.start()` (which clones on a background queue) but then runs `reloadAll()` synchronously on the caller's own thread right afterward - on a brand-new root with no `settings.yaml` yet, that write can land at `workingTree/personal-tasks/settings.yaml` in the narrow window before the background clone finishes, and a naive "remove the destination, then clone into it" sequence would silently discard that write. Fixed by cloning into a fresh temp sibling directory and swapping it into place (`ensureWorkingTreeNow`), with `salvageRacedLocalWrites` folding any such raced-in file into the fresh clone before the swap rather than losing it. A related string-prefix bug surfaced while fixing this: naively stripping a raw path prefix off `FileManager.enumerator`'s reported paths corrupted the relative path when an ancestor directory was itself a symlink (macOS's own `/tmp` -> `/private/tmp`, confirmed live: `settings.yaml` became `privatesettings.yaml`) - fixed by resolving both sides through `resolvingSymlinksInPath` before computing the relative path, not by special-casing `/tmp`.
  - **Verification (phase 4)**: `ShiftGitSyncSelfTest.swift` (`FM_RUN_SHIFT_GIT_SYNC_TESTS=1`, same permanent-self-test convention as `ShiftStoreSelfTest.swift`) creates real disposable local bare git repositories under a scratch temp directory (never the captain's real `manjesh-config`) and covers: a local YAML write staying instant against an unreachable remote; a real commit+push reaching a real second "remote" repo; 5 rapid edits inside one debounce window producing exactly 1 commit, not 5; a real pull (via a second clone that pushed first) bringing new content back; a push failure (remote deleted out from under an already-cloned tree) landing on "Failed" with the local commit still intact; and a genuinely diverged pull (two clones that each committed locally without pulling from each other first) stopping with `.diverged`/"Failed" and no commit gained, lost, or rewritten on either side. Beyond that self-test, this phase was verified against the real *launched* app (not `swift build` alone, per this project's track record): a real built binary, pointed via `FM_SHIFT_GIT_CLONE_PATH`/`FM_SHIFT_REMOTE_URL` at a disposable local bare repo, was run to completion multiple times confirming a clean clone/commit/push cycle every time with no leftover dirty files. **A final, deliberate real pass was then run against the actual `manjesh-config` repo** (per the brief's explicit instruction, with the captain's real local phase 1-3 Shift data temporarily moved aside first so this pass's migration check - `migratesLegacyData` genuinely matches the real remote here - couldn't sweep old dev/test seed content into it): the real app cloned `manjesh-config` fresh, created and pushed the real `personal-tasks/settings.yaml` scaffold (confirmed live via `gh api` reading it back from GitHub), then a task titled `"TEST - cockpit-shift-git-sync verification (safe to delete)"` was added, confirmed live on GitHub, and then deleted and confirmed removed on GitHub (`personal-tasks/tasks/active.yaml` is `"tasks": []`) in the same pass - the `personal-tasks/` scaffold itself (`settings.yaml`, empty `tasks/active.yaml`) is real production infrastructure and was intentionally left in place, only the test task content was cleaned up. The captain's real local phase 1-3 data was restored to its original location immediately afterward.

- **This app had no `NSDraggingSource` before this.** Its three existing drag-aware views (`LogDropZoneView`, `KeyDropZone`, `ShiftImageAttachmentWell`) are *destinations* for Finder drags, and the Sticky Board's "dragging" is hand-rolled `mouseDragged` frame moving inside one canvas. The destination half here follows those three verbatim; only the source half is new. Four things worth not re-deriving:
  - **A card must override `hitTest` to be the event target for its own area - measured, not assumed.** A `ShiftBoardCardView` wraps a `HelmAccentRow`, and a real press routed through AppKit's own hit testing lands on one of that row's internal `NSStackView`s and **never reaches the card's `mouseDown` at all** - so the board simply cannot be dragged, and nothing about how it renders says so. `ShiftBoardViewSelfTest` therefore sends its press through `window.sendEvent`; calling `card.mouseDown` by hand passes either way and proves nothing. (This is also why an `NSDraggingInfo` stub exists in that suite - AppKit implements that protocol privately and the drop half is worth testing.)
  - The minimum-movement threshold before a press becomes a drag is mandatory (AGENTS.md records it twice already); `ShiftBoardCardView.dragThreshold` is 4, matching `CockpitTerminalView`'s, because a stray click here opens an editor sheet.
  - `isDraggingCard` is cleared in `draggingSession(_:endedAt:operation:)`, not `mouseUp` - a drag session consumes the gesture and `mouseUp` may never arrive.
  - **Dragging is never the only way.** Every card carries the same moves in its context menu and as `NSAccessibilityCustomAction`s, so the board works with no pointer - the lesson `StickyNoteHandleView` already learned for its own drag-only affordance.
- **A column's height is derived from the card *count*, then raised from the cards' real frames - and both halves are needed.** This went wrong three ways before it went right, and the captain reacted to it mid-task:
  - A fixed body height made **every** column as tall as the fullest (measured: all three at 305pt with one holding a single 81pt card), so a sparse board rendered large voids and pushed Follow-ups and Projects off the page.
  - **Tying the scroll view's height to its document view's is vacuous**: `NSScrollView` stretches a document view shorter than its clip view to fill it, so `document.height` follows the clip and the constraint is satisfied at any height.
  - A frames-only recompute in `layout()` is correct but lags a render, because the constant changes after the pass that measured it.
  - So `ShiftBoardView.setTasks` computes one height for all three columns from the fullest column's card count (known the instant the data is), and `ShiftBoardColumnView.applyBodyHeight` only ever **raises** it to what the cards actually occupy - which is what stops a card whose title wrapped being sliced through the middle. Monotonic, so it converges in one extra pass.
  - Related: `.fillEqually` on the columns' row was replaced with `.fill` plus explicit equal-width ties, and each column sits in a vertical lane with **stack-level** `setHuggingPriority(.required, for: .vertical)` (gotcha (12) - the content-level API is a no-op on a stack).

- **Deliberately not built**: the reference's inline "type a title in the column" add (the New Task sheet is this app's one creation path and carries project/priority/due/attachment - a second creation path would be the duplication this codebase's conventions warn against; `presentTaskEditor(defaultStatus:)` is how a column's own "+ Add task" puts a task straight into In Progress), and a "Review" column (see above). Weekly Review stayed a tab rather than folding into the board: it answers a different question with entirely different content, and is already the target of a menu item and a search-palette entry that both expect a view to switch to.

**`fm/grand-line-tasks-page-redesign` is the Tasks page against the captain's own reference mockup (`data/grand-line-tasks-page-redesign/reference-design.html`, firstmate-side) - and its first finding was that most of that reference already shipped.** The segmented My Tasks/Weekly Review switcher, the Board/List toggle, the Backlog/In Progress/Done Kanban, per-card project label + priority pill + due date, per-column "+ Add task", the project chip row with its colour dots, the Follow-ups panel and the Projects panel with "N of M tasks completed" over a progress bar were all already real (see the kanban entry above). **Check the reference against the tree before building any of it** - the genuine gaps were four, and one of them was a defect rather than a gap.

- **The mockup's demo data is not obviously fake, and that is the trap the brief flags.** Its project names and task titles read like the captain's real board. Everything here renders whatever the real `ShiftStore` holds; nothing from the reference is hardcoded anywhere.
- **The reference's page head maps onto the drill header, not onto a rebuilt in-page hero** - §6.4's "a page never repeats its own destination name", the same call the Schedules redesign made. `HelmDrillHeader` already showed "Tasks" over a live "N open · N follow-ups · N overdue" subtitle, so only the mockup's primary action was missing.
- **"New task" is a genuinely page-level action, not a hoisted copy, and the distinction is why it is allowed in the cluster.** That cluster carries a page's own actions and never duplicates a control a few points below it (why Console and three of the four Setup pages leave it empty). Here the only other ways to start a task are the "+" on the My Tasks card header - **hidden in board mode** - and a column's "+ Add task", which presets that column's status. In the mode the page opens in there was no plain "new task" at all. `lazy var`, never a computed property: `drillHeaderActions` is read repeatedly and a fresh copy each read cannot carry state.
- **The fourth stat tile ("open tasks") leads, and every count on the page comes off one array.** `render` counts once and hands the same numbers to the tiles and to the column, so a tile and a nav count cannot report different numbers for one word. The suite asserts they match rather than re-deriving either.

**`HelmPageSidebar`'s third adopter, and the one design decision worth not re-litigating: it deliberately does NOT carry project rows.**

- The reference draws both a sidebar project list *and* the horizontal chip row. The chip row is on the captain's own list of what this page needs; the sidebar is not. Building both would be one idea wearing two controls, so the column carries the slice the chips cannot state - **All tasks / Due today / Overdue**, each with a live count - and the chips keep project filtering. `matchesFilters` is the single predicate both the board and the flat list run through, so the two can never disagree about what is showing.
- **A completed task is never "due today" or "overdue".** Both slices ask about outstanding work, so they exclude anything completed or cancelled - which correctly empties the Done column under either, and is the one case a date-only predicate gets wrong (a task finished last week is not late). Same predicates as the stat tiles, deliberately.
- **Follow-ups and Projects are `.action` rows, not filters** - they scroll to a panel, so they must not latch selected and claim the list was filtered (`HelmPageSidebar.RowKind`'s own rule). From Weekly Review they switch back to the board first, since the panel they scroll to is not on that view.
- **The column goes with the board on Weekly Review, and hiding it needs both halves**: `isHidden` *and* swapping the content's leading constraint from the column's trailing edge to the page edge, or the gap it left stays behind it (gotcha (11)). Its own width constraint is `HelmPageSidebar`'s 499, so it never becomes a window-width floor - re-confirmed against `AppShellBodyWidthSelfTest`.

**A real, captain-visible defect this found and fixed: the board sliced its fourth card in half, in every theme.**

- Measured: the column body was **352pt** for **373pt** of cards, cutting the last card through its own priority pill. `ShiftBoardView.setTasks` costed every card at `cardRowHeight` (82), but **a card carries a meta line whenever the task has a due date or subtasks** - measured 103pt with it, 82 without. Four cards where one has a due date therefore under-counted by 21pt.
- **`ShiftBoardColumnView.applyBodyHeight`'s "raise to measured" half is meant to be the net for exactly this and cannot be.** A view's `layout()` runs *before* its own descendants get their frames, so the first pass measures zero - and nothing marks the column dirty again afterwards, because `layoutSubtreeIfNeeded` only descends into views already flagged `needsLayout`. Proven by forcing one extra pass by hand: the body jumped straight to the correct 373. It stays as the net for a *wrapped* title, which no count can predict.
- **The fix is a content-aware plan** (`ShiftBoardView.plannedBodyHeight(for:)` + `cardHeight(for:)`), mirroring `configure`'s own rule for whether a card gets a meta line so the two cannot disagree about what a card costs. Right on the first pass, no settling, and all three columns stay level. `cardRowHeightWithMeta` is measured in the taller (Daylight-family) register for the same reason `cardRowHeight` is 82 and not 81.
- **Verified** with real off-screen renders of the real mounted page in `dusk` and `helm-light` before and after - the before renders are what showed the sliced pill in the first place. `FM_RUN_SHIFT_TASKS_PAGE_TESTS` is window-backed (a column body measured against what its cards really occupy needs real geometry) and joins `run-all-tests.sh`'s `NEEDS_SESSION` list. **Eight injected regressions each reproduced by name**, scripted file copies rather than `git stash`: the flat card-count height (which reported the original defect verbatim - "352.0pt for 373.0pt of cards ... sliced by 21.0pt"), the scope filter ignored, a completed task counted as overdue, a jump row latching as a filter, the column hidden with its gap left behind, the primary action rebuilt per read, a nav count drifting from its tile, and the fourth tile removed.

### The Tasks column lists every project

**`fm/grand-line-tasks-sidebar-project-list` gave the Tasks page's nav column the four groups the captain's reference draws - Workspace, a row per real project, Smart views, and a Settings/Shortcuts footer - replacing a generic "Projects 5" count row.** References: `data/grand-line-tasks-sidebar-project-list/` (firstmate-side: both screenshots plus a static HTML mockup, a *structural* reference and not something to port).

- **The root cause was that nothing iterated the projects, not that the data was missing.** `ShiftStore.projects` was already real and the board's own `ShiftProjectFilterBar` already listed each project individually with its colour; `HelmPageSidebar` simply had no per-project concept, and `buildSidebar()` appended a fixed row list **once** at `loadView`. So the one place a captain would look to see *which* projects exist showed a number.
- **Three more additive changes to the shared component** (on top of `fm/grand-line-hosts-sidebar-restore`'s own `Surface`/`CountStyle`/`setFooter(_:)`, which landed first and which this rebased onto) - Poneglyph and Schedules render byte-for-byte as before, and so does Hosts, which all three suites pin:
  - **`RowIndicator.dot`**: a row led by a filled colour dot rather than an SF Symbol, because a project row is an *identity* marker and not an icon for an action. Both leads are built and one is hidden (`HelmAccentRow`'s own badge arrangement), so a theme change never rebuilds a row. They share one 16pt column so a dot row's label lines up with a symbol row's.
  - **Row groups.** A row's selection is scoped to its group. "Which slice" and "which project" are two genuinely orthogonal one-of-many questions, so picking a project must not un-pick "All tasks" - which is exactly what one shared selection would do. Every existing caller stays in the one default group.
  - **`setSections(_:)`.** Declarative rather than append-only, because the project set changes while the page is open. It carries each group's selection across the rebuild: a re-render that silently dropped the captain's project filter would be worse than the missing rows this exists for. `ShiftController` rebuilds only when the project set's signature changes, so an unrelated edit does not churn the column.
- **`setFooter(links:)` is built ON TOP of Hosts' own `setFooter(_ view:)`, not beside it.** Two footer mechanisms on one column is how a page ends up able to set two; this one assembles a hairline plus a row of muted text links and hands the result to the general one, so there is a single notion of "this column's footer" and a single set of constraints pinning it.
- **The sidebar's project rows and the board's chip row are one filter with two controls, never two filters** - which is what resolves `ShiftTaskScope`'s own standing note about not wanting a second project filter. Clicking a project row writes the same `projectFilter` the chip row writes and calls `ShiftProjectFilterBar.select(_:)` (new: moves the chip without firing `onSelect`, the split `HelmSegmentedTabs.select(_:)`/`HelmPageSidebar.select(_:)` already draw); `render` re-points the column at it. Clicking the selected project clears it, matching the chip's own toggle rather than inventing a second gesture.
- **A dot takes the RAW `ShiftProjectPalette` tint, deliberately uncorrected.** It is the same hue that project's board cards and filter chip already paint, and a sidebar dot that corrected itself would be a *different* colour from the board for the same project - the one thing an identity marker must not be. §2.4's own caveat covers it: the dot sits beside a label naming the project, so it is redundant decoration rather than the sole carrier of meaning.
- **Both Smart views are backed by fields `ShiftTask` genuinely carries** - `priority == .high` for "My priorities", `updatedAt` inside a 7-day window for "Recently updated" (the same window the Done column uses, so "recent" means one thing on this page). A task whose timestamp will not parse is *excluded*: claiming it was touched this week would be worse than leaving it out. They are two more `ShiftTaskScope` cases, i.e. the same one-of-many slice the Workspace rows are, so `matchesFilters` needed no second predicate. Counts are deliberately absent there and on the project rows, matching the reference.
- **The rows moved into a scroll view, and the height rule that keeps every caller working is one optional equality.** `scroll.height == document.height` at `contentTie` (499) is the *only* thing driving the column's height when nothing else does - so Poneglyph and Schedules, which pin only `bottom <=`, stay content-sized exactly as before - and it breaks cleanly for the two pages that genuinely pin their column's bottom (Hosts and Tasks, both so a footer lands on the page's own bottom edge), leaving the content to scroll rather than drawing rows over that footer. At 499 it is below `NSLayoutPriorityWindowSizeStayPut`, so it can never floor the window (gotcha (13)). **A `>=` is not good enough**: it leaves the height ambiguous and the solver picks. The scroll view replaces `stackBottom` as the constraint `setFooter(_:)` re-targets, and a `.panel` column's inset moved onto it, so Hosts' own panel padding is unchanged.
- **Two mechanics worth not re-deriving.** The document is pinned to the clip view **on the width axis only** (gotcha (4)) - a vertical pin fights the clip view's own bounds origin, which is what scrolling moves - and it is a `FlippedView`, or a document shorter than its clip view rests against the *bottom* of it (gotcha (9)). The footer's divider height and its gap are both zero when no footer is set, so a column without one is exactly as tall as it was before this component grew a footer at all.
- **`HelmPageSidebar.debugSelectedRowIDs` reads the rows that are actually rendering selected, not the ids `select(_:inGroup:)` was handed** - and that distinction is what makes the group check real: `select` stores an id whether or not a row in that group carries it, so a check reading the stored value **passed against the injected regression** that put project rows back in the default group. Read what is painted.
- **`debugFooterBottomGap` measures from `minY`**: this view is not flipped, so reading `maxY` measures the distance to the *top* and reports a correctly placed footer as 870pt out of place. And "the footer sits at the column's bottom" is not the whole property - it holds even for a column left hugging its content, so the case also asserts the column itself reaches the page's bottom inset.
- **Verified** with `swift build` (clean debug and release, zero warnings in this app's sources), the release binary confirmed to carry no `FM_RUN_*` strings, the full suite, and real off-screen renders of the real mounted page on `dusk`/`helm-light`/`daylight` at 0, 5 and 25 projects - **without launching the app**, per the README's worktree rule. Re-verified after rebasing onto `fm/grand-line-hosts-sidebar-restore`, which is the one branch that has ever conflicted with this component: the resolution was to re-apply this change on top of main's file rather than take either side, and the Hosts column was re-rendered off-screen as well as re-run, since its rows were the ones moved into a scroll view underneath. **Seven injected regressions each reproduced by name** (scripted file copies, never `git stash`): the per-project rows dropped (which reported the shipped bug verbatim), project rows in the default selection group, the chip row left behind, a dot painted with a fixed hue, the footer links unwired, the column's width made required (caught by `AppShellBodyWidthSelfTest` across every destination), and the column left hugging its content.
