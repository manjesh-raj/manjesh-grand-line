- **`SudoTouchIDData.swift` + Settings' fourth card, "Security" (cockpit-settings-sudo-touchid)** added a live "Touch ID for sudo" row. Its status reads `/etc/pam.d/sudo` and `/etc/pam.d/sudo_local` directly (Automic Vault's `av harden sudo` hardener has no `--json` listing entry the way the gh/aws hardeners do, since it's a root-only, file-content-driven check) - a direct Swift port of `automic-vault/src/isotopes/hardeners/sudo.rs`'s `pam_tid_enabled`/`line_enables_pam_tid`. A real caveat worth knowing: the appended `auth sufficient pam_tid.so` line only takes effect if `/etc/pam.d/sudo` already `include`s `sudo_local` - not true on every Mac - so the row has a distinct "Unavailable" state for that case rather than assuming it's always configured. The Enable button runs `sudo av harden sudo` (not the plain unprivileged form, which only previews and prints "next: sudo av harden sudo") through the same one-shot Console command-tab mechanism (`ConsoleController.openCommandTab` via `AppShellController.runInConsole`, wired from `settings.onRunCommand`/`onRunCommandTracked` exactly like `bootstrap.onRunCommand`) since a real `sudo` password prompt needs a real terminal. The row itself is rebuilt (not just re-themed) on every status change, mirroring Bootstrap's `ghAuthRow` - since `SettingsController`'s other cards are built once and never torn down, this is the first dynamic row in that file, and its own `rebuildSecuritySection` prunes `hoverRows` of the just-removed row's now-orphaned `HoverHighlightView` entry before appending the new one, so that shared re-theming list doesn't grow unbounded across repeated status checks. **`fm/cockpit-settings-sudo-nixdarwin` added a `.notEnabledNixDarwin` status** for nix-darwin-managed Macs: `/etc/pam.d/sudo_local` there is a symlink chain into the immutable Nix store (confirmed live: `/etc/pam.d/sudo_local` -> `/etc/static/pam.d/sudo_local` -> `/nix/store/.../etc-sudo_local`), and `av harden sudo` refuses to write through a symlink (a correct guard against symlink attacks on root-owned PAM files), failing with a bare ELOOP instead - even bypassing that would be pointless, since nix-darwin regenerates the file from the flake on every rebuild anyway. `SudoTouchIDSource.isManagedByNixDarwin()` detects this via `(path as NSString).resolvingSymlinksInPath` (the full-chain resolve, not just the first `readlink` hop - same idiom `DotfilesData.swift` already uses for its own symlink checks) landing under `/nix/store/`. The row's fix on that class of machine is guidance-only text pointing at nix-darwin's own `security.pam.services.sudo_local.touchIdAuth = true;` option, mirroring the gh row's `isotopeMissingPlainGhInstalled` guidance-only case - the app never edits the captain's dotfiles itself. The status *check* (reading file content for `pam_tid.so`) is unaffected by any of this, since reading through a symlink is transparently fine; only the write path `av harden sudo` uses is what breaks. **`fm/grandline-sudo-touchid-disable` made the row two-way**, and the interesting half is that most of the work was deciding when *not* to offer the button. `av` has no counterpart to `av harden sudo` (its hardener has `enable_pam_tid` and no unharden side - re-checked), so the removal is this app's own: `SudoTouchIDSource.disableCommand(path:)`, a `sudo /bin/sh -c '...'` handed to the same one-shot Console tab the Enable action uses, so macOS's own `sudo` prompt stays the authentication gate. It edits `/etc/pam.d/sudo_local` and nothing else, drops only whole lines that `enablesPamTid` itself matches, and rewrites with `cat tmp > file` rather than a `sed -i`/move so a root-owned PAM file keeps its inode, owner and mode; the file is truncated only after the filtered copy exists *and* `cmp` shows it differs, so a failed `awk` can never empty it, and a `-L` guard repeats `av harden sudo`'s own refusal to write through a symlink. **`.enabled` split into three states, because only one of them can be turned off from here** - `.enabled` (a real `sudo_local`, the one that offers a Disable button), `.enabledNixDarwin` (the symlink-into-the-store case, which is the captain's own Mac's actual state: PAM is generated from the flake, so turning it off means `security.pam.services.sudo_local.touchIdAuth = false;` and `rebuild.sh`, exactly as turning it on does), and `.enabledInSudoFile` (the `pam_tid.so` line is in `/etc/pam.d/sudo` itself - the file Apple ships and replaces on a system update, which this app never writes to, so a Disable scoped to `sudo_local` would press cleanly and change nothing). The last one is also checked **before** the `include sudo_local` test now: a line in `sudo` is read by `sudo` directly, so reporting `.pamNotConfigured` there was claiming Touch ID cannot work on a Mac where it demonstrably does. **The awk mirrors `enablesPamTid` field for field rather than approximating it**, including its quirk of splitting on the space character only - so a tab-separated `auth\tsufficient\tpam_tid.so` is left alone, because the status check does not count it as enabling either. Matching exactly is the point: removing a line the app does not believe is there would be the app editing a PAM file behind its own back, and `FM_RUN_SUDO_TOUCHID_DISABLE_TESTS` asserts that equivalence (removed iff `debugEnablesPamTid`) across a matrix of real line shapes rather than against hardcoded expectations. That suite runs the **shipped command string** against scratch files under both zsh and bash, minus only its asserted `sudo ` prefix - nothing re-implements the removal, since a suite carrying its own copy of the rule is the copy that drifts. **Not verified live, and it cannot be from here**: this Mac's only enabled state is the nix-darwin one, where the correct behaviour is to offer no button at all, so a real end-to-end disable would mean mutating the captain's own PAM config for a path the UI deliberately never reaches. `SudoTouchIDSource.classify(sudoContents:sudoLocalContents:isNixDarwin:)` exists so the status decision is drivable without `/etc/pam.d`. One adjacent fix rode along: `SettingsController.descRow` reserved a hardcoded ~160pt for its trailing control column when sizing the wrapping description, and that had already drifted - the font-size presets measure **221pt** and this row's Enabled + Disable + recheck **187** - so the reserve is measured from the real trailing view (floored at 160, so no row reserves less than before). Under-reserving is the dangerous direction: AppKit sizes the label's height for one line at `preferredMaxLayoutWidth`, the text then wraps narrower, and the extra line draws outside the label's own bounds.

- **The app bundle lives at `dist/Manjesh Grand Line.app` (gitignored, renamed from `Firstmate.app` in the cockpit-rebrand-grand-line task).** Built by `native/build_native_app.sh` (plain `swift build -c release` + manual bundle assembly, no py2app, bundle ID `com.firstmate.cockpit.native` - deliberately unchanged by the rename, see below). There used to be a second, older `dist/Firstmate.app` produced by a since-removed Python/WKWebView app via the root `build_app.sh` - that codebase and script are gone, so this is the only app and the only build path now. **Codesigning (cockpit-stable-signing):** the script signs the assembled `.app` with a local self-signed identity named exactly "Firstmate Cockpit Local Dev" (`codesign --force --sign "Firstmate Cockpit Local Dev" --identifier "$BUNDLE_ID"`) when that identity exists in the login keychain (`security find-identity -v -p codesigning`), and otherwise warns and continues unsigned rather than failing - this keeps the app's code identity, and therefore Keychain ACL trust for saved SSH keys (see the "SSH keychain" bullet above), stable across rebuilds instead of getting a new ad-hoc identity every time. See `native/README.md`'s "Local signing setup" section for the one-time per-machine commands to (re)create this cert. **The bundle ID (`com.firstmate.cockpit.native`), the signing identity name (`Firstmate Cockpit Local Dev`), and the Swift module/target name (`FirstmateCockpit`) are all deliberately unchanged by the app's display-name rebrand to "Manjesh Grand Line"** - only user-visible text (window titles, tooltips, button labels, the bundle's `CFBundleName`/`CFBundleDisplayName`) changed. Changing the bundle ID or signing identity would invalidate the captain's already-saved Keychain-backed SSH keys. **`fm/grandline-app-install-to-applications` added an automatic install step after the codesign step: every run of `build_native_app.sh` also `rm -rf`s any existing `/Applications/Manjesh Grand Line.app` and `ditto`s the freshly-built `$APP_DIR` over it (`ditto`, not `cp -R`, to preserve the signature/extended attributes/resource forks)**, so the app behaves like a normal installed app - it shows up in `/Applications` (Finder, an `NSOpenPanel`'s Applications shortcut, etc.) with no separate manual install step, and every rebuild keeps that copy current. This never prompts for sudo (`/Applications` is writable by the admin user without it on a single-user Mac) - if the copy fails for any reason the script warns and continues rather than failing the whole build, and the `dist/` output is unaffected either way. Replacing the bundle while a stale copy is still running is safe: the running process keeps its own open file handles to the old bundle's files, so the swap only affects the *next* launch.

Two non-obvious things any future change to this page should know: (1) `UNUserNotificationCenter.current()` throws an uncaught `NSException` ("bundleProxyForCurrentProcess is nil") when the running process has no real `Info.plist`/bundle identifier - true for the README's own documented `swift run`/bare `.build/debug/FirstmateCockpit` dev workflow - so `UpdatesController.notify` guards on `Bundle.main.bundleIdentifier != nil` first; the packaged app (a real bundle) is unaffected either way. (2) `no-mistakes --version`'s own output ("no-mistakes version v1.37.0 …") contains a decoy "v" inside the word "version" before the real "v1.37.0" token - parse whitespace-separated tokens shaped `v<digit>...`, not the first bare "v" in the string (caught live: the naive version crashed every check silently). no-mistakes has no `--check` flag; its outdated-version banner only prints on stderr from a real subcommand's `--help` (itself a safe no-op), which is what's parsed instead. herdr similarly has no "check without updating" flag - latest-available is read from Homebrew (herdr happens to be homebrew-core tapped here) while the actual Update action still runs herdr's own `herdr update`, never `brew upgrade herdr`. Firstmate's own row shells out to `bin/fm-sync-upstream.sh` (a firstmate-repo file, out of scope for this cockpit repo to commit - see the PR that introduced this page for its exact content) and gracefully reports `.notInstalled` if that script isn't present yet, rather than failing.
- **`CaptainIcon.swift` (cockpit-native-updates-polish) embeds a raster rail icon as a base64 PNG literal, not an `Assets.xcassets` catalog.** This project builds with `swift build` only (Swift Package Manager, CLT, no Xcode project) - `xcrun --find actool` (the tool that compiles asset catalogs) is absent from a CLT-only toolchain, confirmed on this machine, so `.xcassets` is not viable here. An SPM `resources:` bundle was also considered and rejected: `MetalTerminalRenderer.swift`'s own `candidateBundles()` comment documents that this *executable* target's generated `Bundle.module` accessor `fatalError`s (aborts the process, not throws) if it can't resolve the resource-bundle path, and this app's manual bundle assembly (`build_native_app.sh`, no py2app/Xcode step) isn't guaranteed to lay resources out where that accessor looks. A base64-embedded PNG has no bundle path to resolve at all - works identically under `swift run` and any assembled `.app`. Any future non-SF-Symbol rail/UI icon should follow the same pattern: extract/process the asset with `native/scripts/extract-captain-icon.py` as a worked example (luminance/local-contrast thresholding via Pillow), verify the output's alpha channel programmatically (nonzero-but-not-fully-opaque pixel count) before embedding, then wrap it in an `enum` exposing a `static let templateImage: NSImage?` with `isTemplate = true` so it tints via `contentTintColor` exactly like an SF Symbol.

- **Phase 2 (cockpit-bootstrap-dotfiles) added the dotfiles/machine-config card and the global-agent-instructions verification section to `.bootstrap`.** The captain's real machine config is a Nix flake at `~/manjesh/dotfiles` (nix-darwin + home-manager + nix-homebrew), symlinked to the well-known `~/.dotfiles` by that repo's own `bootstrap.sh`/`rebuild.sh`. `DotfilesData.swift` is the model side - live `git`/file checks only, no hardcoded status - mirroring `UpdatesData.swift`'s `run`/`resolveExecutable` `Process` plumbing for git remote/branch/`status --short`, and parsing/rewriting the live `user = "..."` line out of `flake.nix` rather than a literal name in source. Every symlink check (managed items + the three `AGENTS.md`/`CLAUDE.md` targets) fully resolves the chain with `(path as NSString).resolvingSymlinksInPath` (a property, not a method - `readlink -f` equivalent), not just the first hop: confirmed live that `home.nix`'s `mkOutOfStoreSymlink` targets go through an intermediate `/nix/store/.../home-manager-files/...` hop before landing on the real repo file. `~/.zshrc` is deliberately expected to show "not linked" even when everything is fine - its `home.nix` entry is `programs.zsh` (home-manager *generates* the file), not a `home.file` source symlink, so it resolves straight into the Nix store with no repo path in the chain at all. Any future one-shot command tab needs the same flag set at its `addTab` call site.

## Bootstrap could dictate the window's width (UI modernization audit, the functional finding)

**`fm/grandline-bootstrap-window-shrink` closed the one *functional* finding of `data/grandline-ui-modernization-audit/report.md` - the captain-reviewed "visiting Bootstrap can force the whole window ~500pt narrower".** The audit reproduced it once, live, at `c7dea4f`: a window set to 1440x900, navigating Updates -> Bootstrap while the first-visit tool sweeps were still running, left the window at ~975pt and it stayed there. Read `BootstrapController.yieldsToWindowWidth`'s own doc comment before touching a label on that page.

- **The audit's diagnosis named the right class and the wrong view, and the difference is the whole finding.** It blamed "some transient checking-state layout on Bootstrap (in-flight rows/labels)" and told the fix task to bisect the *stepper's in-flight state*. There is nothing special about the loading state: the demand is present in both states, and it comes from `BootstrapController`'s own labels. That file carried **zero** priority adjustments and **zero** inequalities in 2500 lines, so every label it built sat at `NSTextField`'s default **750** horizontal compression resistance - above `NSLayoutPriorityWindowSizeStayPut` (500). Any single-line label whose text is *data* rather than fixed copy is therefore a hard floor on the whole window at whatever width that string needs. **Fourth time this exact class has shipped** (`ToolRowLayout`'s name column, Tools' landing-grid title, F9's eighth action button), and the first time in a page's own hand-rolled labels rather than in a shared component - every shared component had been swept and this file never had.
- **Measured, with `FM_HOME` pointing at a deeply nested directory: `currentPathLabel` reported an intrinsic width of 825pt, the page's own fitting width was 973pt, and a window asked for 960 came back 973.** That is the audit's "~975pt" - and note it is *not* `contentMinSize` (960), which is what the audit assumed ("its minimum"). It is the page's own label floor, which is why the window settled a few points *above* the minimum and stayed there. Three real offenders, and they are exactly the strings the audit's own screenshot shows: the resolved firstmate home (`currentPathLabel`), the dotfiles repo path (`repoLabel`), and the git remote URL (`metaLabel`).
- **`.byTruncatingTail` matters as much as the priority, and one of the offenders proves it.** `currentPathLabel` had asked for `.byTruncatingMiddle` since the day it was written and never once got it: a truncation mode only fires when something has genuinely made the label's *frame* narrower than its text, which at 750 can never happen. Lowering the priority without setting a truncation mode leaves the text clipped mid-glyph instead.
- **Wrapping labels are deliberately excluded** (`yieldsToWindowWidth` returns early on `cell.wraps`). Their intrinsic width is their `preferredMaxLayoutWidth` - <= 520 everywhere on this page, well under any real window - so they are not a floor, and squeezing one below the width its one-line intrinsic *height* was computed at is the documented "second line draws outside its own bounds" defect. Likewise **`ToolRowLayout`'s labels are already `.defaultLow`** and its pill/chip labels are `.required` on purpose, so nothing swept here touches them.
- **`track(_:)` is the one door, and the source guard is what keeps this closed.** This page builds most of its labels from twenty-six `dynamicLabels.append` call sites; a behavioural check can only ever see the labels that happen to be on screen in the state it drives. `track(_:)` appends to the re-theming list *and* applies the rule in one step, and `BootstrapWindowShrinkSelfTest` fails the build on a bare `dynamicLabels.append`.
- **`FirstmateHome.root` is a `static let` resolved once at process start, so a self-test cannot reach this by setting `FM_HOME`** - `BootstrapController.debugHomePathLabel` exists so the test drives the real label instead. The test's long path has to be genuinely long (~130 chars) rather than merely realistic: the floor is only *visible* once the label's intrinsic width plus the page's chrome crosses the app's narrowest allowed window, which is also why the audit's own pass 2 could not reproduce it.
- **What could NOT be reproduced, stated rather than implied.** The audit's literal scenario - programmatically driving Updates -> Bootstrap with a cold `DependencyCheckCache` at 1440x900 - does **not** shrink the window, neither on `main` nor at the audit's own commit `c7dea4f`, measured with the sanctioned probe app (`Scripts/build-probe-app.sh`) and with a headless shell. The audit ran one day before PR #384 deleted `SetupContainerController`, so its Updates->Bootstrap tab-switch path no longer exists in that form either. What *is* reproducible, deterministically and in both registers, is the underlying defect: the page overriding a width the window was asked for. The fix targets that; the specific navigation sequence was a red herring.
- **Verified** by `swift build` (clean debug and release, zero warnings in this app's sources), the release binary confirmed to carry no `FM_RUN_*` strings or the new debug hook, and the full `./Scripts/run-all-tests.sh` run - **without launching the app from the worktree**, per the README's rule; the reproduction used the sanctioned probe bundle, which has its own bundle id and scratch stores. **Three injected regressions each reproduced by name** (scripted file copies, never `git stash` - see this file's own warning about the shared stash stack): the helper reverted to a no-op (which reported the real symptom, `window asked for 1100pt came back 1278.5pt of content`), the same with the property named directly (`resists compression at 750.0, above windowSizeStayPut`), and one bare `dynamicLabels.append` reported by file:line.

- **`setAction(target:action:)` is separate from `init` and replaces rather than stacks.** Every caller holds the pill as a stored property (which cannot reference `self`) and wires it from its own builder, so a second `setAction` call must not leave two recognizers firing one action.
- **A Refresh must be visibly and structurally distinct from a page's mutating action, and on this page that mattered most.** GitHub Sync already owns "Sync All", which fast-forwards eight real forks on GitHub; the captain flagged the confusion risk explicitly. The pill is a small trailing control above the first card, Sync All stays the labelled primary button inside its own; and `finishCheckAll()` deliberately shows **no** `Toast`, unlike `UpdatesController`'s - this page's drill header already states the outcome in those exact words ("8 forks - all in sync"), and reserving the toast for the mutating action is part of what keeps the two legible.
- **The toolbar row is laid out with explicit constraints, not an `NSStackView`** - gotchas (10)/(12) together: a horizontal stack left at `.gravityAreas` has no rule for who absorbs the slack, and a bare `NSView()` spacer has no intrinsic content size, so a hugging priority on one is a no-op. The progress readout is `.defaultLow` compression resistance + `.byTruncatingTail` and its leading edge is a `>=`, so neither it nor the row can become a window-width floor (gotcha (13), `fm/grandline-bootstrap-window-shrink`'s own lesson).
- **`FM_RUN_GITHUB_SYNC_REFRESH_TESTS`** is window-free on purpose (nothing here needs a composited window, so it runs on the blocking CI lane rather than joining `NEEDS_SESSION`). Its sharpest check is a **source guard** that `refreshTapped()`/`checkAll()` can never reach `sync(row)`/`syncAll()` - `check(row)` and `sync(row)` differ by three characters at the call site, and a Refresh that reached the second would look identical on screen and mutate eight real repositories. **The behavioural half genuinely cannot run there**: `GitHubSyncSource.check` shells out to real `gh` against the captain's real forks and has **no test seam**, so driving the real click in CI would mean eight network round trips per run. It was verified live instead (a real mounted page, a real click on the real pill, every row observed entering "Checking..." and none "Syncing...").
- **Confirmed to catch three real regressions by scripted revert** (never `git stash` - see this file's own warning about the shared stash stack): `refreshTapped` re-pointed at `syncAll()`, the subtitle re-added, and the pill built but never wired - that last one being the "renders perfectly and does nothing" case no render can see.
- **A tautological assertion the compiler itself rejected, worth not rewriting: `!(syncAll is HelmRefreshPill)`.** The two types are unrelated (`HelmRefreshPill: HoverHighlightView`, `HelmButton: NSButton`), so Swift warns `cast ... always fails` - and CI fails the build on any warning in this app's sources. The honest fix is the one this file already records: assert behaviour, never silence the warning. The direction worth worrying about (a refactor sweeping Sync All up into the shared pill) is already caught by the lookup for a `HelmButton` titled "Sync All" returning nil.
- **Verified** by `swift build` (clean, zero warnings in this app's sources), the new suite, `FM_RUN_UPDATES_REFRESH_BUTTON_THEME_TESTS` (the migrated page's own regression guard, green unchanged), `FM_RUN_E2E_TESTING_POLICY_TESTS`, the full `./Scripts/run-all-tests.sh` run, and real off-screen renders of the real mounted page in both its idle and checking states - **without launching the app**, per the README's worktree rule: the captain's real packaged instance was running throughout and shares this bundle identity.

## The Schedules page, redesigned against two references

**`fm/grand-line-schedules-page-redesign` rebuilt what `.schedules` renders** - stat tiles, status-grouped rows with a run-history sparkline and a "Review" hand-off, a search field, and two run-history panels - against a captain-supplied HTML mockup (`data/grand-line-schedules-page-redesign/reference-design.html`, firstmate-side) plus a screenshot of a denser status-grouped variant. `SchedulesInsights.swift` is new; `SchedulesCardView`/`SchedulesController` grew. **Presentation only**: nothing about how a schedule is created, run or persisted moved.

- **The whole risk in this class of task is honesty, not layout, and that is what the new suite spends its assertions on.** Both references are standalone mockups carrying fabricated demo data (a fictional "Daily workspace report" schedule, a hardcoded 24-run chart, an invented activity feed), and a page that fabricates renders perfectly. So the rule applied throughout: wire a piece to real recorded data or scope it out, never pad a shape. `FM_RUN_SCHEDULES_REDESIGN_TESTS` therefore checks *where a number came from* rather than that a view exists - 0 bars for a never-run schedule, the tiles counted off the same array the rows were built from, "Review" only where a run genuinely surfaced something.
- **The enabling finding, worth checking before scoping a similar ask: this app already keeps a real per-run log.** `ScheduleRunHistoryStore` (a 7-day JSONL, appended by `ScheduleRunner.execute`) is what makes the sparkline, the activity feed and the 7-day chart all backable - `AutomationSchedule.lastRun`'s single record is not the only history here, which is easy to assume from the row's own meta line.
- **Two honesty caveats shaped the code rather than being footnotes.** The retention window is **7 days, not "the last 14 runs"** the second reference labels its sparkline with, so the strip draws exactly as many bars as there are real entries and states the real count in its tooltip. And the **"Review 2 changes" count is not backable at all** - a run records `ScheduleRunRecord.summary`, an already-composed sentence, with no structured change count anywhere - so the button says "Review", carries the run's own sentence in its tooltip, and navigates to the page that owns that action (`ScheduledActionKind.reviewDestination`). Inventing the number was the one thing the brief ruled out.
- **A per-row decoration whose width varies breaks a column.** The row's trailing cluster is `[review slot, sparkline, time column, overflow, toggle]` and the mono time column is a genuine column - one constant x down the list, which `DaylightDrillPageSlice3SelfTest` measures. So both variable-width elements take a **shared slot width computed once per render pass** (the widest real history across the visible rows; whether *any* visible row has something to review), and both collapse to zero on every row at once when nothing needs them - which is also why a history-free app has no dead gap. Every one of those width constraints sits at `HelmDaylightPriority.contentTie` (499), below `NSLayoutPriorityWindowSizeStayPut`, per gotcha (13).
- **Grouped by status, deliberately instead of the flat-list-plus-filter-dropdown reference 1 shows.** The brief allowed either and asked for one. The groups *are* the filter at this list size (bounded by `ScheduledActionKind.allCases` times a handful of cadences), so a dropdown would ask for an interaction to reveal what a section header already states. The search field stayed, because it narrows rather than re-states.
- **The reference's page header maps onto the drill header rather than being rebuilt under it.** Reference 1 opens with an eyebrow, a 28pt "Schedules" and a subtitle; `HelmDrillHeader` already renders exactly that, and Daylight §6.4's "a page never repeats its own destination name" has been a correction applied to Review, Docs and Health in turn. The same reasoning ruled out reference 2's compact top summary bar (its title-and-subtitle half is the duplicate) in favour of `HelmStatTile` cards for the same three real counts.
- **Two existing assertions were inverted rather than deleted**, per this file's own precedent for a check that has become a record of overturned behaviour. `DaylightDrillPageSlice3SelfTest`'s tick-glyph check asserted one glyph per row because "a schedule has no run history to draw" - no longer true, so it asserts the sparkline's bar count instead, with the *unchanged* property (a never-run schedule draws nothing) intact. Its "exactly one header action" check recorded that the add button was the only page-level action at the time, not a rule; it now asserts each action is the owning view's own wired instance and neither also renders in the body, which is what §6.4's cluster actually guarantees.
- **One store read per render, handed down.** `SchedulesController.renderAll` reads `ScheduleRunHistoryStore.shared.allEntries()` once and passes it to the card, the tiles, the feed and the chart - both so a render is one file-backed store hit rather than one per row, and so the page's numbers cannot disagree within a frame.
- **`DaylightModuleSelfTest.checkLiveModuleWiring` is time-bounded and can flake on a loaded machine - it is not a Schedules regression.** It failed once during this task's verification (four "chip is Checking... after a clean pass" lines) and passed three times standalone, at the base commit, and on a clean second full run. The mechanism is in the check itself: after `debugSetCounts` it calls `drainMainQueue()`, which is a fixed **4 x 10ms of wall clock**, and the canvas coalesces its render onto a `DispatchQueue.main.async` hop that rebuilds seven module cards - so a busy machine can simply not get there inside 40ms. Nothing in this redesign touches the canvas or `BackgroundSignalsPoller`; what it adds is one more mounted destination for the sweep that runs before it. **Re-run it standalone before treating a failure there as yours**, and note that file's own header already records that a headless suite never turns the run loop on its own.
- **Verified** by `swift build` (clean, zero warnings in this app's sources), the full `./Scripts/run-all-tests.sh` run (149 passed / 0 failed / 1 documented skip), and **real off-screen renders** (`bitmapImageRepForCachingDisplay`/`cacheDisplay`, this repo's screenshot substitute) of the real mounted page against real seeded schedules and a real seeded history store on `dusk`/`helm-light`/`daylight` - **without launching the app**, per the README's worktree rule: the captain's real packaged instance was running throughout and shares this bundle identity. That render caught one real defect nothing else could: seven day-bars across a half-page card resolve to ~120pt each, and a rounded 120x80 rectangle reads as a *card* rather than a bar - hence `ScheduleRunOverviewChart.maxBarWidth`. **Six injected regressions each reproduced by name** (scripted file copies, never `git stash` - see this file's own warning about the shared stash stack): the sparkline padded up to its slot count, a never-run schedule grouped as needing you, "Review" offered on a clean run, the active tile counting paused schedules, search narrowed to the title alone, and a fabricated bar for a never-run schedule (which the inverted slice 3 check caught).

## The Updates page shows every row's Check button

**`fm/grand-line-updates-page-check-button-visibility` retired D1's hover-reveal on Setup > Updates, after the captain photographed a list where four of five "npm packages" rows had an empty gap where their Check button should be while every "Homebrew" row showed its own.** Read `UpdatesController.buildRow`'s note and `ToolRowLayout.ActionReveal`'s before reinstating any of it.

- **The split was arithmetic, not a rendering fault, and it is what makes this a bug rather than the approved design.** `ReviewPRListView.actionReveal(row:of:)` is `(count <= alwaysRevealRowCount || row == 0) ? .always : .onAim` - "a short list keeps its actions, a long one keeps its first row's" - and Updates applied it **per category card**. Against the real catalog that is npm packages 5 rows (row 0 visible, four hidden), Homebrew 3 (all visible), Other tools 2 (all visible): two treatments for one kind of row, stacked in one scroll view, with nothing on screen explaining the difference. D1's own discoverability mitigation was doing exactly what it says and still produced a page the captain read as broken.
- **It also made Updates the odd one out among the five pages sharing `ToolRowLayout`.** Bootstrap, Automation, GitHub Sync and Vault all take the `.always` default, so one page opting in split the row component's behaviour across the app - which is why the fix is "this page opts out" rather than "loosen the policy". D1 is untouched where it was approved: `HelmAccentRow`'s mirror still backs Review's PR list and the Hosts/Keys/Snippets lists.
- **`.onAim` now has zero `ToolRowLayout` callers and was deliberately kept rather than deleted.** `abandonPendingClear`'s precedent (delete the un-guarded variant once its last caller goes) was considered and does not transfer: that was one wrong variant of one action, whereas this is half of a deliberately mirrored policy whose other half is live and tested. Deleting it would make the two row components answer the same question differently. The safeguard is the doc note on the enum plus a source guard, not removal.
- **The reusable half is why no render and no `isHidden` check could see this.** `.onAim` hides with `alphaValue`, and `cacheDisplay` - this repo's screenshot substitute - draws an `alphaValue = 0` view **visibly** (the lesson `HostsListSection` already recorded), while `checkButton.isHidden` stayed `false` throughout, which is exactly why the captain's buttons still worked on hover. **Read the alpha.** `UpdatesController.debugRowActionStates` exists for that and reads it back off the real row rather than re-deriving it.
- **`FM_RUN_UPDATES_ACTION_VISIBILITY_TESTS`** (window-backed, so it is in `run-all-tests.sh`'s `NEEDS_SESSION` list) asserts every row's actions at rest, an `.updateAvailable` row's Update button, that the button keeps its **own** hover feedback (the fix had to drop the gating without touching `HelmButton`'s feedback), and a source guard that this page does not opt back in. **It asserts its own discriminating power first**: the bug only bites a category longer than `alwaysRevealRowCount`, so a future catalog whose every category is short would let the policy return with every assertion still passing - that case fails loudly instead. All three injected regressions reproduced by name, including the vacuity guard.

## Settings became a sidebar-navigated master/detail page

`fm/grandline-settings-page-sidebar-redesign`, from a captain report with four
screenshots of the page as it stood.

**The shape that was replaced.** Settings was one continuously-scrolling column
of ten `HelmCard`s, arranged into two columns above 940pt of content width.
That is how it grew: every feature that needed a preference added a card to the
bottom of `cardsInOrder`, and F20, F21, F22 and F23 each added one within about
a week of each other. By the end the captain was scrolling past the fourteen
theme swatches to reach Export/Import, and the two-column round robin meant
Security sat beside Terminal Shortcuts for no reason either of them could
explain.

**The shape now** is the one macOS System Settings uses, and the one the F21
mockup had already drawn for its own sub-page: a `HelmPageSidebar` on the left
listing seven categories, and a detail pane on the right showing only the
selected category's cards. The shell's drill header already carried the back
arrow, the icon tile and the "Settings" title, so the only header change is
that its subtitle now names the selected category.

### The category mapping

Seven categories over the same ten cards. Nothing was dropped, nothing was
rewritten - a category is a grouping of the existing cards and nothing else,
which is what keeps this a navigation change rather than a rebuild of every
toggle and picker.

| Category | Cards |
|---|---|
| Appearance | Appearance |
| Terminal | Connection, Terminal, Terminal Shortcuts |
| Briefings | Morning briefing, Daily review |
| Menu bar | Compact mode |
| Shortcuts & Siri | Shortcuts & Siri |
| Security | Security |
| Backup | Backup & Restore |

The two groupings that merge cards are the two that were already written as
siblings. Connection, Terminal and Terminal Shortcuts are all "how a terminal
tab opens and behaves", and splitting the working directory away from the font
size would make the captain visit two panes to set up one tab. Morning briefing
and Daily review are two briefings over two sets of data, and each card's own
construction comment already says it sits beside the other deliberately.

### What was measured

- **The nav column absorbed the page's slack, and the render showed it.**
  `HelmPageSidebar`'s own width constraint sits at `contentTie` (499) so it can
  never be a window-width floor (gotcha (13)), which means it also merely
  *ties* with another 499 constraint rather than beating it. The detail column
  is capped at 900pt, so a wide window has real slack in the row - and with the
  scroll view's leading tied to `sidebar.trailingAnchor` (the shape
  `SchedulesController` and `CredentialVaultController` both use, where the
  content genuinely wants to be wide) Auto Layout resolved that slack by
  widening the column. Measured at a 1400pt window: the nav rows rendered
  **303pt wide against the component's own 208**. The fix is to pin the scroll
  view to the page by a constant and cap the column with `trailing <=`, which
  leaves the column's own width uncontested and lands the slack to the right of
  the detail pane, where it belongs.
- **Two columns went away rather than being kept per category.** With one
  category on screen there are rarely enough cards for a second column to be
  anything but a ragged gap, and a category with one card would render it at
  half width beside nothing. The detail pane is one column with a required
  `<= 900` cap - required is safe because it is a **maximum** (gotcha (17)'s
  footnote to (13)); a `==` or `>=` at that width would be a window-size cap.
- **The other six categories' cards are detached, not hidden.** Gotcha (15)
  measured that a hidden view is still solved by the window's full-screen
  minimum-size derivation, so `isHidden` would have kept all ten cards'
  constraint chains live. Cards are still built once and reparented, never
  rebuilt, so a toggle keeps its state and its wiring whichever pane it is in.
- **Rendered off-screen in both themes, seven panes each**, through a temporary
  `FM_DEBUG_SETTINGS_RENDER` probe reverted before commit (the "Verifying
  native UI bugs" convention). That probe is what caught the 303pt column; the
  self-tests all passed at that width.

### The suites

`FM_RUN_SETTINGS_SIDEBAR_TESTS` (`SettingsSidebarNavigationSelfTest`,
window-backed) is the new one, and its subject is **silent loss of reach** -
the failure mode where a setting still exists, still works, still syncs, and
has no row that reveals it. Nothing about that is visible in a diff, a build,
or a render of whichever pane happens to be selected. It asserts the category
partition against the page's own card list, a real row press swapping the pane
(through `HelmPageSidebar.debugClickRow(id:)`, the same `pick` the click
gesture calls), that the selected row is painted differently from a resting one
on both a Daylight and a legacy palette, that the header subtitle follows the
selection *and is announced*, and that a representative control per category
still writes through to `AppSettings` via `accessibilityPerformPress`.
Confirmed by injection: a card built and left out of the category map fails
`"a card (Backup & Restore) belongs to no category - it is built, wired, and
unreachable"`; an unwired `onSelect` fails 28 cases; a dropped
`onDrillSubtitleChanged?()` fails `"the page announced 0 subtitle changes"`.

Three existing suites were rewritten rather than relaxed, because each was
asserting the two-column arrangement as a *proxy* for something that is still
true:

- `SettingsThemeLayoutParitySelfTest` now sweeps the sidebar inside its
  fingerprint, measuring each card while its own pane is selected, and
  compares `paneSizes` where it used to compare `isTwoColumn`. Strictly more
  coverage: it is now ten cards across seven panes on all fourteen themes,
  where it was ten cards in one scroll.
- `DaylightDrillPageSlice6SelfTest`'s §7 case became "the detail pane is
  category-driven, not theme-driven", with its own vacuity guard (the
  fingerprint must distinguish at least two panes).
- `Audit3BugFixesSelfTest`'s B9 - "a card is as tall as its own content" -
  sweeps every pane instead of one two-column render. B9's original mechanism
  is gone with the arrangement; the property it is about is exactly what a
  vertical `NSStackView` at the default `.gravityAreas` reintroduces.

### Left out, deliberately

The selected category is **not** persisted across launches; Settings opens on
Appearance every time. macOS System Settings does remember, and it would be a
reasonable follow-up - it is left out here because it is a new `AppSettings`
key and a new restore path, which is a different change from the navigation
one, and because opening on a known pane is the less surprising default while
the shape is new.
