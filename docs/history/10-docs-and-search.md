- **`.docs` (cockpit-docs-viewer) is a rail destination pinned directly above `.updates`** showing the captain's DevOps Playbook (`https://manjesh-raj.github.io/devops-playbook/`, source repo `manjesh-raj/devops-playbook`) in-app. The site is a real interactive app (canvas diagrams, tab switchers, local-storage reading progress in its `script.js`) that needs a real `WKWebView` - but the captain does not want a live network dependency for it, so `DocsController.swift` loads a bundled, synced-on-demand local copy via a `file://` URL (`WKWebView.loadFileURL`) rather than the live site, and its `WKNavigationDelegate` cancels any navigation that leaves the local synced folder, reopening it in the system browser via `NSWorkspace.shared.open` instead - this panel can never become a general browser. An empty state (no local copy yet) offers the same sync action described below. `DocsData.swift` owns where the copy lives (`DocsStore.folderURL`, defaulting to `~/Library/Application Support/FirstmateCockpit/docs/`, override `FM_DOCS_DIR` - same convention as `HostStore`/`SSHKeyStore`, deliberately outside the `.app` bundle for the same `Bundle.module` reason as `CaptainIcon.swift`) and the sync contract (`DocsSyncSource.check()`/`.update()`, wired into `DependencyCatalog` as a new "Documentation" category/"DevOps Playbook" row on the Updates page, following the exact same `CheckOutcome`/`UpdateOutcome` contract every other row uses): **check** compares the local `.synced-commit` sidecar file against the live repo's current `main` commit SHA (GitHub REST, `GET /repos/.../commits/main` - a public repo, so no `gh`/token is required, though see the auth bullet below for why one is used opportunistically); **update** re-downloads the repo root's current file listing (GitHub Contents API, so new/removed pages are picked up automatically) into a fresh temp directory and swaps it into place atomically via `FileManager.replaceItemAt` before recording the new SHA, so a `WKWebView` reload racing an in-progress sync never sees a half-written folder. `DocsSyncCenter` (`DocsData.swift`) is a tiny observer list (mirrors `ThemeManager.observe`'s shape) that `DocsController` uses to reload its `WKWebView` the moment a sync completes, whether triggered from the Updates page or the Docs page's own empty-state button.
- **`DocsSyncSource`'s GitHub requests opportunistically authenticate via `gh auth token` (`fm/cockpit-docs-auth-github-api`).** Captain-reproduced live: an unauthenticated request to `api.github.com` shares GitHub's 60/hour-per-IP quota with every other unauthenticated caller on the machine (`curl`/`gh`/etc.), so unrelated traffic earlier in the day exhausted it and the Documentation row failed with a real 403 and `x-ratelimit-remaining: 0`, even though the repo itself is genuinely public and needs no credentials to read. `DocsData.swift`'s `get(_:)`/`downloadBytes(from:)` now call a small `ghAuthToken()` helper (same `Process`-based shell-out convention as `UpdatesData.swift`'s `run()`, not a new networking abstraction) before every request and add `Authorization: Bearer <token>` when it returns one; `ghAuthToken()` returns `nil` - never throws - if `gh` isn't installed or isn't authenticated, in which case the request goes out exactly as before. Fetched fresh per request rather than cached, and nothing is persisted: no new Keychain entry, app setting, or credential storage was added for this.
- **`fm/grandline-docs-webview-cache-fix` fixed a real `WKWebView` staleness bug** (root-caused by a prior scout task, `grandline-docs-refresh-scout`, and confirmed via a standalone repro harness): `WKWebView` caches subresources (like `script.js`) in memory once a `file://` URL has been loaded once, so re-calling `loadFileURL` on the same URL against the same long-lived instance - which `loadDocsIfAvailable()` always did, including on a `DocsSyncCenter`-triggered refresh after new content synced - does not refetch them, even though the main `index.html` document does refresh. Since the DevOps Playbook builds its shelf/library UI at runtime via `script.js`, newly-synced content stayed invisible until the whole app was quit and relaunched. Confirmed fixes that do NOT work: cache-busting the URL's query string, `URLRequest` cache-policy overrides, non-persistent `WKWebsiteDataStore`. The actual fix: `loadDocsIfAvailable()` now calls `loadFileURL` only when `webView.url == nil` (the very first load); every subsequent call (explicit Reload, or a sync notification) calls `webView.reload()` instead, which does force a fresh subresource fetch.
- **`fm/grandline-docs-knowledge-foundation` ("Knowledge and speed", phase 1) restructured `.docs` from the single embedded browser above into a multi-tab page: Playbook, Runbooks, Postmortems, Search.** `DocsController.swift` is now a fixed tab switcher (`HoverHighlightView` pills mirroring `ShiftController.buildTabRow`'s own fixed two-tab pattern, not the Tools page's dynamic multi-instance `TabChipView` strip - these 4 tabs are permanent, never user-created/closed) with all 4 tab bodies as permanent sibling views, `isHidden`-toggled, per this app's usual "hide, don't rebuild" convention. **Playbook** is byte-for-byte the pre-existing embedded `WKWebView` (unchanged behavior). **Runbooks** is real, git-synced markdown CRUD - create/edit/delete a runbook, each stored as one `.md` file (`# Title` heading + body) named from a slugified title. **Postmortems** lists (and displays) whatever markdown files exist under the `postmortems/` subfolder - phase 1 shipped list/display only; `fm/grandline-sre-lead-postmortem` (phase 2) added the actual writer, see the "SRE Lead" section below. **Search** is a real, working case-insensitive substring search across Runbooks + Postmortems titles/content (`DocsKnowledgeSearch.search`) - deliberately not wired to the global `⌘K` shortcut or terminal command history yet (both explicitly later tasks, once there's a broader index to expand `⌘K` onto). This phase originally shipped a 5th tab, Command Composer, as an explanatory-only pointer at the real feature; `fm/grandline-composer-cleanup-and-polish` removed it outright once the captain confirmed it added nothing beyond a redirect message - see that task's own bullet below.
- **`fm/grandline-docs-no-window-fix` fixed a real, captain-reported regression that same task introduced: the packaged app launched, stayed alive, and never crashed, but showed zero windows.** Root-caused live via the unified log (`log show --predicate 'process == "FirstmateCockpit"'`, not just `sample`/`swift build`) rather than guessed: `DocsController.buildTabBar()` activated `bar.topAnchor.constraint(equalTo: view.topAnchor)` (plus leading/trailing) on the tab bar view *before* that view had been added as a subview anywhere - `root.addSubview(tabBar)` happened one line later, in the caller (`loadView()`). Activating a constraint whose two anchors share no common ancestor throws a real `NSGenericException` ("no common ancestor... illegal"), and since this happened synchronously during the `applicationDidFinishLaunching` notification dispatch (`-[NSApplication _postDidFinishNotification]`), AppKit's own top-level exception handling around that dispatch silently caught and logged it instead of crashing - aborting the whole delegate method partway through, before `window.makeKeyAndOrderFront`/`appLock.lock` ever ran. The process then sat in the ordinary run loop with genuinely zero windows (confirmed via `sample`'s call stack showing the launch method had already unwound, contradicting a hang), until macOS's own Automatic Termination logic (seeing zero windows) eventually quit the app on its own - explaining both "no window" and, later, "the process silently disappears." **This is a real, general AppKit gotcha worth remembering for any future cross-view constraint**: a constraint between view A and view B is only legal to activate once both share a common ancestor in the view hierarchy - build the view, add it as a subview, *then* activate constraints referencing an ancestor, never before. Fixed by moving those three anchor constraints out of `buildTabBar()` and into `loadView()`, right after `root.addSubview(tabBar)`. Verified live against three scenarios (fresh environment, an already-migrated `GrandLineDocs/personal-tasks/` repo, and an old pre-migration top-level `personal-tasks/` repo needing the one-time migration) - all three now show a real window, both via the bare `.build/debug` binary and the real signed packaged `.app`; the migration logic itself was untouched and unaffected.
- **`fm/grandline-docs-runbook-editor-overlap-fix` fixed a real captain-reported bug: clicking "+ New Runbook" showed the editor's title doubled up with the list's own heading and the empty-state text faintly visible underneath, instead of the editor cleanly replacing the list.** Root cause: the Runbooks tab's list-state view (the header row + scrollable list, gotcha (11)'s `NSStackView` built inline in `buildRunbooksContainer`) was a local variable, never stored or hidden - only `runbookEditorContainer.isHidden` was toggled on entering/leaving create/edit mode, so both views (pinned to the identical full-bleed anchors inside `runbooksContainer`) rendered simultaneously. Fixed by promoting that stack to a stored property (`runbookListContainerStack`) and setting its `isHidden` opposite `runbookEditorContainer.isHidden` at every transition (`beginNewRunbook`, `beginEditRunbook`, `cancelRunbookEditor`, `saveRunbookEditor`, and the delete-while-editing path). Verified live via a temporary env-gated probe (reverted before commit) confirming the two containers' `isHidden` are always exclusive across the full create/edit/cancel/save/delete cycle, plus `DocsRunbookDataSelfTest` re-run with no regression.
- **Storage (`DocsRunbookData.swift`): Runbooks/Postmortems live at `GrandLineDocs/runbooks/` (and its `postmortems/` subfolder) inside the SAME local clone of `manjesh-config` `ShiftGitSync` already manages - not a second clone of the same repo.** `DocsRunbookGitSync` (production singleton `.shared`) shares `ShiftGitSync.shared`'s `workingTree` and serial git queue (`ShiftGitSync.sharedQueue`, a new accessor) so both stores' git invocations serialize against the same working tree instead of racing on `.git/index.lock`; it delegates the actual clone/pull/repo-layout-migration work to `ShiftGitSync.shared.ensureWorkingTreeNow()` and only owns its own debounced commit+push, scoped to `GrandLineDocs/runbooks` (mirroring `ShiftGitSync.markDirty()`'s own debounce shape, just without Shift's conflict-resolution machinery - not needed for this phase's markdown CRUD). `DocsRunbookStore` (`FM_DOCS_RUNBOOKS_DIR` override bypasses git entirely, same convention as `ShiftStore`/`FM_SHIFT_DIR`) is the plain-file CRUD layer; `DocsRunbookGitSync`'s init also supports a standalone, non-shared mode (`sharesProductionWorkingTree: false`) used by every self-test so a test instance can never reach the real production clone.
- **Shift's own sync path moved too**: `ShiftGitSync.dataRoot` is now `GrandLineDocs/personal-tasks/` (was a bare top-level `personal-tasks/`) - `Self.shiftSubpath` is the one constant every `git add`/`git status`/`git show <ref>:<path>` call is scoped to. A one-time, self-healing `migrateRepoLayoutIfNeeded()` `git mv`s an old top-level `personal-tasks/` to the new location (committed and pushed) the first time any client with this code clones/pulls a repo still in the old layout - it never re-fires once any client has pushed the move. **A real bug this migration's own live verification against a disposable repo caught**: when the new dataRoot path already has a stray file on disk (e.g. `ShiftStore.init()`'s own documented premature-write race salvaging a lone `settings.yaml` there before this migration ever runs), a naive `git mv personal-tasks GrandLineDocs/personal-tasks` nests the whole old folder one level too deep (`GrandLineDocs/personal-tasks/personal-tasks/...`) instead of renaming it, since `git mv`'s "destination is an existing directory" behavior kicks in. Fixed by moving each child of the old directory individually instead of the whole directory at once whenever the new location already exists - covered by a permanent regression case in `ShiftGitSyncSelfTest.swift` (scenario 8) that seeds exactly that race before running the migration.
- **A real live-repo incident during this task's own verification, worth knowing before ever re-testing this migration against `manjesh-config` directly**: a live run pointed at the real repo (via a scratch `FM_SHIFT_GIT_CLONE_PATH`, no remote override) pushed one unintended commit adding stale `GrandLineDocs/personal-tasks/*` content that didn't match the real current data - reverted immediately (`git revert`, real captain data confirmed untouched throughout, both on the remote and in the real running app's own checkout). The exact mechanism was never fully identified - it did not reproduce in any of the 8 disposable-repo self-test scenarios (including the nesting-race case above) or a separate custom disposable e2e test, only that one live run against the real repo on this real machine. Anyone re-attempting a live real-repo test of this migration should budget for that possibility and verify byte-for-byte content equality before and after, exactly as this task's own investigation did.

SRE Lead's "Generate Postmortem" integration shipped as `fm/grandline-sre-lead-postmortem` - see the "SRE Lead" section below.
- **`fm/grandline-docs-runbook-list-compact-fix` fixed two captain-reported bugs in the Runbooks/Postmortems lists.** (1) Both lists' scroll document view (`DocsController.buildRunbooksContainer`/`buildPostmortemsContainer`) was a plain `NSView()`, not this app's `FlippedView` - the exact AppKit gotcha (9) class of bug: a non-flipped document view puts y=0 at its *bottom*, so a list shorter than the viewport (the common case) rested against the bottom of the scroll area with a large empty gap above it instead of starting under the header. Fixed by switching both to `FlippedView`, matching every other list page in this app. (2) Each runbook/postmortem row was a full-width row stretched to the list's own width (`row.widthAnchor.constraint(equalTo: ...ListStack.widthAnchor)`) - `buildDocRow` now builds a compact, fixed-width (320pt) card instead, following the Tools page's own landing-grid card treatment (`IconTileView` + title/subtitle text stack, a bordered `HoverHighlightView`, tight padding) rather than a stretched banner row. The document view's own width constraint changed from `==` to `>=` the clip view's width, since a fixed-width card can now be wider than a very narrow window without conflicting with that constraint. `DocsController.runbookRowCards`/`postmortemRowCards` (one list per tab) replace the old "walk `stack.arrangedSubviews`" theming loop, matching `ToolsController.cardBorderViews`'s convention, so `applyTheme()` can re-tint each card's border on a theme change.
- **`fm/grandline-docs-runbook-grid-layout` changed the Runbooks/Postmortems lists from `fm/grandline-docs-runbook-list-compact-fix`'s single-column stacked card list into a wrapping multi-column grid**, per captain request to match the Tools page's own landing-grid layout. `DocsController.layoutDocGrid(items:containerWidth:)` is a direct port of `ToolsController.rebuildGrid()`'s columns-from-container-width + `.fillEqually` approach, including its partial-last-row padding fix (`fm/cockpit-tools-page-partial-row-fix`) - a row with fewer cards than a full row is padded with invisible spacers so a lone leftover card never stretches to fill the whole row. The document view's width constraint flipped back from `>=` to `==` the clip view's width, since cards are now sized responsively to available width rather than a fixed 320pt. Column count re-flows live on window resize the same way Tools' grid does (`containerWidthMayHaveChanged`, hooked to `NSWindow.didResizeNotification`), gated on the active tab so a resize while on Playbook never touches either grid. Each tab keeps its own `[DocGridItem]` (disk-read only on `reloadRunbooksList`/`reloadPostmortemsList`, never on a resize-triggered `rebuildRunbookGrid`/`rebuildPostmortemGrid`) so re-flowing the grid never re-hits disk. The card's title label (captain-reported: "Identifying Unhealthy / NotReady Nodes" truncated to "...Nod…") now wraps up to 3 lines instead of truncating at 1, inside a fixed `docCardHeight` (100pt) applied to every card regardless of its own title length - a short title just leaves empty space below it, per this file's established "avoid a scrollable-item's height silently growing" lesson (see the Shift/Diff-tool entries above).
- **`fm/grandline-docs-runbook-delete-icon-corner` fixed a real captain-reported bug in that same card: the delete (trash) icon drifted horizontally/vertically with the title's own length and wrap** - it used to be a trailing arranged subview of the card's `row` `NSStackView` (icon tile + text stack + delete button), which left at its default `.gravityAreas` distribution doesn't stretch to fill leftover width (AGENTS.md gotcha (10)), so the button sat immediately after the title text instead of at the card's fixed corner. Fixed by pulling the delete button out of `row` entirely and pinning it directly to `container`'s (the card's) own top-right corner via fixed `topAnchor`/`trailingAnchor` constraints, with `row`'s own trailing anchor pointing at the button's leading edge (or the container's edge when there's no delete button) instead of the other way around - the title label sizes itself within the remaining space, the icon never moves. Verified live via a temporary env-gated probe (reverted before commit) confirming the icon's distance from the card's top/trailing edges is byte-for-byte identical for a one-line and a 3-line-wrapped title.
- **Phase 4 (`fm/grandline-unified-search`, the final planned phase) expanded `⌘K` from its prior single job (in-terminal find) into a real unified search palette - `UnifiedSearch.swift`.** Reuses phase 1's real `DocsKnowledgeSearch.search` verbatim (via a thin `UnifiedSearchIndex` wrapper) as the backend - no second index/matching implementation - and mirrors `ShiftSearchController`'s own small `NSPanel`-based palette shape (`ShiftSearch.swift`) almost line for line, since both are the same UI pattern over a different content domain. **Terminal command history was investigated and deliberately left out of scope**: the only structured record of "commands the captain has actually run" is Block View's `TerminalBlockTracker` (see the "Block view" section above), which is off by default and only active on hosts with `Host.blockViewOptIn` set - not a safe, already-real, app-wide data source, and expanding Block View's own rollout scope to back a search feature was explicitly out of bounds for this task. (Session logging - opt-in, unstructured raw bytes, and not a command list either - was the other candidate ruled out at the time; it has since been removed outright, see `fm/grandline-remove-session-logging`.) So the palette searches Runbooks + Postmortems only; terminal-history search stays deferred until Block View matures past its current "Stage 0" rollout. Selecting a result calls new `AppShellController.openDocsRunbook(id:)`/`openDocsPostmortem(id:)` wrappers, which switch to `.docs` and call new `DocsController.openRunbook(id:)`/`openPostmortem(id:)` entry points - the exact same "switch tab, then open" behavior the in-page Search tab's own `openSearchResult` already used (now itself calling through these same two methods, so there is exactly one "open this item" behavior regardless of entry point). The topbar Search pill's click is forwarded through a new `AppShellController.onSearchTapped` closure property (mirroring `onPresentHostEditor`'s forward-don't-own convention) rather than owned by that controller, since the palette itself is owned by the app delegate (`AppDelegate.unifiedSearch`, alongside its own `DocsRunbookStore` instance - a second instance is fine and cheap, since the store re-reads its git-synced folder fresh on every call, the same "each page keeps an independent copy of the same underlying check" pattern `UpdatesController`/`BootstrapController` already established). The Edit menu's "Find in Terminal" item lost its `⌘K` keyEquivalent (now blank, menu-only) since a new "Search…" item claims `⌘K`; plain find-in-terminal stays reachable via the console toolbar's own magnifying-glass icon and the Edit menu's `⌘F` - both independent of `⌘K`, confirmed live. `⌘⇧P` (Shift's own palette) is untouched and unaffected - confirmed live it still opens correctly. All four originally-planned "Knowledge and speed" phases (Docs restructure, SRE Lead postmortem generation, Console command composer, unified search) are now complete.
