- **"SRE Lead" (`fm/cockpit-sre-lead`) is a toolbar toggle on a dedicated host page's toolbar (`ConsoleController.swift`, gated on `!isFirstmateConsole` since the shared Firstmate console has no single host cluster to investigate) - not a rail destination.** Clicking the `SRELeadStatusPill` slides open a right-hand pane (`ConsoleController`'s `sreLeadPane`/`sreLeadPaneWidthConstraint`, animated via `NSAnimationContext` + `layoutSubtreeIfNeeded`) that talks to a locally-run Claude Code session investigating the connected host's Kubernetes cluster. **`fm/cockpit-sre-lead-shared-terminal` replaced the tool's whole execution model for kubectl commands - it no longer opens a second SSH connection at all.** Read-only enforcement still lives in exactly one place, `native/Scripts/sre_kubectl_mcp.py`: a dependency-free, stdlib-only MCP stdio JSON-RPC server exposing one tool, `kubectl_readonly`, whose subcommand is checked against a hardcoded `{get, describe, logs, top, events}` set and whose every argument is checked against a conservative safe-character allowlist, before the command ever reaches anywhere it could run - `--allowedTools` also restricts the agent to that one tool plus `Task`/`TodoWrite`, so it has no path to a raw Bash/Read/Write tool either. **Where a command now actually runs: the captain's own already-authenticated interactive tab for that host** - not a second connection, a local kubeconfig, or any credential this app holds. `SRELeadBridge.swift` is a small file-based request/response protocol between this Python script and the Swift app (different processes, no shared memory): the script writes `request-<id>.json` (the validated, `shlex.quote`'d kubectl command) into a per-session `bridge/` directory (`SRELeadSession.bridgeDir`), `SRELeadBridge`'s main-thread poll timer notices it, injects the command into the host page's one `primarySSHTab` (set once, by `ConsoleController.connectSSHIfNeeded`, and never guessed at again even if that tab is later duplicated - see the "Dedicated host pages" bullet for why there's normally only one anyway) wrapped in two fresh random markers (`echo <start>; <command>; echo <end>`, via the same `TerminalView.send(txt:)` `Snippet`'s "Run" action already uses), polls that tab's own `Terminal.getBufferAsData()` for the end marker, extracts everything between the two markers as the real output (searching only buffer content appended after injection, so stale scrollback or an unrelated earlier marker can never be mistaken for this call's own output - see `SRELeadBridge.checkInFlight`), and writes `response-<id>.json` back; the script polls for that file and returns it. **Two concurrency guards, both real, both tested** (`SRELeadBridgeSelfTest.swift`): a request is refused outright (not queued) if another is already in flight, or if the tab shows recent captain activity (`CockpitTerminalView.lastUserActivity`, tracked via a local `NSEvent` monitor scoped to this view as first responder, since `TerminalView.keyDown(with:)` is `public`, not `open`, and can't be overridden from this module) either just before injection or at any point before the end marker appears - the latter discards the (possibly-corrupted) output rather than ever returning it as trustworthy. **Verified live in this environment** (no real EKS bastion available here): `SRELeadBridgeSelfTest.run()` (`FM_RUN_SRE_LEAD_BRIDGE_TESTS=1 .build/debug/GrandLine`) exercises the whole Swift-side polling/extraction/busy-detection surface against a `FakeBridgeTerminal` stand-in; `native/Scripts/test_sre_kubectl_mcp.py` covers the Python-side request/response/timeout logic and re-verifies validation is untouched, including a raw JSON-RPC `tools/call` reconfirmation that `subcommand=delete` is rejected before any request file is written. **Not verified here** (no real cluster/bastion in this sandbox): the actual end-to-end path against a real host - a live interactive tab logged all the way through a real password-gated bastion, SRE Lead calling kubectl_readonly, and real output coming back - which remains the captain's own manual acceptance bar, same as every prior attempt.
- **`fm/cockpit-sre-lead-ux-fixes` fixed three UX problems from the captain's first live end-to-end test of SRE Lead (the bridge mechanism itself worked - real kubectl output flowed through and a real analysis came back).** (1) **Scrollback loss on open/close**: `loadView`'s constraints used to pin `content.trailingAnchor` to `sreLeadPane.leadingAnchor`, so animating the pane's width also resized `content` - and any frame change on a SwiftTerm view triggers `resize(cols:rows:)`, which reflows the buffer at the new column count and can truncate scrollback. `content` is now pinned to the root's full width unconditionally; `sreLeadPane` overlays its right edge (it's added after `content`, so it already rendered on top) instead of pushing it, so toggling the pane never resizes any terminal. Confirmed live with a temporary `FM_DEBUG_SRE_LEAD_SCROLLBACK`-style probe (per the "Verifying native UI bugs" convention below): filled a real shell tab with 300 lines, snapshotted the buffer, opened then closed the pane, snapshotted again - byte-for-byte identical, reverted before commit. (2) **Persona narrated the investigation instead of leading with the finding**: `SRELead.persona` (`SRELead.swift`) now explicitly instructs findings-first, terse-by-default replies with investigation detail (what was checked, what was ruled out, tool-limitation hedging) available only on request - not a vague "be concise" tweak. Real reply quality against this new prompt still needs the captain's own next live test to confirm; the diagnosis of the anti-pattern came from the real transcript of the first live test. (3) **The pane showed a raw `claude` TUI, not a native UI**: the pane used to run an interactive `claude` session in a detached tmux server, mirrored into the pane exactly like the Firstmate Mirror tab (`TmuxMirror.setUp(target: session.tmuxSessionName)`) - showing the captain someone else's CLI chrome (permission-mode banner, box-drawing borders) instead of anything native to this app. That whole tmux/mirror path is gone: `SRELead.setUp` only prepares the MCP config + a scratch/working directory now (no tmux session, no wrapper script - `Process`'s `arguments` array reaches `claude` directly, sidestepping the wrapper-script-for-shell-escaping trick the old tmux path needed for the multi-line persona). `SRELeadRunner.swift` runs one non-interactive `claude -p ... --output-format json` process per question/follow-up and threads conversation context across turns via `--resume <session_id>` (confirmed live, both via `claude --help` and a real two-call local test, that `-r`/`--resume` works with `-p`/`--print`) - `--output-format json` rather than `stream-json`, deliberately: the pane only ever needs the assistant's one final reply per turn, not partial/incremental text or intermediate tool-call events, so the simpler single-object parse was chosen over a streaming line-event parser that would have been harder to validate without a real cluster. `SRELeadChatView.swift` renders the conversation as a native message feed (`NSScrollView` + `NSStackView` of plain text blocks, styled via `HelmTheme`/`FlippedView`) with a single-line input field at the bottom - the same "type your first question" entry point the old tmux pane had, now as a real input field instead of clicking into a raw TUI. `SRELeadBridge.swift`/`sre_kubectl_mcp.py` and the read-only guarantee above are unaffected by any of this - only how the pane renders and how `claude` is invoked changed, not how kubectl commands reach the shared terminal.
- **tmux env propagation gotcha (`fm/cockpit-sre-lead-env-fix`): a tmux server only captures its global environment once, at the moment it first starts, from whichever client spawned it.** Every `new-session -d` against that same server afterward - exactly what `SRELead.setUp` calls on each SRE Lead spawn - inherits that originally-captured environment, NOT the `env:` dict passed to that later `TmuxMirror.run` call, unless the session overrides it itself. So `childEnvironmentDict()`'s PATH fix-up (adding `/opt/homebrew/bin` etc.) only actually took effect the first time a session was created against a fresh server; every later SRE Lead spawn against an already-running server (e.g. a leftover from earlier testing) silently got stuck with whatever PATH that server happened to capture at its own startup, causing the spawned `claude` session's SessionStart hooks to fail with `command not found` for Homebrew-installed tools (`gh-axi`, `lavish-axi`, `chrome-devtools-axi`) even though those tools were genuinely on disk. Reproduced live: started a tmux server with a deliberately stripped PATH, then `new-session -d`'d a second session against it - `which gh-axi` failed (exit 1) using only the `env:` dict, and succeeded once the wrapper script exported PATH itself. Fixed by making `SRELead.setUp`'s generated wrapper script self-sufficient - it now has its own `export PATH=...` line (built from `childEnvironmentDict()`'s resolved value) before `exec`ing `claude`, so it's correct regardless of what the server captured; `TmuxMirror.run(..., env:)` is kept as-is since it's still correct for a fresh server and harmless otherwise. Any future code that spawns a `new-session` against a tmux server that might already be running (not just this file's `TmuxMirror`/`SRELead`) needs the same self-sufficiency, since passing an `env:` dict to `new-session`/`run` alone is not reliable.
- **`fm/cockpit-sre-lead-reply-formatting` fixed the captain's next complaint: replies were findings-first (per the ux-fixes bullet above) but still rendered as one flat, unstyled paragraph, with no explicit conclusion/recommendation structure - "no highlights, no bold, no blocks, no conclusion, no recommendation for the next action."** Two connected pieces, one fixed marker convention shared between them. **Persona (`SRELead.persona`, `SRELead.swift`):** a substantive investigation reply must now be two labeled paragraphs, in this exact literal wording, with no blank line between a label and the rest of its sentence - `**Finding:** <conclusion + minimal evidence>` first, then an optional `**Recommended next action:** <concrete next step>` (omitted only when there genuinely isn't one, e.g. a pure lookup). A short acknowledgement/clarifying-question reply doesn't need this structure. **Rendering (`SRELeadMarkdown.swift` + `SRELeadChatView.swift`):** an assistant message's text is parsed by `SRELeadMarkdown.parse` into blocks (paragraph/bulletList/codeBlock/callout) and each gets a real AppKit view instead of one plain label - bold renders semibold, `` `code` `` spans get a monospace font + tinted background, `- ` lists render as an actual indented bullet list, and a `**Finding:**`/`**Recommended next action:**` paragraph renders as a distinct rounded callout (a `ToolRowLayout.pill`-style label over the body, on a panel tinted with `HelmTint.accent`/`.good` respectively) rather than plain bold text. Block/list/code-fence structure and inline bold/code-span detection both come from Foundation's own `AttributedString(markdown:, options: .full)` parser (confirmed live it already tags runs with the block structure and inline emphasis/code needed here) - not a hand-rolled markdown parser; only the block-grouping-by-`presentationIntent`-identity and the Finding/Recommendation label detection are hand-rolled, since those are app-specific and no generic parser could know about them. **The exact label text is a fixed contract between the persona prompt and `SRELeadMarkdown`'s `findingLabel`/`recommendationLabel` constants** - changing one without the other doesn't break anything visibly (the text still renders, just as a plain paragraph instead of a callout), so keep them in sync deliberately. Parsing is covered by a permanent self-test (`SRELeadMarkdownSelfTest.swift`, run via `FM_RUN_SRE_LEAD_MARKDOWN_TESTS=1 .build/debug/GrandLine`, same convention as `SRELeadBridgeSelfTest.swift`); the block-to-NSView rendering (geometry, non-zero widths/heights across a light and a dark `HelmTheme`) was verified with a temporary `FM_DEBUG_SRE_LEAD_MARKDOWN_RENDER`-style probe per the "Verifying native UI bugs" convention below, reverted before commit.
