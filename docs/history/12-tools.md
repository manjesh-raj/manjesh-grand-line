## Tools

- **`.tools` (`fm/cockpit-tools-page-core`, phase 1 of 3 of a captain-reviewed HTML mockup) is a rail destination pinned directly above `.docs`**, following the identical "pinned above the next fixed destination" convention `.docs`/`.updates`/`.bootstrap` already established. The landing grid (a wrapping grid of clickable tool cards - `IconTileView` + `HoverHighlightView`, the same pattern `SettingsController.rebuildAppearanceGrid` uses for its theme picker) is the tool picker - see the multi-session bullet below for how it's used post-phase-4.
- **`fm/cockpit-tools-page-multi-session` gave the page a Console-style tab strip so several independent instances of a tool can be open at once** (e.g. three separate Diff tabs comparing different things) - the captain's explicit ask, "like duplicating a browser tab." This merged before phase 3 (below) landed, so all nine tools - not just the original six - get this for free. `ToolsController.swift` now only owns the tab strip (`tabs: [ToolInstance]`, a `TabChipView` per tab - the exact same chip class `ConsoleController`/`TabModel` use, not a second implementation), the landing-grid picker, and which tab's view is currently shown; each tab's actual tool logic (inputs, outputs, status, copy-button text - everything every tool puts directly on itself as instance fields) lives in its own `ToolInstance.swift` instance, one per open tab, so two tabs of the same kind hold two genuinely separate objects with no shared mutable state. **New** (the tab bar's "+") shows the landing-grid picker; clicking a card there always opens a *new* tab of that kind via `ToolsController.openNewTab(kind:)`, never re-selecting an existing one - the tab-name convention is `ToolKind.shortName` for the first open instance of a kind ("Diff") and `"\(shortName) N"` for the Nth concurrent one ("Diff 2", "Diff 3", counting only currently-open tabs of that kind, so closing "Diff 2" and reopening a Diff tab reuses that name rather than climbing higher). **Duplicate** (via a tab chip's right-click menu) is `ToolInstance.snapshotContent()`/`restoreContent(_:)` - a `ToolContentSnapshot` enum carrying just that tab's *input* field(s) (never its output, which a fresh tab of the same kind recomputes itself), copied into a brand-new `ToolInstance` of the same kind. **Close** (the chip's own "×", or right-click) removes one tab; closing the last one returns to the landing-grid picker - Tools' own version of Console's "never leave the window empty" rule, since the picker (not a blank tool) is this page's natural empty state. `ToolsController`'s tab methods (`newShellTab`, `duplicateCurrentTab`, `closeCurrentTab`, `renameCurrentTab`) deliberately reuse `ConsoleController`'s exact selector names - originally so the one shared Tab menu's nil-target items dispatched to whichever controller had focus; that menu is gone now (`fm/grandline-console-tabs-restore-tabmenu-fix`, see "## Menu bar"), so nothing routes through it anymore, but the matching names stayed since renaming would be pure churn. **Verified live, not just via `swift build`**: a temporary env-gated probe (reverted before commit, per the convention below) opened two concurrent Diff tabs, set distinct marker text in each, confirmed switching between them preserved each tab's own text (and toggled the correct tab's view `isHidden`) rather than sharing state, duplicated the second tab and confirmed the new tab carried over its exact current input, mutated the duplicate and confirmed the original tab's content was unaffected, then closed tabs down to zero and confirmed the picker returned - plus a mixed-kind check (a YAML tab and a JSON tab open simultaneously, independent). All checks passed with no crash.
- **Nine genuinely functional tools, no stubs**: YAML validate/beautify, JSON validate/beautify (built on `JSONSerialization`, no library needed), Base64 encode/decode, a JWT decoder (header/payload only - no signature verification, called out permanently in the panel's own text, not just after decoding), a Unix timestamp converter (epoch <-> human, both directions, via `ISO8601DateFormatter`/`DateFormatter`), a Mergely-style diff (phase 2, `fm/cockpit-tools-page-diff` - see below), and - phase 3, `fm/cockpit-tools-page-specialist` - a certificate inspector, a cron next-run explainer, and a Kubernetes resource-unit converter, closing out the originally-scoped three-phase Tools page. All nine tools' UI/logic live in `ToolInstance.swift`, one `buildXPanel()`/handler set per kind - phase 3's three tools were built directly against that shape (multi-session merged first), never against the older single-instance `ToolsController`.
- **Phase 3's certificate inspector (`CertInspector.swift`) uses `Security.framework`'s real certificate-parsing APIs - `SecCertificateCreateWithData` + `SecCertificateCopyValues` - never a hand-rolled ASN.1/DER parser**, per the task brief's explicit instruction (the same framework `KeychainKeyStore.swift` already uses elsewhere, just a different API surface). Two non-obvious things confirmed live via a standalone probe before writing the real code (Apple's own header docs don't spell either out): validity dates (`kSecOIDX509V1ValidityNotBefore`/`...NotAfter`) come back as a plain `NSNumber` holding a `CFAbsoluteTime` (seconds since the 2001-01-01 reference date), not an `NSDate` - cast to `NSNumber` and construct via `Date(timeIntervalSinceReferenceDate:)`, not `as? Date`; and each RDN component's "label" in the subject/issuer property list is the raw dotted attribute OID (`2.5.4.3`, `2.5.4.6`, ...), not a human name like "Common Name" - `CertInspector.shortName(for:)` maps the common ones to the short RDN names (`CN`, `O`, `C`, ...) `openssl -subject`/`-issuer` prints, so the two outputs read the same. **Verified against two real certs, not mocked**: `CertInspectorSelfTest.swift` (permanent, `FM_RUN_CERT_INSPECTOR_TESTS=1`) shells out to a real `/usr/bin/openssl req -x509` to generate a self-signed cert with a SAN, parses it with `CertInspector`, and cross-checks subject/issuer/serial/SAN/expiry against `openssl x509 -noout`'s own independent parse of the same file - this machine's `/usr/bin/openssl` is the LibreSSL macOS ships (confirmed live: `-ext subjectAltName` isn't supported, "unknown option -ext"), so the SAN check reads the extension out of a full `-text` dump instead, which both LibreSSL and a real OpenSSL support.
- **Phase 3's cron next-run explainer (`CronExplainer.swift`) hand-rolls the 5-field parser and next-run search in Swift**, per the task brief (a well-understood, small problem that doesn't need a dependency). Standard fields plus `@yearly`/`@annually`/`@monthly`/`@weekly`/`@daily`/`@midnight`/`@hourly` shortcuts and `@reboot` (reported as "runs at startup, not on a schedule," not an error). Implements the classic day-of-month/day-of-week OR rule (`CronExplainer`'s private `domDowMatches`) and searches forward day-by-day (cheap - only descends into the small, bounded hour/minute sets on a day that already matches month + dom/dow) rather than minute-by-minute, so rare combos (e.g. a specific day-of-month in a specific month) stay fast instead of needing millions of iterations. `CronExplainerSelfTest.swift` (`FM_RUN_CRON_EXPLAINER_TESTS=1`) checks both a simple fixed-time headline/next-runs ("5 4 * * *" -> "At 04:05.") and a range/step schedule ("*/15 2 * * 1-5") against hand-verified expected next-run dates and weekdays, not just the headline text in isolation.
- **Phase 3's resource-unit converter (`ResourceUnits.swift`) parses Kubernetes `resource.Quantity` syntax** (binary `Ki`/`Mi`/`Gi`/`Ti`/`Pi`/`Ei` at powers of 1024, decimal `k`/`M`/`G`/`T`/`P`/`E` at powers of 1000 - `K` uppercase is also accepted as a common, harmless typo even though Kubernetes itself only allows lowercase `k`) into an exact byte count, then converts to every common unit at once. `ResourceUnitsSelfTest.swift` (`FM_RUN_RESOURCE_UNITS_TESTS=1`) checks the exact binary/decimal boundary the task's acceptance criteria calls for: `1Gi` is exactly 1,073,741,824 bytes (1024^3) = exactly 1,048,576 Ki = exactly 1.073741824 decimal G - not 1.0 G, which is what an off-by-1024-vs-1000 bug would produce.
- **All three phase-3 tools were verified live in the real running app, not just via `swift build`**: a temporary env-gated probe (`FM_DEBUG_TOOLS_PHASE3`, reverted before commit per the "Verifying native UI bugs" convention below) drove every real handler and real Copy button against real inputs - a real openssl-generated cert (subject/SAN/expiry, then a real clipboard read-back), the same fixed-time and range/step cron expressions the self-test checks plus `@reboot` and the Random button, a CPU millicores<->cores round trip, and the same exact-1Gi boundary case - and swept all 12 `HelmTheme.allThemes` with no crash or AutoLayout break. The app was also launched standalone (`.build/debug/GrandLine` with scratch `FM_HOSTS_FILE`/`FM_KEYS_FILE`/`FM_SNIPPETS_FILE`) and confirmed to start and stay running without crashing. **Not verified**: a real click-through of the actual rendered UI (this sandbox has no Screen Recording/Accessibility permission, per the convention below) - that last-mile visual check is the captain's own.
- **Diff (phase 2) is a direct Swift re-derivation of the reviewed HTML mockup's algorithm, not a port of its JS, and no third-party diff library** - `DiffEngine.swift` (pure logic, no AppKit import) does classic dynamic-programming LCS over lines, groups consecutive delete/insert runs into paired `changed` rows (remainder as pure add/remove against a blank counterpart), then a second LCS pass over whitespace-preserving word tokens for a changed row's two lines to know which words to highlight. `DiffResultView.swift` renders it as a plain `NSStackView` of two-column rows (not two synced `NSTextView`s - this app already had a working "rows in a flipped-document stack view" pattern for every other scrollable list, and it makes word-level highlighting a matter of `NSAttributedString` background-color runs on a label) - lines render single-line/non-wrapping so both columns of a row always stay the same height and therefore aligned. "Show only differences" collapses consecutive unchanged-line runs into a clickable "N unchanged lines" separator (`CollapsedRunView`), keyed by that run's start index so it stays stable across an expand click; `ToolsController`'s Before/After editors prefill a real two-version Kubernetes Deployment manifest (one changed field, one removed line, one added block) matching the pair `DiffEngineSelfTest.swift`'s `manifestPairProducesExactlyOneRemovedOneChangedTwoAdded` case exercises. **A real bug caught during verification**: `DiffResultView.rebuild()` originally activated each new row's `widthAnchor.constraint(equalTo: stack.widthAnchor)` *before* calling `stack.addArrangedSubview(row)` - AutoLayout throws "no common ancestor" for a constraint between two views not yet in the same view hierarchy; every other per-tool panel in this file avoids this because they build their `NSStackView(views: [...])` with the full view array up front, but a dynamically-rebuilt stack (rows added one at a time, needed here since row count varies with the diff and the collapse toggle) has to add the arranged subview first and constrain it second. `DiffEngineSelfTest.swift` (same `FM_RUN_..._TESTS=1` convention as `SRELeadMarkdownSelfTest.swift`, run via `FM_RUN_DIFF_ENGINE_TESTS=1`) covers the line/word LCS and grouping logic permanently; the rendering half (row geometry, collapse -> 4 separators -> click -> expand to real rows, and confirming the image-tag change line renders as two distinct highlight/non-highlight `NSAttributedString` runs rather than one uniform run) was verified with a temporary env-gated launch probe per the convention below, reverted before commit.
- **YAML needs a real parser, so `Vendor/YamlSwift` vendors `behrang/YamlSwift` (MIT, pinned to upstream `master` commit `063286d`)** as actual source files under `Vendor/`, not a remote SPM dependency - this app deliberately has zero remote dependencies (see the SwiftTerm vendoring bullet above; there is no `Package.resolved`). `Package.swift` adds it as a second vendored target (`Yaml`, alongside `SwiftTerm`) that `GrandLine` depends on. See `Vendor/YamlSwift/README.md` for the full rationale. **A real bug caught during verification**: the first version of `YamlBeautify`'s dictionary-value-is-a-list branch rendered the list at the *same* indent as its own key instead of one level deeper, which round-tripped fine for flat manifests but produced YAML the vendored parser itself rejected ("expected dedent after dash indent") for anything with a list-of-maps nested inside a list item (e.g. a Deployment's `containers[].env`) - fixed by indenting one level deeper, the same as the dict-value branch already did.
- **`fm/cockpit-tools-yaml-order-perf-fix` fixed a real captain-reported data-fidelity bug: Beautify alphabetized every mapping's keys instead of preserving the source document's order**, at every nesting level including the top-level document keys - root-caused to upstream `Yaml.dictionary`'s associated value being a plain Swift `[Yaml: Yaml]`, which has no defined iteration order (this used to be treated as a deliberate "deterministic output" trade-off in this file and in `Vendor/YamlSwift/README.md`; a real ~35-deployment manifest with a meaningful 10-key order per deployment showed it's a genuine bug, not a style choice). The parser already builds each mapping key-by-key in source order during recursive descent - the bug was purely that the *accumulator type* it folded those keys into had no memory of that order once folded into a plain dictionary. Fixed with a **local patch on the vendored library**: `Vendor/YamlSwift/Sources/Yaml/YAMLOrderedMap.swift` (new, not upstream) defines `YamlOrderedMap`, an insertion-order-preserving map that replaces `[Yaml: Yaml]` as `Yaml.dictionary`'s associated value everywhere - the enum case, its subscript/`ExpressibleByDictionaryLiteral`/`dictionary` property, and every block/flow-map parsing accumulator in `YAMLParser.swift`. `YamlBeautify.swift` now walks `dict.pairs` (insertion order) instead of sorting `dict.keys`. See `Vendor/YamlSwift/README.md`'s "Local patch" section for the full writeup and what re-syncing YamlSwift from upstream needs to preserve. Permanent regression coverage: `YamlBeautifySelfTest.swift` (`FM_RUN_YAML_BEAUTIFY_TESTS=1`, same convention as the other pure-logic self-tests below) reproduces the captain's exact shape (a top-level `version` key before a `deployments` sequence, each mapping with 10 keys in a specific non-alphabetical order) and asserts byte-for-byte order preservation at every level, plus a map-of-maps case (not just sequence-of-maps) - verified live end to end too, not just via the self-test: a temporary probe opened a real Tools YAML tab, pasted the exact reported shape, clicked the real Beautify button, and confirmed the real output's key order matched the input exactly.
- **The same task also fixed a real, measured perf regression: `ToolsController.containerWidthMayHaveChanged` (added by `fm/cockpit-tools-page-ui-polish`, see below) forced a full Auto Layout resolve of the *entire window's* view hierarchy on every single window resize notification, unconditionally** - it's registered globally (`NSWindow.didResizeNotification`, `object: nil`) and used to call `view.window?.contentView?.layoutSubtreeIfNeeded()` before reading `gridContainer.frame.width`, regardless of whether the Tools page was even the visible destination. Every open Tools tab's full panel lives as a sibling of the landing-grid's `gridContainer` inside `pageStack` (`addTab` calls `pageStack.addArrangedSubview(instance.view)`), hidden but still fully participating in Auto Layout per this app's "hide, never rebuild" convention for permanently-mounted destinations - so this forced full-subtree resolve got measurably more expensive the more Tools tabs a captain had ever opened and left open, and that cost was paid on every window resize app-wide, not just while looking at Tools. **Measured live** (a temporary env-gated probe driving real `NSWindow.setFrame(_:display:true)` calls to simulate a live drag-resize, reverted before commit per "Verifying native UI bugs" below): with Console visible and 0 Tools tabs ever opened, live-resize cost ~3.6ms/frame; with Console visible and 20 Tools tabs open (hidden), the *same* resize cost ~20.2ms/frame - roughly a 5.6x regression paid on a page the captain wasn't even looking at, confirming the multi-session `ToolInstance` architecture (which lets tabs accumulate across a session) as the amplifying factor and the ui-polish-added resize handler as the actual trigger. Neither `FontSizeManager`'s observer fan-out (~7ms with 20 tabs open, trivial) nor `ToolInstance` construction cost itself (~3-7ms per tab, flat, not growing with tab count) turned out to be the cause - both were suspected per the task brief but ruled out by measurement. Fixed by gating the whole handler on `!view.isHidden && pickerShowing` (the grid's column count only matters while the picker is actually on screen) - live-resize cost with 20 tabs open dropped to ~10ms/frame (the remaining gap versus the 0-tab baseline is AppKit's own inherent cost of a window resize touching a larger permanently-mounted hierarchy, pre-dating this bug and out of scope for this fix). `showPicker()` now calls `containerWidthMayHaveChanged()` directly so a resize that happened while a tab was open is still picked up the next time the picker reappears - correctness (the grid still re-flows to a different column count on resize while visible: verified live, 5 rows at a 900pt window vs 2 rows at 1900pt, both before and after this fix) was not traded away for the speedup.
- **Verified live, not just via `swift build`**: a temporary env-gated probe (reverted before commit, per the "Verifying native UI bugs" convention below) launched the real app, navigated to `.tools`, confirmed the grid rendered 5 real non-zero-frame cards and the YAML panel a real non-zero frame on selection, then drove every tool's actual button-click handlers end to end - YAML validate/beautify against a real 3-document Deployment+Service+Namespace manifest (beautified output re-parsed successfully), JSON validate/beautify (valid and invalid input), a Base64 encode/decode round trip, a JWT decode with real `sub`/`iat`/`exp` claim extraction, and an epoch<->human timestamp round trip - and swept `helm-dark`/`helm-light` with no crash or AutoLayout constraint-break warnings.
- **`fm/cockpit-tools-page-copy-buttons` added a Copy button next to every tool's output(s)**, reusing `Toast.swift`'s existing save-confirmation pill (shown on `ToolsController.view`) rather than inventing a second confirmation pattern. `ToolsController.copyButton(action:)`/`refreshCopyButton(_:text:)`/`copyToClipboard(_:)` are the three shared helpers - a plain `NSButton` titled "Copy" (or "Copy header"/"Copy payload" for JWT's two independent outputs), disabled by default and re-enabled/disabled after every action that touches its output by checking whether that output is non-empty, and on click writing to `NSPasteboard.general` (`clearContents()` + `setString(_:forType: .string)`). YAML/JSON/Base64 each have one output and one Copy button; the timestamp converter has two independent outputs (epoch→human, human→epoch) and two buttons; JWT decode has two independent JSON outputs (header, payload) held in their own `jwtHeaderCopyText`/`jwtPayloadCopyText` properties - not scraped from the combined header/payload/claims display text - so each has its own accurate Copy button. Verified live the same way as phase 1: a temporary env-gated probe (`FM_DEBUG_TOOLS_COPY`, reverted before commit) called every tool's real click handlers directly, read `NSPasteboard.general.string(forType: .string)` after each Copy click, and asserted it matched the exact output shown, plus asserted every button's real `isEnabled` state before/after triggering both success and error paths - all 23 checks passed. **Standing convention**: every tool added from phase 2 onward (the diff tool, then the cert inspector/cron explainer/resource-unit converter) should ship a Copy button on its own output(s) by default - this is not something that needs asking for per tool again.
- **`fm/cockpit-tools-page-ui-polish` fixed two real captain-reported bugs in the merged page: a cramped landing grid, and monospace text ignoring the app's font-size setting.** **Grid**: `ToolsController.rebuildGrid()` used to hardcode `columnsPerRow = 3` and a fixed `card.widthAnchor.constraint(equalToConstant: 268)`, so the grid never responded to how much width it actually had - measured live before the fix (a temporary debug probe) at a 1220pt window: container 1120pt wide, 3 fixed 268pt cards filling only 824pt of it (~300pt wasted, hugging the left edge); at 1600pt, container 1500pt wide, same 3 cards still 824pt (~700pt wasted). The fix computes `columnsPerRow` from the container's real width against a `minCardWidth` floor (300pt) and lays each row out with `.fillEqually` distribution (no fixed card width) so cards actually stretch to fill whatever width is available - verified after the fix at the same two sizes: 1220pt -> 3 columns of 364pt each (fills all 1120pt), 1600pt -> 4 columns of ~364.5pt each (fills all 1500pt). Card padding grew 12->16pt and title/description font sizes grew slightly (12.5->13, 10.5->11) for breathing room. The grid re-flows live on resize via `containerWidthMayHaveChanged()`, registered against `NSWindow.didResizeNotification` rather than this view controller's own `viewDidLayout()` - confirmed live that `viewDidLayout()` is **not** reliably re-invoked here on a window resize (this page is a body child of `AppShellController`, not the window's own `contentViewController`, which is the only view controller AppKit guarantees that hook for), so the window-level notification is the correct hook, not a stopgap. **Font size**: `FontSizeManager.swift` is a new singleton mirroring `ThemeManager`'s observe/notify shape - the single source of truth for the monospace point size, persisted through the existing `AppSettings.fontSize` key. `ConsoleController` (every terminal tab) and `ToolsController`/`ToolInstance` (every Tools tab's `codeEditor`-based YAML/JSON/Base64/JWT/cert/cron output, plus `tsEpochOutput`/`cpuCoresOutput`/`cpuMillicoresOutput`, plus `DiffResultView`'s row-number/text/collapsed-separator labels) all register via `FontSizeManager.shared.observe` instead of reading `AppSettings.fontSize` once - Settings' presets and the toolbar/menu zoom actions now go through `FontSizeManager.shared.setSize`/`.step(by:)`, so every open terminal tab and every open Tools tab update live from one change, and a Tools tab opened *after* a size change starts at the current size (`ToolInstance.init` calls `applyFontSize(FontSizeManager.shared.size)` itself) rather than only the next live change. Each consumer's font is offset from the shared size by the same delta its original hardcoded point size had from the default 13pt terminal size (code editors were 11.5 = size-1.5; diff line numbers/text/separator were 10/11/10.5 = size-3/-2/-2.5) so relative weight between areas is preserved as the base size changes. **Any new tool's monospace output should go through `ToolInstance.codeEditor()` (already covered) or call `applyFontSize` for anything else** - don't hardcode a point size. **Verified live in the real running app** (not just `swift build`): a temporary env-gated probe drove real window resizes and read back real card/row frame widths for the grid numbers above; a second probe opened a real Diff tab, typed real before/after text, clicked Compare, then called `FontSizeManager.shared.setSize` twice (9 -> 24) and read the *same already-rendered* `DiffRowView` labels' `.font.pointSize` each time (8/8 at floor-clamped 9, then 21/22 at 24) confirming the live update path with no tab rebuild; a third probe opened a brand-new YAML tab after already setting size 18 and confirmed its editors initialized at 16.5 (18-1.5); a full `HelmTheme.allThemes` (12) sweep ran with no crash. All probes were reverted before commit per the "Verifying native UI bugs" convention below.
- **`fm/cockpit-tools-page-partial-row-fix` fixed a partial-last-row bug PR #93's grid rewrite introduced, and removed the Diff tool's prefilled sample content.** **Partial row**: with 9 tools, a column count that doesn't divide 9 evenly leaves a last row with fewer cards than a full row - since that row's `NSStackView` still uses `.fillEqually` distribution, a lone remaining card (or 2, or 3) stretched to fill the *entire* row width instead of matching a full row's card width. `rebuildGrid()` now pads a partial row's `chunk` out to a fixed `columnsPerRow` slots with plain invisible `NSView()` spacers before building the row, so `.fillEqually` always divides by the same column count regardless of how many real cards are present - real cards stay the same width as every other row's, and the leftover slots are simply empty. Verified live (temporary env-gated probe, reverted before commit, same convention as the ui-polish bullet above): at window widths producing 4/6/7 columns (9 tools -> partial rows of 1/3/2 respectively), every row - full or partial - measured the identical per-card width; live resize back down to the original 4-column width re-flowed correctly with all three rows uniform. **Diff prefill removed**: `ToolInstance.buildDiffPanel()` no longer seeds `diffBeforeInput`/`diffAfterInput` with a sample Kubernetes manifest pair (the `diffBeforeExample`/`diffAfterExample` constants are gone) - a new or duplicated Diff tab now starts with genuinely empty Before/After fields, confirmed live by reading the real editor `.string` right after tab creation. `DiffEngineSelfTest.swift`'s manifest-pair test case is unaffected - it already carried its own local literal copies of that manifest text, not a reference to the removed constants. No other tool's prefilled/placeholder content was touched.
- **`fm/cockpit-tools-yaml-quotes-diff-perf` fixed two more captain-reported bugs found in continued live use: Beautify silently stripping scalar quoting, and the Diff tool itself being slow on a large document (as opposed to the resize-triggered slowness `fm/cockpit-tools-yaml-order-perf-fix` already fixed).**
  - **Quote-preservation fix**: Beautify used to decide on its own, per scalar, whether the output needed quotes (`YamlBeautify.quotedIfNeeded`'s heuristic) - so `selfservice: "tenant-setup-solution-modelling-api-self-service"` lost its quotes (harmless for that specific unambiguous string) but the same logic would have silently changed a quoted `"true"`/`"123"`/`"no"` (a *string* in YAML) into a bare `true`/`123`/`no` (a bool/number, or - since this parser's tokenizer only recognizes `true`/`True`/`TRUE`/`false`/`False`/`FALSE` as booleans, not `yes`/`no` - a plain string that a stricter YAML-1.1 consumer downstream would read as a boolean anyway). Root cause: `Yaml.string` carried only the decoded text, with no record of whether the source scalar was quoted at all. Fixed by adding a `quoted: YamlQuoteStyle` (`.plain`/`.single`/`.double`) associated value to `Yaml.string`, set once at parse time in `YAMLParser.swift`'s three scalar branches (`YAMLQuoteStyle.swift`, a new local patch on the vendored library alongside `YAMLOrderedMap.swift` - see `Vendor/YamlSwift/README.md`'s "Local patch" section). `YamlBeautify.scalarText` now re-emits a `.single`/`.double` scalar quoted, in the same style, unconditionally - never re-decided by the heuristic; `quotedIfNeeded` still runs, unchanged, for a genuinely `.plain` (unquoted-in-source) scalar, since there's no original quoting to preserve there and something still has to decide whether it's safe to leave bare after this beautifier re-indents/re-flows the document. Adding a second associated value to `Yaml.string` required a **manual `hash(into:)`** for the `Yaml` enum (previously fully compiler-synthesized) - `Yaml`'s custom `==` deliberately ignores `quoted` (two `.string`s with the same text are equal regardless of source quoting), and an auto-synthesized `hash(into:)` would have hashed the new field too, breaking Hashable's "equal values hash equally" contract for `YamlOrderedMap` dictionary keys. Regression coverage extended `YamlBeautifySelfTest.swift` (not a parallel test file) with two cases: a quoted `"true"`/`"123"`/`"no"`/`'single-quoted'` mapping asserting every value stays quoted post-Beautify, and the existing 10-key deployment manifest with one field (`selfservice`) quoted in the source, asserting it stays quoted while every other field stays unquoted. Verified live beyond the self-test too: a temporary probe (reverted before commit) ran the captain's exact reported line plus the type-changing cases through the real `yamlBeautifyClicked()` button handler (not just the underlying `YamlBeautify.dump` call) and confirmed byte-for-byte output.
  - **Diff performance fix**: the captain reported the Diff tool itself (not window resize) was noticeably slow on a real 300+ line manifest, specifically at the moment Compare is clicked. A temporary env-gated timing probe (reverted before commit) measured the real per-phase breakdown at 320/340 lines before touching any code: `DiffEngine.lineDiff` (parse + line LCS + per-changed-row word LCS) ~14ms, `DiffResultView` construction ~50ms, the old `setRows` NSStackView-tree rebuild ~90ms - all cheap - versus the subsequent `layoutSubtreeIfNeeded` Auto Layout resolve of that tree: **~13.6 seconds**. Scaling the row count (70/120/220/320 rows -> ~202ms/919ms/4483ms/13598ms of layout time) confirmed this wasn't linear or even quadratic - a ~67x time increase for a ~4.6x row-count increase - the known `NSStackView` pathology where every arranged subview participates in one shared Auto Layout solve simultaneously, so hundreds of rows blow up far worse than the row count. Neither the line/word-diff algorithm nor per-row view construction needed fixing - only how the result set was rendered. Fixed by rewriting `DiffResultView` (`DiffResultView.swift`) from a plain `NSStackView` of permanent per-row `NSView`s into a single-column, view-based `NSTableView`, which is demand-driven - `tableView(_:viewFor:row:)` is only called for rows that actually need to be drawn (the visible rect plus a small buffer), not for every row up front, regardless of total row count. `DiffResultView` is no longer an `NSView` itself - it's a plain object owning `tableView: NSTableView`, which callers (`ToolInstance.buildDiffPanel`) embed directly as the enclosing `NSScrollView`'s `documentView` (this is what makes the demand-driven rendering apply - wrapping the table in another container view would defeat it). - **`fm/grandline-body-width-regression-recur` fixed a THIRD, independent way to reach the "black/blank gap on the right side of the window" symptom (see the `AppShellController` gap history and the Log Analyzer bullet above) - this time on the landing grid's `titleLabel`, and closed the actual structural test gap those two prior fixes each left behind.** Both `bodyContainerWidthTracksASeriesOfResizes` and `bodyContainerTracksWindowAcrossRealisticWidths` (`AppShellBodyWidthSelfTest.swift`) only ever exercise the *eagerly*-mounted destinations (`.overview`/`.console`/`.review`, GL-37's `mountsEagerly` set) plus whatever the app happens to show by default - never one of the eleven *lazily*-mounted destinations (Hosts, Tasks, Log Analyzer, Tools, Vault, Dictation, Schedules, Health, Docs, the other three Setup pages, Settings), so a bug confined to one of those could ship clean through the whole file, and did. **Root cause**: `toolCard(_:width:)`'s `titleLabel` sets `lineBreakMode = .byTruncatingTail` but never lowers its horizontal compression resistance off `NSTextField`'s own `.defaultHigh` (750) default - a priority *above* `NSLayoutPriorityWindowSizeStayPut` (500, gotcha (13)), so the truncation mode was dead code and the label instead refused to compress below its own intrinsic width. Since `containerWidthMayHaveChanged()` only re-lays the grid out while the picker is on screen (a deliberate GL-20 performance gate, see that method's own comment), a captain who opened Tools at a wide window baked that label's too-high floor into a row width that never shrank back down once Tools was hidden again - and since GL-37 mounts a destination once and only ever hides it (never tears it down), that stale floor stayed active in the view tree for the rest of the session, propagating up through the required leading/trailing ties every destination shares via `embed(_:)` into the one `bodyContainer` (gotcha (11)'s "a hidden view's constraints still fully participate in layout," with the Tools landing grid as the source this time rather than Log Analyzer's Compare-tab popups). **Fixed the same way this codebase always fixes this shape**: `titleLabel.setContentCompressionResistancePriority(.defaultLow, for: .horizontal)`, so the label can never outrank the window's own resize preference and its `.byTruncatingTail` mode actually gets to fire. **Closing the structural gap, not just this instance**: `AppShellBodyWidthSelfTest.swift` gained a fifth permanent case, `bodyContainerTracksWindowAcrossAllDestinations`, which visits *every* `RailDestination` (not just the eager three), sweeping several widths while each one is showing (reproducing the exact "rebuild wide, then hide" sequence that baked in the stale floor), then makes a second full pass revisiting every destination at one narrow width - so a floor left behind by destination A that only shows up once a later-visited destination B is narrowed cannot slip through again. Confirmed live to actually catch the regression, not just to pass: reverting the `titleLabel` fix fails every destination shown after `.tools` in rail order, at every width at or below the stale floor; reapplying it passes cleanly. Any future destination or card that repeats this mistake (a truncating/wrapping label with no lowered compression resistance, tied - however many stack views deep - into `bodyContainer`) now fails this case by name instead of shipping.
