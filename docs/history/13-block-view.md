## Block view

**Third build attempt, Stage 0 of a staged rollout (`fm/cockpit-block-view-stage0`).** Two prior attempts shipped and were fully reverted in one day: PR #79/#80 ("on by default" for `.shell`/`.ssh`) crashed the app on every launch, PR #83's SSH-only redo fixed that crash but shipped a real window-layout corruption bug on a real SSH session and was reverted per captain instruction. See `data/cockpit-block-view-scout/report.md` for the full forensics and staged design, and `data/learnings.md`'s block-view entry for the incident history - read both before touching anything here. `main` had zero block-view code before this stage; this is a fresh build, not a resume of the old branches.

- **Off by default, gated by `BlockViewFeature.isEnabled`** (`BlockViewFeature.swift`) - reads `FM_BLOCK_VIEW_ENABLED` (matching `ConsoleController.defaultLoggingEnabled`'s own env-var convention), never an `AppSettings` default-on toggle. This alone prevents a repeat of PR #79's failure mode (a bug in a niche feature taking down every launch) - the flag must be set explicitly to see any of this code run at all.
- **Gated to one opted-in host, not every SSH page**: `Host.blockViewOptIn: Bool` (`Host.swift`, a checkbox in `HostEditorController`), threaded down through `AppShellController.connectHost` → `ConsoleController.connectSSHIfNeeded`/`openSSH` → `addTab`, which only attaches a `TerminalBlockTracker`/`BlockContainerView` to a tab when `case .ssh` **and** `blockViewOptIn` **and** `BlockViewFeature.isEnabled` are all true. Every other SSH host, the Firstmate console's Shell/Mirror tabs, and any ad-hoc quick-connect (no `Host` behind it at all) are completely unaffected - `TabModel.blockViewOptIn`/`blockTracker`/`blockContainer` stay `false`/`nil` for them, byte-for-byte the same as before this task.
- **Stage 0 scope is deliberately the least possible**: `TerminalBlockTracker` (ported from PR #83, OSC 133 `B`/`D` marker parsing - this part was never the source of either prior break, per the scout report) still tracks `blocks` live as markers arrive, but nothing is wired to `CockpitTerminalView.onDataReceived` (the per-chunk hook the scout report's "Mechanism B" blames for a plausible main-thread stall under real scrollback volume) and nothing auto-renders on a tracker change. `ConsoleController`'s toolbar "Refresh" button (`refreshBlockView`, host pages only) is the *only* thing that calls `BlockContainerView.render(_:)` - between clicks, new blocks can complete in the background with no visible effect. No live streaming of a running block's output, no "Explain this," no re-run/copy actions - those are Stage 1/Stage 2, separate future tasks, intentionally blocked until this stage survives real use.
- **`BlockContainerView` is a single-column, view-based `NSTableView` (`usesAutomaticRowHeights`), not an `NSStackView` of permanent rows** - this is a real, measured fix, not a precaution. The first version of this stage followed the original PR #79/#83 design (`NSStackView`) and this task's own volume self-test measured a **~102-second** render at 400 blocks - the identical class of pathology this file's Diff-tool history documents twice already (the ~13.6s blowup at ~340 rows, and the Tools-page resize-handler regression). Switching to a demand-driven `NSTableView` (`DiffResultView.swift`'s own established fix for the same problem) dropped the same 400-block render to ~47ms. `BlockRowView` (the reusable cell) still adds its arranged subviews to its internal header/output `NSStackView` before activating any constraint referencing that stack - the exact ordering PR #83 traced as break #1's root cause (`NSLayoutConstraint._setActive:` throwing when two views share no common ancestor yet) - with an explicit "do not reorder" comment at the call site.
- **One restart entry point, not two**: `ConsoleController.restartTabBookkeeping(_:)` (calls `tab.blockTracker?.reset()`, `tab.blockContainer?.clear()`, re-sends the shell-integration hook) is called from both `startTab` (the initial-start path, and also what `processTerminated`'s auto-reconnect timer calls directly) and `reconnectActive` (⌘R) - the scout report's confirmed "Mechanism A" gap was that the original attempt only reset block state from `reconnectActive`, so an auto-reconnected SSH session kept a permanently stuck "running" block with the new session's output silently bleeding into it. Stage 0's restart behavior is deliberately the simplest correct thing: wipe and re-parse from scratch on every restart, never try to preserve/patch old state.
- **Four permanent self-tests**, each targeting a different class of prior/potential break (`FM_RUN_BLOCK_VIEW_TESTS`/`FM_RUN_BLOCK_VIEW_HIERARCHY_TESTS`/`FM_RUN_BLOCK_VIEW_RESTART_TESTS`/`FM_RUN_BLOCK_VIEW_VOLUME_TESTS=1 .build/debug/GrandLine`): `TerminalBlockTrackerSelfTest` (OSC 133 parsing, no view), `BlockViewHierarchySelfTest` (mounts a real `NSWindow`+`BlockContainerView`, drives real Auto Layout - the class of test that catches break #1's regression), `BlockViewRestartIntegrationSelfTest` (drives a real, non-Firstmate `ConsoleController`'s actual `openSSH`/`viewDidAppear`/`startTab`/`reconnectActive` methods - not reimplementations - through both restart shapes and asserts identical clean state; **verified live to actually catch Mechanism A**, not just to pass: temporarily removing `restartTabBookkeeping`'s call from `startTab` made the auto-reconnect-shaped case fail while the manual-reconnect-shaped case kept passing, exactly the asymmetry the scout report describes), and `BlockViewVolumeSelfTest` (400 synthetic blocks - see the render-time finding above; also found `TerminalBlockTracker.bufferLines(_:)`'s `getBufferAsData()`-per-marker parsing cost is real, not just plausible, at ~4.3s for 400 events - worth carrying into Stage 1's design, which reintroduces per-chunk parsing, rather than re-discovering).
- **What was verified live** (real launched app, both the bare dev binary and the packaged/signed `.app`, via this project's established "verify without a screenshot" convention - temporary env-gated debug instrumentation calling the exact production code paths, reverted before commit, since this sandbox has no Screen Recording/Accessibility permission): flag-off with a `blockViewOptIn` host present in the store stays alive with no behavior change; flag-on drives the real `AppDelegate.connectToHost` → `ConsoleController` path for the opted-in host, feeds synthetic OSC 133 bytes into the real `Terminal`, clicks the real Refresh action, and confirms the real `NSTableView` renders exactly the expected row. **Not verified in this sandbox**: a real SSH connection to a real bastion (the captain's own hands-on checklist in the scout report - multiple real reconnects, sustained real output, real scrollback volume - is still pending and explicitly not satisfied by anything in this stage).
- **Remaining stages, still blocked on Stage 0 merging cleanly and surviving real use first**: Stage 1 (live streaming of a running block's output, reintroducing a debounced `onDataReceived` hook with the output-length cap and diffed-render mitigations the scout report specifies up front) and Stage 2 (interactive actions - re-run, copy, "Explain this"). Neither is scoped or built yet.
- **`fm/cockpit-fix-host-decode-regression` fixed a real production incident this stage's own `blockViewOptIn` field caused**: Swift's compiler-synthesized `Decodable` requires every key listed in a type's `CodingKeys` to be present in the JSON being decoded, regardless of whether the Swift property has its own default value (`= false`) - a default only applies to Swift-side construction (`Host(label:...)`), never to key lookup for a key `CodingKeys` lists. Adding `blockViewOptIn` to `Host`'s `CodingKeys` therefore broke decoding of every `hosts.json` saved before that field existed - the captain's real file, two real hosts, otherwise perfectly valid JSON - and `HostStore.load()` (correctly, by its own existing design) treated the decode failure as file corruption, backed the file up to `hosts.json.corrupt-<timestamp>`, and reset the in-memory host list to empty. The real file on disk was never touched, but the Hosts page showed nothing. **Fix**: `Host` now has a custom `init(from decoder:)` that uses `decodeIfPresent(_:forKey:) ?? <default>` for every field that has a Swift-side default (not just `blockViewOptIn`), so this class of bug can't recur the next time a field is added - `label`/`address` (no default) stay `decode`, required. Declaring a custom `init(from:)` suppresses Swift's synthesized memberwise initializer, so `Host` also grew an explicit memberwise `init(...)` with the same parameter defaults every call site (`Host(label:...)`, self-tests, the host editor) already relied on. **Lesson for any future field added to `Host` (or any `Codable` type with an explicit `CodingKeys` list, e.g. `ShiftTask`/`ShiftFollowUp`/`ShiftProject`): a new field needs an optional type, a custom decode fallback, or a real data migration - a Swift-side default value alone does not protect old on-disk JSON.** Regression coverage: `HostStoreSelfTest.swift` (`FM_RUN_HOST_STORE_TESTS=1`, same convention as `BackupSelfTest.swift`) decodes an old-format JSON blob with no `blockViewOptIn` key at all, drives it through the real `HostStore.load()` path, confirms no corrupt-backup is created, and round-trips a re-save/reload confirming every other field (port, username, agentForward, tags, jumpVia) survives untouched - verified live to actually catch the regression by temporarily reverting the `Host.swift` fix (keeping the test) and confirming the test's exact failure mode reproduces the captain's real bug (decode fails, host list goes empty). Also verified against a read-only copy of the captain's actual real `hosts.json` (never the live file) and against the real launched app's real `HostsController` row content, per this file's "Verifying native UI bugs" convention.
- **`fm/cockpit-fix-block-view-stage0-bugs` fixed two real bugs from the captain's first hands-on test of Stage 0 against a real bastion.**
  - **Bug 1 - duplicate/empty blocks**: a real, reproduced root cause - pressing Enter on a blank prompt line (a common habit, and also how the shell hook's *own* installation cycle behaves) still fires `PROMPT_COMMAND`/`precmd`, closing whatever block is currently open with the *previous* real command's text (`history 1`/`fc -ln -1` doesn't change on an empty line) and empty output, indistinguishable in the UI from a genuine repeat. Confirmed via a real pty harness before touching any code (not assumed): typing the same command, then a blank Enter, then the same command again produced 4 `D` markers all carrying that command's base64 text. **Fix**: the hook now also compares the current history number/counter (`history 1`'s leading number for bash, `$HISTCMD` for zsh) against what it saw at its last close, tagging the OSC 133 `D` marker with a 4th field (`exit;base64cmd;is-real`) - `D` still always fires (so `B`/`D` stay strictly 1:1 and nothing gets stuck `.running`), but `TerminalBlockTracker.closeBlock` discards a `0`-flagged close instead of finalizing it. A genuine back-to-back repeat of the same command still gets its own real, populated block (verified: `TerminalBlockTrackerSelfTest`'s `repeatedIdenticalCommandStillProducesTwoRealBlocks`/`blankEnterBetweenTwoRealRepeatsIsDroppedNotTheReals`). **Known, deliberate residual gap** (documented in `ShellIntegration.swift`'s header, not silently accepted): a remote host with `HISTCONTROL=ignoredups`/`ignoreboth` set also suppresses the history entry for a genuine identical repeat, so that case reports `is-real=0` too and its block is silently dropped rather than shown wrong - judged a smaller, more defensible failure mode (show nothing extra) than the bug it replaces (show something misleading). A full fix would need a bash-preexec-style DEBUG-trap marker, which this file's own header already rejected for misfiring on a compound `PROMPT_COMMAND`.
  - **Bug 2 - the install script visibly echoing**: `ConsoleController.installShellIntegrationIfSupported` used to `send(txt:)` the whole multi-hundred-character one-liner straight into the pty, which a real remote tty echoes back before the shell can run it. Fixed with `ShellIntegration.installSequence` (see its own extensive header comment for the full reasoning): a short `stty -echo`/`unsetopt zle` line (visible, small, unavoidable - echo isn't off yet when it's typed), then the real hook base64-encoded and chunked (600 chars/line, comfortably under a real terminal's canonical-mode line cap - measured 1024 bytes via `fpathconf` on this machine, confirmed live that one long combined line hangs the shell once ZLE is off) accumulating into a shell variable, then a final line that evals it and restores echo/ZLE. `ConsoleController.sendShellIntegrationLines` paces each line 0.12s apart - verified live that zsh's parser loses line-boundary tracking entirely (drops into a `dquote>` continuation prompt) if every line is sent with zero gap. Verified clean (no visible script text, only the one short leading line) via the real `ConsoleController` production path for both bash and zsh across roughly a dozen live end-to-end passes. **Known residual risk, zsh-specific, left honestly documented rather than force-fixed**: exactly once, under this dev machine's own real starship-powered zsh, the full payload leaked visibly instead of just the one expected line - not reproduced again across ~9 further identical passes or a dozen isolated pty probes trying to isolate which line caused it. This pattern points at a race with an async prompt segment (starship forks a background job per prompt) rather than a deterministic bug - rare, not systemic, and not fully eliminable without either accepting the always-visible original behavior or reaching into a specific third-party prompt framework's own job scheduling, which is out of scope. A captain on zsh with an async/background-job prompt (starship, powerlevel10k's async mode, similar) should expect this to be reliable but not airtight.
  - Both fixes verified against the real `ConsoleController` production path (real `addTab`/`startTab`/`installShellIntegrationIfSupported`, real 1.5s + 0.12s timers, a real PTY-backed child process), not just `HeadlessTerminal` - via a temporary env-gated probe (`ConsoleController.debugOpenLocalShellAsSSHTab`/`debugSendToCurrentTab`/`debugCurrentTracker`, reverted before commit per this file's "Verifying native UI bugs" convention) that substitutes a real local `/bin/bash`/`/bin/zsh` for the ssh executable, since this sandbox has no reachable bastion - the same "real PTY child, not a real network hop" substitution `BlockViewRestartIntegrationSelfTest` already uses. All four existing block-view self-tests still pass unmodified.
- **`fm/grandline-sre-lead-per-tab` moved SRE Lead's whole state off `ConsoleController` and onto each `.ssh` tab (`TabModel.sreLead: SRELeadTabState?`, `SRELeadTabState.swift`) - one independent investigation per tab, not one page-level session pinned to `primarySSHTab` (the first ssh tab a host page ever opened, per that field's own now-removed doc comment).** Duplicating a tab (⌘D) or reaching a second server on a dedicated host page previously meant every kubectl injection and every question still targeted tab 1, silently - the design doc that motivated this (`data/grandline-sre-lead-per-tab/design-reference.html`, captain-approved) is Option A there: state on `TabModel`, mirroring `blockTracker`/`blockContainer`'s existing per-tab ownership exactly, rejected Option B (a `[UUID: SRELeadTabState]` dictionary on the controller) since every other per-tab feature in this app already lives on `TabModel` and gets free cleanup on tab removal that way. `ConsoleController` now owns only the shared chrome - the pill, the one fixed slide-open `sreLeadPane`, the header, "Generate Postmortem," and a new shared empty state ("Start SRE Lead for This Tab," `sreLeadEmptyStateView`) - and every started tab's own `SRELeadChatView` is added as a hidden sibling inside the pane, shown/hidden to match whichever tab is `currentTab` (`updateSRELeadPaneContent`, called from `select()`/`applyTheme()`/every phase transition via `updateSRELeadControls()`) - this app's usual "hide, don't rebuild" convention. **Off by default for every tab, including a freshly duplicated one** - a new `TabModel` always starts with `sreLead == nil`; SRE Lead only starts when the captain toggles it on for that specific tab, via the toolbar pill (`toggleSRELead`, now operating on `currentTab`) or the pane's own empty-state Start button (`startSRELeadForCurrentTabClicked`) - both call the same `startSRELead(for:)`, which targets that tab's own terminal as the `SRELeadBridge`'s injection point, never any other tab's. **A captain-specified cap: at most 5 tabs on one page may run SRE Lead (`.starting`/`.ready`) at once** - `activeSRELeadTabCount()` backs it, a 6th attempt shows a clear `NSAlert` ("SRE Lead limit reached... stop SRE Lead on another tab first") rather than silently queuing or refusing, and the pill's own tooltip explains the cap state up front via `updateSRELeadButtonTooltip`. `closeTab()`'s old `if tab === primarySSHTab` special case is gone - **every** closed tab with `sreLead != nil` tears down unconditionally (`tearDownSRELead(for:)`, stopping that tab's own bridge timer, cancelling its own in-flight `claude` process, and removing its own scratch dir - never a sibling's); the shared pane only collapses closed once no tab on the page has any SRE Lead state left (`anySRELeadTabHasState()` - **removed by `fm/grandline-sre-lead-polish`, see the follow-up bullet below**), so tearing down or closing one tab never disturbs a sibling tab's still-running investigation or yanks the pane out from under it. "Generate Postmortem" (`fm/grandline-sre-lead-postmortem`) is unchanged in spirit, just rebased onto `currentTab.sreLead?.chatView` and `currentTab.name` (was `primarySSHTab?.name`) instead of the removed page-level fields. **Verification**: `SRELeadBridgeSelfTest.swift` gained `twoConcurrentBridgesNoCrossTalk` - two independent bridges/dirs/fake terminals, interleaved ticks, confirming neither's request or response (or terminal content) ever crosses into the other, the exact risk the design doc flagged as "should be safe by construction, but not yet actually proven." A new permanent integration self-test, `SRELeadPerTabSelfTest.swift` (`FM_RUN_SRE_LEAD_PER_TAB_TESTS=1`, same convention as `BlockViewRestartIntegrationSelfTest.swift` - drives the real `ConsoleController`'s real `startSRELead(for:)`/`handleSRELeadSubmit(_:in:)`/`tearDownSRELead(for:)`/`closeTab`/`select` methods against a real multi-tab host page, not reimplementations), covers: two tabs reaching `.ready` independently and a fake `claude` script (`SRELead.claudePathOverrideForTests`, same seam as `DictationCleanup`/`SRELeadPostmortem`/`ConsoleCommandComposer`) answering two concurrent distinct questions with zero cross-talk in either chat; switching to a not-yet-started tab showing the empty state (never the other tab's transcript or a blank pane) and switching back showing the original transcript intact; the 5-tab cap refusing a real 6th attempt with no crash and no silent start; and closing one tab leaving a sibling's `.ready` session, transcript, and open pane completely undisturbed. **Verified this last case actually catches a regression, not just passes**: temporarily disabling the cap guard reproduced a 6th tab starting anyway and the corresponding self-test case failing with the exact wrong active-count, confirmed, then reverted.
- **`fm/grandline-sre-lead-polish` fixed two captain-reported UI/UX bugs in the per-tab feature above.** (1) **Pane open/closed state now tracks the *currently selected* tab's own `sreLead`, not "does any tab on the page have state"**: `updateSRELeadPaneContent()` (the one place `select()`/`applyTheme()`/every phase transition already funnels through via `updateSRELeadControls()`) now also calls `setSRELeadPaneOpen(current.sreLead != nil)` on every invocation - so creating/switching to a fresh or duplicated tab with no `sreLead` state shows the pane fully CLOSED (not the open empty state), and switching back to a tab that has one (running, ready, or failed-with-a-visible-error) reopens it showing that tab's own preserved chat. The old `anySRELeadTabHasState()` helper and its call in `tearDownSRELead` (which only closed the pane once *no* tab anywhere had state) are gone, along with the redundant `setSRELeadPaneOpen(true)` in `startSRELead` - one mechanism decides pane-open state now, not two that could disagree. (2) **The pane is now a visually distinct surface, not the same fill as the terminal**: `sreLeadPane`/`sreLeadEmptyStateView` are filled with `theme.chromeBackgroundHex` (this app's "surface" token) instead of `theme.backgroundHex` (the terminal's own token) - **but this pass missed `SRELeadChatView`, which is what actually fills the pane once a tab has a chat, so the fix only ever applied to the not-yet-started empty state; fixed in `fm/grandline-visual-polish-round2`**, the boundary separator (`sreLeadPaneSeparator`) widened from 1pt to 3pt and re-tinted with `theme.accentHex` instead of the subtle `chromeLineHex`, and a new 1pt `sreLeadHeaderDivider` was added between the header and body since both now share the same `chromeBackgroundHex` fill. **A real finding worth knowing before touching this again**: `chromeBackgroundHex` is NOT guaranteed distinct from `backgroundHex` in every theme - checked live across all 12 `HelmTheme.allThemes`, they're numerically identical in `gruvbox-light`/`tokyo-night-dark`/`tokyo-night-light` (3 of 12). The fill-color fix alone would have silently failed to fix the melding complaint in exactly those three themes; the bold `accentHex`-tinted separator bar is what actually guarantees an unmistakable boundary in every theme regardless of whether the two fills happen to match, since every theme's accent is a deliberately bold, saturated color far from either background shade. Any future change to this pane's coloring should keep relying on that separator (or an equivalently theme-proof signal), not just on the two fills differing. **Verified**: `SRELeadPerTabSelfTest.swift`'s `tabSwitchRebindsPaneToCurrentTab` case was extended with explicit `debugSRELeadPaneOpen()` assertions (open for a started tab, closed for a tab with no state, reopened on switching back) - confirmed live to actually catch the regression by temporarily reverting the fix and seeing exactly this case fail (a 6th-tab-cap-style regression check, not just a passing test); the theme-token-parity finding above was confirmed via a temporary env-gated probe dumping every theme's `chromeBackgroundHex`/`backgroundHex`/`accentHex` (reverted before commit, per this file's "Verifying native UI bugs" convention).
- **`fm/grandline-sre-lead-separator-fix` fixed a real follow-up bug in the same separator: it was only visible next to the header text, not along the pane's full height.** Root cause: `sreLeadPaneSeparator`'s own constraints spanned the full pane height correctly, but `sreLeadEmptyStateView` and every tab's `chatView` (`makeSRELeadChat`) had their `leadingAnchor` pinned to `sreLeadPane.leadingAnchor` - the same edge the separator itself starts from - rather than `sreLeadPaneSeparator.trailingAnchor` like `sreLeadHeader` already did. Since both views are added to `sreLeadPane` after the separator, AppKit's default z-order let their own opaque `chromeBackgroundHex` fill paint directly over the separator for the whole height below the header row. Fixed by anchoring both to `sreLeadPaneSeparator.trailingAnchor` instead - one-line-each, matching the header's own existing anchor. Verified live (temporary env-gated probe, reverted before commit): dumped real frames for the separator/header/empty-state/chat views in both the empty-state and started-chat cases, confirmed every other view's `minX` sits at or past the separator's `maxX` in both, and confirmed the probe actually catches the regression by temporarily reverting the fix and seeing the empty-state/chat views' `minX` drop to 0 (covering the separator) before re-applying it.
- **`fm/grandline-sre-lead-app-feel` gave the SRE-Lead-active layout a real "app" shape: with SRE Lead up on the current tab, the terminal renders as a rounded, bordered, elevated card beside the SRE Lead panel, which is now a `HelmCard` surface of its own (captain reference: `data/grandline-sre-lead-app-feel/reference-mockup.html` plus two screenshots in that folder's `captain-screenshots/`; read the mockup, not just the screenshot - its real CSS is the precise source for the spacing/radius shape).** Rendering only; every terminal, tab and SRE Lead behaviour is untouched.
  - **The whole design is shaped by one hard constraint: the terminal's frame must never change when SRE Lead toggles.** That is the bug `fm/cockpit-sre-lead-ux-fixes` fixed once already (a frame change on a SwiftTerm view triggers `resize(cols:rows:)`, which reflows the buffer and can truncate a captain's scrollback), and it is why the pane overlays `content` rather than pushing it. So the tempting implementation - wrap the terminal in a card view and inset it when the pane opens - is exactly what must not be built. Measured, not assumed: building it reproduced 98 cols -> 57 cols and a real buffer change (19208 -> 19509 chars) on open.
  - **How the card exists anyway.** Every terminal on a **host page** is inset from `content` by a *permanent* `ConsoleController.terminalInset` (`cardMargin` 12 + `cardInnerPadding` 8 = 20pt, fixed for the controller's lifetime), and `ConsoleCardChrome` - a hit-test-transparent overlay that is always `content`'s topmost subview - draws the workspace floor, both cards' drop shadows and the terminal card's border on top of it. Toggling SRE Lead only flips that overlay's `isHidden`/`needsDisplay`, so it is a pure appearance change. With the pane closed the inset band is `content`'s own `backgroundHex` - the terminal's *own* background colour - so it reads as ordinary terminal padding, not a card. `terminalInset` is **0 on the shared Firstmate console**, which can never show SRE Lead, keeping its own Shell tab byte-for-byte flush at full column count.
  - **`ConsoleCardChrome.hitTest` returning `nil` is load-bearing, not tidiness** - proven by removing it: the overlay then swallowed every click in the terminal area, so the terminal would go dead whenever the pane was up.
  - **The card's drawn trailing edge stops `gap` short of the pane**, so the terminal's rightmost ~1.5 columns are covered while SRE Lead is open - alongside the ~45 the pane itself has always covered. Nothing is covered on the other three edges, because the terminal is genuinely inset there. That is the deliberate price of never resizing.
  - **The 3pt `accentHex` separator bar is gone.** It existed because `chromeBackgroundHex == backgroundHex` in three of the twelve palettes, so a fill difference alone could not prove the pane was a separate surface (`fm/grandline-sre-lead-polish`). The replacement is structural rather than tonal - a real 12pt gap of workspace floor with a 1pt outline down each side of it - which no palette can collapse, confirmed in real renders of `tokyo-night-dark` and `gruvbox-light` (two of those three). `sreLeadPane` is now just a transparent clipping backdrop; the visible panel is `sreLeadCard`, which clips its own children so the header and chat inherit its rounded corners with no per-child corner masking. Its header gained the mockup's identity block (a `sparkles` `IconTileView` + title + a live phase pill through the shared `ToolRowLayout.pill`).
  - **`HelmCard.elevation(for:)` is the app's one floating-card shadow**, deliberately *not* applied by `applyCardSurface` (every other card in this app is flat on purpose, and `applyCardSurface` is usually paired with clipping, which kills a layer shadow). It is drawn by `ConsoleCardChrome` for both cards using the CG "clip to outside the path, then fill the path" technique, which is the only way to cast an outward shadow onto already-painted pixels without an inner-shadow artefact inside the card.
  - **Decided and worth not re-litigating: no traffic-light header strip inside the terminal card.** The mockup shows one, but the app already has a real tab strip immediately above `content` whose chip carries exactly what that header's title shows, macOS draws the real window controls at the window level (a second set inside a card would be non-functional decoration), and a permanent 42pt strip would either steal rows from every tab forever or force a frame change on toggle - the one thing forbidden here.
  - **Verified**: `SRELeadPerTabSelfTest.scrollbackSurvivesSRELeadToggle` is the permanent guard - it seeds 300 real lines into a real tab, drives the real start/teardown, and diffs the whole buffer *and* `cols`/`rows`; **both halves were confirmed to catch the regression independently**, not just to pass. `HelmContrastSelfTest.checkConsoleCardChromeGeometry` pins the card geometry (card edges on the terminal's inset, exactly one `s3` gap, equal window margins, empty rects at degenerate sizes) and was likewise confirmed to fail on a real regression. Plus real off-screen renders of the real mounted host page across `helm-dark`/`helm-light`/`catppuccin-mocha`/`gruvbox-light`/`tokyo-night-dark`/`solarized-light` in four states each (SRE Lead off, empty state, active with a real Finding/Recommendation exchange, off again) and of the Firstmate console for the zero-inset case, with the terminal's frame measured identical across every toggle and hit-testing confirmed to reach the real `CockpitTerminalView`. All 28 self-test suites pass.
  - **Two probe lessons that cost real time here, both generalisable.** (1) **A SwiftTerm `TerminalView` never calls `draw(_:)` at all in a window that was never `orderFront`ed**, so an off-screen probe captures an empty terminal that looks exactly like a rendering bug - `orderFront(nil)` the probe window first.
