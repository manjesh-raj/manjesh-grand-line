## Poneglyph (personal credential vault)

**Renamed and relocated a second time by the captain (`fm/swap-vault-poneglyph-naming-in-grand-lin-1f`): after seeing PR #344's swap live, he judged it backwards - Automic Vault's hardening panel is the vault he already relies on daily, so it reclaimed the `.vault` Stores destination and the plain "Vault" label (see the section below), and this feature - the captain's own personal credential store - took the name "Poneglyph" in its place, moving under Setup as its fifth tab.** His words: *"the atomic vault, let us move it back to stores and keep that as vault again. The current vault which is basically should be renamed to Poneglyph."* Nothing about what this feature does changed across the move - the same encryption, portability sync, and CRUD described below. The Swift type name (`CredentialVaultController.swift`) was deliberately left as-is (only the label and destination moved) rather than renamed to "Poneglyph*" across its ~12-file family, matching this app's established convention of not renaming every internal type behind a label change (see `VaultController.swift`'s own header for the full history of both swaps).

**A third move (`fm/move-poneglyph-to-stores-space-282a`): the captain asked for the Poneglyph *card* to move off the Engineering space canvas ("Toolchain setup and this machine's settings") into Stores, beside Vault/Docs/Tools/etc.** `DaylightModule.poneglyph.space` now returns `.stores` instead of `.engineering` (`DaylightSpace.swift`), so the module card renders on the Stores canvas, not Engineering's. **Two things this did NOT change, deliberately, because they are separate mechanisms this app already keeps decoupled from a card's space:** the `.poneglyph` rail destination's `slot` (`DestinationRegistry.swift`) still resolves to `.setup` at the time (**this has since changed - see the fourth move below**), so opening it still lands in `SetupContainerController`'s shared segmented-tab container alongside Updates/Bootstrap/Automation/GitHub Sync (unchanged - the same "a destination's slot is independent of which controller populates it, or which space its card shows in" precedent the two prior renames above already established); and `RailDestination.isDailyUse`/`.flyoutTint` were left untouched too, since both have "no remaining consumer in the shell" per `RailDestination.swift`'s own doc comment (dead/historical greppable state from the pre-Daylight icon rail, not a live UI surface). **A real gotcha found while making this move**: `DaylightModule.canvasOrder` is literally `allCases` - i.e. **enum declaration order is load-bearing for a space's card layout order** (unlike `RailDestination`'s own case order, which that enum's header explicitly says no longer drives anything). Moving `.poneglyph` to `.stores` in the `space` switch alone would have put its card *first* on the Stores canvas (ahead of Vault/Docs/Runbooks/Postmortems), since its case was declared right after `.githubSync` - so the case declaration itself was relocated too, to sit right after `.vault`, so the card renders beside the destination it is most often discussed alongside. **Any future space reassignment for a module needs the same two-part check**: update the `space` switch (`DaylightSpace.swift`) *and* consider whether the case's declaration position should move too, or it will render in the wrong place within its new space's grid despite passing every membership-only self-test.

**A fourth move, this one structural rather than cosmetic (`fm/poneglyph-own-destination-and-strawhat-toolbar-shortcut`): the captain reported that clicking into Poneglyph from its Stores card showed a page titled "Setup" with an Updates/Bootstrap/Automation/GitHub Sync tab strip above it - a captain-visible contradiction with the third move above, which had already put its *card* in Stores while its *destination* still shared Setup's container.** `RailDestination.poneglyph.slot` (`DestinationRegistry.swift`) now returns its own `DestinationSlotID.poneglyph` instead of `.setup`, mirroring exactly how `.strawHat` already had its own slot rather than sharing one - `SetupTab.poneglyph`/`SetupContainerController`'s `poneglyph` parameter are both gone (`SetupContainerController` now takes only `updates`/`bootstrap`/`automation`/`githubSync`), and `CredentialVaultController` (already conforming to `DaylightDrillActions` on its own, so no new conformance was needed) is registered as its own `AppShellController.mounter` slot. `RailDestination.bodyTitle`'s then-existing `slot == .setup ? "Setup" : title` rule meant the page showed "Poneglyph" with no tab strip, automatically, with no change to that computed property itself. (That property is gone now - `fm/grandline-separate-setup-destinations` made the identical move for the four pages left behind, which left it a pure alias for `title`.) **What deliberately did NOT move**: `DaylightModule.poneglyph`'s `space` (still `.stores`, from the third move) and its `hue`/`HelmDaylight.swift` domain-hue mapping (still amber, grouped with the four genuine Setup pages) - both are independent of which `DestinationSlotID` a destination's *page* renders into, the same "a destination's slot is independent of everything else about it" precedent the third move's own bullet already established, now proven a second time from the opposite direction (this time the slot moved and the space/hue didn't, rather than the space moving and the slot not). `DestinationMountingSelfTest.test_poneglyphIsSeparateFromSetup` mirrors `test_schedulesIsSeparateFromAutomation`/`test_healthIsSeparateFromSettings` exactly and is the permanent regression guard - confirmed to catch a real regression by temporarily re-adding `.poneglyph` to `SetupTab` and watching it fail on the leftover "Poneglyph" tab-pill label, the same way its two siblings were each confirmed. The same task added two more toolbar quick-access icons - see the `DaylightBarController` bullet below.

**The history below predates the second rename and the third/fourth moves, and describes this same feature throughout as "the `.vault` destination"/"Vault", "under Setup", or "a Setup tab"** (it is now Poneglyph, its own standalone destination, reachable from its own Stores card):

**The captain's own personal credentials store: reveal or copy a token into the clipboard in one click, get every credential back on a new machine with no export/import step, and full CRUD (`fm/implement-grand-line-secrets-vault-poneg-ad`).** The authoritative design is `data/plan-secrets-vault-for-grand-line-34/report.md` (a scout task, reviewed live with the captain across four rounds in Lavish) - **read it before extending any of this**, along with `CredentialVaultCrypto.swift`'s and `CredentialVaultModels.swift`'s own headers, which carry the per-decision reasoning.

- **This replaced Automic Vault's panel *here*, and that panel is not gone (historical - see the correction above for where each feature lives now).** It moved under Setup as a fifth tab and was renamed **Poneglyph** at the time - see the section below, and `VaultController.swift`'s header, for the captain's own words. **Why the two had to be separated rather than merged:** Automic Vault is, by its own written product docs and ADR 0010, *not* a retrieval-based password manager - it authorises what a CLI may do with a credential and deliberately exposes no "give me the raw secret" operation. Its `av list` returns names only. So it can never answer "paste my Gmail password into a browser", and building this feature on it would have meant fighting its architecture at every step. Two genuinely different things had both been answering to "Vault".
- **Two independent passwords, by the captain's decision** (*"Let us have different passwords for the vault as well as the application password"*). The vault's master password is not derived from, and does not unlock, the whole-app lock (`LockScreenController`), and vice versa. The app lock still gates the window; this gates this page. **The whole app locking does re-lock the vault** (`AppShellController.showLock` -> `CredentialVaultController.lockForAppLock`) - not because the overlay needs help hiding a subview of its own window, but because the derived key and every decrypted value have to leave memory when the captain walks away.
- **The master password is never stored anywhere, in any form** - the captain asked for that explicitly. It is typed, handed to `CredentialVaultCrypto.deriveKey` once, and dropped; there is no property on the store and no field in the file format it could be written into. Optional Touch ID unlock stores the **derived key**, never the password, in the Keychain (`CredentialVaultKeyStore`) behind this app's own `LAContext.evaluatePolicy` challenge - the in-app-gate pattern `KeychainKeyStore.swift`'s header explains this unsigned build forces (`SecItemAdd` with any `kSecAttrAccessControl` fails `errSecMissingEntitlement` here). That key is `ThisDeviceOnly` and deliberately does **not** travel: a new Mac's first unlock is always the password, which is what stops the Keychain copy from making the password decorative.
- **Crypto: PBKDF2-HMAC-SHA256 (`CommonCrypto`) into AES-256-GCM (`CryptoKit`), with a per-item HKDF subkey.** Argon2id is the better KDF and was rejected for one concrete reason, not a preference: it has no native Apple API, and this app's standing rule is that a dependency arrives as vendored committed source only when there is no way around it. The report records the Argon2id upgrade as real later work. **The round count lives in the file, not in the source** (`CredentialVaultFile.KDFParameters.rounds`, default 600,000) - that is what makes "tunable" true rather than aspirational: raising the constant applies to vaults written afterward and on the next password change, and an older vault still opens because it carries the count it was written with.
- **Everything about a credential is encrypted, including its title.** The file's only plaintext is its scaffolding: the format version, the KDF parameters (which a legitimate open needs) and one opaque UUID per item. The report is explicit about why - "item names like 'AWS Root Account' are themselves worth protecting once the file is routinely git-pushed". The audit log is sealed as **one** blob rather than per event, which also hides the event *count*. **`CredentialVaultSelfTest.checkNothingReadableLeaksToDisk` greps the real bytes of the real file** for planted titles/accounts/tags/notes/values - reasoning about whether the format encrypts a field is exactly the claim that survives a refactor while stopping being true.
- **Portability is the encrypted file itself riding `manjesh-config`, in a new dedicated folder.** `grand-line-vault-backup/vault.enc.json` at the repo root - a **sibling** of `automatic-vault-details-backup/`, which stays untouched (the captain's explicit instruction), and deliberately **not** under `GrandLineDocs/`, which is where this app's *documents* sync. When git sync is active the repo copy *is* the live file, so there is no second copy to drift and no export step. A new Mac gets everything the moment Bootstrap's existing dotfiles-clone step runs. `CredentialVaultGitSync` is the fourth copy of `DocsRunbookGitSync`'s shape (shared working tree, shared serial queue - two queues issuing `git` against one tree race on `.git/index.lock` - `ConfigRepoPrivacy` gate, bounded `Subprocess.git`, quit-time on-queue bounded flush per audit 2 §4.3).
- **`VaultRecipeGit`'s "backup the recipe, not the values" judgement is not overturned - it is satisfied differently.** That mechanism exists because a *plaintext* secret export was rejected earlier in this app's history. The bytes pushed here are AES-GCM ciphertext under a key stored nowhere, so a leaked clone discloses what a stolen powered-off laptop would: nothing. The encryption does the work rather than the choice of what to omit. **The commit subject is deliberately contentless** ("Vault: encrypted credential store updated") - a message naming what changed would publish in the repo's plaintext history the very titles the format encrypts, and the self-test asserts it.
- **Reveal and Copy are two separate one-click actions, on every list row, and neither implies the other.** This is the captain's own correction, twice over: *"Reveal and copy should be separate, with their own icons. I don't always want to reveal when I copy, for example while screen sharing"*, and *"I do not want to go inside each of them here"*. So Reveal toggles the value onto the row and never touches the clipboard; Copy writes the clipboard and never puts the value on screen. **Both directions are asserted** in `CredentialVaultViewSelfTest` by clicking the genuine `NSButton`s - "Copy did not reveal" is as much the requirement as "Copy copied", and a suite that only checked the positive half would pass with the split collapsed.
- **The revealed value renders in the row's own meta line, in `HelmType.code()`, replacing the account line.** Two reasons, both real: the table has a fixed `rowHeight` (every sibling `HelmAccentRow` list in this app fixes it, and a third line would make *every* row taller for the one that is revealed), and the switch to monospace is itself the signal that what is on screen is the secret rather than a description of it. **Item Detail was kept, not removed** - for notes, exact timestamps, edit, delete and the per-item audit history, which a row genuinely cannot show.
- **The audit log is values-free by construction, not by filtering.** `VaultAuditEvent` has no field a secret could travel in; an update event names the changed *fields* ("notes, tags"), never the values. **`reveal` and `copy` are separate `Kind` cases** rather than one `accessed` case with a flag: whether a value has ever been on screen is exactly the fact worth keeping, and collapsing them would lose it. Capped at `maxAuditEvents` (2000, `FleetLogStore`'s own number and direction - oldest first, because trimming the newest would leave the log permanently stale rather than merely bounded).
- **Clipboard auto-clear only fires if `NSPasteboard.changeCount` has not moved since the copy** (`CredentialVaultClipboard`). Genuinely new functionality - the report confirmed by grep that no auto-clear existed anywhere in this app. Without the count check the timer is a hazard rather than a safeguard: copy a password, paste it, copy a URL from a browser, and 20 seconds later this app would silently wipe the URL. `lock()` *abandons* a pending clear rather than firing it, because a locked vault has no business reaching into a pasteboard the captain may since have filled from elsewhere.
- **GL-01 matters more here than anywhere else in the app, and the unlock screen has a third state because of it.** "The file is missing" and "the file is there and unreadable" are different, and collapsing them would offer a *create a new vault* screen while the captain's real encrypted credentials sat one directory away - which the first write would destroy. `VaultLoadState` keeps them apart, `createVault` refuses whenever *any* file is on disk (readable or not), and the `.unreadable` gate state deliberately offers **no** primary action at all. The view suite asserts that by walking the real view tree for a create button rather than by reading a mode flag: the absent button is the property that protects the credentials, not the flag being right.
- **Every `Codable` type here decodes an older file**, via hand-written `init(from:)` with `decodeIfPresent` fallbacks. Swift's synthesised decoder requires every declared key to be *present* regardless of a Swift-side default - the landmine that once made every existing `hosts.json` undecodable when `Host` gained one field. For a file that is the captain's only copy of his real credentials, getting this wrong is not cosmetic. Adding an *optional* field therefore needs no `formatVersion` bump; a **newer** format version is refused outright rather than opened and partially rewritten.
- **`FM_CREDENTIAL_VAULT_DIR`, and `FM_SHIFT_DIR` as the fallback.** The store is reachable from a bare `CredentialVaultStore()`, which with no override resolves to `CredentialVaultGitSync.shared` - the captain's real clone. Both `main.swift`'s `#if FM_SELFTESTS` block and `ci.yml` set the narrow override, the store honours `FM_SHIFT_DIR` too, and it is named in `E2ETestingPolicySelfTest`'s store-family guard. **`DaylightModuleSelfTest.checkCanvasConstructsNoStores` also bans `CredentialVaultStore(` from the canvas** - the hub card reads injected state (`HomeCanvasController.credentialVaultState`), because a store built there would reach that clone on every hub render.
- **Auto-lock is idle-based and deliberately does NOT fire on navigating away.** A vault that closed itself every time the captain looked at Console would be unusable, and the whole-app lock already covers walking away. `viewDidDisappear` stops the timer (GL-13) without locking; the timer sets a `tolerance` (§3.4).
- **Verified** by `swift build` (clean debug and release, zero warnings in this app's sources), the release binary confirmed to carry no `FM_RUN_*` strings, and the full suite - **without launching the app**, per the README's worktree rule (the captain's real packaged instance was running throughout, and this repo has no process isolation between builds sharing one bundle identity). **Twelve injected regressions each reproduced by name**: a plaintext title in the file, a verifier that always opens, the per-item subkey collapsed to one shared key, the clipboard clearing regardless of `changeCount`, a corrupt vault reading as absent, a reveal logged as a copy, Copy also revealing, Reveal also copying, an unreadable vault offering Create, search matching the secret value, the root appearance left unforced, and auto-lock ignoring "Never".
- **Still open, deliberately:** a real end-to-end pass on the captain's own machine (a real master password, a real push to `manjesh-config`, a real Touch ID prompt, a real restore on a second Mac) is his own check - none of it is reachable from this sandbox, and the app was never launched. Phase 4 of the report's build plan is also untouched: the global hotkey / menu-bar quick-find-and-copy, and the Argon2id upgrade.

## Vault (`.vault`, Automic Vault's hardening panel)

**Renamed and relocated twice by the captain.** First, `fm/implement-grand-line-secrets-vault-poneg-ad`: this page was the `.vault` destination and became Poneglyph, the fifth tab of Setup, while the new personal credential vault took over `.vault`/"Vault" - his words at the time: *"Since we are using lot of the ship and one piece theme, I would suggest the name of the application or the feature instead of tool hardening as 'Poneglyph.'"* Then, `fm/swap-vault-poneglyph-naming-in-grand-lin-1f`, after seeing the two live: this panel reclaimed the `.vault` Stores destination and the plain "Vault" label, and the personal credential vault took the name "Poneglyph" in its place under Setup (see the section above) - his words: *"the atomic vault, let us move it back to stores and keep that as vault again."* `VaultController.swift` (briefly `PoneglyphController.swift`, originally `VaultController.swift` before the first rename) is this page's type - it never needed renaming since it is, again, "the Vault". **Nothing about what it does changed across either move** - the same `av` reads, the same Console-tab `av save`/`av inject`, the same recipe export. `VaultData.swift`/`VaultRecipe.swift`/`VaultRecipeGit.swift` kept their type names throughout both renames on purpose: the decisions were about this panel's label and its place in the navigation, not about renaming every internal type, and this app already draws that distinction (its own display-name rebrand left the bundle id, signing identity and module name alone). `FM_RUN_VAULT_LOADING_STATE_TESTS` moved with its subject to `FM_RUN_PONEGLYPH_LOADING_STATE_TESTS` and back to `FM_RUN_VAULT_LOADING_STATE_TESTS` again.

**The history below predates both renames and describes this same panel throughout** (it says "the Vault page"/"`.vault`" or "Poneglyph"/"Setup's fifth tab" in different places, all referring to this one panel - Automic Vault's hardening panel is at `.vault`/"Vault" again, current as of this section's own title):

**`fm/grandline-vault-tab` originally made this a rail destination pinned directly above `.docs` and below `.tools`** (so the bottom-anchored utility group reads Tools, Vault, Docs, Updates, Bootstrap, Settings), embedding Automic Vault (https://github.com/automic-vault/automic-vault) rather than reimplementing its security model - the same "thin native window onto another system" pattern this whole app already follows for firstmate/herdr/Homebrew.

- **`VaultData.swift` is the only code that shells out to the real `av` CLI**, mirroring `UpdatesData.swift`/`NotSyncedData.swift`'s `Process`+`Pipe` plumbing exactly. `av list`/`av doctor --json` only ever return secret *names* and tool metadata (confirmed live - never a value), so those run as an ordinary background check. Install/update reuses `UpdatesSource.check`/`.update` on the *existing* `DependencyCatalog` "automic-vault" entry (`UpdatesData.swift`, Security category) - not a second brew-cask implementation.
- **`av save NAME` is never run as a background `Process` - confirmed live it fails outright ("failed to open /dev/tty") when piped a value via stdin**, since it reads the secret value from the real terminal's own tty. `VaultController` only ever builds the command *string* (`VaultSource.saveSecretCommand(name:)`, name-only, value never touches this app) and runs it through `AppShellController.runInConsole` - the same real Console-tab mechanism every sudo/interactive Bootstrap/Settings action already uses. `av inject +NAME -- cmd` is confirmed live to work fine as a background process (Automic Vault's own approval prompt, when one fires, is handled by its separate menu-bar app, not `/dev/tty`) but is *still* routed through the same Console tab rather than captured by this app, since the injected command is free text and may print anything - Grand Line must never be the thing that logs a command's real output.
- **`VaultSource.isSafeToken` is a conservative allowlist (letters/digits/underscore/dash)** gating what's allowed to be spliced unquoted into the `-lc` shell string `openCommandTab` runs - stricter than whatever `av save` itself accepts, since the only job here is "safe with no quoting," not "matches every name av would allow."
- **No secret value is ever stored, cached, or logged by this app** - every listed secret gets a static "Hardened" label (true by construction: `av list` only returns Keychain-backed entries), and `av doctor --json`'s per-tool `issues` count drives a status pill plus the page's one quiet-until-it-matters attention banner (hidden whenever no tool has real issues - no polling, no fake liveness, per `PRODUCT.md`).
- **Verified live against the real `av` CLI on this machine** (real secrets, real "claude" launcher, real brew-cask "Update Available" status) via a temporary env-gated probe in `main.swift`/`AppShellController`/`VaultController` (reverted before commit, per this file's "Verifying native UI bugs" convention) - `av save`/`av inject`'s Console-tab path was verified by code review + the isolated `/dev/tty` and background-process probes above, not by triggering a real interactive save/inject from the running app in this sandbox.

Copies only the name string already shown in the row (`NSPasteboard.general`) - never a secret value, which this app has no access to regardless (see the bullets above).

**`fm/poneglyph-fix-touch-id-icon-alignment-ad-bf` fixed a captain-reported misalignment of the small `touchid` glyph next to a credential's title, and separately added captain-controlled manual reordering of the credential list - a follow-up inbox message said to solve both together, since the alignment fix and the required final ordering turned out to be the same change.**

- **The misalignment was `HelmAccentRow`'s own known shape, not a bug local to Poneglyph.** `titleRow` (`[titleLabel, titleAccessory]`) centers its accessory glyph against the *title label's own line height*, then that whole `titleRow` sits as the top line of a vertical `textStack` (kicker/titleRow/meta) which is centered as one block within the full row height - so an accessory glyph riding along in `titleAccessory` never lines up with the row's own trailing action icons, which center directly against the full row. Rather than touch `HelmAccentRow`'s shared `titleRow`/`textStack` layout (used by Shift's own paperclip-icon rows and others), the fix moved the glyph entirely: `CredentialVaultController.row(for:)` no longer sets `content.titleAccessorySymbol`; instead `CredentialVaultRecordView` (`CredentialVaultListSection.swift`) gained a plain `NSImageView` (`touchIDIndicator`, an `HelmSymbol.image("touchid", ...)` template glyph tinted `HelmTheme.mutedInk`) inserted as the **first** arranged subview of the row's own trailing `actions` stack - before Reveal, Copy, and the overflow button - so a row with both a tag chip and Touch ID reads `[chip] [fingerprint] [eye] [copy] [...]`, with the fingerprint now centered exactly like every other icon in that cluster because it *is* one.
- **Manual sort order is a new persisted field, not a UI-only reorder.** `VaultCredential.sortOrder: Int` (with the usual `decodeIfPresent(... ) ?? 0` fallback, since every existing on-disk credential predates the field) plus `VaultCredential.displayOrder(_:_:)` (sortOrder, then title, then id as tiebreakers) replaced a plain alphabetical-by-title sort in `CredentialVaultController.renderList()`. The captain's own words ruled out any date-based scheme: *"Anything, I should be able to sort anything irrespective of whether it's created first or last."*
  - **`CredentialVaultStore.normalizeSortOrderIfNeeded()`** is a one-time, idempotent migration called from `finishUnlock()` right after loading `credentials` - it seeds `sortOrder` per-category from the exact order the list already showed (alphabetical), so a file written before this field existed shows **no reshuffle** the first time it unlocks under the new code. It's safe to run on every unlock (only mutates when a value actually differs).
  - `add()` appends a new credential to the end of its category via `nextSortOrder(inCategory:)`, never leaving it at the struct's `0` default (which would otherwise jump it to the top). `update()` preserves the existing `sortOrder` unless the credential's category changed, in which case it's re-appended to the end of the new category via the same helper.
  - **`reorderCategory(_:orderedIDs:)`** is the one write path a captain-driven drag goes through - it re-numbers `sortOrder` for exactly the ids in the category the drag happened in, then calls `finishWrite` (the vault's normal encrypted-save path) only if something actually changed.
- **Drag-and-drop reuses this app's one existing `NSTableViewDataSource` reorder mechanism (`ShiftBoardCardView`'s pattern), not a new one.** `CredentialVaultDragPasteboard` (a private pasteboard type, `"com.firstmate.cockpit.vault.credential-id"`, mirroring `ShiftBoardPasteboard`'s own naming) is what stops a foreign Finder/text drag from being mistaken for a credential reorder. `CredentialVaultListSection` implements `pasteboardWriterForRow`/`validateDrop`/`acceptDrop` the standard way: a drop is only accepted at `.above` with both the dragged and boundary rows resolving to the **same category** (`categoryGroup(atBoundary:)` walks the row just above and just below the drop insertion point) - a captain cannot accidentally drag a credential out of its category group this way, matching how the group headers are rendered as non-record rows. `onReorder(draggedID, beforeID)` is the one closure the section fires; `CredentialVaultController.reorderCredential(id:before:)` re-derives the category's full ordered-id list from the live store (never trusting stale UI state) and calls `store.reorderCategory`.
- **A real gap the drag self-test almost shipped with, worth remembering: asserting the *model*'s order isn't the same as asserting the *rendered table*'s order.** `CredentialVaultViewSelfTest.checkDragReorderWithinCategory`'s first draft only checked `store.credentials.sorted(by: displayOrder)`, which passed even when a scripted revert of `renderList()`'s sort (back to plain alphabetical) was in effect - the store was right, but nothing painted it. The fix reads `list.debugItem(row)?.content.title` for the category's rows in table order and compares that against the expected post-drag sequence; only then did reverting `renderList()`'s sort correctly fail the test. Any future list-reorder feature in this app should assert the rendered row order, not just the backing store's sort.
- **`fm-poneglyph-fix-touch-id-icon-alignment-ad-bf`'s CI run (`macos-14`) found the alignment fix above was still off by exactly 0.5pt across all three swept themes - real, deterministic, not flaky - and a first follow-up fix (syncing `NSControl.controlSize`, since `HelmButton(size: .small)` never touches AppKit's own real controlSize) made ZERO measurable difference on CI, byte-for-byte the same failure before and after.** That disproved the controlSize/alignmentRectInsets-asymmetry theory outright (confirmed directly, not just by CI's report: dumping `alignmentRectInsets` on the dev machine before/after setting `controlSize = .small` showed byte-identical frame AND insets values regardless of controlSize - the theory was never actually true on either machine). **The real mechanism, found by dumping AppKit's own installed constraints rather than guessing further: `actions.alignment = .centerY` installs one `'NSStackView.Align' view.centerY == stack.centerY'` constraint per arranged subview - correct, unconditional, and equally applied to all four (touchID + 3 buttons).** The bug is a **tree-walk-order bug, not an insets bug**: `NSView.layout()` runs once per view during a top-down `layoutSubtreeIfNeeded()` pass, and a view's own override only resolves what constraints attached to *that* view govern - a descendant gets its own separate `layout()` call, LATER in the same pass, that can (and for an `NSStackView`, does) re-derive and overwrite its own arranged subviews' positions from its own internal `.Align` constraints regardless of what an ancestor did moments earlier. The first fix attempt placed a manual frame-correction override on `CredentialVaultRecordView.layout()` (an ANCESTOR of the `actions` stack) - it "worked" locally purely by coincidence, since this dev machine's underlying Auto-Layout-resolved answer already happens to be correct on its own; a dedicated probe (artificially perturbing `touchIDIndicator`'s position by exactly -0.5pt inside `layout()`, matching CI's exact reported shape, with the correction toggle-able via a temporary env var) proved the ancestor-level correction was **silently discarded every single time** by the stack's own subsequent layout pass - the same probe, reproducing CI's precise failure message verbatim ("got 10.0 vs 10.5"), confirmed the correction only actually sticks once moved to `layout()` **on the stack itself**. **Fix**: `TrailingActionsStack: NSStackView` (`CredentialVaultListSection.swift`) is a small private subclass of the `actions` stack, carrying `glyphToCorrect`/`referenceCandidates` and overriding `layout()` to force `touchIDIndicator`'s frame origin to match the first visible reference button's `frame.midY` exactly, unconditionally, after `super.layout()` runs - since this stack's own `layout()` is the LAST call in the tree walk for this relationship, nothing runs afterward to undo it. **The general lesson: when a manual post-layout correction "doesn't stick" or "makes no difference," suspect where in the view tree the override lives before suspecting the geometry theory itself** - `super.layout()` inside an ancestor's override does not recursively resolve or "lock in" a descendant's own internal Auto Layout arrangement; that descendant gets its own, separate, LATER `layout()` call in the same pass, and only an override on THAT view is guaranteed to run last for whatever it itself controls.
- **Verified** with `swift build`/`swift build -c release` (clean, zero `FM_RUN_*` strings in the release binary), `FM_RUN_CREDENTIAL_VAULT_TESTS`/`FM_RUN_CREDENTIAL_VAULT_VIEW_TESTS`, and the full `./Scripts/run-all-tests.sh` suite (143 passed / 0 failed / 1 documented skip, `fm.themeID`/`fm.fontSize` unpoisoned) - real off-screen renders across `helm-dark`/`helm-light`/`daylight` confirmed the glyph sits in-cluster and vertically aligned for a credential with both a tag and `requiresTouchIDToReveal`. All three fixes - the alignment fix, the "rendered order, not just model order" drag-reorder gap, and this `TrailingActionsStack` correction - were confirmed via scripted revert-and-restore (never `git stash`) to actually catch their respective regressions, the last one by directly reproducing CI's exact reported failure text via a temporary, idempotent -0.5pt perturbation probe and confirming the stack-level correction (and only the stack-level correction, not the earlier ancestor-level one) neutralizes it back to `delta=0.0` - all probe instrumentation removed before commit.

## Poneglyph F16/F17: TOTP, secure notes, a generator, a menu-bar popover, a printable recovery key and CSV import

**`fm/grandline-feature-f16-f17-poneglyph-totp-recovery` built both Poneglyph recommendations from full review #3 §8 in one branch, because they are one subsystem and splitting them would have put two lanes into the same security-sensitive files at once.**
Shapes follow the captain's own reviewed mockups (F16 and F17 in the `grandline-future-features-mockups-artifact` deck).

### F16, and the three decisions inside it

- **TOTP is `TOTP.swift`, about 200 lines including the comments, with no dependency.**
  RFC 6238 is RFC 4226 with the counter fixed to `floor(unixTime / period)`, and CryptoKit ships all three hash functions, so the whole algorithm is one `HMAC.authenticationCode` call plus the RFC's own dynamic truncation.
  `Insecure.SHA1` is the correct primitive here and is documented as such in the file: RFC 6238's default is HMAC-SHA1, HMAC-SHA1 is unaffected by SHA-1's collision weakness, and refusing it would mean refusing essentially every real 2FA secret the captain already holds.
- **The suite asserts the RFC's own eight published vectors across SHA1/SHA256/SHA512, not "it produced six digits".** That matters because a truncation off by one byte, or a counter written little-endian, still produces six plausible digits forever - the captain would find out at an AWS console at 2am. Confirmed to catch a regression: forcing `offset = 0` in the dynamic truncation failed all eight by name.
- **A secure note is not a parallel store.** `CredentialKind` is a second axis beside `CredentialCategory` (what a credential *is*, versus what it is *about*), and a note's body lives in the same sealed `secret` field a password does - so it takes the same per-item HKDF subkey with no new storage path. What differs is only the treatment: multi-line editing, opened rather than revealed, and **no Copy on the row** (prose on the pasteboard is how a break-glass procedure ends up in a chat window). The row says `3 lines · encrypted with the vault key` rather than showing the first line, which is GL-14's instinct applied to a row.
- **The generator lives inside the Add sheet**, which is the mockup's own stated judgment call. Randomness is `SecRandomCopyBytes` behind a `RandomNumberGenerator`, handed to Swift's `random(in:using:)` so nothing ever reaches for a biasing `%`. The printed entropy is computed (`log2(alphabet) * length`, `8 bits * words`) rather than decorative - which is why the word list is exactly 256 words and a self-test fails if it drifts. "Use this password" is the only write into the form: dragging the slider must not overwrite a password the captain had already typed.
- **The menu-bar popover is the third instance of one shape**, deliberately - `ShiftMenuBarController` -> `StrawHatMenuBarController` -> `PoneglyphMenuBarController`, same status item, same `.transient` popover, same `AppLockGate` registration, same `prepareToShow()` split for the suite. It owns no store (GL-23: `CredentialVaultStore` caches, so there is exactly one, and it belongs to the page); everything forwards through `AppShellController`, the way `askCrewFromMenuBar` already does. It refuses to open at all while the app is locked (`AppLockedSurface.poneglyphMenuBarPopover`, its own case) and shows a "Poneglyph is locked" line - not an empty list - while the *vault* is locked, because those are different states.
- **One clock.** `TOTPTicker.shared.now` is the only `Date` any TOTP surface reads. F7's focus timer is why that rule exists; here the cost of breaking it is worse than a confusing test - the row and the popover would show the same credential with two different countdowns and a captain would paste an expired code. The ticker runs only while something observes it, at a stated tolerance (audit §3.4), and the page drops its subscription in `viewDidDisappear` (GL-13).

### F17's cryptography, and the one thing not to undo

**The vault key is derived directly from the master password** - `vaultKey = PBKDF2(password, kdf.salt)` - so there was no key-wrapping envelope to add a second wrap to. The design actually shipped:

    recoveryKEK = PBKDF2(recoveryCode, recoverySalt, rounds)
    wrap        = AES-GCM-seal(the vault key's 32 raw bytes,
                               HKDF(recoveryKEK, recoverySalt, ".../recovery-wrap"))

- **The password path is byte-for-byte unchanged.** Enrolling a recovery key adds one optional field to the file and alters nothing about how a password opens the vault; a vault with no key printed is exactly the file it was before this feature existed. The recovery path recovers the *same* key and hands it to the *same* verifier check.
- **The code is 160 random bits** (20 bytes, 32 Crockford base32 characters, printed as eight groups of four). That, not the PBKDF2 pass over it, is what makes the recovery door no easier than the password door - so shortening the code to something friendlier to type is the one change here that would quietly turn this into a backdoor. `CredentialVaultRecovery.swift`'s header says so at the top.
- **Crockford's alphabet** (no I, L, O, U) with its documented aliases on the way back in, because a captain transcribes this by hand off paper.
- **A password change drops the wrap, deliberately.** The wrap holds the *old* vault key's bytes and every payload is re-sealed under a new one, so unwrapping would hand back a key that opens nothing - a far worse outcome than "your recovery key no longer works". It cannot be re-wrapped either: the code is shown once and stored nowhere, so the app does not have it. Asserted by the suite rather than only documented, because it is the property a future maintainer is most likely to "fix" into a silent one.
- **A recovery unlock can set a new master password without the old one, and that path is gated on nothing else.** `resetMasterPasswordAfterRecovery` refuses unless `unlockedViaRecoveryKey` is set (and `lock()` clears it). Without that gate it would be "any unlocked vault can be re-keyed without the old password", which would weaken every ordinary session - an unattended unlocked window could be taken over permanently.
- **`persist()` carries the wrap forward by hand.** It is neither an item nor a header the three-way merge reasons about, so without that line a write that adopted on-disk changes would silently discard an enrolment made seconds earlier.

### The printed card, and this app's first print view

`CredentialVaultRecoveryKitView` draws a US Letter page in explicit black on white and **deliberately does not observe `ThemeManager`**. A themed view sent to a printer under Dusk prints a near-black rectangle - the captain would burn a cartridge on a card they then could not read. The same view renders the PDF that "Save as PDF" writes, so the printed page and the saved file cannot drift. Nothing on the card identifies the vault beyond its file name: a recovery key taped inside a filing cabinet should not also be an inventory of what it opens.

Asserted by **pixel**, not by "the view exists" - a print view that draws nothing still lays out and still produces a PDF. The check samples in `rep.colorSpace` and scales point coordinates by `rep.pixelsWide / bounds.width` (both AGENTS.md rules), asserts the page's bottom margin is genuinely blank first so "found ink" means something, and re-renders under a dark theme to prove the ground stays white.

### CSV import

Column layouts were taken from real exports rather than guessed - 1Password 8 (`Title,Url,Username,Password,OTPAuth,Favorite,Archived,Tags,Notes`), 1Password 7's older `notesPlain` spelling, Bitwarden (`folder,favorite,type,name,notes,fields,reprompt,login_uri,login_username,login_password,login_totp`, whose `type` column is the only one of the three that states a kind) and Chrome (`name,url,username,password,note`). Anything else still imports as `.generic` by fuzzy header match.

- **The mapping is resolved by column *name*, even for the known formats.** An export with one extra column would otherwise shift every field by one, which is the worst possible failure here: it imports, and every password is wrong.
- **A malformed row is skipped and reported by line number**, never dropped silently; a row whose 2FA column will not parse imports *without* the seed and says so, rather than storing one that would produce wrong codes forever.
- **Nothing is written unencrypted.** The parser is pure logic with no I/O, the sheet holds the CSV text only while it is open, and the write goes through `CredentialVaultStore.importCredentials` -> the same `persist()` a manually-added credential takes. The suite greps the real file on disk for an imported title, password and 2FA seed and finds none of the three.
- **`\r\n` is ONE `Character` in Swift**, so it matches neither `"\r"` nor `"\n"`. Measured, not reasoned: the first version of `CSVParser` parsed a Windows-exported CSV - which is what all three of these managers write - as a **single row** with the line breaks buried inside field values, and reported one malformed credential instead of 148 good ones. The suite's CRLF case is the guard.
