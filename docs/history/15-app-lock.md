## App lock

**`fm/grandline-app-lock` adds an app-level password gate independent of the Mac's own login/Touch ID** - a captain-approved night-sailing lock screen covering the whole window (rail included) until the correct password is typed. Reuses Automic Vault for the password itself rather than inventing a second secret store.

- **The password is a fixed secret name, `GRANDLINE_APP_PASSWORD` (`VaultSource.appPasswordSecretName`), set by the captain themselves via `av save`/the Vault tab - this app never writes it and has no first-run setup screen.** `VaultSource.checkAppPasswordConfigured()` (`av list`) decides which of the lock screen's two states to show - a real password form, or (if the secret doesn't exist) a static "run `av save GRANDLINE_APP_PASSWORD`, then relaunch" message with no form at all. Absence of the secret always means "can't get in," never "let anyone in."
- **`VaultSource.verifyAppPassword(_:)` mirrors the Vault tab's own `av inject +NAME -- command` mechanism** (see the Vault section above) but runs it as a background `Process` rather than through a visible Console tab - a password check has nothing worth showing the captain. The typed guess travels to the comparison shell via one environment variable (`GRANDLINE_LOCK_CANDIDATE`), never spliced into argv/the shell command text, so it never appears in a process listing. **A real, load-bearing finding**: on an unsigned dev binary rebuilt each time, Automic Vault's own approval flow can require a real interactive click on its menu-bar app's popup (a "new" caller identity each rebuild) - invisible to this app, since the check runs headlessly with no Console tab. A shell-invoked `av inject` (a long-trusted caller) auto-approves near-instantly by comparison; this asymmetry, not a bug in this app's code, is what made early live verification of this path flaky in this sandbox until tests were restructured to drive `AppLockController`'s pure timer state directly instead of a real password submission for anything that isn't specifically testing the password check itself.
- **`AppLockController` (`AppLock.swift`) is the whole idle/hard-logout state machine, with no Vault/UI dependency of its own** - `onLock: (AppLockReason) -> Void` is the only way it talks to the outside world, wired to `AppShellController.showLock` in `main.swift`. Every threshold (`idleThreshold` 1h, `sessionThreshold` 12h, `pollInterval` 30s) is overridable via `FM_APP_LOCK_IDLE_SECONDS`/`FM_APP_LOCK_SESSION_SECONDS`/`FM_APP_LOCK_POLL_SECONDS` purely for live verification, never read from `AppSettings` (no way to configure a longer window from inside a locked app). `tick()` checks the 12h-since-last-unlock condition *before* the 1h-idle condition, so a captain who happens to cross both at once gets the `.sessionExpired` message, not the ordinary idle one - covered permanently, deterministically, by `AppLockControllerSelfTest.swift` (`FM_RUN_APP_LOCK_TESTS=1`) via an injected fake clock/idle-time provider (no real Timer or real `CGEventSource` involved), including the exact "unlock at hour 11 resets the 12h clock from there, not from launch" case the brief called out.
- **Idle detection is `CGEventSource.secondsSinceLastEventType(.hidSystemState, eventType: .null)`** - the standard, no-extra-permission "system-wide seconds since last real HID event" recipe (unlike a global `NSEvent` monitor, this needs no Accessibility permission). **`fm/grandline-lock-and-rail-fixes` fixed a severe live regression here: the captain reported the app re-locking every `pollInterval` (10-30s) even during continuous active use**, right after this feature (PR #129) shipped. The threshold/poll constants were already correct (3600s/30s, confirmed by the self-test, which passes unchanged before and after this fix) - trusting the system-wide counter as the *only* idle signal was the bug. Two changes: the state ID moved from `.combinedSessionState` (which additionally folds in "events posted by the current process via a private event source" - the wrong signal for a system-wide check, and the more plausible one to misbehave on this unsigned/ad-hoc-signed dev build) to `.hidSystemState`; and `AppLockController` now also tracks `lastLocalActivityAt` via a **local** `NSEvent` monitor (`localActivityMonitor`, added in `start()` - needs no Accessibility permission since it only observes events already targeted at this app's own windows) and uses `min(systemIdleSeconds(), secondsSinceLocalActivity())` as the effective idle reading (`effectiveIdleSeconds()`) - so a captain demonstrably, continuously interacting with this app's own UI can never be misread as idle no matter what a single system-wide counter reports on a given machine. Genuine inactivity still locks correctly since both signals go stale together. **Known sandbox-only caveat, not a defect**: the system-wide counter alone returned a huge, clearly-bogus value (~935,000s) when the *test binary* was launched headlessly (`nohup ... &`, no real interactive login/WindowServer session) in this repo's own agent sandbox - the same sandbox quirk plausibly explains why software-injected/synthetic events (which don't register as real HID input) can't move that counter either, which is exactly why the local-activity fallback above was verified live in this sandbox by injecting synthetic `NSEvent`s via `NSApp.sendEvent` and confirming they still suppressed a lock (through the local monitor, not the system counter) while a genuinely idle period with no such events still locked on schedule.
- **`AppLockController.start()` opts the poll timer out of macOS App Nap** (`ProcessInfo.processInfo.beginActivity(options: [.userInitiated, .idleSystemSleepDisabled], reason:)`, held for the controller's whole lifetime) and schedules the `Timer` in `.common` run-loop modes, not just `.default`. This is a real fix, not a precaution: App Nap throttling a backgrounded app's timers is exactly the failure mode this feature most needs to avoid, since its entire point is catching an app left unattended/backgrounded - confirmed live in this sandbox that a plain `scheduledTimer` fired once near launch and then stopped firing entirely for many seconds of otherwise-idle time until this fix was applied.
- **`LockScreenController.swift`** is the night-sailing scene - `CAGradientLayer` sky, fixed-position `CALayer` stars (deterministic, not randomized, so it renders identically on every launch/probe), a `CAShapeLayer` wave drifting via a looping `CABasicAnimation`, and a bobbing sailboat. **The sailboat is a real `NSImageView` laid out inside the same `NSStackView` as the title/subtitle/form** (Auto Layout-positioned, still layer-animatable via `.layer?.add`), not a freeform `CALayer` placed at a fixed fraction of the window's height - the first draft used the latter and a captain screenshot on a real (much taller than the 1220x720 default) window caught the boat landing squarely on top of the password field, since a height-fraction and an Auto-Layout-centered stack are two independent layout systems with no reason to agree at every window size. The password field is a custom-styled translucent pill (`isBordered = false`, `focusRingType = .none`, a `lock.fill` icon, a manually-built `placeholderAttributedString` since the plain `placeholderString` setter always renders in the system's default gray) rather than the stock system text field, after live captain feedback that the stock look clashed with the scene; its text is vertically centered by pinning the field's own natural-height frame to its taller pill container's `centerYAnchor` rather than top/bottom-pinning it to the container's full height - a plain `NSTextFieldCell` does not vertically center text within a frame taller than its own line height (confirmed live: it stayed visibly top-aligned until this fix). **Distinct animations for success vs. failure, per captain ask**: a wrong password shakes the field's pill container *and* rocks the boat (`playUnlockFailureAnimation`); a correct one sails the boat off to the right while fading it out (`playUnlockSuccessAnimation`), and **the overlay only actually hides once that animation's `CATransaction` completion block fires** (`onUnlockAnimationFinished`, not `onAttempt`'s own completion) - hiding immediately on a successful verify would cut the flourish off before it's ever visible, since the overlay would already be gone. **`fm/grandline-lockscreen-theme` reversed the original "fixed palette regardless of theme" decision above** per a later captain ask: the scene now follows the app's active Helm theme's light/dark `mode`, live, the same way every other view in this app does (`ThemeManager.shared.observe` registered in `loadView`, per `ThemeManager.swift`'s own checklist) - it is a permanent, app-lifetime singleton (owned by `AppShellController`), so the returned observation token is discarded like every other such observer in this app. Night mode is unchanged (the original palette above); day mode is a genuine second "daytime sailing" palette, not a dimmed copy - a glowing sun layer swapped in for the star layers (both built once at `loadView` time and toggled via `isHidden`, never added/removed, so there's no frame with neither or both), a brighter blue-to-pale-horizon sky gradient, a lighter turquoise wave, and dark ink/boat/field-pill colors instead of white (a translucent white pill and white text lose contrast against a pale sky). All of this lives in one `applyTheme(_ theme:)` method that the observer calls on every change, including while the screen is already on-screen and locked - it does not force `view.appearance`, since every color here is drawn explicitly (layer fills, `NSAttributedString` foregrounds) rather than via a system-semantic color. Verified live (not just `swift build`) via a temporary env-gated probe (reverted before commit, per this file's "Verifying native UI bugs" convention) driving the real controller end to end in both themes: initial dark-mode colors, a live theme switch to light while already locked (confirmed via the same instance, not a fresh one), a wrong-password shake+distress animation firing correctly in both themes, and a successful-unlock sail-away+fade animation completing (`onUnlockAnimationFinished` firing) in both themes.
- **The avatar's click action (`IconRailController.avatarClicked`) is now a themed `NSPopover` "Logout" row (`AvatarLogoutPopoverController`), replacing the old `NSApp.orderFrontStandardAboutPanel` call.** A bare `NSMenu` (this task's first draft) read as unstyled system chrome next to the rest of this app's deliberately-themed surfaces, per live captain feedback - follows `ShiftMenuBarController`'s own small-`NSPopover` convention instead. Logout is double-confirmed via two sequential `NSAlert`s (captain's explicit ask) before calling `onLogoutRequested`, which the app delegate wires to `appLock.lock(reason: .manualLogout)`.
- **While locked, every main-menu item except Edit (Cut/Copy/Paste/Select All/Find, all `nil`-target/responder-chain-routed) and the App menu's Hide/Quit is disabled** (`AppDelegate.setContentMenusEnabled`, driven by `AppShellController.onLockStateChanged`). The lock overlay being opaque and topmost already blocks mouse clicks on hidden content via ordinary AppKit hit-testing, but most of this app's menu items have a concrete `target` (not first-responder-routed), so a keyboard shortcut like ⌘N would otherwise still reach a hidden destination's action. Edit is deliberately left alone since the lock screen's own password field needs standard Cut/Copy/Paste (e.g. pasting a password from a manager via ⌘V) - and since the overlay always grabs first responder for its own field while locked, those actions can't reach anything else regardless.
- **Verified live** (real launched dev binary, real `GRANDLINE_APP_PASSWORD` secret in this machine's actual Automic Vault, real captain live-review across several iterations - see this task's PR for the screenshot-driven history): launch always shows the lock screen before any content; a wrong password is rejected with the shake/rock animation and the field stays enabled for another try; a correct password plays the sail-away/fade animation and then unlocks (content visible, menu re-enabled); the idle re-lock path was confirmed via `AppLockControllerSelfTest`'s deterministic proof plus a real Timer-driven live run showing `isLocked` correctly flip back to `true` after a shortened threshold. The 12-hour hard-logout path's *live* Timer-driven confirmation was inconclusive in this specific sandbox for the reasons above (App Nap before the fix; CGEventSource's headless-launch quirk potentially still masking the session check behind a spuriously-early idle firing even after the fix) - its correctness rests on the deterministic self-test (which explicitly proves session-expired takes priority over idle at the same tick) rather than a clean live 12-hour-equivalent run; a future task touching this area should re-attempt a live confirmation from a real, interactively-launched instance rather than assuming the sandbox's headless-launch behavior generalizes.
- **`fm/grandline-lock-and-rail-fixes` added `IconRailController.setUnlocked(_:)`** - the rail's own sailboat mark (`IconRailController`'s `mark`, now a stored property rather than a `loadView`-local `let`) switches to a heavier SF Symbol weight and gains a subtle continuous bob (the same `CAKeyframeAnimation`-on-`transform` recipe `LockScreenController.startAnimationsIfNeeded`'s boat bob uses, smaller-amplitude since this is a fixed 34x34pt rail icon, not a 72pt centerpiece) once the captain is past the lock screen; static/inert while locked. `AppShellController.showLock`/`hideLock` call `rail.setUnlocked(false)`/`setUnlocked(true)` respectively - a captain locking mid-bob always sees the mark go static immediately, not finish its cycle.
- **`fm/grandline-vault-bootstrap-fix` closed two gaps in the lock screen's `av`-availability messaging and fixed the impossible bootstrap instruction in `setup-guide.md`.** `setup-guide.md` no longer offers the Vault tab's "+ Add Secret" as a first-setup option for `GRANDLINE_APP_PASSWORD` - that tab lives inside the main UI, behind this same lock screen, so it's only reachable to rotate an already-set password, never to set the first one; the terminal `av save` command (or Automic Vault's own native app) is the only real first-bootstrap path. `VaultData.swift`'s `AppPasswordAvailability.avUnavailable` case (av not on PATH at all) is now wired up in `LockScreenController` with its own message plus a real "Install Automic Vault" button (`onInstallAutomicVault`, wired in `AppShellController` to `VaultSource.updateInstall()` - the same Homebrew-cask mechanism Updates/Vault already use for this catalog entry) - verified live via a temporary `FM_DEBUG_FORCE_APP_PASSWORD_STATE` override (reverted before commit) plus a real end-to-end install click against this machine's already-installed cask. A second, captain-flagged gap surfaced mid-task: `av list` can fail with "Automic Vault approval service is not running" when its LaunchAgent-backed menu-bar helper isn't up (confirmed live: `launchctl bootout gui/<uid>/com.automicvault.menubar-helper.plist` reproduces the exact error) - `checkAppPasswordConfigured()` previously folded this into `.avUnavailable`, wrongly implying no password is configured. It's now a distinct `.serviceNotRunning` case (matched via a `serviceNotRunningMarker` substring check on the combined stdout/stderr), with its own "starting it now" message and no false "no password configured" claim. `showLock` calls the new `VaultSource.ensureServiceRunning()` (`open -a "Automic Vault"`, fire-and-forget) before the first check, and `AppShellController.applyPasswordAvailability` retries every 1.5s indefinitely while `.serviceNotRunning` persists and the lock screen is still showing. **Live-verification finding**: launchd's on-demand socket activation means a plain "menu-bar app quit" (`osascript -e 'quit app "Automic Vault"'`, LaunchAgent still registered) is invisible to this whole mechanism - `av list` transparently respawns the agent itself, no error at all - so `.serviceNotRunning` in practice only fires for a genuinely deregistered/not-yet-installed LaunchAgent. Also confirmed live: after a real `bootout`, `open -a` on the plain `.app` bundle can spawn a non-launchd-supervised duplicate that leaves subsequent `av` calls hanging indefinitely rather than failing fast - recovered by killing that duplicate and re-registering via `launchctl kickstart -k gui/<uid>/com.automicvault.menubar-helper`. Not a code fix (this is `av`'s own launchd-activation behavior, out of this app's control), but worth knowing before trying to force this state again: use `bootout`, not a menu-bar quit, and prefer `kickstart -k` over `open -a` to restore it afterward if a test run goes sideways.
- **`fm/grandline-vault-wake-recheck-fix` closed the remaining gap: a captain-reported false "not installed"/"not configured" lock-screen message after waking a Mac that had been asleep for hours, despite `av` being genuinely installed and the password secret genuinely present.** Root cause, live-reproduced (not just inferred): `checkAppPasswordConfigured()`'s failure branch only special-cased the exact `serviceNotRunningMarker` text - *any other* non-zero-exit `av list` failure fell straight through to `.avUnavailable` ("Automic Vault isn't installed"), and a plain `av list` had no timeout at all, so a transiently unresponsive approval helper (confirmed live: `kill -STOP` on the `AutomicVaultMenubar` process makes `av list` hang indefinitely - still blocked after 90+s with zero output, no internal timeout of its own) blocked the check forever with no error text to even classify. Fixed with a new `AppPasswordAvailability.transientFailure` case covering both (1) the check timing out (`VaultSource.runWithTimeout`, a `DispatchSemaphore`+`terminationHandler` watchdog mirroring `FleetData.swift`'s `crewState` pattern, bounded to 5s and scoped only to this app-lock check - `loadSnapshot()`'s own `av list`/`doctor --json` calls for the full Vault page are unbounded exactly as before) and (2) any non-zero exit whose text doesn't match the known marker. `AppShellController` retries `.transientFailure` on the identical 1.5s cadence already used for `.serviceNotRunning` (factored into a shared `scheduleAppPasswordAvailabilityRetry` helper) rather than ever showing it as a hard, final state. Live-verified all four reachable classifications on this machine without touching the real secret: `.configured` (clean success), `.notConfigured` (a safe temporary probe checking a bogus, definitely-unsaved secret name against a real successful `av list`, never the real `GRANDLINE_APP_PASSWORD`), `.serviceNotRunning` (real `bootout`, unchanged), and `.transientFailure` (real `kill -STOP`/`kill -CONT` on the helper - confirmed the check now returns in exactly the 5s timeout bound instead of hanging forever, then correctly resolves back to `.configured` once resumed). `.avUnavailable`'s own guard (`resolveExecutable("av") == nil`) is untouched by this fix and wasn't re-verified live, since forcing it would mean moving/hiding the real root-owned `/usr/local/bin/av` on the shared dev machine - out of scope for a safe, reversible check.
- **`fm/grandline-vault-background-launch` fixed a captain-reported focus-stealing bug in the same `ensureServiceRunning()`**: plain `open -a "Automic Vault"` activates (brings to the front) whatever it targets regardless of that app's own `LSUIElement` setting - `LSUIElement` only suppresses a Dock icon/menu bar presence, it does not stop `open` from activating the process - so Automic Vault visibly came to the foreground on every Grand Line launch/relock, not just the "service wasn't running yet" case. Fixed by adding `-g` (do not bring the app to the foreground) to the same `open -a` call - no other change to `ensureServiceRunning()`'s call site, timing, or the `.serviceNotRunning`/`.avUnavailable` retry logic above. Verified live: quit Automic Vault entirely, ran `open -g -a "Automic Vault"` directly, confirmed its `AutomicVaultMenubar` process started and `av list` succeeded, while the frontmost app never changed away from the app already in focus.
- **`fm/grandline-vault-no-unnecessary-relaunch` found the `-g` fix above was incomplete: Automic Vault's real main window ("Detectors/Hardened Tools/Secrets") was still visibly popping up on nearly every Grand Line launch/relock.** Root cause, confirmed live: `/Applications/Automic Vault.app`'s executable (`AutomicVaultMenubar`) is kept alive independently by its own `RunAtLoad: true` LaunchAgent (`~/Library/LaunchAgents/com.automicvault.menubar-helper.plist`), so it is almost always already running by the time `ensureServiceRunning()` fires - and `open -a`/`open -g -a` on an app that's already running triggers macOS's standard reactivation/"reopen" handling regardless of `-g`, since `-g` only suppresses *foreground activation*, not the app's own window-restore behavior on reopen. The fix is `VaultSource.isServiceRunning()` (`pgrep -x AutomicVaultMenubar`) - `ensureServiceRunning()` now calls `open -g -a "Automic Vault"` only when the helper genuinely isn't already running; when it is, it does nothing. Verified live end to end: with the helper running, calling `ensureServiceRunning()` is a confirmed no-op (no `open` call at all); with the helper genuinely killed (`launchctl bootout` + killing any lingering process), `ensureServiceRunning()` still starts it and `checkAppPasswordConfigured()` recovers from `.serviceNotRunning` to `.configured` - the `fm/grandline-vault-bootstrap-fix` retry flow is unaffected. `isServiceRunning()` is `internal`, not `private`, so `VaultDataSelfTest` can assert it against this machine's real state.

- **The lock screen is the "Daylight Harbour" gate now, and it was the last pre-Daylight surface in the app (`fm/grandline-home-login-redesign-plan`).** A design proposal (`data/grandline-home-login-redesign-plan/report.md`, reviewed on a Lavish page) established with a one-line grep that this was the only full-window surface with **zero** design-system usage - `grep -c "isDaylight\|HelmCard\|HelmButton\|HelmType\|HelmMetrics"` returned 28 for `BootstrapController`, 7 for `HomeCanvasController`, 4 for `SetupContainerController` and **0** here - while being the first thing seen on every launch. It had been excluded on purpose twice in writing (`daylight-ui-design.md:57`'s must-NOT-change list, and `ui-report.md:109`'s "Lock screen is a deliberate scene - keep"); the captain chose Direction A, "keep the scene, rebuild it out of tokens". Presentation only - no store, auth, subprocess or state behaviour changed.
  - **Read this before assuming this screen has a Touch ID path: it does not, and never did.** `LAContext` in this codebase is used **only** for SSH key unlock (`KeychainKeyStore.swift:148-154`, `SSHKeyMaterializer.swift:32`). This screen collects a password and `AppShellController` verifies it by shelling out to Automic Vault - `av inject +GRANDLINE_APP_PASSWORD -- /bin/sh -c '[ "$GRANDLINE_APP_PASSWORD" = "$GRANDLINE_LOCK_CANDIDATE" ]'` (`VaultData.swift:312-321`), candidate passed by **environment variable** so it never reaches `ps`. That is why the screen has states a biometric gate would never have (`.serviceNotRunning`, `.transientFailure`, `.avUnavailable`). The design brief for this very task asserted the opposite and was corrected; a future brief may too.
  - **The one structural change, and it is the reason this screen is testable at all now: the sky gradient is a *sublayer* of a plain `wantsLayer` root, not `root.layer` itself.** It used to be the root layer, and that is precisely why the full UI audit recorded this screen as *"Not verifiable by off-screen capture ... Assessed from source only"* (`grandline-full-ui-audit/report.md:71, :473`) - `cacheDisplay` renders a view whose root layer is a `CAGradientLayer` as blank white. `LockScreenSelfTest.checkRenderProbeSeesTheScene` now samples a real rendered sky pixel (and asserts `root.layer !== skyLayer` directly, since a "tidy-up" reassigning it is a one-line regression). **Any full-window surface in this app that wants to be screenshot-verifiable must follow the same rule.**
  - **Every colour is theme-derived; the file has zero colour literals** (it had eleven `NSColor(calibratedRed:)` triples plus a whole second hand-tuned dark palette). Dark resolves through `DaylightTokens.dusk` like every other Daylight surface. **The 12 pre-Daylight palettes still have to work** (§2.8 keeps `allThemes` intact), so the scene builds from `HelmDomainHue` pairs - which fall back to that theme's own `HelmTint` slots off Daylight - blended over `theme.backgroundHex`. Verified by real render on `daylight`/`dusk`/`helm-dark`/`gruvbox-light`; Gruvbox Light comes out a warm sandy harbour with no blue leaking in.
  - **Hue by state, a captain decision:** the resting/locked states take **blue**, and `.noPasswordConfigured`/`.avUnavailable` take **amber** - Setup's own hue - so the gate borrows Setup's colour exactly when it is telling the captain to go do setup. `LockScreenController.ContentState.hue`/`.symbol` own that mapping. Title copy is **"Welcome back, Manjesh"** (not "Captain"), also the captain's own words.
  - **`HelmButton.domainHue` is set from `applyTheme`, never at construction** - setting it re-points a `.primary`'s fill on *all* thirteen themes, and the corrected fill is `DaylightPalette.primaryButtonFill`'s job, not a literal. Measured live and reproduced by the suite: white on the **raw** amber `h1` is **3.27:1**, the corrected `#A66910` is **4.52:1**. The suite asserts both halves, so the exception cannot quietly widen.
  - **One deliberate deviation from the approved mockup, recorded rather than silently dropped:** the mockup drew a `lock.fill` glyph inside the password well. It is not built. `HelmSecureTextField` owns its own chrome, and the only ways to get a glyph inside it were to fork a second secure-field component or hand-roll a well around a raw `NSSecureTextField` - which `checkNoRawTextInputs` bans and which would re-split the input taxonomy Phase 0 spent a whole phase unifying.
  - **The boat is positioned by Auto Layout with priorities, never by a fraction of the window's height** - that fraction was this file's first draft and a captain screenshot on a tall window caught it landing on top of the password field. It sails on the sea now: one **required** anti-overlap constraint (`boat.top >= card.bottom + s5`, relating two subviews only, so it can never cap the window - gotcha (13)) plus two waterline pins at priority **250/400**, both below `NSLayoutPriorityWindowSizeStayPut`. On a window too short for both, the boat rides up and the card stays intact.
  - **The sea is drawn with quadratic arcs, two layers deep, and that is not decoration.** The old wave was a straight-line zigzag; at the sea's real on-screen size it read as a row of triangles, which the near-black night palette hid and Daylight's pale one did not. `swellPath(width:height:crest:)` is the smooth, seamlessly-tiling replacement, with a paler swell behind drifting at a different rate.
  - **`FM_RUN_LOCK_SCREEN_TESTS=1`** is the suite (window-backed, so it joins `run-all-tests.sh`'s `NEEDS_SESSION` list). **All six injected regressions reproduced by name**, not merely passed: `root.layer = skyLayer` restored, the raw amber fill, a password form offered in `.serviceNotRunning`, the shadow host set to clip, the field-centring fix reverted, and a plain `NSTextFieldCell` on the secure field.
