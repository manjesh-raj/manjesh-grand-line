## Dictation

**`.dictation` (`fm/grandline-dictation-mvp`, phase 1 of a captain-approved Lavish plan) is a rail destination pinned directly above `.docs` and below `.vault`** (so the bottom-anchored utility group reads Tools, Vault, Dictation, Docs, Setup, avatar) - a first-party, in-process dictation pipeline. A third-party "OpenSuperWhisper" integration was explicitly rejected as impractical during plan discussion (different build system, a Rust-based engine incompatible with this app's plain-`swift build`-only, no-Xcode convention) - see `native/README.md`. Phase 1 is deliberately minimal: real permission status, the fixed hold-to-record shortcut, and the actual capture/transcribe/paste pipeline - no history, no personal vocabulary, no shortcut recorder, no cleanup pass (all explicitly phase 2/3, not built at the time).

- **Engine**: 100% Apple frameworks, no vendored engine (`DictationEngine.swift`). `AVAudioEngine` captures microphone audio into an `SFSpeechAudioBufferRecognitionRequest` while the hotkey is held; `SFSpeechRecognizer` transcribes it, requesting `requiresOnDeviceRecognition = true` whenever `recognizer.supportsOnDeviceRecognition` is true for the current locale/OS (falling back to Apple's server-backed recognition otherwise - not every locale/OS combination supports on-device). `DictationPermissions` is the one source of truth for all three permission reads (`AVCaptureDevice.authorizationStatus(for: .audio)`, `SFSpeechRecognizer.authorizationStatus()`, `AXIsProcessTrusted()`) and the three real system-prompt request calls - both `DictationController`'s manual "Request access" buttons and `DictationEngine.startRecording()`'s own inline auto-request (see below) go through it, never a second permission-reading path.
- **Hotkey mechanism reuses Shift's own global-hotkey pattern, not a second one.** `DictationHotkey.swift` is built on the identical local+global `NSEvent` monitor / `AXIsProcessTrusted` shape `ShiftGlobalHotkey` (`ShiftQuickCapture.swift`, phase 5) already established for ⌥Space - see that file's header for the full local-vs-global-monitor/Accessibility-trust reasoning, which applies here unchanged. The one real difference: Right ⌥ Option is a modifier key, so it fires `.flagsChanged` events (keycode 61, `kVK_RightOption` - Left Option, keycode 58, is deliberately never matched), not `.keyDown`/`.keyUp`; `DictationHotkey.handle(_:)` tracks held/released transitions itself rather than relying on distinct down/up event types. Both hotkeys' monitors coexist independently - confirmed live (a real launched app with both features active; also structurally true since each installs its own independent `NSEvent` monitor pair). There is one shared Accessibility trust grant for the whole app (one "Grand Line" entry in System Settings) - Shift's launch-time `requestPermissionIfNeeded()` and Dictation's page-driven one both call the same `AXIsProcessTrustedWithOptions` API and don't conflict.
- **Permission requests fire "the first time genuinely needed," per the task brief - not eagerly at launch (unlike Shift's own eager Accessibility request).** Microphone/Speech Recognition: `DictationEngine.startRecording()` (called from the hotkey's onDown) checks `DictationPermissions` itself and, if a permission is `.notDetermined`, calls the real `AVCaptureDevice.requestAccess`/`SFSpeechRecognizer.requestAuthorization` inline before actually opening the microphone - this is the real "hold Right ⌥ Option" usage flow, not just the Dictation page's manual buttons. A `wantsToRecord` flag guards against the key being released before the async system dialog resolves (a very likely shape for a captain's first-ever tap) - if the key comes up before permission resolves, recording never starts even if the grant lands moments later. Accessibility: requested only from the Dictation page's own "Request Accessibility Access" button (`DictationPermissions.requestAccessibility()`), since there's no natural "just tried to use it" moment to hook for a modifier-key hold that literally cannot fire without that trust already granted.
- **Paste mechanism: `NSPasteboard` + a synthetic Cmd+V (`CGEvent`), not the Accessibility `AXUIElement` text-insertion API.** `AXUIElement` insertion (e.g. `kAXSelectedTextAttribute`) only works against apps exposing a conforming Accessibility text role for their focused element - which excludes most terminal emulators, including this app's own SwiftTerm-based Console tabs, and many Electron/web-based editors. A synthetic Cmd+V lands anywhere a real paste keystroke would, a strictly larger and more predictable target set, for the same Accessibility-trust cost. `DictationEngine.pasteAtCursor` always writes the pasteboard (useful even without trust - a captain can paste manually) and only posts the synthetic keystroke once `AXIsProcessTrusted()` is true.
- **The Dictation page (`DictationController.swift`) is deliberately sparse**: a Status card (icon/title/detail driven by `DictationStatus`, plus a "Request access" button for whichever permission is missing) and a Shortcut card (states the fixed Right ⌥ Option combo and that a shortcut recorder is coming later), following `VaultController`/`ShiftPanelView`'s existing card layout rather than inventing new chrome. Status refreshes on every `viewWillAppear` (no polling, per PRODUCT.md's "quiet until it matters") and live via `DictationEngine.onStatusChanged` → `AppShellController.setDictationEngineStatus` → `DictationController.setEngineStatus` while the page happens to be visible, so a captain watching this page while dictating sees "Recording…"/"Transcribing…" for real.

- **`fm/grandline-dictation-transcribe-hang-fix` fixed a real captain-reported bug in the core pipeline above: a hold-and-speak often showed "Recording…" then "Transcribing…" for a long time, then silently reverted to "Ready" with the transcript never pasted - no error, no feedback.** This machine turned out to have a real audio input device and a real interactive login session (contrary to the "not verified in this sandbox" note directly above, which was written from a different, non-interactive sandbox), so this was reproduced live rather than patched blind - a standalone harness mirroring `beginCapture` exactly, feeding it real mic audio via a real `AVAudioEngine` tap while `say` produced real speech through the speakers. **Root cause, confirmed live - a delayed empty result, not a true hang**: with `shouldReportPartialResults = false` (the original setting) and on-device recognition, holding the hotkey through a few seconds of trailing silence after speech ends (an entirely ordinary usage pattern - not releasing the instant the last word finishes) reliably (3/3 live runs) produces a **non-final** result carrying the correct, complete transcript, followed several seconds later by a **final** result (`result.isFinal == true`) whose `bestTranscription.formattedString` is an **empty string** - a real `SFSpeechRecognizer` quirk. Since `shouldReportPartialResults = false` meant the non-final result's real text was never looked at, and `finish(text:)`'s "only paste on final, only if non-empty" guard discarded the empty final text, the outcome matched the report exactly: no paste, no error, `finish` calling `onStatusChanged?(DictationPermissions.currentStatus())`, which resolves straight back to `.ready`. A quick-release-right-after-speaking case (no trailing silence) was unaffected by this quirk and always worked, which is presumably why phase 1's own original live verification pass didn't catch it. **Fix (`DictationEngine.swift`)**: `shouldReportPartialResults` is now `true`, and every result (partial or final) with non-empty text updates a new `bestTranscriptSeen`; `finish(text:)` falls back to it whenever the result it was actually called with is empty or nil (covering the empty-final-result quirk above, and a genuine recognition error trailing a good partial). `stopRecording()` also schedules an 8s bounded timeout (`finishTimeoutWorkItem`) after `endAudio()` that calls `finish(text: nil)` if no final result has landed by then, so a final result that genuinely never arrives can no longer wait forever - it finalizes with whatever was heard, or nothing. A new `DictationStatus.didNotCatchThat` case ("Didn't catch that - try again") is what `finish` shows on genuine silence/no usable transcript, replacing what used to be an indistinguishable silent revert to `.ready`. **Verified live end to end** (same real hardware/session as the repro): a real hold → real `say`-produced speech → real trailing silence → real release round trip pasted the correct transcript into a real, frontmost TextEdit document (confirmed by reading the document's real text afterward, not just the pasteboard) in every run; a silence-only hold → release showed the new "Didn't catch that" status with no paste and no crash; the quick-release-right-after-speaking case (already working) was unaffected. `DictationHotkeySelfTest` was re-run post-fix with no regression - the hotkey mechanism, permission-request flow, and `pasteAtCursor` itself were untouched, per this fix's own scope.

- **`fm/grandline-dictation-stuck-transcribing-fix` fixed a real, live-reproduced bug: the status page could get stuck on "Transcribing…" forever, with no error and no revert - captain-reported with the shortcut set to Right ⌘ Command, but the root cause turned out to be keycode-independent, not a Command-specific interaction at all.** Reproduced live with real HID-level `CGEventPost` events on this machine (whose `SFSpeechRecognizer` fails fast with `kLSRErrorDomain` "Siri and Dictation are disabled" - a system-level setting, same constraint the phase-2 verification bullet above already documents) and confirmed to reproduce identically with the default Right ⌥ Option, proving the race has nothing to do with which key is held. **Root cause**: recognition can complete (a real final result, or - as reproduced here - a fast error) *before* the hotkey is ever released. `finish(text:)` used to never reset `isRecording`, so the *later* `stopRecording()` call (on release) still passed its own `guard isRecording`, overwrote `finish(text:)`'s already-correct final status back to `.transcribing`, and scheduled a second `finishTimeoutWorkItem` - whose eventual `finish(text:)` call then hit the existing `guard !isFinishing` and silently returned, never updating the status again. Stuck on "Transcribing…" forever. **Fix (`DictationEngine.swift`)**: `finish(text:)` now tears down audio capture (`isRecording = false`, remove tap, stop the engine) itself the moment recognition actually ends, whenever `isRecording` is still `true` at that point - so a `stopRecording()` call arriving later on release correctly no-ops via its own existing `guard isRecording` instead of stomping the already-finalized status. The normal case (hotkey released before recognition completes) is unchanged, since `isRecording` is already `false` by the time `finish(text:)` runs in that order. **Defense-in-depth, per the task brief's explicit ask**: every `onStatusChanged` call now goes through a new `report(_:)` helper that also arms a `hardCeilingWorkItem` (`finishTimeout + 5` = 13s) whenever `.transcribing` is reported - an absolute wall-clock watchdog that forces the displayed status to `.didNotCatchThat` if still showing `.transcribing` by then, deliberately bypassing `isFinishing`/`isRecording` entirely so "stuck forever" stays impossible even against a future bug this fix didn't anticipate, not just the specific race found here. Verified live (temporary env-gated logging in `DictationEngine.swift`/`DictationHotkey.swift`, plus a temporary `main.swift` hook to force the hotkey's shortcut in-process without ever touching the real, shared `AppSettings.dictationShortcut` UserDefaults key - both reverted before commit, per this file's "Verifying native UI bugs" convention): the exact stuck state reproduced pre-fix with Right ⌘ Command, resolved correctly post-fix for both Right ⌘ Command and Right ⌥ Option (no regression), and all three existing Dictation self-tests (`DictationHotkeySelfTest`/`DictationDataSelfTest`/`DictationCleanupSelfTest`) still pass.
- **`fm/grandline-dictation-visual-feedback-hud` added a floating on-screen HUD (`DictationHUD.swift`) since Dictation previously gave zero visual feedback anywhere except its own rail page - useless for a feature whose whole point is dictating into whatever app currently has focus, never Grand Line's own window.** `DictationHUDController` is a small, additive second subscriber to the exact same `DictationEngine.onStatusChanged` callback the Dictation page's status card already used (`main.swift` now fans that one callback out to both `AppShellController.setDictationEngineStatus` and `dictationHUD.handle(status)`) - no second status-broadcast mechanism was invented. The HUD itself is a borderless `NSPanel` (`[.borderless, .nonactivatingPanel]`, `level = .floating`, `ignoresMouseEvents = true`, shown via `orderFrontRegardless()` - never `makeKeyAndOrderFront`) so it can appear above whatever app the captain is dictating into without ever taking key-window status or activating Grand Line - confirmed live (see below).   **What was wrong in the code, as opposed to on the machine.**
  Two things, and the second is the one that had kept the captain stuck through two rounds.
  First, the gate asked the wrong question: `pasteAtCursor` guarded on `AXIsProcessTrusted()`, which answers "may this process drive other apps through the Accessibility *API*", while the operation underneath it is `CGEvent.post` - governed by post-event access, which CoreGraphics exposes as its own `CGPreflightPostEventAccess()`.
  Second, and independently real: when that gate read false the app *did nothing about it*.
  It logged, it set `.copiedOnly`, and it told the captain to go remove and re-add the row in System Settings by hand.
  The captain did that, twice, and the app still only copied - so "tell the human to repair TCC" had already been shown not to work before this task started.

  **The fix.**
  `DictationEngine.pasteGateIsOpen(postEventAccess:axTrusted:)` is the rule, `postEventAccess || axTrusted` - strictly more permissive than the old gate, so it can only ever add a paste attempt that used to be refused and can never suppress one that used to happen.
  `requestPostEventAccessIfNotYetAsked()` is the recovery: on a closed gate it calls `CGRequestPostEventAccess()` once per launch, which presents the system's own post-event-access prompt and registers the *currently running* binary's signature with `tccd` rather than relying on whichever older signature the existing Settings row was recorded against.
  That is the supported in-app version of the hand repair the previous round had to delegate to the captain.
  Three details that shaped it: the prompt is asynchronous from the caller's point of view, so the dictation that raises it is still copy-only and the function says `false` rather than pretending otherwise (`.copiedOnly`'s detail copy now says the next one will paste); `pasteAtCursor` can run off the main thread, because `SFSpeechRecognizer`'s `recognitionTask` callback carries no queue guarantee, so the OS call is hopped to main while the once-per-launch decision stays synchronous and therefore assertable; and the latch is read and written under an `NSLock` (GL-28).
  `pasteAtCursor` is shared with `SnippetExpander`, so system-wide snippet expansion gets the same gate and the same recovery.

  **Verified.**
  Two new cases in `DictationEngineSelfTest`, both confirmed to catch a real regression rather than merely to pass.
  `pasteGateOpensOnPostEventAccessAloneNotJustAXTrust` asserts the pure rule over all four inputs (its first check is the discriminating-power one - the gate must still refuse when neither permission is present); reverting `pasteGateIsOpen` to `axTrusted` alone fails it by name on the `postEventAccess: true, axTrusted: false` check, which is the captain's exact bug.
  `anUntrustedSuiteNeverRaisesARealTCCPrompt` proves a suite can never put a real system dialog in front of the captain: deleting `requestPostEventAccessIfNotYetAsked()`'s `accessibilityTrustOverrideForTests != nil` early return makes the request counter read 1 and fails it.
  Writing that second case surfaced a trap worth recording: the once-per-launch latch is process-global, so the *first* case to reach a closed gate consumes it and every later case then short-circuits for the wrong reason - the injection passed until `debugResetPostEventAccessRequestStateForTests()` existed and the case called it.
  An order-dependent self-test that passes for the wrong reason is exactly the "a check that cannot fail" shape `AGENTS.md` warns about.
