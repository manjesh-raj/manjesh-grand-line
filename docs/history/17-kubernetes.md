## Kubernetes context/namespace safety badge

`fm/grandline-k8s-context-badge` built item 1 of the `grandline-k8s-toolkit-scout` recommendation (`data/grandline-k8s-toolkit-scout/report.md`) - a toolbar pill on a dedicated host page naming the current `kubectl` context/namespace, since a bastion's own shell prompt can never show this (kube-ps1, the tool this replaces, is a shell function that can't be installed on the bastion).

- **`KubeContextBridge.swift` is a NEW, lightweight sibling of `SRELeadBridge`, not a reuse of it - read that file's own header before touching either.** `SRELeadBridge` exists to bridge a genuine cross-process gap (`sre_kubectl_mcp.py`, a Python subprocess, has no shared memory with this Swift app), so it's a file-based request/response protocol. This badge has no AI reasoning step and always runs the same two fixed, hardcoded commands (`kubectl config current-context` / `kubectl config get-contexts`, combined into one injection with a separator marker) - the caller and the consumer of the result are the same Swift process, so there's nothing for a file-based protocol to bridge. It reuses `SRELeadBridge.swift`'s exact `SRELeadBridgeTerminal` protocol (`TabModel` already conforms) and the identical marker-wrap-and-search mechanism, just driven directly with a completion closure. `KubeContextParser` is the pure parsing half (context/namespace from the combined output, plus the `looksLikeProduction` heuristic - a documented, deliberately simple case-insensitive `"prod"` substring match that also flags e.g. `"preprod-eks"` on purpose, erring toward caution).
- **Per-tab activation (`fm/grandline-k8s-badge-fixes`, issue 3 - superseding this bullet's original per-host design).** `Host.kubeContextBadgeOptIn` (field/init-param/CodingKeys/custom-decode-fallback in `Host.swift`, a `HelmToggleRow` in `HostEditorController.swift`, threaded down through `AppShellController.connectHost` -> `ConsoleController.connectSSHIfNeeded`/`openSSH`/`addTab`) is now **availability only** - whether a tab from that host even offers the toolbar toggle at all. It no longer creates or starts a `KubeContextBridge` by itself. The captain's real setup - one saved bastion whose tabs sometimes reach a `kubectl`-capable box further in and sometimes don't (a plain entry hop, a second tab reached via a startup snippet) - has no way to be told apart just from how a tab was opened, so the original per-host auto-start put a bridge on a plain entry-hop tab too, and that tab's `kubectl` could never succeed - the actual cause of the spam issue 1 fixed. Activation is now an explicit per-tab click on the toolbar toggle (`ConsoleController.activateKubeContextBadge(for:)`/`deactivateKubeContextBadge(for:)`, wired to `toggleKubeContextBadge`), mirroring `TabModel.sreLead`/`SRELeadTabState`'s own precedent exactly - `TabModel.kubeContextBadgeStatus` (`KubeContextBadgeStatus.swift`, mirroring `SRELeadPhase.swift`) is the per-tab display state (`.notStarted`/`.checking`/`.active(info)`/`.unavailable(message)`), and `kubeContextButton` (a real `HelmButton`, not a static pill) is the toggle - never activated automatically by `addTab`, never inherited by a duplicated tab. Still **no** `BlockViewFeature.isEnabled`-style global kill switch - it has none of Block View's fraught two-app-crashing-regression rollout history, and per-tab activation alone is judged sufficient gating.
- **Cross-bridge collision guard, in both directions.** SRE Lead's own bridge and this one can both target the same tab (a captain can start SRE Lead on the very tab whose host also opted into the badge), and two independently-injected marker-wrapped commands overlapping on one real shared shell genuinely interleave keystrokes, corrupting both. `SRELeadBridge` gained `isBusy: Bool` and an `isTerminalBusyElsewhere: (() -> Bool)?` closure (checked in `beginProcessing`, defaulting to `nil` = "no sibling to worry about," so every pre-existing caller/test is unaffected); `KubeContextBridge` carries the identical pair. `ConsoleController` wires each bridge's closure to read the *other* bridge's own `isBusy` at the two construction sites (`activateKubeContextBadge(for:)`; `startSRELead(for:)`), so neither bridge needs to know the other's concrete type.
- **Refresh cadence and backoff (`fm/grandline-k8s-badge-fixes`, issue 1 - superseding this bullet's original "retries forever" design)**: `refreshInterval` 5 minutes while genuinely succeeding (raised from an original 30s - a captain-flagged "every few minutes, not every 30s" bar), `busyRetryInterval` 5s for a transient refusal (captain typing, a sibling bridge mid-command, a refresh already in flight - never counts toward give-up), `failureRetryInterval` 10s for a **genuine** command failure (`kubectl` not on PATH, no current context set). After `maxConsecutiveFailures` (3) genuine failures in a row, `KubeContextBridge.hasStoppedRetrying` flips true, the poll timer is invalidated outright, and the toolbar shows a distinct "Context Unavailable" state - no more automatic retry until the captain clicks it again, which calls `bridge.start()` (the one entry point for both first activation and an explicit "try again," resetting the failure count). All four intervals/the cap are instance-overridable for tests. A refresh **failure below the give-up threshold never clears an already-known-good badge** (`TabModel.kubeContextBadgeStatus` stays `.active(info)`) - a transient refusal just means the badge might be a little stale until the next attempt, never a blank badge; once given up, the status deliberately switches to `.unavailable` rather than silently keeping stale info forever.
- **Short label extraction (`fm/grandline-k8s-badge-fixes`, issue 2)**: the toolbar toggle's own visible text is `KubeContextInfo.shortLabel` (-> `KubeContextParser.shortLabel(for:)`), not the raw `kubectl config current-context` output - a real AWS EKS context is a whole ARN (`arn:aws:eks:us-east-1:682528822458:cluster/raas-prod`), unreadable at a glance. Only the one well-known `arn:...cluster/<name>` shape is shortened (to `<name>`); anything else (a friendly name, an ARN with no `cluster/` segment) passes through byte-for-byte unchanged rather than being guessed at. The full, never-shortened context name is always still shown in the toggle's tooltip. Issue 4 (the "gray for UAT" coloring - a case-insensitive substring match on `"prod"`) was confirmed correct and left unchanged; the tooltip now states the non-matching case explicitly too ("No 'prod' pattern matched").
- **`KubeContextBridgeSelfTest.swift`'s `perTab_*` cases are the concrete proof for issue 3**, driving a real `ConsoleController`/`TabModel` (mirroring `SRELeadPerTabSelfTest.swift`'s own convention - real `.ssh` tabs against unreachable `127.0.0.1`, no real kubectl needed) rather than reasoning about it: activating the toggle while one tab is `currentTab` never constructs a `KubeContextBridge` object for a sibling tab, a closed tab's activated badge never disturbs a sibling's, and a duplicated tab never inherits its source's already-active bridge. All three of this task's fixes (backoff/give-up, short-label parsing, per-tab isolation) were confirmed live to catch a real injected regression by name, not just to pass - reverting the give-up branch left two backoff cases failing, and reinstating the old per-host auto-activation in `addTab` left two `perTab_*` cases failing.
- **The Python side (`sre_kubectl_mcp.py`) widened `_ALLOWED_VERBS` to include `config`, but only its two read-only subcommands** (`_CONFIG_READONLY_SUBCOMMANDS = {"get-contexts", "current-context"}`, checked via a dedicated branch in `_validate_args` *before* the generic character-set/smuggled-verb checks even run) - `config`'s real write forms (`use-context`, `set-context`, `delete-context`, `rename-context`, `set`, `unset`, ...) are refused explicitly, since none of them are stopped by the generic checks (a hyphenated word like `"use-context"` is plain, safe-looking text with no shell metacharacters and no "apply"/"delete"-style substring). **This badge never calls into that script/MCP tool/`claude` at all** - the widening exists so the identical read-only-enforcement single-source-of-truth (`_validate_args`) stays correct in case SRE Lead's own AI is ever asked about the current context/namespace too. `test_sre_kubectl_mcp.py`'s `ConfigSubcommandTests` is the permanent proof every write form still fails while both read-only forms (and only those, with no extra arguments) pass.
- **A real, worth-remembering SwiftTerm finding from this task's own live end-to-end verification**: `SRELeadBridge`'s (and now `KubeContextBridge`'s) `searchFromLine`-based "did new content arrive" check (`allLines.count > searchFromLine`) only detects growth once the terminal's buffer has already started **scrolling past the visible viewport** - `Terminal.getBufferAsData()`'s line count stays pinned at "just enough to fill the screen" for as long as everything still fits on one screen, since new content overwrites in place rather than appending to a growing list until something actually needs to scroll off the top. A verification session that never exceeds the terminal's own row count will never see the count grow, no matter how much real command output has actually printed - this is not a bug in either bridge, just a precondition ("the session has more prior content than fits on one screen," true of any real bastion session almost immediately) worth knowing before chasing a similar "the bridge never sees my command complete" symptom in a short-lived test session.
- **Live end-to-end verification**: no real Kubernetes host is available in this environment, so this was verified against a real `ConsoleController` + a real local `zsh` PTY child process + a faked `kubectl` shell script standing in for a real cluster (`kubectl config current-context` -> `preprod-eks`, `kubectl config get-contexts` -> a two-row table) - the real, unmodified `KubeContextBridge` correctly injected the combined command, detected completion, extracted the exact output, and parsed it into `KubeContextInfo(contextName: "preprod-eks", namespace: "raas-uat")` with `looksLikeProduction == true`. The probe padded the session with ~80 lines of prior output first, per the scrolling finding above - without that padding the same real mechanism never saw the buffer grow and the check never completed. Probe code was reverted before commit, per this file's "Verifying native UI bugs without a real screenshot" convention.

## Kubernetes cluster browser + multi-pod Log Tail (`.kubernetes`)

**`fm/grandline-k8s-cluster-tail` built items 1 and 5 of the `grandline-k8s-toolkit-scout` recommendation together, as one standalone destination** - the multi-pod Log Tail (stern-equivalent) and the read-only Cluster browser (k9s-equivalent). Read `data/grandline-k8s-toolkit-scout/report.md`'s "second dimension" section and its interactive mockup's stern/k9s/★-Shape sections before extending any of it (the report lives in firstmate's own `data/`, not this repo's).

- **The shape was decided by the report, not by this task: Shape C, the hybrid.** Its own analysis is that promoting the Cluster browser tips the recommendation - "k9s's real-world value proposition is one dedicated screen for cluster state, not a toggle on my terminal" - so one standalone `.kubernetes` destination owns the two big screens, the host page keeps the ambient context badge (an anchor has to live in the chrome of the terminal being typed into, and no standalone page can replace that), and the host toolbar's "Tail Logs" becomes a **pre-scoped deep link** into this page (`AppShellController.openKubernetes(hostID:showTail:)`, the same idiom Overview's ready-to-merge tile uses to reach Review). Both entry points, one implementation.
- **Standalone-but-host-scoped, and the report is blunt that claiming otherwise would be dishonest.** The bridge types into one specific host's already-authenticated session, and that session is the only cluster credential that exists anywhere (five prior attempts, PRs #70-73, proved a second automated connection can never complete the password-gated hop - `sre_kubectl_mcp.py`'s own header says "do not resurrect a second-connection approach"). So the page opens on a **scope strip** built from `HostSessionRegistry` - this app's one answer to "which hosts are live" - and shows an honest wall plus an "Open Hosts" action when nothing is live, never an empty table that reads as an empty cluster.
- **`KubeBridge.swift` is the one piece of plumbing both features consume, and its one genuinely new idea versus its two siblings is a serialized request queue.** `SRELeadBridge` bridges a real cross-process gap (a Python MCP subprocess writing request files), so it is a file-based protocol; `KubeContextBridge` always sends two fixed hardcoded commands and needs no request concept at all. This sits between them: same Swift process on both ends, but a *varying* command per request. Both siblings handle a second request by **refusing** it - fine when there is only ever one, useless when a Cluster refresh is inherently three commands and a tail poll is one per selected pod. `enqueue`/`enqueueBatch` accept work and issue it **one at a time**; the hard constraint (at most one command in the tab, ever) is unchanged, only the caller-facing shape differs. A queued request past `queueDeadline` is failed `.busy` rather than waiting behind contention forever - without that, a captain typing for a minute builds a backlog of stale polls that all fire at once when they stop.
- **Backoff and give-up were inherited deliberately, not rediscovered.** `fm/grandline-k8s-badge-fixes` had to add exactly this to the context badge after the captain's first real use (a plain entry-hop bastion with no `kubectl` on PATH got the identical failing command every 5s forever), and the task brief for this one said in as many words not to re-learn it. So: `maxConsecutiveFailures` **genuine** failures in a row (never a `.busy`/`.discarded` refusal, which costs nothing and says nothing about whether `kubectl` works) trips `hasStoppedRetrying`, every queued request is failed rather than left dangling, the timer stops, and only the captain's own `resume()` gets back in. Proven by `KubeBridgeSelfTest`/`KubernetesDestinationSelfTest`, both confirmed to catch the regression rather than merely to pass.
- **No allowlist was widened - unlike the context-badge task, this one needed nothing from `sre_kubectl_mcp.py`.** All five verbs either feature uses (`get`, `describe`, `top`, `events`, `logs`) were already in `_ALLOWED_VERBS`. `KubeCommand` is a **closed enum** of read-only forms, which is the structural reason nothing can smuggle a mutating verb through (the same reasoning `ScheduledActionKind` uses for F11); any token that reaches a real shell as a bare word (namespace, pod name) goes through `KubeCommand.isSafeToken` first and an unsafe one refuses to build the command at all rather than falling back to some "safe" default. **There is no exec/edit/delete/scale here and there must never be one, even as a convenience** - a mutating action belongs in the Command Library behind its own risk gate. `KubernetesDestinationSelfTest.noMutatingCommandIsEverInjected` asserts that against everything the page typed across a full exercise, not by reading the enum.
- **The scout report calls the parsing "the real engineering" and leaves the `-o json` vs. human-columns call to the build. The call is human columns, and `KubeResources.swift`'s header states why**: every byte arrives through a *terminal buffer* that hard-wraps at the tab's column count, so one 40KB JSON document becomes hundreds of wrapped rows where any elided row corrupts the whole document rather than one row of it, while a wrapped table degrades to one missing pod; and `-o json` is ~two orders of magnitude more text echoed **visibly into the captain's own bastion session**. Two mechanics worth not re-deriving: kubectl renders every table through a `tabwriter` with padding 3, so **splitting on runs of 2+ spaces is safe** where offset-slicing at the header's own columns breaks the moment a value overflows its column; and `KubeTable` reads values by **column name**, so a kubectl that adds a column is handled and one that renames a column degrades to "that field is missing" rather than to a mis-assigned value. A trailing free-text column (events' `MESSAGE`) needs `lastColumnIsFreeText`, and the self-test's fixture carries a **doubled space** inside that message specifically so the parameter is load-bearing - without one, the case passes with the parameter removed (found by injecting that exact regression).
- **`KubeTable` scans for its header rather than assuming line 0**: kubectl writes deprecation warnings to stderr, which lands interleaved in the same terminal buffer ahead of the table, and requiring line 0 would turn a good table into a failure.
- **GL-14's rule holds throughout**: `KubeResourceParser.Outcome` is `.rows`/`.empty`/`.failed`, so "no pods in this namespace" and "kubectl failed" never render the same. A failing `kubectl top pods` (a cluster with no metrics-server - a normal configuration) degrades to "no cpu/mem columns" and swaps in NODE, never to a failed pod list.
- **Log Tail specifics.** 5s poll (the report's own reasoned range is 5-10s; 5 is chosen because the report calls this a triage tool, and the cost lands in the *dedicated feed tab* rather than anywhere the captain is typing). The `--since` window is deliberately **wider** than the poll interval (`overlapFactor` 3): sampling exactly one interval every interval loses every line landing in the gap between one command finishing and the next starting, and the bridge's own queueing makes that gap variable. That guarantees duplicates, which is what `KubeLogMerger`'s dedupe exists for - losing lines silently is the worse failure. `maxSelectedPods` (6) is a real cap with a stated reason, refused visibly rather than ignored: each pod costs its own serialized command per cycle. `-f` is never used and cannot be: a long-lived follow never terminates, so its end marker never prints and the single-flight bridge would be wedged for the session. The UI says all of this (`KubeLogTailSession.limitsNote`) rather than implying live streaming.
- **Per-pod colour is a `HelmTint`, never a fixed hex palette, and that is the `SSHKeyType.accentHex` lesson applied.** The obvious reach is `HostCatalog.accents`' eight literals - which AGENTS.md already records were picked against `helm-dark` and measurably washed out on Gruvbox Light once they landed on a real accent bar, which is why that type carries a `HelmTint` now. A log line's colour is *text on a surface*, the most contrast-sensitive use there is. `.critical` is excluded (it is what an **error line** is drawn in, so a pod permanently coloured error-red would make all its lines read as failures) and `.neutral` is excluded (it *is* the ink). Assignment is by **first appearance**, never by hash and never re-sorted - a colour that moved when an unrelated pod appeared would break the mental map the captain builds within seconds - and survives `clear()`, since emptying the window does not change their selection.
- **The feed tab is explicit and visible, never a silent background tab.** A host with exactly one tab is auto-adopted (no ambiguity); with several, the page waits for a pick rather than commandeering the captain's working tab - which is the whole reason it has a visible picker plus a "Duplicate a tab for the feed" button. `ConsoleController.duplicateTabForKubeFeed()` re-runs the same launch spec, so the jump-box hop replays automatically and only the password-gated hop is left by hand, and it deliberately does **not** select the new tab.
- **Every list is a demand-driven `NSTableView` from the first draft.** This codebase has hit the `NSStackView`-of-many-rows pathology four times in production (Diff ~13.6s at ~340 rows, Block View ~102s at 400, Review's "stuck forever on Loading", the Tools resize handler). The Cluster browser is the app's **only** multi-column table with a real `headerView` - every other one is single-column with `headerView = nil` - because reading columns against each other is the whole point of a k9s-equivalent. Column widths are fractions re-derived from the **clip** view's width (gotcha (4)), and columns are rebuilt only when they genuinely change so a 30s refresh never discards the captain's own column resizing.
- **Both poll loops stop when the page is not on screen** (`viewDidDisappear`), because every poll types a *visible* command into the captain's own bastion session - GL-13's rule applied to a much louder kind of background work. The Cluster sweep also fetches only the table actually showing (Pods always, since the Log Tail's picker is fed from it too), which is the mockup's own "each costs one more get, run only when that tab is opened".
- **The controller is three files** (`KubernetesController.swift` + `+Behaviour` + `+Render`) for the same reason `ConsoleController` is six (GL-36), and with the same Swift consequence that split already records: `private` is file-scoped, so every member reached across those boundaries is `internal`. **Treat the whole `KubernetesController*.swift` family as private to itself.**
- **Two suites.** `FM_RUN_KUBE_BRIDGE_TESTS` is pure logic against `FakeBridgeTerminal` and literal kubectl output - it runs in CI. `FM_RUN_KUBERNETES_DESTINATION_TESTS` mounts the real page in a real window and drives its real handlers, so it is in `run-all-tests.sh`'s `NEEDS_SESSION` list. **Eight injected regressions were each confirmed to reproduce by name**, not merely to pass: the give-up branch removed, `isSafeToken` widened to accept anything, `startedAt` stamped after injection instead of before (a real production bug this found - a keystroke landing *during* `sendCommand` was invisible to the discard guard), `lastColumnIsFreeText` dropped from events, a feed tab auto-adopted while several were open, every table fetched speculatively, the pods table's health tint dropped on the way into the row, and the give-up state's own retry button hidden (which would make giving up a dead end rather than a pause).
- **A self-test lesson worth not repeating: a model-level assertion is not a rendering assertion.** The health-tint regression above passed every check until the suite started reading `KubeResourceTableView.debugRows` - the *rows the table was actually handed* - rather than only the parsed `[KubePod]`. A signal that never reaches the table is invisible to a model-level check.
- **Not verified against a real cluster, and cannot be from this environment.** No bastion is reachable here and the credential is a password-gated hop by policy. Every fixture is real `kubectl` output text taken verbatim from the scout report's own captures, driven through the real bridge/parser/render path; what is unproven is only that a real bastion's kubectl prints those exact shapes. A live end-to-end pass (duplicate a tab, log in through hop 2, watch a real sweep and a real tail) is the captain's own check.
- **`fm/grandline-k8s-feed-tab-stall-fix` fixed a real, live-reported bug: a request queued behind feed-tab contention (the captain typing in the feed tab, or a sibling bridge holding it) rendered as an indistinguishable generic "Refreshing…" spinner, with zero indication of why nothing was happening.** The captain's real repro was checking on the feed tab by typing a manual login (`su -l ...`, `k8 get po`) directly into it - which is exactly the activity that keeps `KubeBridge.pump()`'s `userActivityQuietWindow` check (line ~448) true for as long as they kept typing, and the request just sat queued with no signal to the UI at all (`pump()`'s two contention `return`s never called `onStateChanged?()`). Fixed with `KubeBridgePendingReason` (`.waitingForQuietTab` / `.busyElsewhere`), a new `KubeBridge.pendingReason`/`pendingSince` pair set only from `pump()` (via a `setPendingReason` helper that only fires `onStateChanged?()` on an actual change, so being blocked on the same reason tick after tick at the 0.25s poll cadence doesn't become a 4Hz UI repaint), consulted by a new `KubernetesController.pendingWaitText()` in both `renderClusterStatus(running:)` and `renderFeedStatus()` - so the Cluster tab's status line and the Feed card both distinguish "waiting for the tab to be idle" from genuinely running, with an elapsed-seconds count. `adoptFeedTab`'s `onStateChanged` closure now also re-renders the Cluster status label live while `isRefreshingCluster` is true, so the text updates as `pendingReason` changes mid-sweep, not just at sweep start/end. The Feed tab card's own subtitle now states up front that typing into it pauses automated commands, rather than leaving that to be discovered by confusion.
- **The bounded-max-wait question (the task brief's fix #3) was answered by recognizing `KubeBridge.queueDeadline` (45s) already IS a bounded wait with an automatic retry** (`expireStaleQueuedRequests` fails a stale-queued request with `.busy`, and the page's own 30s cluster-poll timer retries once `isRefreshingCluster` goes false again) - so the fix keeps refusing-and-visible (option b from the brief) rather than adding a send-anyway override (option a), since sending while the captain is mid-keystroke is precisely the interleaving hazard `KubeBridge.checkInFlight`'s discard guard (line ~531, unchanged) exists to prevent. No new "retry now" affordance was added: the existing manual Refresh button already serves that role once the bounded wait genuinely elapses (`isRefreshingCluster` flips back to `false`), and contention that clears on its own resolves within about a poll interval (0.25s) with no captain action needed - an override would only matter for a pathological multi-tens-of-seconds-continuous-typing case, which the now-visible countdown at least makes legible instead of silent.
- **Both new pending-reason self-tests were confirmed to catch the regression by name**, not merely to pass - temporarily reverting `pump()`'s three `setPendingReason(...)` calls back to bare `return`s reproduced `pendingReason == nil` (instead of `.waitingForQuietTab`/`.busyElsewhere`) in `KubeBridgeSelfTest` and the literal generic `"Refreshing…"` string in `KubernetesDestinationSelfTest`'s new `clusterRefreshShowsWhyItIsWaitingOnFeedTabActivity` case, both restored to green once the fix was reapplied. **A costly mistake worth flagging so it isn't repeated**: reverting via a Python script edit and then running a bare `git checkout -- <file>` on a brand-new branch with no commits yet resets the file all the way back to the pre-task committed state, silently discarding the real fix along with the temporary revert - always `git diff`/`git stash` a specific known-good state (or just re-apply the intended edit) rather than reaching for `git checkout --` to "undo a quick experiment" on an uncommitted file.
- **`fm/grandline-k8s-refresh-stuck-audit` found the stall recurred AFTER the stall-fix above, and the two bugs are genuinely different - a request could get stuck *before* `pump()`'s own pending-reason machinery ever saw it.** The captain's repro (switching the feed-tab picker to a different tab, per this file's own hypothesis 4) never touched the feed tab directly, so `pendingReason` correctly stayed `nil` - and yet the page rendered a permanent, un-explained "Refreshing…" with zero commands ever reaching the current feed tab. **Root cause**: `KubeBridge.stop()` (called by `KubernetesController.teardownFeed()` on every scope/feed-tab switch) cleared `inFlight = nil` without ever calling that request's own `completion` closure - it only ever failed what was still sitting in `queue`. If a `refreshCluster()` sweep's first command (`getPods`) was already genuinely in flight (waiting on its markers) at the exact moment the captain switched tabs, that one dropped completion left `enqueueBatch`'s own "how many of these N commands are still outstanding" counter permanently above zero - so the outer completion (the only thing that ever sets `KubernetesController.isRefreshingCluster = false`) never fired. Every later `refreshCluster()` call (manual, poll-timer, or the newly-adopted tab's own auto-refresh) then silently no-oped on `refreshCluster()`'s own `guard !isRefreshingCluster` before ever touching the new bridge - which is exactly why the current feed tab showed zero trace of any injected command. **Fixed** by having `KubeBridge.stop()` resolve a dropped in-flight request's completion too (`.failure(.unavailable(...))`, bypassing `deliver(_:_:)` so a teardown-driven stop still never counts toward the give-up threshold, matching the already-queued items' own treatment) - `retarget()` inherits the fix for free since it calls `stop()` internally. **Also added, per the task's own explicit mandate, a hard ceiling independent of that root cause**: `KubernetesController.clusterRefreshHardCeiling` (75s, a `checkRefreshWatchdog()` timer ticking every 5s) forces `isRefreshingCluster` back to `false` and a distinct "Something went wrong - no response after Ns" state with a real `clusterRetryButton` ("Try again") if a refresh has been running longer than any real kubectl round trip plausibly takes - deliberately reading nothing from `bridge`'s own internals, so it defends against this bug *and* any future one along the same chain. A `refreshGeneration` counter (bumped on every `refreshCluster()` call, checked in `finishRefreshCluster`) is what stops a request the watchdog already forced past - which `KubeBridge` has no way to cancel and which may still straggle in later - from clobbering whatever a genuinely newer refresh has since rendered; `retryStuckClusterRefreshTapped()` also resets the bridge itself (`stop()`+`start()`) rather than only this page's own flags, so the captain's own explicit retry works even when the *original* stuck command never resolves on its own (a single-flight bridge has exactly one in-flight slot, and queuing fresh work behind a permanently wedged one would just stall identically). Branch-point logging was added throughout `KubeBridge` (`AppLog.ui`, matching this app's GL-11 convention - `.info` for issue/success/resume/retarget/stop, `.error` for a genuine failure/give-up/the watchdog firing) specifically so a third occurrence is diagnosable from `log show`/Console.app without another blind round-trip. **A real, non-obvious lesson from writing the regression test for the generation guard**: `KubeBridge` is strictly FIFO and single-flight, which makes it effectively *impossible* to naturally reorder two real completions from the same bridge instance so a stale one arrives after a fresher one (the stale request's own remaining legs always finish draining before a newer batch queued behind it can even be issued) - an initial version of that test used two real batches through the real bridge machinery and passed even with the guard deleted, because both batches happened to use the identical fixture text and (unbeknownst to the test) the stale one always completed *first* anyway. The guard is legitimate defense-in-depth against a future change to the ordering (in this file or in `KubeBridge`), not a scenario reachable through today's normal call paths - so its regression test (`finishRefreshCluster`/`debugFinishRefreshCluster`, made non-`private` for exactly this) drives the guard directly with a synthetic stale generation and a distinctly-different fixture, rather than fighting the bridge's own real serialization to construct an impossible ordering. Every fix in this task - `KubeBridge.stop()`'s in-flight resolution, the watchdog firing, the retry button working through a permanently-wedged original request, and the generation guard - was confirmed to catch its own injected regression by name (a scripted, reversible temporary revert of each specific mechanism, never `git stash` - see the bullet above on why) before being restored.

- **`fm/grandline-k8s-ui-revamp` is the first-real-use overhaul: four captain-reported problems, all four with a regression-catching test.** Read this before touching the feed tab's terminal geometry, `KubeBridge`'s marker search, or the describe panel.
  - **Bug 1, and the only genuine *data-corruption* bug this page has had: a `kubectl get pods -o wide` line is routinely wider than the feed tab's terminal, so the emulator hard-wraps it and `Terminal.getBufferAsData()` reports the continuation as its own line - which `KubeResources` reads as a row.** The captain's screenshot showed a pod whose NAME was `5` (the tail of `RESTARTS`) and a fake row reading `NODE` / `NOMINATED NODE` / `READINESS GATES` - kubectl's own wrapped header tail. **Fixed at the source, not by detecting it afterwards**: the feed tab (and *only* the feed tab) is pinned to a wide, shallow geometry by `CockpitTerminalView.applyMachineReadableGeometry`, applied in `adoptFeedTab` and released in `teardownFeed`. `machineReadableColumns` is **240** and the number is measured, not chosen - the worst realistic `-o wide` line on the captain's cluster is **207** columns (that constant's own doc comment shows the per-column arithmetic). Making it stick needed **SwiftTerm patch 5** (`minimumColumns`), because `processSizeChange` re-derives `terminal.cols` from the view's pixel width on *every* `setFrameSize`, so `resize(cols:rows:)` alone is undone by the next layout pass - see `Vendor/SwiftTerm/README.md`'s "Fifth patch". The visible cost, accepted deliberately and scoped to one tab: that tab renders more columns than its frame shows and clips on the right. `KubeTable`'s two wrap guards (a post-header line that is itself a header; a row materially short of the header's column count) are **defence in depth only** and degrade a wrap to *one missing row* rather than a fabricated one - the brief rules them out as a primary fix and they are not one.
  - **Bug 2 had two independent mechanisms, and the first one is the interesting one.** (a) `KubeBridge` searched for its markers from `searchFromLine`, an **absolute** buffer index recorded at injection time. A feed tab's scrollback is bounded, so once it saturates the emulator evicts from the top: the buffer stops growing (`allLines.count > searchFromLine` is false forever) and every surviving line shifts down, so a command that ran perfectly reports `timeout`. That is exactly "one describe worked, the next timed out shortly after". The search is **marker-relative** now (`KubeBridge.markerIndex`) - both markers carry a fresh UUID per request, so a whole-buffer search is exact rather than a guess, and `searchFromLine` survives only as a fast-path hint. **Order still matters**: the *end* marker's absence means "still running", while an end marker with no start marker before it is a genuine `markersNotFound` - reversing that breaks every backoff case. (b) The queue was strictly FIFO, so a describe click landed behind whatever the 30s poll had just queued. `KubeRequestPriority` inserts `.interactive` work ahead of queued `.background` work - **order only**: single-flight, both guards and the deadline are untouched, and nothing already injected is ever preempted.
  - **Bug 4 was real and is the one worth remembering, because it was measured rather than argued.** A full-buffer read (`currentBufferLines()`, i.e. `getBufferAsData()` + split) costs **107ms on the main thread** at the interactive geometry (10,000 lines x 150 cols) and **38ms** at the feed tab's (2,000 x 240) - measured with a headless `Terminal` via a temporary probe, reverted before commit. The bridge did one of those **per command issued** (purely to record an index it no longer needs - now gone) plus one every 2.5s while in flight (`fullScanEvery` 10 -> **40**, so every 10s; a command is bounded at 20s so the scrolled-away safety net still fires twice) plus one on completion. Roughly **~1.5s of main-thread stall per 30s poll cycle** became **~76ms** - and the main thread is the whole app's UI thread, which is why this read as *app-wide* sluggishness rather than a slow page. Three more, each its own cause: the sweep now fetches only the visible sub-tab's data (`sweepCommands`, so a non-Pods tab runs **one** command rather than three); `KubeBridge`'s 4Hz poll timer **stops when idle** (it used to run for the life of the app once a feed tab had ever been adopted, including while this page was closed - `enqueue` restarts it, so it is an idle-stop, not a teardown); and the pod picker no longer destroys and rebuilds one `NSButton` per pod on every poll (`renderPodPicker` is guarded on a real signature change), while `KubeResourceTableView.setContent` no longer reloads twice per call nor at all when nothing changed, and `layoutColumnWidths` no longer re-assigns a column width from inside `layout()` on every pass (a self-perpetuating relayout).
  - **Layout: the work area is pinned to the page bottom with explicit constraints, not stacked.** The page was card / card / work-area in a vertical `NSStackView` at the default `.gravityAreas` distribution, which has no rule for who absorbs leftover height - so the table kept a 320pt box and the rest of the window was dead space (the captain's "tiny scrollable box on an otherwise-empty page", and the reason it double-scrolled). Hugging priorities cannot fix that: a `HelmCard` is constraint-driven with no intrinsic content size, so content hugging on it is a no-op (gotcha (12)). Scope and Feed were also merged into one `sessionCard` - two stacked card headers cost ~120pt of chrome on a page whose content is a table - and remain two independently shown/hidden *sections* inside it.
  - **The describe panel is a real drawer**: a slide-in overlay on the table's trailing edge (the `ConsoleController` SRE Lead pane idiom), with its own spinner, an honest "queued behind N Kubernetes commands" state, Copy, a real close button and Escape. It **overlays** rather than displacing, so opening one never reflows the rows being read, and a completion for a pod the captain has navigated away from is dropped rather than written into what they are now looking at.
  - **Five AppKit findings from building that panel, every one measured in a real off-screen render rather than reasoned about.** They cost most of this task's time and generalise well beyond it: (1) **A child pinned to *both* edges of a view whose width animates to zero is unsatisfiable at the closed end**, so AppKit breaks one of those constraints and the panel never recovers - the content lives in an inner view pinned to the drawer's *trailing* edge at a fixed width instead, which is also what makes it read as sliding rather than being squeezed. (2) **`layoutSubtreeIfNeeded()` on an ancestor does not descend into a subtree whose own `needsLayout` is false**, so changing a constraint constant deep inside settles the view you changed and leaves its children laid out at whatever width they were built with - and no constraint is ever reported as broken. Call it on the view that owns the change (`relayoutDescribeContent`). (3) **`HelmButton` does not clear `translatesAutoresizingMaskIntoConstraints`** - everywhere else in this app it lands in an `NSStackView`, which clears it for you; in a hand-constrained container AppKit's synthesised frame constraints silently win over every explicit one. (4) **An `NSTextView` is rich text by default, so `font`/`textColor` only touch the *typing* attributes** - text already in the view keeps what it had, which on a dark output card means invisible glyphs; set `isRichText = false`. (5) A nested `NSStackView` title column inside a horizontal `.fill` stack collapses to zero width and no combination of hugging/clipping priorities recovers it (gotcha (12) again) - the header is built from explicit constraints now.
  - **A probe limitation worth knowing, stated rather than papered over:** `cacheDisplay` does **not** draw an `NSTextView`'s glyphs in a window that was never ordered front (the same class of limitation this file already records for SwiftTerm's own `TerminalView`). The describe panel's text was verified instead by measuring the real state - 3,418 characters in `string`, a non-zero `NSLayoutManager.usedRect`, and a light ink resolved against the dark card - not by seeing it in the render.
  - **Verified** by `swift build` (clean debug and release, zero warnings in this app's sources), the release binary carrying no `FM_RUN_*` strings, the full suite, and real off-screen renders of the real mounted page across `daylight`/`helm-dark`/`gruvbox-light` - **without launching the app**, per the README's worktree rule. **Nine injected regressions each reproduced by name**, not merely passed: the column floor lowered to a window-sized terminal (the fixture wraps again), the pre-fix index-relative marker search (the describe never completes) *and* its extra buffer read (2 reads per command), the feed tab never widened, the sweep fetching pods and metrics on every tab, the bridge's idle-stop removed, and the pre-fix content-sized work area (which reported the captain's own complaint back: "the table is only 235pt of a 780pt page - still a box on an empty page").
