## Incident mode (F8, `fm/grandline-feature-f8-incident-mode`)

F8 of the production-readiness review's feature roadmap (section 25 of
`data/grandline-production-review/MANJESH_GRAND_LINE_PRODUCTION_REVIEW.md`, with the
captain-approved mockup in that folder's `lavish-plan.html`) - "Start Incident" on a host page,
after which SRE Lead turns, Log Analyzer captures and runbook runs attach themselves to one shared
record, and "End Incident" feeds that record to the existing postmortem generator. Four files:
`IncidentModels.swift` (record + `IncidentSources`, the phrasing layer), `IncidentStore.swift`
(YAML-in-git persistence), `IncidentCardView.swift` (the card), `ConsoleController+Incident.swift`
(the toolbar action and the attach points).

- **Every attach point is a hook on an event that already happens - there is no detection here and
  no second execution path anywhere.** SRE Lead's own reply completion (`handleSRELeadSubmit`), the
  capture `analyzeLogsTapped` already built, `LogAnalyzerController`'s own save, and the runbook
  summary `run_runbook` writes. `IncidentSources` is the direct counterpart of `FleetLogSources` /
  `NotificationSources`: format at the edge, detect nowhere new.
- **The runbook signal needed a new channel, and it is deliberately a notification rather than an
  interception.** A bridge request carries only `{"command": ...}`, so the Swift side cannot tell a
  runbook's steps from any other kubectl call and inferring it would be guesswork. `run_runbook`
  now drops one `event-<id>.json` summary (title + step counts, never command text or output) into
  the same bridge directory when it finishes, and `SRELeadBridge.drainEvents` claims it on the
  **idle** cadence - not the 5Hz tick, for GL-34's reason. The runbook still executes exactly where
  it always did.
- **The card is an `NSPopover` on the toolbar button, not an inline strip, and that is a hard
  constraint rather than a preference.** A strip between the toolbar and `content` would change
  every `TerminalView`'s frame, which reflows the buffer and can garble scrollback (the bug
  `fm/cockpit-sre-lead-ux-fixes` fixed, and `ConsoleController.terminalInset`'s whole reason for
  being permanent) - during an incident, which is the worst possible moment. The *button* is the
  always-visible active-incident indicator (red, showing `INC-014`), and starting an incident opens
  the card immediately. This is the one deliberate deviation from the mockup's layout.
- **Written as it happens, never batched.** `start`, every `append`, `end` and `setRCA` each reach
  disk before returning, so a crash mid-incident costs at most the artifact of the entry being
  written. **What that does *not* buy, and F2 (session restoration) is the only thing that will:**
  after a relaunch the "Active incident" state is not re-attached to the host page it was running
  on - the incident is still active and still shown the moment that page is opened again, but the
  app will not reopen the page. Do not paper over this with partial session restore.
- **Storage rides `ShiftGitSync` exactly like `LogAnalyzerStore`** (own `incidents/<YYYY>/<INC-nnn-slug>/`
  subtree, `ShiftYamlBridge` for the YAML, `FM_INCIDENTS_DIR` override **and** the `FM_SHIFT_DIR`
  fallback - see `CommandLibraryStore`'s own lesson about a store inside that subtree ignoring it).
  An incident's whole job is to reference investigations, so putting the two in different places
  would let the record and its evidence end up on different machines.
- **The one free text this feature writes is an SRE Lead transcript snapshot, and it is redacted on
  the way in.** `incident.yaml` holds ids, titles, counts and one-line summaries only
  (`IncidentTimelineEntry.sanitize` makes the one-line rule structural, like `FleetLogEvent`'s);
  the transcript lands in `artifacts/<entry-id>.md` via `LogRedactor.redact`, and the generated RCA
  in `rca.md`. Neither is ever inlined in the record.
- **`FleetLogEventKind` gained `.incident`** - the filter row is built from `allCases`, so it gets
  its own pill. Deliberately not folded into `.investigation`: a Log Analyzer artifact and a
  declared incident are different things and worth filtering apart.
- **The postmortem is the existing generator, fed a different input.** `endIncidentClicked` calls
  the same `SRELeadPostmortem.generate(hostLabel:transcript:)` the SRE Lead pane's own button
  calls; what changes is only that `IncidentStore.aggregatedTranscript` assembles every turn's real
  text plus a one-line account of every capture and runbook run, in order, instead of one tab's
  chat. A generation failure leaves the incident ended with the whole timeline intact and no RCA -
  it never un-ends anything.
- **A saved investigation attaches to the incident on whichever host page handed over the capture
  it was built from** (`AppShellController.logAnalyzerCaptureSource`, weak). That is the only
  honest correlation available - the Log Analyzer has no notion of a host - and a clipboard
  analysis or an investigation reopened from history clears it first, so a save then attaches to
  nothing rather than to whichever host happened to be last.
- **`FM_RUN_INCIDENT_TESTS`** covers the create/append/end round trip against real disk (every
  persistence case builds a *fresh* store over the same directory), the one-active-incident-per-host
  rule, the redaction boundary (grepped in the real bytes of every file under the incident
  directory), the aggregate the generator is fed, and the F6 wiring - both the round trip and a
  source guard that the call sites exist, since the round trip alone would still pass with them
  deleted. **Confirmed to catch three real injected regressions**, not merely to pass: dropping the
  one-active guard, skipping the redaction, and deleting the F6 append. `test_sre_kubectl_mcp.py`
  gained three cases for the event emission, likewise confirmed to fail when the emitter is removed.
- **Verified with `swift build` (clean debug and release, zero warnings in this app's sources), the
  release binary confirmed to carry no `FM_RUN_*` strings, all 63 runnable suites, and the Python
  suite - without launching the app**, per the README's worktree rule. (Re-verified after rebasing
  onto F7 and then F9, both of which landed while this was in review. F7's conflict was AGENTS.md
  only, additive on both sides - its console changes are in `ConsoleController+Sessions.swift`,
  which this touches nowhere. F9's was one hunk in `connectHost`: **F8's per-connect wiring has to
  sit before F9's `guard navigate else { return }`**, or a host connected by a multi-host send
  would silently never get its incident button or its evidence-open route.)

No production code changed. **The general lesson, worth internalizing rather than re-deriving a third time in this file**: any self-test measurement of `debugLiveInstanceCount` (or any other liveness counter) taken right after a call that constructs/destroys AppKit views must itself be inside (or immediately preceded by) its own `autoreleasepool`, exactly like every repeated-call stress-test loop already has to be - a one-shot baseline capture is not exempt just because it only runs once.
  - **A real, generalisable self-test-harness pitfall, worth not rediscovering**: an early version of the long-session stress test ran 300 raw `selectSpace` calls with **no** enclosing `autoreleasepool` anywhere in the call stack - `main.swift` dispatches straight to `AppShellBodyWidthSelfTest.run()` with no top-level pool of its own, unlike a real app's `NSApp.run()`, which guarantees one drain per discrete event. That specific arrangement produced a large (into the thousands), apparently-permanent excess that an explicit `RunLoop.main.run(until:)` drain afterward did *not* clear - reading exactly like a severe, confirmed leak. Wrapping each iteration in its own `autoreleasepool` (the only arrangement that actually represents the shipped app) made it disappear completely. **Any future stress test that repeats a call many times in a raw loop must wrap each iteration in its own `autoreleasepool`, or a pure self-test-harness artifact will read as a production bug** - this is the same lesson `DaylightModuleSelfTest.checkCanvasAndDrillHeader`'s own header already drew from a milder version of the same trap (20 switches, not 300), restated here because 15x the iteration count made the *size* of the artifact large enough to look definitive rather than merely suspicious.

- **`fm/grandline-drill-header-title-truncation-fix` found and fixed a real, reproducible AppKit bug behind a captain screenshot of `HelmDrillHeader`'s title truncating to a few characters plus an ellipsis ("Con…" instead of "Console") even though the subtitle rendered fully and the row otherwise looked correctly sized - conclusively **not** the window-width-cap class (gotchas (13)/(14)); `AppShellBodyWidthSelfTest`'s own bodyContainer-width checks were unaffected and untouched.** **A genuinely new AppKit finding, worth generalising beyond this one header: once an `NSStackView`'s `.leading`-aligned arranged subview has been genuinely squeezed below its natural cross-axis width by an external `<=` constraint, the stack's own reported cross-axis width can get stuck at that narrowest-ever value *permanently* - even after the squeeze condition fully clears (the constraint loosens, the constraining sibling is removed, the window widens back up, or the label's own `stringValue`/`intrinsicContentSize` changes to something completely different and much shorter).** Confirmed live with a disposable `HelmDrillHeader` instance driven directly (not through `AppShellController`): none of `invalidateIntrinsicContentSize()` on the labels, `needsLayout`/`needsUpdateConstraints`, an explicit `layoutSubtreeIfNeeded()`, deactivating/reactivating (or entirely replacing) the external `<=` tie, removing and re-adding the labels as arranged subviews, nor even a round-trip *window* resize to a much larger size ever let the stack's own resolved width grow back - it stayed frozen. This is a **different, more persistent flavor** than gotcha (14)'s "a required equality tie needs a live re-assert after a resize" - here the mechanism is internal to `NSStackView` itself (an apparent one-way ratchet on cross-axis size, not merely a constraint object failing to reassert), and no `NSLayoutConstraint`-level intervention this task tried could unstick it. **The fix**: stop using an `NSStackView` for the title/subtitle column at all - `HelmDrillHeader`'s `textColumn` is now a plain `NSView` with explicit constraints (each label pinned by `topAnchor`/`leadingAnchor`/`bottomAnchor`; the column's own width is a required `>= child.trailingAnchor` from each label, never something `NSStackView` derives internally). A plain `NSView`'s geometry is nothing but its own active constraints, re-solved fresh on every layout pass - it has no equivalent sticky internal state. **Any other narrow-column-of-labels-with-a-flexible-ceiling in this codebase (a vertical `NSStackView` whose cross-axis width can be genuinely squeezed by an external constraint, not just a fixed one) should be treated as a candidate for this same trap** - re-derive the case with a disposable instance before trusting that "it's just a caching/invalidation issue" the way gotchas (12)/(13)/(14) turned out to be; this one specifically was not fixable by any constraint-level intervention, only by removing the `NSStackView` from that dimension. Why it read as *intermittent* rather than permanent: it only manifested after switching *away from* a destination whose own action cluster (or a narrow window) had genuinely squeezed the row at some point in the session - the "Con…" screenshot's own title/action content had nothing to do with the truncation; whatever was shown immediately before it did, and a captain who'd never visited a wide-actions/narrow-window destination first would never see it at all. `AppShellDrillHeaderTitleSelfTest.swift` (`FM_RUN_DRILL_HEADER_TITLE_TESTS=1`) is the permanent regression coverage, including a minimal, disposable-`HelmDrillHeader` reproduction independent of `AppShellController`'s larger dependency graph - **confirmed live to actually catch the regression**: temporarily reverting `textColumn` back to an `NSStackView` reproduces the exact captain-reported failure shape (a real "Console" title resolving to 79pt against its own freshly-computed 104pt intrinsic need) and reapplying the plain-`NSView` fix passes again. Also folded in, per live captain feedback on the same screenshot round: `DaylightBarController.contentGap` (the gap between the floating bar's bottom edge and the body/drill-header area beneath it) tightened from §2.7's spec-stated 20pt down to `HelmMetrics.s3` (12pt) - a deliberate, captain-visual-correction override of that written spec number, the same kind of override this file already records for several rail-spacing decisions above.
- **`fm/grandline-theme-observer-cache-guard-audit` audited every destination controller for the general shape of PR #278's Settings-page-blank bug ("a `ThemeManager.shared.observe` closure fires synchronously at registration, and if the function it calls has an early-return guard comparing against a stored cache value that gets set regardless of whether real content exists, the premature call can poison that cache and make the REAL call - once content finally exists - skip populating it") and found no second instance.** All 18 rail destinations (`RailDestination.allCases`, `HomeCanvasController` excluded per the prior investigation's own ruling, `SettingsController` excluded beyond what #278 already fixed) were traced: `AutomationController`, `BootstrapController`, `ConsoleController`, `DictationController`, `DocsController`, `FleetController`, `GitHubSyncController`, `HealthController`, `HostsController`, `LogAnalyzerController`, `ReviewController`, `SchedulesController`, `SetupContainerController`, `ShiftController`, `ToolsController`, `UpdatesController`, `VaultController` all register their `ThemeManager.shared.observe` in `loadView()`, and every one of them is safe for one of three reasons, confirmed by reading the exact function the closure calls (never assumed from the closure's own name): (1) the rebuild/repaint function has **no** early-return cache guard at all - it unconditionally clears and repopulates its container every time (`ToolsController.rebuildGrid`, `SchedulesCardView.setSchedules`, `HealthCardView.rebuild`, `GitHubSyncController.applyTheme`, `BootstrapController.rebuildDynamicSections`'s six `rebuild*Section` callees, `AutomationController.rebuildStepper`, all unconditional); (2) the content the closure would touch is built via an **eager property initializer** (`private let x = ...`) rather than a `loadView()`-local variable, so it already exists - correctly populated - by the time the observer's premature synchronous fire runs, regardless of `loadView()`'s own internal ordering (`ToolsController`'s `gridContainer` is populated by an explicit `rebuildGrid()` call *before* the observer registration; `AutomationController.steps`/`SchedulesCardView`/`HealthCardView` are all eager `let`s); or (3) the guard's blocking condition is a **flag correctly initialized to a value that prevents premature completion** rather than a `nil`-vs-computed-value comparison that any first real value would clear (`VaultController.hasLoadedOnce` starts `false` and only flips once a real fetch lands; `BootstrapController.maybeSeedInitialDriftStatus`'s guard depends on `isLoadingDotfiles`/`isLoadingSoftware`, both hardcoded `true` at construction, so the premature fire correctly bails and the real seed only ever happens once both background checks genuinely complete). The one property matching the *exact* dangerous shape elsewhere - `SettingsController.lastAppearanceGridWidth` (a second, unrelated cache inside the same already-fixed file) - was checked and found safe too: `rebuildAppearanceGrid()` has no early-return gate on it at all, it is purely read by the separate resize-driven `containerWidthMayHaveChanged()` to decide whether to bother calling that always-unconditional rebuild. A codebase-wide grep (`guard X != Y else { return }` and `guard X == Y else { return }`, both directions, plus every `private var last*`/`cached*` property) turned up exactly one other instance of a stored comparison-cache poisoned this way, ever: the already-fixed `SettingsController.swift:330`. Leaf self-theming components built via `init()` (`HelmModuleCard`/`HelmPlateCard`/`HelmGradientTile`/`HelmDrillHeader`) all register their own `ThemeManager.shared.observe` *after* `buildChrome()` has already run, the opposite (safe) ordering from the bug.
  - **What shipped instead of a fix, since none was needed: `DestinationMountingSelfTest.everyDestinationRendersRealContentOnFirstLoad`, a new permanent case generalizing PR #278's own `checkSettingsRendersOnFirstLoad` to every destination.** The real finding of this audit wasn't a second bug - it was that the *existing* `everySlotIsReachableAndMountsCleanly` case (which already visited every `RailDestination` on every run) only ever asserted "mounted" and "`isHidden == false`," never "has real content" - so it would have passed throughout the entire lifetime of #278's own bug, mounted-visible-blank included. - **`fm/grandline-updates-refresh-button-light-mode-fix` fixed a real, captain-reported theming bug on Setup > Updates: the "Refresh" pill (`UpdatesController.checkAllPill`) rendered washed-out/near-invisible in light mode on a fresh load, and only rendered correctly after a dark -> light round trip - and found this is a genuinely different mechanism from PR #278/#279's, worth knowing before assuming every "fixed by a theme round trip" report is that same cache-guard shape.** `checkAllPill.layer.backgroundColor` read back **correct** immediately after a fresh `loadView()`, in every theme tried, with no round trip needed - confirmed empirically, which rules the #278/#279 poisoned-cache mechanism out entirely: `applyTheme()` has no early-return guard at all, so the value was never wrong. **The real defect is one level down, inside how the color is applied, not what it's applied to**: `checkAllPill` is a `HoverHighlightView` (`HelmUIComponents.swift`), a component that owns its own persistent `normalColor`/`hoverColor` state specifically so a mouse hover cycle can restore the right fill on exit (`mouseExited` calls `setBackground(normalColor, animated: true)`). `applyTheme()` never set either property - it wrote `checkAllPill.layer?.backgroundColor = accent.cgColor` straight to the CALayer, bypassing that tracked state entirely. Since `normalColor`/`hoverColor` both defaulted to their construction-time `.clear`, the moment the cursor entered and left the pill even once (near-certain for a clickable control the captain would move toward), `mouseExited` overwrote the correctly-painted fill with the untouched `.clear` default - and nothing repainted it again until the next theme change re-ran `applyTheme()` and wrote the accent straight back onto the layer (bypassing `normalColor` once more, so the *next* hover cycle strands it again the same way). This explains the light-mode-specific symptom precisely: with the fill stranded at `.clear`, the pill's near-white `onAccent` icon/label sit directly on the page background - "washed out" on a light page, much less noticeable on a dark one where white text still reads fine with no fill under it at all. **Confirmed live via `UpdatesRefreshButtonThemeSelfTest.swift`** (`FM_RUN_UPDATES_REFRESH_BUTTON_THEME_TESTS=1`): a fresh `loadView()` and a theme round trip both read the correct accent with no interaction; a real `mouseEntered`/`mouseExited` pair driven through the pill (any real `NSEvent` works - `HoverHighlightView.mouseEntered`/`.mouseExited` never read anything off the event itself) left the fill at `.clear` before the fix and restored to the accent after it - **confirmed to catch the regression by name**, reverting the fix reproduces the exact "stranded at `.clear`" failure. **Fix**: `applyTheme()` now sets `checkAllPill.normalColor`/`.hoverColor` instead of writing the layer directly - the same pattern every other filled `HoverHighlightView` pill in this app already uses (`HelmFormSheet`'s `closeSquare`, `DaylightBarController`'s pills/rows, `ShiftProjectViews.openRegion`, etc. - a codebase sweep for every `HoverHighlightView` instance found this caller was the outlier; most already set both properties correctly). **Any future filled/colored `HoverHighlightView` must set `normalColor`/`hoverColor`, never write `.layer?.backgroundColor` directly** - a direct write "looks" correct until the first hover cycle silently erases it, and the erasure is invisible in a static screenshot taken before any interaction, which is exactly why this shipped unnoticed. A follow-up audit similar to #279's (grep every `HoverHighlightView` instance for a direct, non-`.clear` `layer.backgroundColor` write with no matching `normalColor`/`hoverColor` assignment in the same file) was not run in full for this task - it was scoped to the one reported button - and would be a reasonable next step if this class of bug recurs elsewhere.
- **`fm/grandline-github-sync-badge-inconsistency`: a status pill is painted once, for one theme, and nothing re-resolves it - so the pill must be painted from the THEME pass, never from the status pass.** Two captain reports, a day apart, one root cause: GitHub Sync showed eight forks all reading "In Sync" with four rendering a solid dark-green pill beside four light muted green ones *in the same light theme* (and pressing Sync on a dark one flipped just that row while its text never changed), and Updates showed two rows both reading "Update Available" as one light tan pill and one solid dark one. **Ruled out first, because it would have been the worse finding: this was NOT two states hiding under one label.** `GitHubSyncStatus.inSync`/`DependencyStatus.updateAvailable` carry no payload that reaches the pill and `pillVisuals` is a total function of the case, so two rows in one status cannot resolve different hues - the variable was *time*, not state.
  - **The mechanism.** `ToolRowLayout.pill` resolves a fill and a label tone for **one** theme (`HelmContrast.tintedSurface`) and bakes both into the layer and the label; nothing re-resolves them afterwards. And `ToolRowLayout.applyTheme` deliberately never touches the pill - it is handed to `build` as one of `statusViews`, not as part of `Views`' own chrome - so a row's theme pass re-themed its icon, labels, border and accent bar and left the pill alone. Both controllers therefore painted the pill **only from `render(_:)`, i.e. only on a status change**, and a theme switch left every pill wearing the palette it was last painted in. Because each repo's/tool's check completes on its own schedule, a switch part-way through the opening sweep froze the rows that had already reported in the old palette and let the rest land in the new one - two treatments, one status, one theme.
  - **The fix is one owner, not one more call site**: the paint moved *into* `applyThemeToRow`, which `render` already ends by calling - so a status change and a theme change both reach it, and a future status added to `pillVisuals` cannot forget the theme half. `theme:` is now passed explicitly at both sites rather than left to the parameter's `ThemeManager.shared.theme` default: each controller keeps its own `theme` copy, and a pill resolved against a different theme than the row around it is the same class of split.
  - **The audit that bounds the scope, and it is worth not re-deriving: of ~20 `ToolRowLayout.pill` call sites, exactly two had a theme path that never repainted the pill - `GitHubSyncController` and `UpdatesController`'s tool rows, i.e. precisely the two screens the captain reported.** Every other caller is safe for one of three reasons, each checked rather than assumed: the call is *inside* an `applyTheme` (`HelmCard`, `HelmModuleCard`, `CredentialVaultInspector`, `DictationController`); the owner's `applyTheme` re-invokes the render method that paints it (`ShiftController.applySyncPill`, `LogAnalyzerController.renderCorrelation`, `CredentialVaultController.renderClipboardCountdown`, `CommandLibraryViews.renderDetail`, `ConsoleController+SRELead.updateSRELeadStatusPill`); or the whole row is torn down and rebuilt on a theme change (`HealthCardView`, `BootstrapController`'s `rebuildAfterThemeChangeIfVisible`). `UpdatesController+AppRow` was already correct - it passes `theme:` explicitly and `renderAppRow()` is called from `applyTheme`, which is exactly why the *App* row never showed the defect while the tool rows above it did.
  - **A tell worth recognising in a screenshot: the card border was right while the pill was wrong.** `attentionHex` is derived from `pillVisuals` *inside* `applyThemeToRow`, so the accent bar and border were already re-resolved on every theme pass. A row whose border matches its neighbour while its pill does not is this bug, not a hue mistake.
  - **`FM_RUN_STATUS_PILL_THEME_TESTS`** (window-backed, in `run-all-tests.sh`'s `NEEDS_SESSION` list) is the guard. It mounts both real pages, reports half the rows' status, switches theme, reports the rest, and requires every pill to match one painted **fresh in the current theme** - it reads what the layer and label were *actually painted with* rather than re-deriving from the status, because a check that re-derives cannot see a drift between the painted value and the current theme, which is the entire bug. It drives the **real** `ThemeManager.shared.setTheme` (so each page's own `observe` closure runs, and the wiring from toggle to repaint is under test rather than hand-mirrored), capturing and restoring `fm.themeID` in a `defer`. Neither page's `viewWillAppear` is ever called - both start real `gh`/`brew`/`npm`/`git` sweeps from it. **Confirmed to reproduce the captain's screenshots by scripted revert** (never `git stash`): rows 0-3 came back at `#263738` solid dark with a light-green label beside rows 4-7 at `#DDEBE6`, and Updates at `#3C332B` vs `#EEE7DD` - the 4-of-8 split and both colour pairs the captain photographed. **One case is honestly a forward guard rather than a reproduction**: the sync-round-trip case passes pre-fix too, since it involves no theme change - it pins "no visible badge change other than what a real state transition justifies", which the fix must not break.
