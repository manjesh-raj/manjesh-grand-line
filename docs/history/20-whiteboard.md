## Whiteboard (embedded Excalidraw)

**`.whiteboard` (`fm/grand-line-whiteboard-excalidraw`) is a rail destination hosting the real, vendored `@excalidraw/excalidraw` in a `WKWebView`, plus an AI action that draws a diagram onto it from a plain-English description and then refines it turn by turn (see the iterative-refinement bullet below).** Five Swift files - `WhiteboardAssets.swift` (where the bundle is), `WhiteboardWebView.swift` (the bridge + display gating), `WhiteboardDiagram.swift` (the Claude call and what a reply is allowed to contain), `WhiteboardController.swift` (the page) and `WhiteboardComposerPopover.swift` (the prompt) - plus two suites and `native/Vendor/Excalidraw/`, the bundle itself (**read its README before touching any of it**). Placement: Stores space (alongside Docs/Tools/Vault/Dictation), `isDailyUse == false`, `domainHue == .violet` (this app's own AI hue).

- **Embedded rather than reimplemented, and vendored rather than fetched - two separate decisions, both recorded in `Vendor/Excalidraw/README.md`.** The short forms: rebuilding an infinite hand-drawn canvas in AppKit would stay permanently behind the real thing; and this app has zero remote dependencies and is offline-first, so the built bundle is committed (8.7MB: an ~8.1MB single IIFE script, 145KB CSS, 480KB of woff2). `swift build` never touches it. `Scripts/build-excalidraw-web.sh` regenerates it and is the only thing in this repo that needs node/npm - build-time only, never at launch.
- **Offline is enforced, not promised, and `FM_RUN_WHITEBOARD_TESTS` reads the bytes rather than trusting the comment.** `web/index.html` carries `default-src 'self'` + `connect-src 'self'`, which is what makes the CDN font fallback baked into the library (`ASSETS_FALLBACK_URL`) unreachable; `frame-src` is deliberately *absent* so it inherits `default-src` and Excalidraw's embeddable-link feature has nowhere to load into; the web view uses a **non-persistent** data store, so nothing is written to disk. The suite parses the CSP out of the meta tag rather than substring-searching the file - the page's own comments discuss directives by name, and the first draft of that check failed on its own explanatory comment.
- **The AI asks for Excalidraw's *element skeleton*, not its real element shape, and that is the whole robustness story.** A full element carries `id`/`seed`/`version`/`versionNonce`/`updated`/`boundElements`/`containerId` plus arrow-and-label binding bookkeeping that has to agree across elements; `convertToExcalidrawElements()` exists precisely so a host can hand the library a small skeleton and let it fill all of that in. So the prompt asks for the documented small surface, and `WhiteboardDiagram.parse` only checks things it can actually check: valid JSON, a list of objects (a `{"elements":[…]}` wrapper is accepted too - models produce it and it is unambiguous), a `type` in a **narrowed** allow-list, and a `maxElements` (300) cap. `image`/`embeddable`/`iframe` are refused **by name**: the first needs a `fileId` that only exists for a file already in the scene, and the other two exist to load a remote URL the CSP blocks anyway, so accepting one would only draw a broken box.
- **`ClaudeOneShot`'s sixth caller, adding no new invocation shape** - `ConsoleCommandComposer` is the sibling to copy from, including the `claudePathOverrideForTests` seam. Unlike Console's composer the result is applied immediately rather than shown for review: a shell command is dangerous and a diagram is not, and Excalidraw's own ⌘Z takes it back.
- **Battery: the gating is three layers, and the first two are the load-bearing ones.** (1) The destination is lazy (`DestinationRegistry`) *and* the page is only loaded on first mount, so a session that never opens the Whiteboard starts **no web content process at all** - measured, machine-wide WebKit.WebContent count 0 before opening and exactly 1 after. (2) WebKit's own visibility state does the work: a `WKWebView` whose NSView is hidden reports `document.visibilityState === "hidden"` and stops compositing and `requestAnimationFrame`, and the destination model already hides the view. That only holds because the page has **no always-on loop** - keep it that way (`whiteboard.js`'s one rAF loop is a probe that stays dormant until a native call starts it). (3) `suspend()`/`resume()` pause Excalidraw's own CSS transitions and drop focus - the part WebKit cannot know about. `viewDidHide`/`viewDidUnhide` are the trigger, the same *effective*-visibility signal `CockpitTerminalView.refreshDisplayGating` uses and for the same reason.
- **Measured live on the real app** (a separately-bundled probe copy with its own bundle id and every `FM_*` store pointed at scratch, so the captain's running instance was never touched): visible+frontmost the page ticks ~30fps (63 rAF frames in 2s, `visibilityState=visible`) and its WebContent process burns **+0.05s CPU over 20s idle (~0.25%)**; navigated away it reports `visibility=hidden`, `suspended=true`, **1 frame in 3s** (the one already scheduled before the flip, then nothing) and **+0.02s over 20s (~0.1%)**. Total WebContent CPU for a whole session including loading the 8MB bundle, mounting React/Excalidraw and rendering an AI diagram: **0.91s**.
- **A real limitation of the window-backed suite, stated rather than papered over: a process launched from a terminal cannot measure the *visible* half.** A suite is not a composited UI app (activation policy `.accessory`, `NSApp.run()` never called), so the window server never composites its windows and WebKit reports the page `hidden` **even while the view is shown** - confirmed by reading `visibilityState` back through the bridge, and identical for a `nohup`-launched unbundled binary. `WhiteboardViewSelfTest` therefore asserts only the direction a regression would break (hiding always reaches the page) and prints a NOTE for the other half. To measure the visible half, assemble a `.app` with its own bundle id and `open` it - that is what produced the numbers above, and `open --env KEY=VAL` is how the store overrides get in.
- **`WKWebView.takeSnapshot(with:)` is the way to see a web-hosted page from an agent session** - `cacheDisplay`/`bitmapImageRepForCachingDisplay` (this repo's usual screenshot substitute) does not capture web content. It returned real PNGs of the real canvas with a real AI diagram on it, which is how the light/dark theme sync and the diagram quality were actually verified rather than assumed.
- **The page has no `HelmPageToolbar`, deliberately.** Excalidraw owns the body edge to edge inside one card; every canvas action is already in its own toolbar a few points below, and a second strip repeating it is the duplication §6.4 exists to remove. The three *page-level* actions (Generate diagram, Fit to content, Clear) are hoisted into the shell's drill header cluster. `DestinationMountingSelfTest`'s label floor needs an honest override for this page for the same reason: the body is a canvas, and its only native labels are the loading/unavailable states.
- **The AI action is a conversation, not a one-shot box (`fm/grandline-whiteboard-iterative-refine`).** It shipped as "type a description, get a diagram, done": a follow-up like "make this bigger" was read as a completely fresh, context-free request, so the only way to adjust a diagram was to rewrite the original description and regenerate from nothing. After a first generation the popover is in **refine** mode - the title reads "Refine the diagram", the turns so far are listed above the field, the button says "Refine", and "Start over" appears. Read `WhiteboardDiagram.swift`'s "Iterative refinement" header section and `WhiteboardComposerPopover.swift`'s "two modes" section before changing any of it.
  - **A refine turn carries two independent kinds of context, and they answer different questions.** The **board**, re-serialized from the live canvas on *every* turn (`snapshot` in `whiteboard.js`), is the load-bearing half: the whole point of embedding a real Excalidraw is that the captain moves, deletes and draws with its own tools between two AI turns, so what the model *said* it drew and what is on the board are two different things and only one is the truth. **`claude --resume <session_id>`** - threaded exactly as `SRELeadRunner` does, this app's established precedent for a remembering AI feature - is the second half, carrying the *intent* accumulated over several turns that a bare board dump cannot express. Neither alone is sufficient: resume alone drifts from reality the first time a box is nudged, board-only forgets why the diagram looks the way it does.
  - **Because the board half carries correctness, a failed resume is recovered from rather than lost.** A turn that fails *while resuming* is retried once without `--resume` - a genuine equivalent, since the prompt already carries the whole board - which turns "the session went stale" into a turn that just worked. A *fresh* turn's failure is never retried: there is no session to blame, so a second identical call would only double the wait.
  - **A refinement always replaces the board, so the prompt's two loudest rules are load-bearing rather than stylistic**: reply with the COMPLETE revised diagram (anything left out is deleted from the canvas), and keep the ids it was given (which is what makes a refinement read as the same diagram edited rather than a new one that looks similar). `WhiteboardDiagram.formatRules` is shared verbatim by both prompts - a rule that drifts between them is a diagram that renders on turn one and fails on turn two, which is exactly the bug this file already shipped once.
  - **`WhiteboardDiagram.run(turn:resumeSessionID:)` is the single entry point** (`Turn.fresh`/`Turn.refine`), replacing the old `generate(description:)`. Two copies of everything after the prompt - resolving `claude`, bounding the wait, parsing, sanitising - is how the two paths would start disagreeing about which replies are acceptable.
  - **The append checkbox is unchanged and is *not* the same mechanism** - checked before assuming otherwise: it only ever decided whether `loadScene` adds the new elements to the live scene or replaces it, and passed no context to the model at all. It is still offered, still byte-identical, for a **first generation only** - a refinement inherently replaces the board with its own revision, so the add-or-replace question does not exist there. The example chips are likewise hidden mid-conversation, where they would read as "click to throw this away".
  - **Two ways out, and they do different things on purpose.** "Start over" drops the conversation and leaves the board alone (clearing it is the destination's own Clear action, which asks first - a popover button that silently wiped real work would be the worse surprise, and the status line says so). Clearing the board *does* end the session, since a board with nothing on it has nothing to refine.
  - **`snapshot` is deliberately lossy, in a stated direction, and three of its jobs are not field copies.** Excalidraw publishes no inverse of `convertToExcalidrawElements`, so it reconstructs the documented skeleton surface only: a shape's caption lives as a separate `text` element with a `containerId` and is folded back into `label`; an arrow's bindings come from `startBinding`/`endBinding`; and a frame's membership lives on each *child*'s `frameId`, not on the frame. **A bound caption inherits its container's `frameId`** - naming it as a frame child produces a skeleton the app's own validator refuses and `convertToExcalidrawElements` crashes on, found by a real self-test run rather than by reading the code. Note also that **a skeleton's `id` is a reference key for bindings, not the id the drawn element ends up with**: `convertToExcalidrawElements` mints its own, so a snapshot reports the *real* ids and a test must find elements by label, not by the id its fixture used.
  - **Verified** with `swift build` (clean debug and release, zero warnings in this app's sources), the release binary carrying no `FM_RUN_*` strings, and all 93 runnable suites - **without launching the app**, per the README's worktree rule (the captain's real instance was running throughout). `FM_RUN_WHITEBOARD_TESTS` gained the refine-prompt contents, the board encoder, and a real multi-turn exchange through the actual `Process` path against an argv-recording fake `claude`; `FM_RUN_WHITEBOARD_VIEW_TESTS` gained the snapshot round trip through the real page and a full multi-turn exchange driven through the popover's own button target/action. **Seven injected regressions each reproduced by name**: the board dropped from the refine prompt, `--resume` never threaded, the stale-session recovery removed, a follow-up sent as a fresh generation, turns never recorded, "Start over" keeping the session id, and Clear no longer ending the session.
  - **A pre-existing harness hazard was fixed while writing this, and it is worth knowing before adding a case:** `WhiteboardViewSelfTest`'s composer scenarios waited on "the status is not the interim one", which the *previous* case's leftover status already satisfies - so a wait could return before the turn it was waiting for had even started, and a completion landing later rewrote the popover's state in the middle of the next case (producing a run of unrelated-looking failures, including a spurious "could not start claude: file doesn't exist" from a since-deleted fake script). Every scenario now calls `debugClearStatus()` *before* clicking and waits for a genuinely new terminal status via the shared `settled(_:)` predicate, which excludes **both** interim statuses. Do the same in any new scenario.
- - **`fm/grandline-devops-space-and-diagram-tool` added a *deterministic* text-to-diagram path beside the AI one: `WhiteboardDiagramDSL.swift` (the parser, the layout and the component library - pure logic, no AppKit) and `WhiteboardDSLPopover.swift` (a second popover on this page, plus a native structure preview).** Read the first file's header before touching either; it carries the decisions below in full.
  - **It never calls a model, and that is enforced as a source guard rather than left to convention.** `WhiteboardDSLSelfTest.checkNoModelCall` fails the build if `WhiteboardDiagramDSL.swift` so much as mentions `ClaudeOneShot`/`resolveClaude`/`Subprocess`/`URLSession`/`Process(`. The reason it has to be a *source* check: a `claude` call added here would still produce a diagram - just slowly, non-deterministically and broken offline - so every behavioural case would keep passing. This is also why **this suite runs in CI** while its AI sibling cannot (that one needs a fake `claude` on disk).
  - **The mode is picked, never inferred from the arrow spelling.** Reading `-->` as a flowchart edge and `->` as a sequence message would let one character silently decide the whole shape of the output. An explicit `HelmSegmentedTabs` picker (also what the captain's reviewed mockup shows) removes the trap instead of making it load-bearing - and with the mode known, **each mode accepts both spellings**. The one place they still differ is *inside* sequence mode, where `-->` is a dashed reply and `->` a solid call: mermaid's own convention, a styling difference within one element type rather than a mode switch.
  - **The label is peeled off before anything is tokenised as an arrow**, or `A --> B: maps a->b` tears itself apart. Split on the **first** colon (a later one, in a URL, survives), then split the remainder on arrows longest-token-first (`-->` before `->`, or the shorter token eats the longer one's tail and glues a stray `-` to a node name). A hyphen inside a name (`api-gateway`) is untouched, because neither token matches `-g`.
  - **Flowchart layout is Kahn's algorithm taking `rank[v] = max(rank[v], rank[u]+1)`** - the *longest* path, so a node sits below every one of its inputs rather than the first that reached it. Rows run top to bottom (mermaid's own `graph TD`, and the direction a fan-out reads best), each row centred against the widest. **A cycle is laid out, not refused** - a retry loop is an ordinary thing to diagram - so anything Kahn leaves unranked is placed afterwards in first-appearance order, one rank below its highest already-ranked input.
  - **Labels are computed before widths, and widths before layout.** The first draft measured the bare name, laid out, then widened a typed node's box for its emoji - which left the row off its own centre line and could eat into the gap the arrows need. Order matters here; a later re-measure is not a fix.
  - **Flowchart arrows are bound to both shapes; sequence messages are deliberately bound to nothing.** Excalidraw binds arrows to *shapes*, and a lifeline is a `line` - a binding would either be refused or land on the actor box at the top and drag every message up to it. Absolute geometry between two lifeline positions is both what works and what a sequence diagram means.
  - **A component is a styled `rectangle` with a bound label and an emoji, never an image** - `image`/`embeddable`/`iframe` are not in `WhiteboardDiagram.allowedTypes`, so an icon set would be a second asset pipeline for something this canvas cannot draw. Its colours are **literal hexes, and that is the correct exception**: they are painted inside Excalidraw's own canvas by Excalidraw, not by this app's chrome, and every one is a default Excalidraw swatch verified present in the vendored bundle. The seven presets are reachable from the DSL as `kind(Name)` (with aliases) **and** as a clickable palette; `DiagramComponent.named` plus an alias-collision check keep the two from disagreeing about what exists.
  - **A palette click always appends, whatever the replace checkbox says** - that checkbox is about the diagram the *text* describes, and a palette button that wiped a board would be the worst possible surprise. Pinned by its own case, and confirmed to catch the regression.
  - **`whiteboard.js` needed no change at all.** The DSL path reuses the existing `loadScene` bridge call and `WhiteboardController.load(elements:append:)` verbatim - one sink, so the two paths cannot drift about what "insert" means - which is what keeps `Scripts/build-excalidraw-web.sh` out of this change entirely (see that script's own note: a JS edit needs a rebuild, because the app loads the committed artifact).
  - **It is a popover on this page rather than a destination, and the captain's "output still lives as normal Excalidraw elements" constraint is most of the reason.** A separate destination would have to reach across into `WhiteboardController` for its `WKWebView` - a dependency pointing the wrong way, on a lazily-mounted page (GL-37) - and the captain would type on one page and watch the result appear on another. The board *behind* the popover is the reviewed mockup's middle panel.
  - **The preview is a *structure* preview and says so.** It cannot be faithful (Excalidraw draws with a hand-drawn font at a roughness this process has no renderer for), so it uses the app's own ink on the app's own field fill with each component's hue as an accent - which is also what keeps it legible in all fourteen themes rather than only the light ones Excalidraw's pastel palette is designed for.
  - **A test-only accessor must read the thing it names.** `debugHasPreview` originally returned `parsed != nil`, so injecting "the preview is never handed the diagram" passed silently - the only UI injection of five that did. It reads the preview view's own box count now. **Any `debug*` hook that stands in for a downstream view is worth this check before trusting the suite that uses it.**
  - **Verified** by `swift build` (clean debug and release, zero warnings in this app's sources) and the full suite - **without launching the app**, per the README's worktree rule. **Twelve injected regressions each reproduced by name**: label-split-after-arrows, first-arrival ranking, sequence spacing flattened, sequence messages bound, a disallowed element type, a `claude` call, comment-shifted line numbers, a palette click honouring the replace checkbox, Insert left enabled on a parse failure, the preview never handed its diagram, the popover unwired from the canvas, and a typo'd toolbar symbol.

**Not persisted, and that is a stated decision rather than an omission.** A board survives navigating away and back (the destination stays mounted for the process's life) but a relaunch starts fresh. Persisting it would mean choosing a store, a format and a backup story for a scratch surface, and half-persistence would be worse than none; Excalidraw's own Save/Open actions cover a board worth keeping.
- **Two suites**: `FM_RUN_WHITEBOARD_TESTS` (pure logic - asset resolution including the `FM_WHITEBOARD_WEB_DIR` precedence, the offline CSP, the prompt's contents, every parse branch, the real `Process` path against a fake `claude`, and the destination tables; runs in CI) and `FM_RUN_WHITEBOARD_VIEW_TESTS` (window-backed - mounts the real page, waits for the real Excalidraw component to report ready, loads a real skeleton through the real bridge, checks append grows the board, and measures the hidden-state gating; in `run-all-tests.sh`'s `NEEDS_SESSION` list).
- **`fm/grand-line-whiteboard-generate-crash` fixed a real, captain-reported crash: generating a diagram for "Kubernetes request path" (and any prompt where the model groups elements into a boundary box) surfaced a raw JS error, `undefined is not an object (evaluating 'o.children.forEach')`, in the popover.** Root-caused by reading the vendored bundle's own `convertToExcalidrawElements()`: it iterates every `"frame"`/`"magicframe"`-typed skeleton element and calls `.forEach` on its `children` field with **no nil guard** - a frame with no `children` key (which is exactly what an unguided model produces, since the prompt never mentioned the field) throws deep inside the library. Reproduced live, byte-for-byte, with a standalone `WKWebView` loading the real bundle directly - this is the fast, reliable way to reproduce/verify a Whiteboard bug without going through the whole composer/Claude plumbing. Fixed at two layers, deliberately: (1) `WhiteboardDiagram.parse()` now validates a `"frame"` element's `children` is a non-empty array of strings that reference other declared ids in the same skeleton (never itself), refusing with a specific message *before* the skeleton ever reaches the page - the prompt also now documents the requirement with a worked example; (2) `whiteboard.js`'s `loadScene` wraps its own `convertToExcalidrawElements` call in a **second, inner** try/catch that replaces *any* internal library error (not just this one) with one generic, always-actionable message, logging the real detail to the JS console for debugging rather than ever putting it in the reply the captain sees - this is the defense-in-depth half, proven independently by `WhiteboardViewSelfTest.checkFrameChildrenSafetyNet`, which calls `controller.debugLoad` directly (bypassing Swift-side `parse()` entirely) with a malformed frame skeleton. **A change to `src/whiteboard.js` needs `bash Scripts/build-excalidraw-web.sh` re-run before it takes effect** - the app loads the *committed* `web/whiteboard.js` artifact at runtime, never the source, and `swift build` has no way to know the source changed since it isn't a Swift/SPM input. Both new checks were confirmed to actually catch their regressions (not just pass) by re-introducing each bug in isolation, rebuilding, and watching the specific new assertions fail with the exact original symptoms, before restoring the fix. **A real, unrelated self-test race was found and fixed along the way**: `WhiteboardViewSelfTest.checkComposerDrawsOntoTheCanvas`'s second scenario waited on `!composer.debugStatus.contains("Drew") && !composer.debugStatus.isEmpty` - a condition already satisfied by the *synchronous* interim status ("Asking Claude for a diagram…") set the instant the button is clicked, before the async `claude` call even starts. So it never actually waited for the real completion; the stale completion (reading a since-`defer`-deleted fake-`claude` script path) fired later and clobbered whatever test ran next with a spurious "could not start claude: ... No such file or directory". Fixed by waiting for the interim status to be gone (`!contains("Asking")`) instead, matching the positive-outcome wait every other scenario in that file already uses - **any new scenario added to this suite should wait for a specific terminal status, never for "no longer the initial empty/placeholder state," which the interim status can satisfy on its own.**

### Every component draws a real icon, and the captions that used to clip

**`fm/grand-line-whiteboard-component-icons-overhaul`: the captain reported a placed component
rendering as a blue box with a monitor emoji and the text "S", the rest of the label gone - and,
separately, that the whole library looked like "a simple square with the text and some icon".** Both
are fixed. Read `WhiteboardLabel.swift`'s header, `Scripts/build-whiteboard-icons.py`'s docstring
and `Vendor/Excalidraw/README.md`'s two new sections before extending any of it.

- **The clipped caption was TWO independent bugs, and finding only one of them would have left the
  captain's own screenshot unfixed.** Every plausible single explanation is wrong, and each was
  ruled out by measurement rather than reasoning:
  - **Not the container's size.** The same caption truncates at the same character in a 120pt box,
    a 260pt box and a 900pt box.
  - **Not wrapping.** A 240pt-tall container shows one truncated line, not several.
  - **Not length.** A 30-character ASCII caption renders in full.
  - **Bug one, the general case: Excalidraw measures a text element before its own webfont has
    loaded, sizes the element to fallback metrics, and clips the real render to that width.** The
    rule is exact and was fitted against 11 samples with no exceptions: *a bound caption is clipped
    iff its Excalifont width exceeds its fallback width + 10* (the bound-text padding). Fixed in
    `src/whiteboard.js` by not posting `ready` until the font is genuinely in use. Two things that
    look like that fix and are **not**, both measured: `document.fonts.ready` resolves while every
    face is still `unloaded`, and `document.fonts.load(spec)` resolves *before* the face is usable
    by `measureText`. Only polling the measurement against a family that certainly does not exist
    reports the truth.
  - **Bug two, and it survives the font fix: a *bound* caption containing `U+FE0F` (VARIATION
    SELECTOR-16) is truncated regardless.** Proven independent by rendering the emoji caption with
    all seven Excalifont faces confirmed loaded - still `🖥️ Se`. Proven not to be about emoji at
    all by `A\u{FE0F}B Server`, which has none and truncates to `AB S`. `WhiteboardLabel` strips
    both presentation selectors from every caption at the point one is built.
- **`WhiteboardLabel` must work on `unicodeScalars`, never `Character`s, and shipping it the obvious
  way makes it a silent no-op.** `U+FE0F` is folded into the grapheme cluster it modifies, so
  `"\u{1F5A5}\u{FE0F} Server".contains("\u{FE0F}")` is **false** - a `Character`-based filter
  leaves the selector exactly where it was while reporting success. Caught by its own self-test, not
  by reading it; the same trap this file already records for CRLF.
- **The library is 62 real icons now: a white chip carrying the component's glyph in its role hue,
  generated by `Scripts/build-whiteboard-icons.py` from committed Material Symbols sources.** The
  caption is the component's plain title (or, for a typed DSL node, the captain's own node name) and
  carries no emoji at all.
  - **AWS Architecture Icons are deliberately NOT bundled**, and that is a licence conclusion rather
    than a scoping one. The asset package ships no licence file of any kind, the icons page grants
    only permission to *create diagrams*, and the AWS Trademark Guidelines say the opposite of what
    bundling needs (s3(d) bars sublicensing; s15 declines authorisation for AWS content in third
    party materials). Service *names* are still used as captions, which is ordinary nominative use.
  - **The official Kubernetes icons ARE safely licensed** (Apache-2.0 or CC-BY-4.0, per
    `kubernetes/community`'s own `icons/README.md`) and were verified as such. They are not used
    because they are full-colour badges in their own visual language, and mixing them would put two
    icon styles side by side in one diagram. That is a follow-up the captain can ask for, not a
    licence refusal.
- **The chip is white-with-a-coloured-glyph because Excalidraw inverts images on a dark canvas, and
  that was measured.** It applies `invert(93%) hue-rotate(180deg)` to every image in dark theme,
  **SVG included** - its own guard for SVGs compares the cached mime type against a map with no
  `svg` key, so it never fires. That transform flips lightness and keeps hue, so a white chip
  becomes a near-black chip and the glyph stays the same hue a shade lighter, which is what a dark
  diagram should look like. A solid role-coloured tile with a white glyph - the AWS look - was
  rendered beside it in both registers and is better in light and visibly inverted in dark, which is
  the register this app defaults to.
- **`WhiteboardDiagram.appAuthoredTypes` is one type wider than `allowedTypes`, and the asymmetry is
  the point.** `image` stays out of the set a *model* may use, for that set's own stated reason: an
  image skeleton is meaningless without a `fileId` naming a file already in the scene, and a model
  has no way to put one there. `DiagramDSL` does - it mints the id from a closed enum and sends the
  matching file in the same `loadScene` call - so widening `allowedTypes` would hand the model the
  type as well, which is exactly what is being refused.
- **A node is `[rectangle, image]` in one group, and which element is which matters.** The rectangle
  stays the arrow-binding target, so every existing connector keeps working; the caption stays a
  *bound* label (pinned to the bottom, with the icon above) so it still re-centres, re-wraps and
  double-click-edits with its container. A standalone text element was tried and is **worse**: it
  clips for exactly the same font reason, and it needs its centre computed by hand.
- **`whiteboard.js`'s `loadScene` takes an optional `files` array now**, added before the elements
  that reference it - an `image` whose `fileId` names a file the scene does not have yet renders as
  a broken placeholder and **stays** broken, because nothing re-resolves it later. The payload is
  omitted entirely when there is no artwork, so a plain `A --> B` diagram sends byte-for-byte what
  it always did.
- **Four assertions elsewhere were inverted rather than deleted**, each having become a record of the
  old behaviour - the same precedent this file records for `SessionRestoreSelfTest` and
  `checkSettingsTwoColumnLayout`. The one worth naming states its own now-false premise in its
  comment: "the emoji is the icon - there is no image element type this canvas will accept".
