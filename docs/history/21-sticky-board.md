## Sticky Board

**`.stickyBoard` (`fm/grandline-sticky-board`) is a freeform corkboard of draggable, colored sticky notes for quick thoughts - the captain's own request, given a proposed second HTML reference (a "detective corkboard" mockup with pushpins/string) as inspiration only. `StickyBoardModels.swift` (the note model + six literal paper colors), `StickyBoardStore.swift` (`StickyBoardGitSync` + `StickyBoardStore`), `StickyBoardViews.swift` (the canvas + note card + drag mechanics) and `StickyBoardController.swift` (the destination) are the whole feature.**

- **Persisted as one batched YAML file in a genuinely new, dedicated sibling folder - `GrandLineDocs/sticky-board/notes.yaml`** - sharing `ShiftGitSync.shared`'s working tree and serial queue exactly the way `DocsRunbookGitSync` already does (see that file's own header), rather than nesting inside `personal-tasks/` the way `CommandLibraryStore`/`IncidentStore` do. `StickyBoardStore` checks `FM_STICKY_BOARD_DIR` first, then falls back to `FM_SHIFT_DIR` (`<dir>/sticky-board`) - the fallback is what let this land with **zero edits to any pre-existing self-test harness's `withScratchEnv`**, since every one of them already sets `FM_SHIFT_DIR` to stay off the real clone. GL-01's refuse-to-overwrite-on-parse-failure guard is a single-file version of `ShiftStore`'s own (one `isInFailedLoadState` flag rather than a `Set` of paths, since this store owns exactly one file).
- **A real, live near-miss during this task's own verification, worth internalizing rather than re-deriving**: the *window-backed* self-test (`StickyBoardViewSelfTest.swift`) constructs `StickyBoardController()` directly, which calls `StickyBoardStore()`'s **production** `init()` - and unlike every store this codebase has added a global test-process safety net for (`FleetLogStore.shared`, `ScheduleStore`/`ScheduleRunHistoryStore` - see `main.swift`'s own `#if FM_SELFTESTS` header comment on why a *per-suite* `withScratchEnv` fix keeps missing this class of bug), `main.swift`'s global self-test redirect block had no entry for `FM_STICKY_BOARD_DIR` yet. Running the new suite left a stray, uncommitted `GrandLineDocs/sticky-board/` folder sitting in the real local clone of the captain's actual `manjesh-config` (never pushed - the 3s debounce never fires before a headless suite process exits - but a real hazard, and the reason a handful of otherwise-inexplicable flaky failures showed up: repeated runs kept adding real notes to the same real file, so `debugNoteViews.values.first` was picking a different accumulated note each run). Fixed by adding `FM_STICKY_BOARD_DIR` to `main.swift`'s existing global redirect block (the same one `FM_FLEET_LOG_DIR`/`FM_SCHEDULES_FILE`/`FM_SCHEDULE_HISTORY_DIR` already live in) - **any future store reachable from a bare, no-argument production constructor needs an entry there too, checked *before* writing its first self-test**, not caught after the fact.
- **The note cards are plain, frame-positioned `NSView`s inside a plain (non-Auto-Layout) fixed-size canvas** (`StickyBoardMetrics.canvasSize`), deliberately sidestepping the whole class of window-size-cap/required-constraint gotchas this file's own catalogue documents repeatedly for freeform/draggable content. Drag is scoped to the note's own header row only (`StickyNoteHeaderView`'s `mouseDown`/`mouseDragged`/`mouseUp`, with a 3pt movement threshold before committing to a drag - mirroring `CockpitTerminalView.localSelectionDragThreshold`'s own documented fix for "an ordinary click reads as a drag on the first pixel of jitter") so a click inside the body `NSTextView` still places a caret and starts editing normally, with no ambiguity about which gesture was meant.
- **Note paper colors are a deliberate, literal exception to this app's theme-token rule** - six fixed (paper, ink) hex pairs, each independently verified to clear WCAG AA's 4.5:1 text floor via `HelmContrast.ratio` (`StickyBoardSelfTest.swift`, not eyeballed). Only the board's own background/card/toolbar chrome tracks the active `HelmTheme`; an already-placed note's paper color is asserted byte-for-byte unchanged across a live theme sweep in `StickyBoardViewSelfTest.swift`. A note's rotation (`StickyNote.rotationDegrees`) is rolled once at creation and persisted - never re-randomized on reload.
- **Two self-test suites**: `FM_RUN_STICKY_BOARD_TESTS` (pure logic - contrast, a full CRUD round trip through `StickyBoardStore(root:)` re-read by a fresh instance, the GL-01 guard, the env-var fallback order, and a real commit+push against a disposable local bare git repo mirroring `ShiftGitSyncSelfTest`'s own harness verbatim - never the captain's real repo) and `FM_RUN_STICKY_BOARD_VIEW_TESTS` (window-backed, in `run-all-tests.sh`'s `NEEDS_SESSION` list - a real theme sweep via `debugApplyTheme` rather than `ThemeManager.shared.setTheme`, real synthesized drag events, and a real click on the real `Toast` "Undo" button found in the live view tree).
- **Explicitly deferred, per the captain's own instruction**: a plain notebook/journal-style note-taking page is a separate, not-yet-scoped feature - do not build it as part of touching this one. A checklist/checkbox note variant was also left out of v1 as a stated nice-to-have, not a gap.
- **`fm/grandline-sticky-code-preview-polish` is the captain's first-live-use pass over both new features, and its headline finding generalises far past them: a destination that never forces `root.appearance` re-themes only *half* of itself, and every layer-colour self-test in the world will still pass.** Read this before diagnosing any future "some of the page doesn't follow the theme" report.
  - **Root cause.** `ThemeManager.swift`'s checklist item 2 - force `root.appearance = NSAppearance(named: theme.mode == .dark ? .darkAqua : .aqua)` inside the theme observer - was obeyed by every destination in this app *except* the three most recently built ones. `StickyBoardController` and `CodePreviewController` had **zero** occurrences of `appearance`; Docs, Review, Hosts, Settings, Updates, Shift, Log Analyzer, Kubernetes, GitHub Sync, Dictation, Bootstrap, Runbooks, Postmortems and Schedule History all have it. The consequence is specific and matches the captain's screenshots exactly: layer-backed fills (page root, card, canvas, status bar) tracked the theme fine, while **everything resolving a system semantic colour** - scroller track and knob, the field editor AppKit lends an `NSTextField`, an `NSMenu` popped from a row, the language popup's menu, focus rings - kept following the *OS's* light/dark. On a Mac in system Dark with a light Helm theme selected, both pages rendered dark scroll chrome on a light surface, and vice versa.
  - **Why it survived review, and the lesson for the next reviewer.** `StickyBoardViewSelfTest` already swept four themes and asserted the root/card/canvas layer colours - all green, all correct, all blind to the actual bug. A layer-colour assertion cannot see this class of defect at all. The guard that can is one line: compare `view.effectiveAppearance.bestMatch(from: [.aqua, .darkAqua])` against the theme's mode. Both suites carry it now, and both were confirmed to catch the regression by name (reverting the fix reproduces "should be NSAppearanceNameDarkAqua, was NSAppearanceNameAqua" - i.e. the captain's exact symptom).
  - **`WhiteboardController` had the same gap** (`grep -c appearance` returned 0 at the time), deliberately left alone by this task since it's a third destination its own suites don't cover and the captain hadn't reported the bug there yet. `fm/grandline-whiteboard-theme-appearance-fix` closed it once the captain confirmed: the identical one-line fix (`view.appearance = NSAppearance(named: theme.mode == .dark ? .darkAqua : .aqua)` in `WhiteboardController.applyTheme()`) plus a `debugApplyTheme(_:)` accessor and the identical `effectiveAppearance.bestMatch` assertion, swept across `daylight`/`dusk`/`helm-light`/`helm-dark` in `WhiteboardViewSelfTest.checkThemeAppearance` - confirmed the same way (revert the fix, see `dusk`/`helm-dark` mismatch with `NSAppearanceNameAqua` instead of `NSAppearanceNameDarkAqua`, restore it). Every full-window destination in this app now forces its root's appearance except `WhiteboardComposerPopover`'s own popover (already handled separately, since a popover forces `popover.appearance` rather than a view's) - a codebase-wide "every destination forces appearance" *guard* (as opposed to fixing each instance found so far) is still the natural next step flagged by this note's own predecessor, not yet built.
  - **Sticky Board's colours are now THREE categories, not two, and conflating them is the way to break this feature.** (1) Board/toolbar/footer/overlay chrome: full `HelmTheme` tokens, like any page. (2) The cork surface and its wood frame (`StickyBoardCork`): **literal hues chosen by `theme.mode`** - cork is cork, so it is not a theme token, but a corkboard in a dark room is a darker cork, so its tone genuinely switches. All seven light palettes show the identical cork; all seven dark ones show the identical darker cork. (3) A note's own paper (`StickyNoteColor`): one literal value, byte-identical in all 14 themes. The captain's own wording resolved a real contradiction inside the brief here: its acceptance-criteria line said the board should be "a green cork/felt tone", while both of its more detailed sections said brown/tan cork and explicitly "NOT the green felt board mentioned in the earlier detective mockup". Per this file's standing rule, the captain's explicit description outranks a stale summary line - the board is cork brown/tan.
  - **The cork is a tiled, procedurally drawn `NSImage` pattern, not a photo and not a flat fill.** A 2200x1500 canvas redrawing several thousand individual specks on every `draw(_:)` would put real work on the main thread every time a note is dragged; a pattern fill is one `NSRectFill` regardless of canvas size, and the tile is built at most once per light/dark mode and cached. The grain is **seeded, not random** (`StickyBoardCanvasView.seededSpecks`, a plain LCG): a fresh `Int.random` per tile would re-roll the board's grain on every relaunch and make an off-screen render impossible to compare against a baseline.
  - **A self-test lesson worth not repeating, because the first version of the check passed against a completely flat board.** "Does the cork texture actually paint?" is the one thing no colour-*property* assertion can answer - a pattern fill can be configured perfectly and paint nothing. So the check renders the canvas and counts distinct pixel tones (a flat fill gives exactly 1, real grain gives ~30). **The trap: the first draft sampled the region at the canvas origin, where new notes cascade from** - so it was counting the *note's* own rendering as grain and reported 52 tones against a board with the texture removed. Sample somewhere no note has been placed (`x: 1400, y: 1000`) before trusting a "the surface renders" check on this page.
  - **Notes are resizable now**, so `StickyBoardCanvasView.clamp(_:size:)` takes the note's own size - a shared `noteSize` constant would let a grown note's bottom-right corner be dragged off the board. The grip is its own 16x16 view in the corner rather than a hit-test region inside `StickyNoteView`, for the same reason the drag handle is its own view: the note's body is a live `NSTextView`, and a corner test done on the card has to reason about which subview would otherwise have taken the event. It carries the same minimum-movement threshold the drag handle does.
  - **`StickyNote` gained `title`, `width` and `height`.** This store's YAML decoder is hand-written with `?? default` fallbacks, so it is **not** the synthesised-`Codable` trap that cost this app a whole `hosts.json` - but the rule is the same and `StickyBoardSelfTest.checkLegacyNoteDecode` pins it against a real pre-upgrade `notes.yaml` rather than trusting the reading. Confirmed to catch a regression: removing the fallback makes a legacy file decode to zero notes, which cascades into eight unrelated failures.
  - **Fonts go through `StickyFont`, a feature-scoped role accessor modelled on `ShiftFont`**, never an inline `NSFont(name:)` per call site. Two things that buys: a ranked fallback chain (a typo'd name returns `nil` and the usual `?? .systemFont` hides it completely - `NSFont(name: "Chalkboard-Regular", ...)` is a real example, `Chalkboard` resolves and `Chalkboard-Regular` does not), and one place for a self-test to assert the resolved face is **not** the system font. Body/title are Noteworthy (handwriting, per the captain's index-card reference); the board header is American Typewriter.
  - **The board's "CASE: MY THOUGHTS" header is a deliberate, captain-requested exception to Daylight §6.4's "a page never repeats its own destination name"** (the rule Review, Docs and Health were each corrected for). It is kept under the 20pt hero floor `DaylightDrillPageSelfTest` polices, so it reads as a label stuck on the board rather than a second page title. Its "● ACTIVE" pill states something true rather than being a permanent sticker - an empty board reads EMPTY and an unreadable one reads UNREADABLE (GL-14's rule). Its ink is corrected against the **cork** via `HelmContrast.legibleOn`, not against the theme's own background: a dark theme's near-white `chromeInkHex` on light tan cork is illegible.
  - **`DaylightBarIconButton` is the bar's shared icon-square chrome**, extracted from `DaylightThemeToggleButton` when this task added the Sticky Board / Code Preview quick-access icons - three copies of the same 34pt bordered tile is how this app ended up with the "two icon-button languages" finding its own UI audit spent a phase undoing. `NotificationBellButton` deliberately stays separate (it carries a badge and therefore a wider control frame). Each quick-access icon uses its destination's **own** `RailDestination.symbol`, so the bar icon and the card it opens cannot drift apart, and the suite asserts each symbol genuinely resolves - `NSImage(systemSymbolName:)` returns nil silently and this app has shipped an invisible icon that way before.
  - **A new quick-access icon appends to the trailing end of that group, never gets slotted in by topic** (`fm/grandline-tasks-quick-access-icon` added Tasks; `fm/poneglyph-own-destination-and-strawhat-toolbar-shortcut` added Straw Hat Pirates and Poneglyph; `fm/grandline-daylight-console-shortcut` added Console - so the row is search -> Recents -> Sticky Board -> Code Preview -> Tasks -> Straw Hat Pirates -> Poneglyph -> Console -> theme -> bell -> avatar). The group reads in the order the captain asked for each shortcut, and appending is what stops adding one from moving an icon a captain already has muscle memory for. Adding one is a `DaylightDestinationButton(destination:)` property plus six mechanical edits in `DaylightBarController` - the target/action loop, `addSubview`, relinking the previous last icon's `trailingAnchor` to the newcomer, `keyViewChain`, the `applyTheme` sweep, and `debugDestinationButtons()`. **Only two of those six fail loudly if forgotten** (a missing constraint collapses the row's widths; a missing subview traps on "no common ancestor"); an icon left out of the target/action loop, the key loop, the theme sweep or the debug list renders pixel-identically, which is why `DaylightModuleSelfTest.checkBarDestinationIcons` asserts the expected destination list as a **literal** - deriving it from `debugDestinationButtons()` would pass for any set of icons in any order - and drives a real `performClick` per icon. Confirmed to catch all five: a dropped debug entry, an unwired target/action, a missing key-chain entry, an unsatisfiable constraint relink, and a *satisfiable* reorder.
  - **Each icon costs the bar's one compressible joint exactly 42pt (34pt square + an `s2` gap), and that budget is the only thing an addition can regress.** Measured before and after adding Console, on a real window at eleven widths from 1920 down to 420: the window holds every one of them exactly in both builds, so nothing caps it (`checkBarDoesNotCapWindow` is what guards that, and it still passes at 420pt). What does move is the pill-row/search-pill overlap this bar has always had at narrow widths - its onset shifted one step earlier, from ~950pt to ~1050pt, i.e. by exactly the 42pt. The group is trailing-anchored, so an addition also slides every existing icon 42pt left together; the convention protects their *relative* order, which is what muscle memory is built on, not their absolute x. A drill page frees 454pt by hiding the space pills (A2), so this only bites on the canvas.
  - **`fm/poneglyph-own-destination-and-strawhat-toolbar-shortcut` added two more in the same pass, per a captain follow-up message on the same task rather than the original brief (Console followed later the same way, which is why the bullet above states the current row rather than this one).** Both follow the "append, never slot in by topic" rule and the same six-edit checklist above verbatim - no new mechanism, `DaylightDestinationButton(destination: .strawHat)`/`DaylightDestinationButton(destination: .poneglyph)` reusing each destination's own `RailDestination.symbol` (`person.3.fill`/`doc.text.image`, both already rendering elsewhere - the Overview canvas card and the Stores canvas card respectively - so the icon and the page it opens can't drift apart). `DaylightModuleSelfTest.checkBarDestinationIcons`'s literal expected-destination-list and its six-edit-checklist assertions both needed the two new entries added (`debugDestinationButtons()` now returns 5, in that order) - updating them is what actually re-verified the checklist rather than just adding two more buttons that happened to compile. **Correction (`fm/strawhat-toolbar-shortcut-use-jolly-roger-icon-69c3`): the "reusing each destination's own `RailDestination.symbol`" claim above was true for Poneglyph but wrong for Straw Hat Pirates in exactly the way this file's own `RailDestination.drillHeaderArtwork` bullet already warned about - the toolbar icon fell back to the generic `person.3.fill` glyph while the destination's own drill header and its Overview canvas card both correctly rendered `StrawHatFlag.image`, the crew's Jolly Roger.** `DaylightBarIconButton.init` gained an optional `artwork: NSImage?` parameter (defaulting to `nil`, so every other caller - the theme toggle and every other quick-access icon, Poneglyph included - is byte-for-byte unaffected): when set, the artwork fills the icon square edge to edge (`.scaleProportionallyUpOrDown`) instead of a small centred glyph, with the image view given its own `cornerRadius`/`masksToBounds` clip (it is a *sibling* of `iconBackground`, not its subview, so `iconBackground.layer?.masksToBounds` clips nothing there). `DaylightDestinationButton.init` now passes `artwork: destination.drillHeaderArtwork` - which is `nil` for every destination but `.strawHat`, so this reuses the exact same field the drill header already reads rather than inventing a second one, and a future artwork-carrying destination gets the toolbar icon right for free the moment it's added to `drillHeaderArtwork`. `DaylightBarIconButton.debugUsesArtwork` (`#if FM_SELFTESTS`) and `DaylightModuleSelfTest.checkBarDestinationIcons`'s per-button `expectsArtwork == RailDestination.drillHeaderArtwork != nil` assertion are the permanent regression guard - confirmed live to catch the exact regression by name (`Straw Hat Pirates: debugUsesArtwork=false, expected true`) by temporarily reverting `DaylightDestinationButton.init` to drop the `artwork:` argument and re-running the suite.
  - **Code Preview's font zoom adds no new preference.** The page already *observed* `FontSizeManager` (that is how it picks up a change made in Settings); it simply had no way to change it from there. The two toolbar buttons call the same `FontSizeManager.shared.step(by:)` `ConsoleController.zoomIn`/`zoomOut` already use, so persistence comes free via `AppSettings.fontSize` and the terminals and the editor can never disagree about "the monospace size". Covered by driving the real buttons' target/action, so a button wired to nothing fails.
  - **`fm/grandline-audit-ui-fixes` closed the other half of that "not yet built" guard, and it was a popover rather than a destination.** The captain-reviewed UI findings of `data/grandline-full-app-audit/report.md` (findings 1-4; the audit's other six sections are separate, unauthorized work and were not touched). Two of the four were the *popover* shape of the bug the bullets above fix for destinations, and the general lesson is worth stating once: **AppKit supplying an `NSPopover`'s vibrant material says nothing about which side of light/dark that material resolves against.** `ShiftMenuBar.swift` said so explicitly - its content controller's own doc comment justified having no theming at all with "a popover already gets its own vibrant background from AppKit for free" - and its header, both stat rows and the quick-add field's editor are deliberately plain `.labelColor` system-semantic text, so on a Mac in system Dark with a light Helm theme selected it rendered near-white text on a light material. The incident popover (`ConsoleController+Incident.swift`) had the same gap for the opposite reason: `IncidentCardView` derives every colour it *paints* from `theme`, so the card body was always right and only what AppKit resolves semantically inside it (the note field's editor, the evidence list's scroller chrome, focus rings) followed the OS.
    - **`FullAppAuditUISelfTest.checkEveryPopoverForcesAppearance` is the guard, and it is the point of the task** rather than the two fixes: a file owning an `NSPopover()` must also set `.appearance = NSAppearance(named:` somewhere (allowing `ConsoleController`'s six-file GL-36 family to satisfy it from any of its files). All eight of the app's popovers pass it now; two only started to here. **Confirmed to catch both regressions by name** - removing either appearance line fails the guard *and* the matching behavioural case.
    - **The open-time set is the load-bearing half; a live theme observer is the belt.** `NSPopover` reads its appearance when it is shown, so `ShiftMenuBarController.prepareToShow()` (extracted from `iconClicked` precisely so a self-test can drive the real path without a live `statusItem.button`) sets it on every open, and `ConsoleController.showIncidentCard()` does the same. Both *also* re-force it on a theme change while already open - for the menu-bar item via its own `ThemeManager.observe`, for the incident card from `ConsoleController+Toolbar`'s existing `applyTheme`. In practice a transient popover cannot survive reaching the theme control, which is exactly the reasoning that justified the original omission, so it is closed rather than argued about.
  - **`StickyNoteHandleView` (`StickyBoardViews.swift`) is how a note is moved and resized without a mouse** - the same task's finding 3, and the one genuinely new capability in it. Before it, `StickyNoteHeaderView` and `StickyNoteResizeHandleView` were plain `NSView`s with raw mouse handlers and no accessibility markup at all: everything else on a note was already mouse-free (real text controls, a real `NSButton` menu), so position and size were the page's one complete VoiceOver dead end. The shared base class carries both halves GL-16 established on `HoverHighlightView` - `acceptsFirstResponder`/`canBecomeKeyView` plus a real `focusRingType = .exterior` and `drawFocusRingMask` (a control the keyboard can reach has to show where the keyboard is), and `isAccessibilityElement`/`.handle` role/label/help plus four `NSAccessibilityCustomAction`s so the directions are reachable from the VO rotor without knowing the arrow-key binding. Three things worth not re-deriving:
    - **A nudge is coalesced before it is persisted** (`commitDelay`, 0.35s), because this file's own rule for the mouse is that only a drag's *end* is written and a held arrow repeats at ~25Hz. A rotor action flushes immediately instead - it is one deliberate act, not one repeat of a held key - and `resignFirstResponder` flushes too, so a run that ends by tabbing away is still written.
    - **`applyNudge` returns whether anything moved**, so a nudge into the canvas edge neither schedules a pointless write nor reports success to VoiceOver (a rotor action that announces a move that did not happen is worse than one that says it failed).
    - **"the override returns true" and "an assistive client can reach it" are different claims.** A view whose `isAccessibilityElement()` is false is *ignored* and AppKit hoists its children in its place, so `StickyBoardViewSelfTest` asserts the handles appear in the note's own `accessibilityChildren()` as well as asserting the overrides - only the first of those is the fix. Confirmed to catch the regression: reverting to the pre-fix plain-`NSView` behaviour fails 11 named assertions.
    - Also here: the note timestamp was a raw `.systemFont(ofSize: 10.5, weight: .bold)`, i.e. below GL-32's `HelmType.minimumUIPointSize`, and is `HelmType.chip()` now (that exact designed size and weight, scaled and floored - measured live at 11.0pt at Default and 14.3pt at Larger). The self-test asserts the **resolved point size**, not the call site, so it catches a regression to any other literal. And the two Kubernetes tables (`KubernetesViews.swift`) are `HelmTableView` rather than bare `NSTableView()`s - the app's last tables still drifting from that shared component. Zero behaviour change today (with no `doubleAction` wired, the subclass's `keyDown` falls straight through, and arrow-key selection already reached `tableViewSelectionDidChange`), confirmed by a real off-screen render before and after.
    - **`NSApp` is nil until `NSApplication.shared` has been touched at least once** - it is an implicitly-unwrapped `NSApplication!`. Every other window-backed suite in this repo gets away with `NSApp.setActivationPolicy(.accessory)` only because it builds an `NSWindow` first; a suite whose first AppKit call is a status item (or anything else) has to reach for `.shared` or it crashes on an unwrapped nil.
