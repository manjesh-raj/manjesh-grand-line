## Straw Hat Pirates (Overview > Crew)

**Phases 1 and 2 of the captain-approved "Straw Hat Pirates" plan - a conversational AI crew.** Phase 1 (`fm/implement-straw-hat-pirates-phase1-luffy-fb98`) proved the surface with one persona and plain prose; phase 2 (`fm/implement-straw-hat-pirates-phase2-crew-6927`) added Nami, Chopper and Robin, the structured reply envelope that lets one call speak as several of them, and confirm cards for every proposed write. The plan of record is firstmate-side: `data/deepen-straw-hat-pirates-plan-explore-ja-3a/straw-hat-pirates-plan.html` (round 2 - the wire contract in `#contract`, the roster in `#roster`, milestones in `#milestones`) plus its round-1 predecessor `data/plan-straw-hat-pirates-ai-assistant-for-b7/`. **Read `#contract` and `#roster` before extending any of this.**

- **It is a tab on Overview, NOT a rail destination, and that is a captain override of the plan's own phase-1 line.** The plan says "new destination + rail icon"; the captain's approval says *"This will be inside overview section."* So `FleetController`'s tab strip is three tabs (`Overview | Log | Crew`), and the feature inherits that page's mount, theme observer and appearance forcing instead of repeating the five-touch destination recipe. `StrawHatViewSelfTest` asserts no rail destination named for it exists, so re-adding one has to be a deliberate edit.
- **Nine files, and the split is the point.** `StrawHatCrew.swift` (the `StrawHatMember` roster + the crew persona + the `claude`/working-dir resolvers), `StrawHatEnvelope.swift` (the reply schema, the closed `StrawHatProposalKind` enum and the three-rung parser - pure logic, no AppKit), `StrawHatContext.swift` (the bounded read-only snapshot + the turn envelope), `StrawHatProposalExecutor.swift` (the one place a proposal becomes a store write), `StrawHatRunner.swift` (the turn runner), `StrawHatChatView.swift` (transcript + composer), `StrawHatCrewViews.swift` (the portrait tile, the crew strip, the confirm card), `StrawHatPortraits.swift` (generated), `FleetController+Crew.swift` (the tab, its height derivation, the turn cycle). That last one is a separate file for GL-36's reason - `FleetController` already carries four unrelated features - with GL-36's consequence: **treat the `FleetController*.swift` family as private to itself**, since `private` is file-scoped and the crew members it reaches are `internal`.
- **`StrawHatRunner` is the ninth `ClaudeOneShot` caller and adds no new invocation shape.** `SRELeadRunner` is the sibling it copies: one non-interactive `claude -p ... --output-format json` per turn, persona re-sent via `--append-system-prompt` every time, `session_id` threaded back through `--resume`. **What it deliberately does not copy: `--mcp-config`, `--allowedTools` and `--permission-mode bypassPermissions`.** The crew still has no *tools* - phase 2 gives them *facts* (a pushed snapshot) and a way to *propose* a write, never a tool call - so an allowlist would still describe a capability that does not exist. Read-only MCP tools are phase 2.5; **writes stay out of MCP entirely and always will** - confirm cards are the only write path this feature will ever have.

### The reply envelope, and the three rungs (M2.1)

- **The contract is one fenced ```json block carrying a `sections` array**, each section a `speaker` (a roster raw value) plus `text`, optional `proposals` and an optional `followup`. `StrawHatCrew.persona` and `StrawHatEnvelope.parse` are a **hand-maintained wire contract with no compiler check between them** - the same seam `CodePreviewTheme.Key` documents for its own Swift/JS pair. `StrawHatSelfTest` asserts every `StrawHatProposalKind` raw value and every `StrawHatMember` raw value actually appears in the persona, so a rename cannot silently leave the model guessing at a vocabulary the app then refuses.
- **The ladder's invariant is that a reply is never dropped.** Rung 1 = validated envelope; rung 2 = the envelope parses but names a voice or kind the app does not know, so that section still *renders* (unattributed) and the offending proposal is **dropped, counted, and never executed**; rung 3 = no usable envelope, so the whole reply renders as one ordinary Luffy block (phase 1's behaviour). Rung 3 is reachable from *every* failure inside 1-2 (unparseable JSON, no `sections` key, an empty array, sections carrying nothing usable).
- **A section with an unknown speaker has its proposals refused too, not just its attribution.** Executing them would trust exactly the half of the envelope that has already proven unreliable. **This is easy to leave untested**: an injected regression removing that guard passed the whole suite, because the fixture's unaboard speaker also carried an *invented kind*, which the kind check refuses anyway. A rung-2 fixture must pair an unaboard speaker with a **valid** kind or the speaker guard is not exercised at all.
- **There is deliberately no brace-balanced last-resort scan** - `LogAnalyzerAI.decodeJSONObject` ends with one and is right to, because *its* reply is always meant to be JSON. Here most replies are prose, and Luffy explaining a config file legitimately contains `{ ... }`. **Testing this needs the one fixture a scan would genuinely destroy: an *unfenced* inline example whose widest brace span really is a valid envelope.** A weaker fixture (braces that do not form a usable envelope) passes whether or not the scan exists, because `parse`'s own `sections` check neutralises it - which an injected regression proved.
- **A reply that is genuinely *both* prose and envelope keeps both.** An early draft resolved that tension by dropping one side: keeping only the envelope silently discarded a "how does your reply format work?" explanation, while requiring the envelope to be the *entire* reply would drop every confirm card the moment a model prepended "Sure!" - the far more common violation, and one that takes a task the captain actually asked for with it. `StrawHatEnvelope.Extracted` carries the surrounding prose and `parse` emits it as unattributed sections in place, so neither trade has to be made.
- **Caps are stated, never silent** (`maxSections` 6, `maxProposalsPerSection` 8): these become permanent arranged subviews of the transcript stack, and a runaway list of confirm cards is worse than a truncated one because every card is a button that writes.

### Confirm cards, and the confirm-only guarantee (M2.2)

- **`StrawHatProposalKind` is the security mechanism**, exactly like `KubeCommand` and `ScheduledActionKind`: a `kind` the model invents is not a case, so it **cannot execute** - structurally, not by review. No default case, no string passthrough, no "run it if it looks safe" branch. Phase 2 ships three (`add_task`, `add_follow_up`, `create_runbook_draft`); the plan's phase-3 set is deliberately absent and the suite asserts it has not grown early, in the persona *and* in the enum.
- **Nothing writes until a real press**, and that is asserted by counting store contents before and after *parsing* rather than described in a header. `StrawHatProposalExecutor.execute` is reachable only from a `HelmButton` action; there is no path from `parse` to it.
- **Undo is real for one kind and deliberately absent for two**, per GL-33's rule that an undo must restore the value the caller already had. `DocsRunbookStore.deleteRunbook(id:)` exists and the created runbook's id is in hand, so a runbook draft gets a real `Toast.showUndo`. **`ShiftStore` has no delete for a task or a follow-up** (it has `add`/`update`/`setTaskCompleted`/`setFollowUpStatus`/`snooze` and nothing else), so those get a plain `Toast.show` - an "Undo" there could only pretend, which is the same test that keeps undo off an SSH key delete. Adding a real Shift delete is a genuine new capability across that store, its YAML layer, its git sync and its conflict resolver.
- **Nothing is invented on the way into a store.** A confirmed task takes `ShiftTask.fresh()`'s own defaults for priority and project, because the model was asked for neither. An unreadable `due` string leaves the record **undated** and the card says "couldn't read …" - a wrong due date presented as the captain's own choice is worse than none. `resolvedDue` tries strict ISO first, then `ShiftDateParser`, so "tomorrow" means the same thing whether the captain typed it or Nami proposed it.

### The context snapshot (M2.3)

- **This is the plan's *push* strategy** - a small snapshot injected into every turn, zero added latency because it rides the same single call. The *pull* alternative (read-only MCP tools) is phase 2.5 and is what scales this past the point injection can.
- **GL-14 is the rule that shapes it: unknown is never rendered as zero.** A health registry that has not reported is a stated `unavailable:` line, not a clean bill of health; an unreadable docs folder is stated rather than reported empty. Counts are exact and only *titles* are capped, with the overflow stated.
- **`capture` takes `healthStates` as an explicit parameter rather than the registry**, because `ServiceHealthRegistry` is a singleton with a `private init` (correctly - the app has one). Passing the registry would have left the GL-14 "nothing has reported yet" branch reachable only on a machine that happened to have reported nothing, which is the one branch most worth asserting. **Prefer a parameter over a test-only initializer on a production singleton.**
- **`StrawHatTurn.prompt` owns all three of a turn's labelled blocks** (`[CONTEXT]`, `[RECAP]`, `[MESSAGE]`). Phase 1 had the recap half in `StrawHatRunner`; putting the context beside it there would have meant two files agreeing on how a turn is framed, and a nested `[MESSAGE]` inside another the first time someone composed them.
- **A stale `--resume` is recovered with a recap, not by dropping the session**, and the recovered turn carries the *same* snapshot as the attempt it replaces. `WhiteboardDiagram` established retry-without-resume and it works there because that feature re-sends the whole board; a chat turn has no such second channel, so dropping `--resume` alone would lose the thread - exactly what the captain would notice.

### Portraits and the contributing glow (M2.4)

- **`StrawHatPortraits.swift` is generated by `native/Scripts/build-straw-hat-portraits.py`** from the plan artifact's own images (which live in firstmate's `data/`, outside this repo, and are not committed here). Base64, not an asset catalog or an SPM resource, for the reasons AGENTS.md's `CaptainIcon.swift` bullet records: `.xcassets` needs `actool`, absent from a CLT-only toolchain, and `Bundle.module` `fatalError`s when it cannot resolve a path this app's own `build_native_app.sh` never copies. **The originals are full scene images, so each is face-cropped by a hand-tuned box before downscaling** - a geometric centre crop reads as colour mush at 26pt. `--check` regenerates and diffs, so a reviewer can confirm the committed file matches its inputs. 96px = 3x the largest tile, ~115KB of base64 for all four against ~1.8MB for the originals.
- **The glow is state, so it lives where state changes.** A glow parked on the newest reply block would stop meaning anything by the second turn, so the reply block's portrait is *static* (an identity) and the glow lives on a **crew strip** above the transcript, lighting whoever contributed to the most recent reply. It is derived from `messages` rather than pushed in, so it cannot disagree with the transcript and a theme rebuild lands back on the same state. **While a turn is in flight nobody is lit** - the app does not know yet who will answer, and lighting a guess is exactly the plausible-but-wrong this feature must never do. An unattributed (rung-2) section lights nobody.
- **A crew member's tint is a `HelmTint`, not a `HelmDomainHue`, and never `.critical`.** A domain hue resolves to a uniform `.neutral` on all twelve non-Daylight palettes, which would collapse the per-crew differentiation M2.4 exists to provide; and `.critical` on a benign identity paints an alert bar on something that is not an alert (the trap AGENTS.md records for Dictation's history rows). The suite asserts both, plus that the four are distinct.
- **The pulse is gated on `HelmMotion.isReduced`**, which gets the lit end state instantly. `debugIsPulsing` reads the animation off the layer, because a gate that is read and then ignored is invisible from every other angle.
- **`strawHatWithoutImplicitAnimation` is deliberately NOT `HelmMotion.withoutImplicitAnimation`.** That helper is Reduce-Motion-*gated* on purpose, for the Daylight gradient cross-fade. A standalone ring layer's `frame` tracking a window resize has no such history and must be instant in both states.

### Four real layout defects a render caught, and the two AppKit traps behind them

Nothing was launched (the captain's packaged instance shares one bundle identity), so this used `bitmapImageRepForCachingDisplay`/`cacheDisplay` in a temporary env-gated probe, reverted before commit. All four are now pinned by geometry assertions in `StrawHatViewSelfTest`.

- **`HelmButton` does not clear `translatesAutoresizingMaskIntoConstraints`, and the confirm card added one to a plain `NSView` rather than a stack.** AppKit then synthesised **required** frame constraints from `HelmButton.init`'s own `sizeToFit()` and they silently beat every explicit constraint - pinning the action column to the button's 53pt and truncating the wider confirmed label to "✓ Adde…". Measured (column 53, label needed 93.5); no `NSLayoutConstraint` warning fires. **This is the documented trap, and the card is now the live example of it.**
- **The card's row is laid out with explicit constraints, not an `NSStackView`** - the same conclusion `ToolRowLayout` reached for the same three-column shape. Two of the three columns are views with **no intrinsic content size** (a plain `NSView` and a nested stack), where hugging priorities are a documented no-op (gotcha (12)), so `.fill` picked the action column as the stretch target: it resolved to **871pt of a 998pt card** while the text column sat at 67, wrapping a one-line title over three lines and truncating the detail beside a wide empty gap.
- **A low-priority `width == 0` collapse constraint must not *tie* with the view it is competing against.** At `.defaultLow` (250) it tied with the text column's own 250 hugging and the solver picked wrong; 499 breaks the tie and stays below `NSLayoutPriorityWindowSizeStayPut` (gotcha (13)). The required `>=` constraints still win, so the column never collapses below whichever child is showing.
- **A vertical stack's `.leading` alignment left-aligns children at their own intrinsic width** rather than stretching them, so a wrapping label with `.defaultLow` compression resistance collapses and wraps early. Each child is width-tied to the column.
- **A confirmed card keeps its detail line.** An early draft replaced it with the toast's own message, which both duplicated the toast a few points away and threw away the due date the card was showing. The confirmation is the done label's job; the detail's job is to say what the record is.

### Phase 2.5: the crew's read-only MCP tools

**`fm/implement-straw-hat-pirates-phase25-mcp-fb52` built M2.5a/b/c: four read-only MCP tools the crew calls themselves, on the same zero-API-key `claude` CLI path.** `native/Scripts/luffy_stores_mcp.py` (the server, stdlib-only, `sre_kubectl_mcp.py`'s shape), `Scripts/test_luffy_stores_mcp.py`, `StrawHatTools.swift` (the session + the pinned allowlist), `StrawHatMCPSelfTest.swift`. Read the server's module docstring and `StrawHatTools.swift`'s header before extending any of it.

- **The finding this phase rests on, and it corrects round 1 of the plan: real MCP tool use already works on the CLI path.** Round 1 filed native tool use as a Phase-4 luxury needing the direct Anthropic API - true of the Messages API, and wrong here, because `SRELeadRunner` has passed `--mcp-config`/`--strict-mcp-config`/`--allowedTools` on every turn since SRE Lead shipped. So the crew got genuine tool use with no API key, no new networking and no new credential.
- **`--permission-mode bypassPermissions` is NOT passed, and that is measured rather than reasoned.** `SRELeadRunner` passes it; this deliberately does not. With a throwaway MCP server and a real `claude -p` call: `--allowedTools "mcp__probe__magic_number"` **alone**, no `--permission-mode` at all, genuinely ran the tool (`permission_denials: []`, and the reply carried a value only the tool could supply); the same call with the allowlist pointed at a different name left `permission_denials` naming the attempted tool and **the server's handler never ran**. So the allowlist alone both permits and restricts, and `bypassPermissions` would be a strictly broader grant for nothing. `StrawHatMCPSelfTest` asserts the flag's *absence*, because a regression that adds it back renders identically.
- **Read-only holds at two layers that fail independently.** (1) The CLI: `--allowedTools` pinned to exactly four `mcp__luffy-stores__*` names - **no `Task`, no `TodoWrite`**, unlike `SRELead.allowedTools` (its persona asks for subagent delegation; the crew's does not). (2) The server: four handlers in one closed `_TOOLS` table, no fallthrough, and **no write primitive anywhere in the file** - asserted by walking the real AST for a write-mode `open`, `os.remove`/`rename`, `shutil`, `subprocess`. Those are different guarantees: "the tool list is read-only today" and "this file cannot write". Proposals + confirm cards remain the only write path, permanently.
- **`sre_kubectl_mcp.py` needs a verb allowlist because its tool takes a command to run; nothing here does.** Every tool reads a fixed location handed over in the environment (`LUFFY_SHIFT_DIR`/`LUFFY_DOCS_DIR`/`LUFFY_COMMANDS_DIR`/`LUFFY_HEALTH_SNAPSHOT`), so there is no injection surface to allowlist - the only caller-controlled value is a search string, compared against text already read from disk.
- **The server reads the app's YAML with a hand-written reader, and that is safe only because the app owns both ends.** It cannot `import yaml` (stdlib only, zero pip deps), and it does not need to: those files are the output of one serializer (`YamlBeautify.dump` over `ShiftYaml`/`CommandLibraryYaml`), which emits a tiny fully-known subset - **every key and every string value double-quoted**, `null` bare, `[]`/`{}` inline, two-space indent, block sequences of block mappings whose first line is inlined as `- "key": value`. `_read_app_yaml` reads exactly that and **raises on anything else** (flow collections, anchors, block scalars, multi-document, tabs), so a file written by something else degrades to a stated read failure rather than a plausible wrong answer.
- **That agreement is the one assumption here that could silently rot, so hand-written fixtures are explicitly not its test.** A change to the Swift serializer would leave the Python suite's own fixtures passing while the real store stopped being readable. `StrawHatMCPSelfTest.checkCrossLanguageStoreRead` is the authority: it writes a **real** `ShiftStore`, `DocsRunbookStore` and `CommandLibraryYaml.writeCommand`, then runs the **real** script as a real subprocess over stdio and asserts it reads back what Swift wrote (including a quote inside a value, the thing a naive reader gets wrong). Confirmed to catch the regression: disabling the inlined-first-line branch fails it with the real error, `active.yaml isn't in a format I can read`.
- **M2.5b, the health bridge: health is the one store a subprocess cannot open** (`ServiceHealthRegistry` is in-process, lock-guarded), so `StrawHatRunner` writes a per-turn JSON snapshot atomically (`.tmp` + rename, `SRELeadBridge`'s own discipline) and the tool reads it. **Built from the turn's own `StrawHatContextSnapshot`, not re-read from the registry** - so the pushed `[CONTEXT]` block and the pulled tool carry the same values and cannot disagree within one turn. GL-14 crosses the boundary explicitly as `available: false` + a reason: `StrawHatContextSnapshot.healthAvailable` exists because inferring it from an empty array plus a string match against `unavailable` would be a second, weaker encoding of something `capture` already knows.
- **Store roots are supplied by the caller, never resolved here** (`StrawHatStoreRoots`, built in `FleetController+Crew`). Duplicating three stores' env precedence would drift, and constructing a `CommandLibraryStore` for its `.root` is the mistake GL-24 fixed (that instance is shared precisely because two caching copies diverged) - so `AppShellController` hands `FleetController` the shared store's `root` URL and nothing more. Going through the real stores is also what makes a self-test's `FM_SHIFT_DIR` reach the tools with no extra wiring.
- **Losing the tools degrades, never breaks.** No `python3`, no script, an unwritable scratch dir or no roots at all → `setUpTools` returns `nil`, the turn runs with byte-for-byte phase 2's argv, and the pushed snapshot still tells the crew what it told them before.
- **`Scripts/test_*.py` now run as part of `run-all-tests.sh`** (and therefore CI's blocking `--ci` job, excluded from `--session-only`'s windowed subset), discovered by glob so a new one joins automatically and skipped with a note when `python3` is absent. Until this phase they ran only when somebody typed the command by hand, so `test_sre_kubectl_mcp.py`'s kubectl allowlist and this phase's write-refusal proof - the two most security-relevant assertions in the repo - had never once run in CI. Confirmed a failing Python suite genuinely exits 1.
- **Verified** by `swift build` (clean debug and release, zero warnings in this app's sources), the release binary confirmed to carry no `FM_RUN_*` strings or new probe symbols, and the full suite (129 Swift passed / 0 failed / 1 documented skip, plus 88 Python tests) - **without launching the app**, per the README's worktree rule (the captain's real instance was running throughout). **Thirteen injected regressions each reproduced by name** (7 Python, 6 Swift; scripted file copies, never `git stash`): a write-capable tool added to the dispatch table, a write-mode `open`, an unreadable store reported as empty, health's "not checked" flattened into available, a tool renamed out of sync with the Swift allowlist, a silent cap, the YAML reader guessing past unknown input, `Task`/`TodoWrite` added to the allowlist, `--permission-mode` added back, the inlined-first-line YAML branch removed, the per-turn health write dropped, the bridge claiming health regardless, and the MCP config pointed at the wrong root.
- **Live end-to-end verified through the real `claude` CLI** (a temporary env-gated headless probe, reverted before commit - safe because it exits before `NSApplication.shared`, unlike a GUI launch). Against seeded scratch stores, with a tool-call log from a shim wrapping the real handlers: Robin answered with an unguessable value present **only** in a runbook's *body* (which the pushed snapshot never carries - it carries titles) via a real `docs_search` full-body fetch; Luffy quoted a saved command's exact template and its `destructive` risk via a real `command_search`; and asked to read `/etc/hosts` the crew correctly reported it cannot read files, confirming the allowlist blocks everything outside the four tools.

### Phase 3: the rest of the roster, and the write/handoff split

**`fm/implement-straw-hat-pirates-phase3-roster-22af` built M3.1-M3.3 - Zoro, Usopp and Franky, their three proposal kinds, the two navigation handoffs, and "Ask your crew" on Overview's dashboard tab.** The roster is now the plan's full v1 seven; Brook still needs no code, Jinbe is still deferred, and **Sanji's role is still an open captain decision** (no persona clause mentions the Morning Briefing, and `checkPersona` asserts that).

- **`StrawHatProposalKind.isNavigation` is the load-bearing addition, and it decides what the captain has to *do* with a proposal.** Six kinds write and render as a `StrawHatConfirmCard` behind a confirm button; `open_sre_lead`/`open_destination` write nothing and render as a `StrawHatHandoffRow` link that runs on the click itself, because a confirm button in front of a link would teach the captain that a confirm press sometimes means "this changes nothing" - which devalues every *other* confirm press. `StrawHatSelfTest` asserts **both sides as literal lists**: a kind that writes somewhere and is filed as navigation would be an unconfirmed store write that renders, works and looks right, and no generic consistency check could see it.
- **Three payloads are resolved to a real enum *at parse time*, never carried as a string** (`ScheduledActionKind`, `RailDestination`, and a strict cadence grammar). A model that invents an automation or a destination therefore produces **no proposal at all** - the same structural refusal an invented `kind` gets, one level in - and the executor's `switch` has nothing left to validate. The cadence parser is deliberately strict rather than reusing `ShiftDateParser`: a date and a *recurrence* are different things, and a job firing at the wrong hour every day forever is worse than a refused draft.
- **`StrawHatHandoff.allowedDestinations` is an allowlist narrower than `RailDestination`, and the exclusions are the point.** A link row runs on one click with no confirmation, so "which pages may a model put a one-click link to" is a real question: `.poneglyph`/`.vault` (a crew member linking to a credential store is the phishing-shaped move to make structurally impossible), `.settings`/`.bootstrap`/`.updates`/`.automation`/`.githubSync` (machine configuration, not a conversational handoff), `.dictation`, and `.overview`/`.homeCanvas` (a link to the page the chat is on is a dead link).
- **`open_sre_lead` deliberately never connects a host that is not already connected**, and that restraint is what keeps "a handoff writes nothing, so it needs no confirm card" literally true. Forking a real `/usr/bin/ssh` - possibly prompting for Touch ID to materialise a key - is not navigation. A host with no live session lands on Hosts, where Connect is the captain's own click. **The app resolves *which* host, never the crew** (they cannot see hosts at all): `AppShellController.openSRELeadForCrew` matches a hint against the live-session registry, exact label first then a unique substring, and **refuses to choose between two** rather than guessing - the same conservative shape `KubeContextParser`/`MultiHostSend` already take.
- **`save_command_draft` is the one kind with a second gate, and it is not optional.** A stored `CommandRiskLevel` is a record of a *human* having read the text, and every later sink (the detail pane, `⌘K`, F9's fan-out) reads that stored level instead of asking again - which is exactly how audit #2 §5.3 found a `readOnly` command a model had rewritten reaching a terminal unconfirmed. So a crew-authored command goes through `confirmAIAuthored(… intent: .saveTemplate)` and its stored risk is `heuristicRisk(of:)` (which never answers `.readOnly`), never anything the model said - `StrawHatProposal` carries no risk field at all. A multi-line command is refused at *parse* time too, since only its first line would be visible in that alert. `commitCommandDraft` is split from the gate the way `CommandLibraryPageView` splits its own, and a source guard asserts it has exactly one production caller which confirms first.
- **`add_sticky`/`create_schedule_draft` invent nothing.** A note's position/colour/tilt are the app's, through the same `StickyBoardMetrics.cascadeOrigin(index:)` the board's own "New Note" button uses (extracted out of `StickyBoardController.nextPosition()` for this, so a proposed note lands in the next free slot rather than stacked at the origin), and a confirmed note is flushed to disk immediately rather than waiting on the board's 1.5s write debounce. A schedule takes `.changeOnly` and `isEnabled` exactly as the Schedule Editor's own Save does. **Four of the six kinds now get a real GL-33 undo** (runbook, sticky, schedule, command); `add_task`/`add_follow_up` still get a plain toast, because `ShiftStore` has no delete for either.

### The card moved off Home, onto Command (`fm/grandline-home-card-reorg`)

**The captain's third placement ask for this card, and the first one that gives it a space of its own.**
He reviewed the live Home page and asked for the crew card on the Command page instead.
The two earlier asks recorded above were both Overview-only orderings - beside the briefing and the fleet board, then last in the Overview grid.
This one is a different kind of move: the card is not being reordered on Home, it is leaving Home.

- **The mechanism is two lines in `DaylightSpace.swift`, and neither is new.**
  `DaylightModule.strawHat.space` goes from `nil` to `.command`, and `.strawHat` joins the `appearsOnOverview` exclude list.
  That is the same pair `.tasks`, `.hosts` and every other spaced module already carries - a module with a real space stops being an Overview-only card, and `isVisible(in:)` needs no change at all.
  The card itself, its destination, its artwork and its subtitle are untouched.

- **The declaration moved with it, to the end of the Command group.**
  `canvasOrder` is `allCases`, so declaration order is render order.
  Leaving `case strawHat` at the very end of the enum would have rendered identically *today* - it is last either way - but only by accident, and the next module appended below it would have silently pushed the crew card ahead of its own.
  Appending it to the group is the precedent `.commandLibrary` and `.poneglyph` both already set in this file, and it keeps the Command canvas reading Tasks / Merge queue / Console / DevOps Commands / Straw Hat Pirates.

- **The ordering assertion moved rather than being deleted.**
  `DaylightModuleSelfTest` used to assert `visibleModulesForTests.last == .strawHat` on Overview; it now asserts the same property on Command.
  Worth knowing about its limits, because this is exactly the "a check that cannot fail" shape: reverting the declaration to the end of the enum does **not** fail it, since last-in-group and last-in-enum coincide right now.
  Moving the declaration into the *middle* of the group does fail it, by name, which is what was actually measured - so the check discriminates real placement, it just cannot distinguish deliberate placement from a coincidence that happens to agree.

- **`StrawHatViewSelfTest`'s placement assertions were inverted a second time, by the same rule the file already records.**
  They had become a record of the old behaviour.
  `checkOwnCardAndDestination` now asserts the card does *not* render on Home and *does* render on Command, and the two real-canvas render cases select `.command` before reading the cards.
  `checkOverviewSubtitleIsFixed` was renamed `checkCanvasSubtitleIsFixed`, since its name was the last thing still claiming Overview.

- **Console and Schedules came off Home in the same pass, and their `space` was deliberately not touched.**
  Both were part of the original trim's "operational pulse" set; the captain has since found both redundant, because each already carries a card one pill away (Console on Command, Schedules on Operations).
  This is the presentation-only opt-out `appearsOnOverview` exists for - both still render on their own space's canvas, and the trim check's own "every trimmed module is still reachable on its own space" loop proves it.
  Home is five cards now: Morning briefing, Claude, Fleet, Merge queue, Health.
