## The body-width tie repairs itself on every layout pass, not only on a resize

**`fm/grand-line-body-width-selfheal-layout-fix` closed the *persistence* half of gotcha (14)'s bug class, which is the half that made it unusable.** A scout investigation (`data/grand-line-stray-window-glitch-scout/report.md`, "BUG B") captured the captain's own window live: the window server held a **1512pt-wide backing surface** while AppKit had only laid out and drawn ~670pt of it, so the remaining ~842pt was undrawn black and his UI was clipped mid-glyph. He had to quit and reopen to clear it.

- **The repair was already correct; its trigger set was too narrow, and that is the whole finding.** `AppShellController.reassertBodyContainerWidthTie()` had exactly two call sites - `loadView` and `NSWindow.didResizeNotification` - which its own comment stated as a limitation in as many words ("can't survive past the very next resize"). So the moment the tie broke or the frame went stale for any *other* reason, the window stayed visibly broken until the captain happened to resize it or restart. Nothing else re-derived it: not a navigation, a theme change, a font-scale change, a full-screen transition or an ordinary layout pass. **AGENTS.md records four separate destinations that each shipped a width floor reaching this same symptom** (gotcha (13)/(14), `fm/grandline-body-width-regression-recur`, `fm/grandline-f9-detail-row-width-cap`, `fm/grandline-bootstrap-window-shrink`), each fixed individually - a fifth is expected, and this makes the fifth self-healing rather than needing its own task.
- **The repair rides `ChromeFusionRootView.layout()` now, beside the traffic-light reposition - the same too-narrow-trigger shape, already solved one layer up.** `WindowChromeFusion.swift`'s header records that a manual reposition is undone by any forced `layoutSubtreeIfNeeded()` and that re-applying from the content view's own `layout()` is what covers it; `bodyContainer` never got that treatment. **A layout pass is when a constraint conflict actually resolves**, so repairing from there catches it at the moment it happens. Both original call sites stay as belt-and-braces (launch covers the window's still-off-screen launch-time resizes; a resize can occur with no layout pass after it).
- **`view.needsLayout = true` before `view.layoutSubtreeIfNeeded()` is load-bearing, and omitting it broke a test that had passed for two years.** `layoutSubtreeIfNeeded()` only invokes `layout()` if something already marked the view dirty (the same AppKit behaviour `ChromeFusionRootView`'s own title-KVO note records). Reactivating a constraint *does* mark things dirty, so the resize observer used to work by accident; once the repair also runs from inside a layout pass, that earlier call **consumes the dirty flag** and the observer's own call moments later becomes a silent no-op. Measured: without the line, `widthSelfHealsAfterATieIsSilentlyBroken` - which exercises only the resize path and passed before this task - fails with the body frozen at its pre-break 1512. **Adding a second caller to a method that ends in `layoutSubtreeIfNeeded()` can break the first caller; mark dirty explicitly rather than relying on a side effect.**
- **The re-entrancy guard is honest defence, not a proven necessity - measured, removing it neither hangs nor recurses in the suite.** It is kept because the one case it protects is exactly the case the whole repair exists for: a required-constraint conflict the resolve genuinely cannot satisfy leaves the width stale after the inner pass, so an unguarded second entry would force another pass, and another - spinning the main thread. A visibly-wrong window is a far better failure than a hung app.
- **It does not reintroduce GL-20's resize-frame cost, and that was measured rather than argued.** GL-20 had deliberately gated this method behind a cheap staleness check precisely because an unconditional resolve on every resize frame defeats every child controller's own visibility gate. A temporary counter (reverted before commit) across ten idle layout passes on a settled window: ten entries, **zero** forced layout passes - the gate returns early on all of them, so the per-pass cost is two frame reads and two `isActive` checks. Only a genuine break or a genuinely stale frame pays for a resolve. **A probe that counts "repairs" must increment *after* the `guard needsLayout`** - placing it before counts entries instead, which first read as a 10-out-of-10 oscillation and sent this investigation chasing a regression that was not there.
- **A frame assertion cannot test this, and finding out why is the transferable part.** The obvious regression test - break the tie, make the frame stale, drive a layout pass - cannot be written: **there is no way to make `bodyContainer`'s frame genuinely stale without resizing the window, and resizing the window posts the very notification the case exists to do without.** Measured: setting the *content view's* frame directly leaves `bounds.width` reporting the new value while Auto Layout's own engine still solves against the window's real width, so `bodyContainer` correctly resolves to the window's width and the assertion proves nothing about which trigger repaired it (a first draft failed for exactly this reason and read like a broken fix). The honest discriminator is **whether the tie is active again** after a layout pass, which is what `AppShellController.bodyWidthTieIsActiveForTests` exists for; the break is asserted before the pass so it cannot pass vacuously, and a closing resize proves the reactivated tie genuinely *binds* rather than only that a flag flipped.
- **The `AppLog.ui.error` reactivation diagnostic is reachable for the first time** - the scout report found `log show` returned 0 lines precisely because the repair never ran. Confirmed by a temporary `print` beside each of the two log calls (reverted before commit): it fires 4 times across the two self-heal cases. Note `log show` yields nothing at all for the **unbundled** `.build/debug` binary, so a probe is the only way to confirm reachability from a self-test - do not read an empty `log show` as evidence the branch did not run.
- **Verified** by `swift build` (clean debug and release, zero warnings in this app's sources), the release binary confirmed to carry no `FM_RUN_*` strings or either new test hook, and `FM_RUN_APP_SHELL_BODY_WIDTH_TESTS` / `FM_RUN_WINDOW_CHROME_FUSION_TESTS` (the latter because the fix shares the traffic lights' own `layout()` override) - **without launching the app**, per the README's worktree rule. **Three injected regressions each reproduced by name** (scripted file copies, never `git stash`): the `onLayout` call removed (the new case fails while the resize case still passes - proof the two guard genuinely different triggers), the `needsLayout` line removed (the *resize* case fails - the inverse split), and the re-entrancy guard removed (no failure, which is what makes this entry's claim about it honest rather than overstated).

## `contentView` is NOT kept in sync with the window, and that is what made the black region come back

**`fm/grand-line-window-glitch-fix`: the captain's black-region glitch recurred *after* #412's self-heal shipped, and the reason is one sentence of inherited-but-false reasoning.** Read `AppShellController.windowContentWidthIsStale()`'s own doc comment before touching the repair.

- **The live signature, measured read-only on his own running app while it was glitched** (no second instance launched, no interaction - `CGWindowListCopyWindowInfo` plus window-scoped `screencapture -l`): the window was **1512pt** wide (its titlebar window reported exactly that, and its backing surface measured 1512pt) while its **content window reported 1064pt**, with content drawn only to 1063pt - **449pt of undrawn black**. His own screenshot cuts the *top bar* at the same x, which is the tell that identifies this as `contentView` rather than any one page mis-laying-out. His log carried **zero** reactivation lines. It cleared when the window was resized, exactly as before.
- **The false assumption: "`root` is this window's own `contentView`, which the OS keeps in sync with the window unconditionally - confirmed live".** That is stated in `reassertBodyContainerWidthTie`'s own doc comment and inherited from the scout report behind #412. It is wrong, and it is load-bearing: `bodyContainerWidthIsStale()` measures `bodyContainer` against `root`, so when **`root` is itself the thing that drifted** the check answers *no* and the repair returns having found nothing wrong. Reproduced exactly - window 1512 / `contentView` 1064, at which point `bodyContainer` is *correctly* 1064. Ordinary layout passes do not fix it; **only a window resize does**, which is precisely the captain's "I had to resize or restart".
- **So the repair needs two independent references, not one.** `windowContentWidthIsStale()` measures `root` against the *window* (`window.contentRect(forFrameRect:)`) - the one geometry AppKit genuinely owns - and is checked **before** the body-vs-root test, because that test is blind while `root` is wrong. Width only, deliberately: every measurement of this bug is about width, and repairing height too would widen a narrowly-understood fix into geometry it never exercised.
- **A second, independently load-bearing half: `view.needsLayout = true` is SWALLOWED when set from inside that view's own `layout()`.** Measured with a standalone probe, not assumed - a view that re-marks itself dirty from inside `layout()` and asks for five further passes gets **zero**, while the same mark made *outside* `layout()` is honoured every time (3 mark+force cycles -> 3 passes), and a forced pass with no mark is a no-op. So #412's "marking the view dirty schedules the very next pass, which is where the repair lands" is **not true**, and from the layout-pass trigger - the repair's only *continuous* trigger - the flag was discarded and nothing further happened. A nested `layoutSubtreeIfNeeded()` is not the answer (AppKit forbids it and traps on macOS 14), so `scheduleDeferredRepair()` queues the repair for the next run loop turn, where forcing one is legal.
- **That deferral is bounded on purpose** (`maxDeferredRepairsSinceHealthy`, 4, reset on every pass that finds nothing wrong). An unfixable drift would otherwise re-queue at run loop cadence and spin the main thread - the existing re-entrancy guard's own reasoning applies verbatim: **a visibly-wrong window is a far better failure than a hung app.**
- **This is NOT the width-floor class the #412 writeup predicted would recur**, and that was ruled out by measurement before the real cause was found: all 27 destinations were swept at his exact theme (`catppuccin-mocha`), font size (18), window size and **against a copy of his real store data**, including letting async content settle and then zooming - every one holds 1512. A page shipping a width floor is a real class (four prior instances), it is simply not this.
- **Why the existing suite was blind, and it is the reusable half.** `widthSelfHealsAfterATieIsSilentlyBroken` and `widthSelfHealsOnALayoutPassWithNoResize` both start by *deactivating* the tie and both then prove binding via a `setFrame` - i.e. via the resize trigger that has always worked. Neither can see a drift that leaves the tie active. `widthSelfHealsWhenContentViewDriftsFromTheWindow` is the new case; it drives **ordinary run loop turns only** and carries a vacuity guard that the tie is still **active**, so it cannot quietly degrade into re-testing the broken-tie scenario.
- **All three injected regressions reproduced by name**, with distinct signatures that prove each half is independently load-bearing: the root-vs-window check removed (`contentView stayed 1064.0 wide against a 1512.0-wide window` - the captain's own numbers, while every *other* case still passed), the deferred repair removed (`contentView resynced to 1512.0 but bodyContainer stayed 1064.0`), and the `insideLayoutPass` guard removed (which also fails `theWidthRepairNeverForcesANestedLayoutPass` by name). **A `#if FM_SELFTESTS` sentinel that is unreachable by construction must be kept when a test asserts it stayed 0** - deleting the increment makes that assertion vacuous, which nearly shipped here.
- **Verified** by `swift build` (clean debug and release, zero warnings in this app's sources), the release binary confirmed to carry no `FM_RUN_*` strings, and the full `./Scripts/run-all-tests.sh` run (155 passed / 0 failed / 1 documented skip, `fm.themeID` unchanged) - **without launching the app**, per the README's worktree rule: the captain's real packaged instance was running throughout and shares this bundle identity.

**`fm/grand-line-selftest-window-leak-followup` closed the scout report's "BUG A" (`data/grand-line-stray-window-glitch-scout/report.md`): the captain's stray dark panel showing three grey traffic lights was a *sibling crewmate's* self-test window, real and clickable, on his own display.** ~20 suites parked a window at `x: -20_000` and this file documented that as invisible. It was not. `SelfTests/OffScreenProbeWindow.swift` is the one place a window-backed suite gets an `NSWindow` from now; read its header before touching any of it.

- **Three separate mechanisms had to be closed, and the report names only one.** They are independent - fixing any one alone still leaks.
  - **`NSWindow.init(contentRect:)` discards the origin you give it.** A window *asked* for `x: -20_000` is placed by AppKit's own initial-placement logic at **`x: 160`, fully on screen**, before anything is ordered in - and **`constrainFrameRect` does not prevent this**, measured. So the factory takes a **size** and parks afterwards; accepting a rect would invite the next caller to believe a number that does nothing.
  - **`orderFront` re-constrains an already-parked window** onto the bottom-left corner. This is the half `constrainFrameRect` fixes, and it is load-bearing - measured side by side, a plain `NSWindow` snapped to `(0, 0)` while the subclass held.
  - **A resize undoes the parking**, which only shows up once the window genuinely starts off-screen. The suites resize constantly and nearly every `setFrame` they issue passes `x: 0` (`AppShellBodyWidthSelfTest` alone sweeps a dozen widths per case). The subclass therefore **pins its origin** on every geometry mutation rather than being positioned once. Measured: `setFrame(_:display:)` is also the funnel for `setContentSize` **and for `zoom(nil)`** - so a suite that clicks the real zoom button still observes a real size change and no longer flashes a maximised window onto the display - while `setFrameOrigin` and `setFrameTopLeftPoint` reposition on their own and need their own overrides.
- **"Just stop calling `orderFront`" is the wrong fix, and the report says so.** A never-ordered window is invisible and still gets a real `windowNumber`, but it is `isVisible == false`, which `KubeContextBridgeSelfTest` and `TerminalDisplayGatingSelfTest` read deliberately and which SwiftTerm needs before it draws anything. Off-screen-but-visible is the property, which is why no suite needed a behavioural change.
- **The guard sits on `order(_:relativeTo:)`** - the funnel every `orderFront`/`makeKeyAndOrderFront` goes through - and `exit(1)`s naming the creating file:line, so a regression fails the suite's own run instead of leaking silently. Deliberately **not** a check inside `constrainFrameRect`: that method is asked about frames the window is never given. `E2ETestingPolicySelfTest.checkSuitesUseTheOffScreenProbeFactory` is the source half, banning a hand-rolled `NSWindow(contentRect:` anywhere in `SelfTests/` (one per-site `// OffScreenProbe-exempt:` marker exists, for the control case that must observe the unfixed shape).
- **`E2ETestingPolicySelfTest.mountsAWindow` keyed on the `NSWindow(` marker**, which this migration removes from every suite - so it now matches `OffScreenProbe.window(` too. **A migration that deletes a token another guard greps for silently disarms that guard**; check for one before a sweeping rename.
- **A `setFrame` in these suites is usually a *resize*, not parking - do not "clean up" one without reading what it measures.** Removing `WindowChromeFusionSelfTest.makeWindow`'s apparently-redundant `setFrame(x: -20_000, …)` broke `test_a1FusionReclaimsHeight`: it was setting the **window frame** to 720, so the stock window's content came out 32pt shorter than the fused one's, which is the entire measurement. Passing a *content* rect of the same height made both 720 and the reclaimed height 0.
- **Two CI-only failures followed, and both are worth carrying forward more than the fix itself.**
  - **`AppShellController.reassertBodyContainerWidthTie()` called `layoutSubtreeIfNeeded()` from inside `ChromeFusionRootView.layout()`, which AppKit forbids** - "It's not legal to call -layoutSubtreeIfNeeded on a view which is already being laid out. If you are implementing the view's -layout method, you can call -[super layout] instead." **On macOS 26 that logs; on the macos-14 runner it traps** (`Trace/BPT trap: 5`, exit 133), which is why `AppShellBodyWidthSelfTest` died on CI while passing locally. It is **pre-existing on `main`** - measured with a temporary depth counter, `main`'s own behaviour forces the same **12** nested passes - so this was a latent crash the off-screen change merely made more likely to fire, not one it introduced. `reassertBodyContainerWidthTie(insideLayoutPass:)` now marks the view dirty and returns when it is already inside a pass (AppKit schedules the next one, which is where the repair lands) and forces only from the launch and resize callers. `AppShellBodyWidthSelfTest.theWidthRepairNeverForcesANestedLayoutPass` is the guard, and it carries **two** counters on purpose: `repairsInsideALayoutPassForTests` must be non-zero or "it forced none" is vacuous, and `nestedLayoutForcingsForTests` must be zero. Confirmed to catch the regression by name.
  - **A real `NSDraggingSession` cannot be driven in a window the window server ignores.** `ShiftBoardViews.swift:334` is the app's only `beginDraggingSession` call and `ShiftBoardViewSelfTest` is the only suite that drives it; it starts a session and never sends a matching mouse-up, so off-screen the session sits waiting and the next `performClick` blocks behind it in `NSCoreDragManager._dragUntilMouseUp`. Measured over five runs each: **1-3s on screen, 4-25s off it** - unbounded enough to hit CI's 300s per-suite bound twice, against ~4s on `main`. `OffScreenProbe.window(needsWindowServerMouse:)` is that one suite's opt-out: on-screen geometry, `alphaValue = 0` so nothing is drawn. **`ignoresMouseEvents` must not be set with it** - measured, that reproduces the hang, being the same "the window server will not deliver mouse events here" condition by another name - and a matching `leftMouseUp` does not shorten it either.
- **The origin forcing lives in `constrainFrameRect`, never in a `setFrame` override**, and that is the narrower mechanism rather than a correctness fix: that one hook is consulted by `setFrame`, `setFrameOrigin`, `setFrameTopLeftPoint`, `setContentSize`, `zoom(nil)` and `orderFront` alike, so nothing else needs overriding, and AppKit uses what it returns without re-deriving. Construction is the only path that skips it, which is what the factory's explicit park covers.
- **Two measurement traps this cost real time to, both worth recognising.** A `cd` that fails in a compound command leaves the *previous* working directory in place, so `$(… ./.build/debug/FirstmateCockpit …)` silently produced empty output and a grep count of **0** - which read exactly like "the fix works". **Check the binary exists before trusting a zero.** And the captain's own mouse genuinely does wedge `performClick` on this machine (this file's own `FM_RUN_SHIFT_BOARD_VIEW_TESTS` note), which masked a real regression as the known flake for several rounds - an A/B has to show the *baseline* passing, not just the change failing.
- **Verified by pid-attributed `CGWindowListCopyWindowInfo` sampling** (read-only, no pixels; `optionAll` + `kCGWindowIsOnscreen`, since an off-screen window is absent from `optionOnScreenOnly`), running each suite as a child so a **sibling lane's concurrent run cannot be mistaken for this one's** - which matters, because one was running unfixed code throughout and its windows do appear in an unattributed sweep. Ten window-backed suites: **0 on-screen windows, with 2-42 real windows observed each** (so the check is not vacuous). **The negative control is what makes that mean anything**: with the overrides removed, every one of the six suites retested leaked, reproducing the scout's own live geometry - `TerminalDisplayGatingSelfTest` at `(0, 0, 700, 432)` and `SessionSwitcherSelfTest` at `(0, 0, 900, 232)`, bottom-left.
- **The one on-screen window any suite still produces is AppKit's own, not one of ours**: `CGWindowListCopyWindowInfo` reports a full-screen `layer=500` window during `SHIFT_BOARD`, and 500 is `CGWindowLevelForKey(.draggingWindow)` - the drag manager's overlay, created by the `beginDraggingSession` the app makes identically on `main`. Every probe window is `layer=0`.
- **`NSApp` is nil until `NSApplication.shared` is touched** - an `NSApp.setActivationPolicy` as a probe's first statement is a silent `SIGTRAP` with no output at all. This file already records it; it cost a build here anyway.

## The black band above the top bar is the menu-bar strip macOS reserves in full screen, and it is filled from outside the window

**`fm/grandline-settings-black-band-real-fix`: the captain reported "a solid black horizontal band spanning the full width at the very top of the window, above the toolbar row" three times.** Two Settings-page rounds (#458, #461) each claimed to have fixed it and neither had touched it. It is not on the Settings page, it is not painted by this app, and it is on every page.

- **What it actually is, measured on the captain's own running instance** (read-only - `CGWindowListCopyWindowInfo` plus window-scoped `screencapture -l`, no second instance launched, no interaction): his window is in a full-screen Space, and macOS hands it **`1512x949` of a `1512x982` display**, keeping the top **33pt** for the menu bar. Two windows live in that strip - the Window Server's own `Menubar` at layer 24, and the app's full-screen titlebar container at layer 26. Captured individually: the app's is **fully transparent, alpha 0 on every pixel**, and the menu bar's is **opaque `(0, 0, 0, 255)` on every pixel**. The band is the menu bar's own window painted black because the captain has the menu bar set to auto-hide (`defaults read NSGlobalDomain _HIHideMenuBar` = 1). The captured main window's own top row is the theme's chrome, not black - the app's half was never wrong.
- **It is macOS, not this app, and that was settled with a control rather than by reasoning.** A 40-line stock AppKit app written for this task gets the identical `1512x949` full-screen frame and the identical 33pt black strip above its own flat teal content, in three variants: plain `.titled`; `.fullSizeContentView` plus a transparent title-less titlebar (this app's own shape); and one whose delegate returns `[.fullScreen, .autoHideMenuBar, .autoHideDock, .autoHideToolbar]` from `window(_:willUseFullScreenPresentationOptions:)`. Adding `NSPrefersDisplaySafeAreaCompatibilityMode = false` to the bundle's plist changes nothing either. **A full-screen window cannot reach that strip** - do not spend another round trying to make it.
- **So the strip is filled from outside the window.** `FullScreenMenuBarFill.swift` places a borderless non-activating panel over it, painted with the active theme's page ground, only while the main window is genuinely in full screen. The app's ground then runs to the physical top of the display, which is what A1's "the floating bar becomes the top edge" was always supposed to look like.
- **The window level is the whole fix, and it decides two separate things.** The fill must be **above** the opaque menu-bar window (24) to be seen at all - a first attempt at 23 painted the correct colour and changed nothing on screen. And AppKit silently constrains a window out of the menu bar's strip below level 25: measured, the same proposal (`y 949...982`) comes back `y 917...949` from a `.titled` window at level 0, a borderless window at level 0 **and** a borderless panel at 23, and unchanged only from a panel at 25. So the level-23 attempt was invisible *and* one strip-height too low, and both symptoms read as "the panel never appeared".
- **Sitting over the menu bar's window is only acceptable because the fill steps aside.** A tracking area on the panel's own content view makes it transparent *and* `ignoresMouseEvents` on `mouseEntered`, so a revealed menu bar both shows and clicks; a 0.2s poll that exists only while the pointer is inside the strip restores it on the way out, so the idle cost is zero (GL-13). Confirmed live on a launched probe app: pointer parked mid-screen, the strip is the page ground; pointer warped to the top, the fill yields and the system's own titlebar reveal takes over; pointer back down, the fill returns.
- **Why two rounds of investigation missed it, which is the transferable part.** Both rendered the Settings page **off-screen** and pixel-diffed it. An off-screen render has no full-screen Space, no menu bar window and no reserved strip, so it *structurally cannot* reproduce anything in that region - a clean diff there was never evidence about the real window. #461's own writeup concluded the black pixels were "not app-painted", which was correct and was read as "not real". **For any defect in the title-bar-adjacent or menu-bar-adjacent region, an off-screen probe is not a substitute for a real window; enumerate the real window list and capture the individual windows.** Two cheap commands would have ended either round in minutes: `CGWindowListCopyWindowInfo` (which window owns the strip, and at what layer) and `screencapture -o -l <windowID>` (what that one window actually paints, alpha included).
- **`screencapture` works from an agent shell on this machine now**, which AGENTS.md's "Verifying native UI bugs without a real screenshot" section says it does not. Screen Recording has since been granted to the shell, so real screenshots and real per-window captures are available; the env-gated-instrumentation substitute is still the right tool for geometry, but it is no longer the only one. `screencapture -x` (whole screen) and `screencapture -x -o -l <id>` (one window, alpha preserved) both return real content.
- **Verified** by `swift build`, `FM_RUN_FULL_SCREEN_MENU_BAR_FILL_TESTS` and the full `./Scripts/run-all-tests.sh`, plus the live probe-app captures above in Dusk and Daylight (before: `(0,0,0)` for the top 33pt; after: the theme's own ground, `(25,26,31)` and `(244,242,235)` respectively, from row 0 down to the bar). **Three injected regressions reproduced by name** (file copies, never `git stash`): the level lowered to 23 (fails both the level check and the constraining check), the hover yield unhooked (fails the yield check twice), and the non-full-screen early return removed (fails the "no fill outside full screen" check). A fourth candidate - an explicit `constrainFrameRect` override - was **removed rather than kept**: measured, level 25 already exempts the panel, so the override could not fail and this file's own "a check that cannot fail is worse than no check" applies to the code as well as the test.
- **Not verified**: the live half was measured on the *probe* app (`Scripts/build-probe-app.sh`), never by driving the captain's own instance, and the probe is `LSUIElement` so it has no menu bar of its own to reveal - the reveal was confirmed by the system titlebar sliding down, not by seeing menu titles. The Settings page specifically was not captured under the fix: navigating the probe to Settings blocks on a Keychain ACL prompt (`GoogleOAuthClientStore.read`) because each probe build is a new ad-hoc signature. Neither gap is about the band, which is page-independent by construction.
