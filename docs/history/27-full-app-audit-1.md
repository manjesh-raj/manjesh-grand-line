## Overview/Console/Hosts audit fixes (`fm/cockpit-fix-core-audit`)

A QA scout audit (`data/cockpit-audit-core/report.md`) found 11 issues across the Overview, Console, and Hosts rail destinations; this task fixed all of them. Two open product questions the report registered as captain decisions were resolved as: Console tabs adopt the Tools page's numbered-disambiguation naming convention, and IPv6 quick-connect is fixed rather than left broken.

- **`FleetNotifier.start()`** (`FleetNotifier.swift`) now carries the same `guard Bundle.main.bundleIdentifier != nil else { return }` that `UpdatesController`/`ShiftNotifications` already had - it was the one `UNUserNotificationCenter` caller missing it, and crashed the bare dev binary outright once "Bell & notifications" had ever been turned on from the packaged app.
- **`OpenPRsSource.fetch()`** (`FleetData.swift`) now scans project clones concurrently (bounded to 6 in flight via a semaphore + concurrent queue) instead of one at a time - measured ~9.2-10.7s sequential down to ~2.8-4.1s against this machine's real 14 clones. `FleetController.refresh()` also renders `snapshot()`'s fast fields immediately, showing a loading placeholder in "Ready to merge" rather than blocking the whole page on the PR fetch too.
- **`FleetDataSource.crewState`** (and, until E1 deleted it, `FirstmateBackend`'s own backend probes) now enforce a real timeout (15s) on their subprocess calls via a `terminationHandler` + `DispatchSemaphore` watchdog (killing the process on timeout where the caller owns it) - the old code's timeout was either a stale comment describing a bound that didn't exist, or no bound at all on a main-thread call.
- **`HostStore.load()`** backs up an undecodable `hosts.json` to `hosts.json.corrupt-<timestamp>` before ever calling `persist()` again, and exposes `loadFailureBackupPath` so `AppDelegate` can toast a one-time warning - previously a corrupted file was silently discarded and then permanently overwritten by the next save.
- **Host/port-forwarding validation** (`HostEditorController.save()`, `PortForwardingController.save()`) now range-checks every port (1-65535), requires a non-empty destination host for Local/Remote forwarding rules, and warns on a duplicate host label at save time (`HostEditorController` takes an `existingLabels` set from `AppDelegate.presentHostEditor`) - all previously silent gaps that only failed later, opaquely, at `ssh` connect time.
- **`HostCatalog.parseQuickConnect`** (`Host.swift`) now handles IPv6 literals correctly: bracket notation (`[::1]:2222`) for an explicit port, and a bare unbracketed literal (`::1`, `2001:db8::1`, more than one colon) is treated as the whole host at the default port instead of being corrupted by splitting on the last colon.
- **Console tab naming** (`TabModel.kindIdentity` + `ConsoleController.numberedName(for:)`) ports the Tools page's convention: bare kind name for the first open tab of a kind, "N" appended for each concurrent one after that (`Shell`, `Shell 2`, `Shell 3`, ...), counting only currently-open tabs so closing one frees its number. Applies to `newShellTab`, `duplicateTab`, `openFirstmateHost`, and `openSSH`.
- **`ConsoleController.renameTab`** now restores focus to `currentTab`, not the tab that was just renamed - right-click Rename on a background tab no longer steals keyboard focus from whatever was actually on screen.
- **`ConsoleController.reconnectActive`**'s `.mirror` branch now waits (via `waitForProcessExit`, a bounded 50ms-interval poll on `tab.terminal.process.running`) for the old tmux/herdr client to actually exit before starting the new one - previously a still-running old process could make SwiftTerm's own `startProcess` guard silently no-op the whole reconnect attempt. (Both this branch and `waitForProcessExit` itself are gone as of `fm/grand-line-remove-firstmate-mirror` - there's no more herdr-attached tab kind to reconnect.)
- **`ConsoleController.closeTab`** now tears SRE Lead down (`tearDownSRELead()`) when the closed tab is `primarySSHTab` and SRE Lead is active, matching what `shutdown()` already did for the whole-page-closing case - the pane no longer sits in a stale "ready" state after its one dependent tab is gone.
- Verified against the real launched app (both the bare dev binary and the packaged, signed `.app`) via the project's own "verify without a screenshot" convention (temporary env-gated debug instrumentation calling the exact production code paths, reverted before commit) - not just `swift build`. The exact race in Finding 9 (reconnect vs. an old process not yet reaped) could not be forced in this sandbox; only a non-racing regression check (reconnect still completes) was run.

- **`fm/grand-line-audit-fixes` implemented the captain's decisions on the end-to-end audit (`data/grand-line-e2e-audit/report.md`, findings E1-E4, B1-B9, P2-P6).** E1's mirror removal has its own bullet near the top of this section; what follows is the rest, and the parts worth not re-deriving.
  - **Terminal painting is gated on visibility, and that is Grand Line patch 4 on the vendored SwiftTerm** (`Vendor/SwiftTerm/README.md`'s "Fourth patch"). The measured problem: with a tab attached to the fleet's own live session, the app burned ~6-16% CPU and 2.9% GPU **sustained while merely backgrounded**, was the machine's top CPU consumer, and a `sample` put nearly all of the main thread in `CA::Transaction commit -> TerminalView.draw`. Not a SwiftTerm bug - nothing ever told it to stop, and this app checked neither `NSApplication.isActive` nor `NSWindow.occlusionState` anywhere. `CockpitTerminalView.refreshDisplayGating()` is the policy: **suspended** when nothing can see the view (hidden view, hidden ancestor, closed/minimised/fully-covered window), **throttled to ~2Hz** when visible but the app is not frontmost (it must not freeze - a backgrounded window can still be partly visible). The **model is never gated** - every byte still reaches the buffer, so scrollback stays exact and a resumed view needs no reconnect. The gate lives on the view (`viewDidHide`/`viewDidUnhide` fire on *effective* visibility) rather than being wired per page, so the console's tab switching and the shell's `isHidden` destination model both reach it for free. `windowOccluded` is tracked from the occlusion **notification**, never read live: a window only reports `.visible` for a process the window server composites, so a headless context reports "not visible" for a live window and suspending on that reading would freeze a real terminal. **Live-measured** with a temporary counter in `queuePendingDisplay` over 4s of continuous output: 177 display passes / 1102ms CPU visible+active, 8 passes / 169ms throttled, 0 passes / 266ms suspended (the residual being the feed and parse, which are deliberately never gated).
  - **The local Whisper engine is released after `DictationEngine.whisperIdleUnloadInterval` (2 minutes) idle, and that is the captain's "no background process" rule, not an optimisation.** A whisper context creates a ggml Metal device whose residency keeper is an infinite `usleep(5ms)` loop - 200 wake-ups a second for the life of the process, found in *all 3259 samples* of a 5-second `sample` and matching Activity Monitor's "202 idle wake-ups" exactly - and it used to be cached for the whole session, so one dictation started that waker forever. `whisper_free` (the engine's `deinit`) runs `ggml_metal_rsets_free`, which is what actually stops the thread; nothing short of releasing the engine does. **Live-measured with `ps -M` inside the test process: 8 threads before the load, 9 while resident, 8 after the release.** The cache is lock-guarded (loaded on a background queue, released from main). Turning the Settings toggle off releases it immediately.
  - **`AppActivityState` is the one shared "has the captain been away for a while?" answer** (5 minutes of continuous inactivity - deliberately not `NSApp.isActive`, which flips every time they click into another app). Three pollers consult it: `FleetNotifier` (30s -> 120s), `BackgroundSignalsPoller` (15min -> 30min), and `ShiftGitSync`'s periodic pull (paused - the only fixed-cadence *network* poll, and pure prefetch). **Three deliberately do not, each for a stated reason** in that file's header: `ShiftNotificationScheduler` (an in-memory scan whose whole job is alerting the captain *while they are away*), `ScheduleRunner` (it runs their scheduled work), `AppLockController` (the security timer). `BackgroundedPollGate` **skips ticks rather than re-arming timers**: one always-running timer is self-correcting, a cancelled/re-armed one is a state machine that can get stuck slow or stopped - the failure mode this app has been bitten by twice.
  - **`HelmAccentRow`'s labels are capped at their own column (`label.width <= textStack.width`, compression resistance dropped to `.defaultLow`) - and the ties must be skipped for a row built with a caller-owned `contentView`**, which never adds those labels to the tree, so constraining them throws "no common ancestor". Without the caps, `.byTruncatingTail` never fires (nothing ever makes the label's *frame* narrower than its text) and the card's `masksToBounds` slices the string mid-glyph: measured at a 1263pt meta label inside a 339pt column. `Content.metaWraps` is the opt-in for a read-only browsing surface with vertical room; every list row keeps its predictable single-line height. `ToolRowLayout` has carried this same fix for itself since §5.4.
  - **A page that rebuilds on `viewWillAppear` or on a theme change should rebuild on *change* instead, and never while hidden** (P2/P3/P4). Health and Schedules both learn about real data changes directly (the health registry; `ScheduleStore.onChange`/`ScheduleRunner.onRunStateChanged`), so a visit rebuilds only when something moved while the page was hidden, the theme changed, or the rows' own relative wording ("last ran 3m ago") is a minute stale. **But the *first* render is never deferred** - a mounted page that has never been populated renders a blank body, which is PR #278's exact shape and what `DestinationMountingSelfTest.everyDestinationRendersRealContentOnFirstLoad` catches; this pass reintroduced it once on Schedules and the suite caught it.
  - **`ShiftStore.reloadAllAsync` splits the reload into a pure, off-main `parseAll` and a main-thread `apply`.** The parse touches no store state; every decision with a side effect - GL-01's per-file failure tracking (what stops this store writing an empty list over a file it could not read) and the first-run settings scaffold write - stays exactly where it was. The store's own threading contract is unchanged: nothing mutates it off the main thread.
  - **`VaultSnapshot.secrets`/`.tools` are optional: `nil` = the read failed, `[]` = it succeeded and there is nothing** (B1, the GL-14 class on a security surface). Both recipe-backup actions refuse a degraded snapshot - an export is *committed and pushed to a git remote*, and one built from a failed read would claim this machine has no secrets. `parseSecretList`/`parseDoctorTools` exist as pure functions for the same reason: `loadSnapshot` shells out to a real `av`, so nothing could otherwise reach the failure branch, which is exactly why the bug shipped.
  - **Four new suites**, all window-backed except the third: `FM_RUN_TERMINAL_DISPLAY_GATING_TESTS`, `FM_RUN_AUDIT_UI_FIXES_TESTS` (one case per finding id, B3-B9), `FM_RUN_APP_ACTIVITY_STATE_TESTS`, `FM_RUN_AUDIT_PERF_FIXES_TESTS`, plus `FM_RUN_VAULT_LOADING_STATE_TESTS`. Every case was confirmed to catch its own injected regression by name - several reproducing the audit's exact measurements (a 4pt nav-pill label, a 78.5pt Health footer, a `(0,0,0,0)` lock ribbon, a 1263pt meta label).

## AppKit-expert audit fixes (`fm/grand-line-appkit-audit-fixes`)

The captain-approved fixes for `data/grand-line-appkit-expert-audit/report.md` (H1-H3, M1-M6, L3, S1-S6, Pr1, P1-P2, T1-T5, A1-A2 and the tech-debt notes), one finding per commit. Read that report for the evidence behind any of them. `FM_RUN_APPKIT_AUDIT_TESTS` is the new suite for the findings too small to want one of their own; the rest extended the suite that already owned their area. What is worth carrying forward:

- **Two of the prior audit's own fixes were incomplete in a second code path, and both re-created the exact bug they had removed.** #291 added B1's `isDegraded` guard to Vault's two *manual* export paths and not to the F11 *scheduled* one, which then committed and pushed a "0 secrets" recipe unattended (H1); and E4's `stopAnimations()` cleared the `animationsStarted` latch that had been the only thing stopping `viewDidLayout` from re-attaching the lock screen's infinite animations to the now-hidden overlay (H2). When a fix is applied at a call site rather than at the thing being called, check every other caller - and when a fix removes a latch, check what that latch was incidentally protecting.
- **`Swift treats CRLF as a single grapheme cluster`**, so `"a\r\nb".contains("\n")` is **false**. Any "is this one line?" check has to compare `unicodeScalars` against `CharacterSet.newlines`. This was the S3 payload's own shape and the first implementation let it straight through.
- **Reaching for `AVAudioEngine.inputNode` *instantiates* it, which blocks in a process with no audio input** - it hung `DictationEngineSelfTest` outright. Every teardown path in `DictationEngine` goes through `removeTapIfInstalled()` for that reason; never touch `inputNode` on a path that may not have recorded.
- **`NSViewController.dismiss(_:)` raises rather than no-opping when nothing presented the controller** - measured, and contrary to gotcha (6)'s "documented no-op" note. A sheet's own close action should guard on `presentingViewController != nil`.
- **A layout defect that comes from `.gravityAreas` tie-breaking cannot be caught by measurement alone** - it can measure correct on one run and wrong on the next, which is what makes the class hard to see. `AppKitAuditSelfTest`'s M5 case pairs a real two-width measurement with a source guard, and only the guard reproduces the regression.
- **The AI-authored command gate is `CommandRiskConfirmation.confirmAIAuthored`, and it is unconditional by design.** A model-written command has no risk level anyone vouched for, so the heuristic beside it only decides how loud the alert is and can never clear a command. Every path that sends a model-written command to a terminal must route through it; `AppKitAuditSelfTest` asserts the Log Analyzer calls its sink from exactly one place.
- **`main.swift`'s `#if FM_SELFTESTS` process-entry block now redirects `FM_SCHEDULES_FILE` and `FM_SCHEDULE_HISTORY_DIR` as well as `FM_FLEET_LOG_DIR`** (Pr1). One consequence worth knowing: `DestinationMountingSelfTest`'s Schedules label floor had been passing off the leak that redirect closes, and now measures the page's genuine empty state.
- **A theme change repaints every page and rebuilds only the visible one** (P1). Bootstrap, Automation and Vault defer their teardown-rebuild to the next `viewWillAppear` via a local `needsThemeRebuild` flag - a new page answering a theme change with a rebuild should do the same.
- **Verified by the full suite (91 passed, 0 failed, 1 documented skip) plus clean debug and release builds, deliberately without launching the app**: the captain's real packaged instance was running throughout, and this repo has no process isolation between builds sharing one bundle identity.

## Full-app audit, section 4 ("Bugs")

**`fm/grandline-audit-bug-fixes` closed all ten findings in section 4 of `data/grandline-full-app-audit/report.md` (five confirmed, five "suspicious - needs a live check").** Read that section for the original evidence. Coverage: `FM_RUN_AUDIT_BUG_FIXES_TESTS` (new, pure logic, runs in CI - 4.4/4.5/4.8/4.10) plus cases added to the suite that already owns each area (4.1 `KubernetesDestinationSelfTest`, 4.2/4.6 `StickyBoardSelfTest`, 4.3 `RecentDestinationsSelfTest`, 4.7 `SessionSwitcherSelfTest`, 4.9 `StickyBoardViewSelfTest`). **Every case was confirmed to catch its own regression by scripted revert, not merely to pass.**

- **One of the five "suspicious" findings did NOT reproduce, and the guard for it is kept anyway because its sensitivity half is what makes that claim worth anything (4.9).** `StickyBoardCanvasView.draw` fills with `NSColor(patternImage:)` and sets no `patternPhase`, which in general anchors a pattern to the *window* rather than to a scrolling document - so on a 2200x1500 canvas inside a real `NSScrollView` the cork grain would slide under the notes on every scroll. Measured on the real canvas: it does not. **AppKit sets the pattern phase from the view's own origin while drawing a view, and a document view's origin scrolls with its content**, so the grain is already document-anchored. `StickyBoardViewSelfTest.checkCorkGrainIsDocumentAnchored` samples the same *document* rect at two scroll offsets and requires >5 distinct tones in the patch first (a flat-cork sample matches itself at any offset, so "identical" would otherwise be vacuous); injecting the window-anchored phase moves 2665 of 10000 pixels, which is how the clean result is known to be real rather than unmeasurable. **Two probe lessons worth not re-deriving**: `cacheDisplay` on the *canvas* starts a fresh context at the canvas's own origin, which resets the pattern phase and hides the exact effect under test - render through the **clip view**; and the first sample point has to be somewhere with real grain in it.
- **4.7 was real, worse than the audit suspected, and the two-part fix's second part is load-bearing - measured across three states rather than reasoned about.** The strip's ✕ was a `HoverHighlightView` carrying its own `NSClickGestureRecognizer` *nested inside* the pill container that carries `pillClicked`'s, with no exclusion policy. Driving a real `NSEvent` at the ✕'s own centre through `NSWindow.sendEvent`: **as shipped, neither handler fired - the ✕ was simply dead**; with the audit's recommended `NSButton` swap alone, `onSelect` fired and `onClose` did not, i.e. a ✕ click *switched to* the session it was ending; only the swap **plus** an `NSGestureRecognizerDelegate` on the pill's recognizer gives `onClose` alone. **The delegate's rule is "an `NSControl` with a non-nil `action`", not "any `NSControl`"** - a pill's own label is an `NSTextField`, so the naive version silently kills most of the pill's clickable surface (caught by the test, not by reading it). Any future control added inside a pill is covered without further work.
- **Event routing in a headless suite needs a real `windowNumber`.** A window that was never ordered in has none, and `NSEvent.mouseEvent(windowNumber: 0, …)` routes nowhere - which reads exactly like "the handler is not wired". `orderFront(nil)` on an `.accessory` process is enough and steals no focus. **Build it with `OffScreenProbe.window(...)` and never `NSWindow(contentRect:)` directly** - passing `x: -20_000` to `NSWindow.init` does *not* park a window off-screen, which this file claimed for two years and which was measured false: AppKit's initial placement ignores that origin (the window lands at `x: 160`) and `orderFront` re-constrains whatever survives onto the screen's bottom-left corner. A scout enumeration caught the result live on the captain's own display; see `SelfTests/OffScreenProbeWindow.swift`. Do **not** reach for `activate` - the captain's own instance shares this machine - though `makeKeyAndOrderFront` is safe on a probe window, which stays off every screen even while key. The one thing this still cannot reproduce is a genuinely *active* app, so a suite should say so rather than implying otherwise.
- **`FleetLogStore.Line` / `ScheduleRunHistoryStore.Line` (`.event`/`.entry` vs `.opaque`) exist because a JSONL trim rewrote the file from *decoded* records (4.5).** Both stores' headers promised "one bad line can only ever cost itself" and both broke it: every line `decodeLines` skipped - an old line a future schema change made unreadable - was silently deleted the next time the log crossed its cap, potentially months of history at once. The cap still counts *events*; an opaque line is never trimmed and is rewritten byte for byte. **The bound stays real** because every line this app writes is an event, so the opaque set can only be as large as whatever an outside edit or a schema change left behind. A test for this needs a file that already contains an undecodable line *plus* enough appends to cross the cap - appending and reading back passes either way.
- **`IncidentStore` distinguishes "no incidents" from "could not read the directory" (4.4, GL-21 class), and refuses rather than guessing.** `scan()` returns `(incidents:complete:)`, only a **complete** scan is cached (caching a partial read would freeze "no incidents" for the session and defeat the retry), `nextIncidentID()` returns `nil` on an incomplete one, and `start()` gained `StartFailure.couldNotRead`. A directory that does not *exist* is genuinely empty - only an existing-but-unenumerable one is a failure, or the first incident on every machine would be refused. Confirmed by injection: with the fix reverted, an unreadable tree reissues `INC-001` while `INC-001` is already on disk, and `directory(forID:)`'s prefix scan then resolves the *older* incident's folder.
- **`SSHKey`/`Snippet` have hand-written `init(from:)` decoders now, preventively (4.8) - do not delete them back to the synthesised ones.** Same landmine `blockViewOptIn` once tripped on `Host`: a Swift-side default does **not** make a key optional to the synthesised decoder, so the next field added to either struct would have made every existing `keys.json`/`snippets.json` undecodable, which the store then correctly reads as corruption and replaces with an empty list. Nothing was broken when this landed; the test simulates the future field addition by decoding JSON that predates it.
- **The Sticky Board's local write is debounced (`StickyBoardStore.persistDebounce`, 1.5s) and preserves records it cannot decode (4.2/4.6).** `persist()` re-serialises **every** note and writes the whole file synchronously on the main thread, and that used to happen once per character typed - only the git commit was debounced. Text and title debounce; anything structural (add/delete/restore) still writes immediately, and an immediate write cancels the pending one because `persist()` always writes the whole in-memory array anyway. **Three flush points, all required for the debounce to be safe**: `viewWillDisappear`, a field giving up focus (`onEditingEnded`), and `applicationWillTerminate` via `AppShellController.shutdownStickyBoard()`. `reloadAll()` flushes first, or it reads the file over a queued edit. Separately, `unreadableRecords` keeps a record whose `color` this build does not know (a case a *newer* build added - the cross-machine skew this store's git sync exists to serve) and writes it straight back, merged by `created_at` so it keeps its position; before this, `reloadAll()` compactMapped it away and the next write committed and **pushed** the deletion.
- **`ConsoleController.isTabBusy(_:excluding:)` is the one symmetric answer to "is another bridge mid-command on this tab" (4.1).** Three bridges can hold one tab - SRE Lead's and the context badge's live on the `TabModel`, the Kubernetes feed's lives on a different destination entirely - and the guard used to be one-directional: `KubeBridge` checked both console-side bridges, neither checked back, and *neither* consulted the feed bridge. `KubernetesController.isFeedBridgeBusy(onTab:)` plus `ConsoleController.isKubernetesFeedBridgeBusy` (wired by the shell, on **host** consoles - the Kubernetes page scopes to a saved host, so the shared Firstmate console is never its feed) is the third direction. Written as "everyone except me" so a fourth bridge is one enum case, not three call sites that can each be forgotten. **The typing quiet-window does not substitute for this**: `lastUserActivity` comes from an `NSEvent` monitor, and a bridge's own `send(txt:)` produces no `NSEvent`.
- **A Recents `.host` row for an ended session reconnects instead of doing nothing (4.3).** `RecentDestinations`' header is explicit that a closed host page stays listed, which made `switchToSession`'s "no-op for a host with no live session" guard - correct for the strip and the ⌘⌃ shortcuts, which only ever name live sessions - reachable here as a silently dead click. `AppShellController.onReconnectHost` is the forward-don't-own seam (the shell has no `HostStore`); it returns whether the host still exists, and a host deleted outright has its row dropped via `RecentDestinations.forget` rather than left as one that can only ever do nothing. **Pruning happens in the app delegate's own host-delete diffing, never in `removeHostConsole`** - that is also what "End session" calls, and an ended session's row must stay and reconnect.
- **`CodePreviewStore.delete` reports a failed delete (4.10)**, with "the file is already gone" as the one case that is genuinely success. A swallowed delete is invisible by construction: the panel has already closed the tab, so the only symptom is the snippet returning on the next launch - still synced to GitHub.
- **One adjacent gap found and deliberately NOT fixed, flagged instead:** `CodePreviewController.shutdown()` is never called from anywhere, despite its own doc comment saying the app delegate calls it on quit (`applicationWillTerminate` shuts down consoles and, now, the Sticky Board). Its debounced edits therefore rely on `viewWillDisappear`/`suspend()` alone. Out of section 4's scope, so left for a separately-scoped task.

## Full-app audit, section 3 ("energy/battery")

**`fm/grandline-audit-energy-fixes` closed the standing per-session energy costs in section 3 of `data/grandline-full-app-audit/report.md`.** Read that section for the original measurements. Coverage: `FM_RUN_AUDIT_ENERGY_FIXES_TESTS` (new, pure logic + source guards) plus behavioural cases added to `SRELeadBridgeSelfTest` and `KubeContextBridgeSelfTest`, next to the fakes those two bridges already have. **Every case was confirmed to catch its own regression by scripted revert (never `git stash` - see this file's own warning about the shared stash stack), not merely to pass.**

- **3.3 was already fixed and was deliberately not touched.** The Sticky Board's per-keystroke synchronous full-file rewrite had landed in the section-4 (Bugs) task as bug #6 - `StickyBoardStore.persistDebounce` (1.5s) plus `flushPendingWrite()` from `viewWillDisappear`, `shutdown()`, `onEditingEnded` and `deinit`. Verified before starting rather than re-derived.
- **`SRELeadBridge` is event-driven now, and the reason it keeps a slow sweep is the interesting half (3.1).** Its 5Hz timer used to run from session start to teardown, doing two `FileManager` directory enumerations a second per SRE-Lead-active tab (up to the 5-tab cap) forever, including backgrounded. A request arrives as a file *another process* writes, so nothing in-process knows when to look - which is exactly why `KubeBridge`'s full idle-stop does not transfer: its own requests are enqueued in-process (`enqueue` calls `start()`), so it can never miss one. Here the wake-up is a kernel event, so a `DispatchSource` vnode watcher (`.write` plus `.delete`/`.rename`, delivered on `.main` because handling a request touches AppKit/SwiftTerm) is the primary signal and `idleSafetyNetInterval` (30s, 120s backgrounded) is the bounded fallback behind it. **Dropping the sweep entirely would mean a dropped event strands a tool call forever rather than for one interval** - the same "don't fully trust the event, keep a cheap re-check" posture gotcha 14 and `fullScanEvery` already take. Net: idle work went from 2 scans/second to 2 per 30s while *improving* responsiveness (claimed on the write, not up to `idlePollInterval` later). **`directoryChanged()` clears `lastIdleScan` before ticking** - without that the idle throttle swallows the very event that woke it, which is a real case in the suite. **There is deliberately no visibility pause here**, unlike 3.2: an SRE Lead investigation is asynchronous, so a tab the captain navigated away from must still be served, and the watcher already makes that free.
- **`KubeContextBridge`'s pause is a *pull*, and that is the correctness half (3.2).** A periodic refresh does not merely burn a wake-up - it types a visible `kubectl config ...` command into the captain's own live bastion session, and it used to do that every `refreshInterval` whether or not anyone could see the tab (the only gates were the typing quiet-window and the sibling-bridge busy check). `shouldPauseRefreshes` is therefore consulted **at the moment of every attempt** in `beginRefreshIfDue`, so no command can leak into an unseen session even if every visibility notification is missed; `refreshGating()`'s push (from `viewDidAppear`/`viewDidDisappear`, `select(tabID:)`, `markCurrentTabAsRead()`, and `AppActivityState.observe` - this app's first adopter of that long-advertised callback) is only the energy half. `ConsoleController.isConsolePageOnScreenForPeriodicWork()` is the predicate, and a **background tab counts as invisible** because the console shows one terminal at a time.
  - **`pause` had to be distinct from `stop()`/`start()`, and skipping that is a real regression.** `start()` deliberately resets `consecutiveFailureCount`/`hasStoppedRetrying` (activation and the captain's explicit retry both mean "clean slate"), so pausing with `stop()` and resuming with `start()` would silently re-arm a badge that had already given up - breaking `fm/grandline-k8s-badge-fixes`' "stop retrying automatically" contract on every hide/show cycle. A suite case pins it.
  - **An in-flight command is watched to completion even while paused.** It has already been typed into the real shell, so its output is coming either way, and abandoning it would leave `inFlight` - and therefore `isBusy`, the seam `SRELeadBridge` reads before injecting - stuck set for the life of the tab.
  - **The timer is a one-shot at `nextAttemptAt` now, not a fixed 0.3s repeat**, so a healthy 300s window costs 1 wake-up instead of ~1000. Floored just above zero so a clock adjustment cannot busy-loop; `Timer.tolerance` only ever *delays* a fire, so a one-shot can never arrive early.

Four callers ask for `parseTasks()` (`FleetNotifier.start()`'s baseline, its poll, `FleetController.refresh()` via `snapshot()`, `ReviewController.refresh()`), each on its own global queue, so at launch three genuinely concurrent fan-outs of the identical sweep land within a second or two: 3x the `fm-crew-state.sh` spawns to answer one question. `ttl` is deliberately **far shorter than `FleetNotifier.pollInterval`** (a suite case asserts `< poll/2`) so every poll misses it by construction and no transition is ever detected later than before - this is a coalescer, not a freshness cache, the opposite end of the same idea as `DependencyCheckCache`'s 15 minutes. - **An unbounded suite runner turns one hung suite into six hours of macOS runner minutes and a log that names nothing.** That is not hypothetical - it is what the first windowed run cost. `run-all-tests.sh` now bounds each suite (`FM_SUITE_TIMEOUT`, default 300s) and reports an overrun as `TIMEOUT <flag>` while continuing, so one hang no longer hides the other hundred results; every CI job also carries `timeout-minutes` as the backstop. The bound polls a background pid rather than using `timeout(1)`, which is GNU coreutils and absent on macOS.
- **`--ci` and `--session-only` are orthogonal: the first says *where* this is running, the second says *which* suites.** So `--session-only --ci` is the windowed CI job (that selection, minus `CI_UNSUPPORTED`) and is deliberately not an error. An earlier draft made them mutually exclusive, which left no way to express "the window-backed suites, on a runner".
- **A hermeticity check must assert "not the captain's real data", never "matches one particular scratch path shape" - and this cost two separate false positives.** The check this task added asserted every store override resolves under the process's own `temporaryDirectory`; CI legitimately points them at `${{ runner.temp }}`, which is as disposable as a directory gets and deliberately *not* the runner's `TMPDIR`, so the blocking job went red on three correct paths. **The identical bug was already sitting in `AppKitAuditSelfTest.test_pr1`**, which required the literal substring `selftest-process-` and therefore announced "the captain's real schedules.json is being read on every test run" about a runner scratch directory - an alarming claim, and a false one. Both now derive the real store root the same way every store derives it and compare **component-wise** (a `FirstmateCockpit-scratch` sibling is a genuine string prefix of `FirstmateCockpit` without being inside it). Any future variant of this check wants the same shape.
- **`native/MANUAL-CHECKS.md` is the honest boundary written down**, so a green `run-all-tests.sh` is not mistaken for "verified". It covers only what a suite provably cannot reach - a suite process is never composited, so a `WKWebView` reports `hidden` even when shown, SwiftTerm draws nothing in a never-ordered-front window, and Energy Impact, biometric prompts, real notification buttons and every real remote path need a genuine session.

**Not attempted, and why**: nothing from §7's list. The two coverage gaps §7 *names in passing* but does not put on its strategy list - `SRELeadRunner`'s `--resume` loop, and `BackupUI`/`BackupGitHub`/the Tools converters - are left for a separately-scoped task; the audit's own priority order put the five items above them, and stretching this task to cover them would have meant less scripted-revert verification on the work that was asked for.

- **The half-themed guard's whole value is the window it mounts into, and a guard hosted in the real app's window would catch nothing.** `main.swift` calls `window.followHelmTheme()`, so `window.appearance` already tracks the theme and every view inside inherits a correct `effectiveAppearance` whether or not it sets one - a check run there passes for a destination that does nothing at all, and would have shipped green through all four historical half-themed bugs. `DestinationMountingSelfTest.everyDestinationForcesItsOwnAppearance` sets the host window to the **opposite** mode, so inheritance produces the wrong answer and only a destination that genuinely forces its own appearance can pass. The historical bugs were all in the second, so a mount-only sweep would be the weaker half.

- **Tab shortcuts are a local `NSEvent` monitor (`TabKeyboardShortcuts.swift`), and the modifier match must be exact rather than `contains`.** `⌘⌃1`…`⌘⌃9` is the session switcher's (`main.swift`'s Hosts menu) and `contains(.command)` would steal all nine while every positive case still passed - which is the one injection that proves this suite is worth having. - **F2's safety property is `ConsoleController.addTab`'s `if hasAppeared` guard, and `SessionRestoreSelfTest.hostPagesComeBackWithoutConnecting` is what stops a refactor removing it silently.** A restored host page is mounted hidden, so **its `ssh` does not run until the captain opens it** - which is the same moment they would have clicked Connect. Only the page that was showing at quit appears at launch, so a captain with six host pages open gets six pages back and exactly one connection. Without this, restoration would open a fistful of SSH connections and Touch ID prompts at every launch.
  - **What is restored**: the showing destination (including a host page), the shared Console's `.shell` tabs with their names, the Tools page's tabs, and which hosts had a page. **What is not**: scrollback and any live process state (there is no way to resume a real PTY child), a host page's *extra* duplicated ssh tabs (each would be a second real connection and a second Touch ID prompt), one-shot command tabs (a finished `rebuild.sh` must not re-run - the same distinction `processTerminated` already draws), and SRE Lead / Log Analyzer / form state.
  - **GL-31 wins over a saved destination**: a machine with no firstmate home resolved still lands on Setup. Tabs are restored either way; only the destination defers.
  - **`RailDestination` is `String`-backed now**, purely so a destination has a stable identity to persist. Raw values are the case names, compiler-derived; renaming a case invalidates a saved state rather than silently restoring the wrong page.
  - `SessionRestoreState` has **hand-written decoders** - a synthesized `Decodable` requires every declared key to be present, which is exactly how `blockViewOptIn` once made every existing `hosts.json` undecodable. The suite asserts an older build's state still decodes, so the lesson is enforced rather than only written down.
  - **The incident half needed no new code.** `IncidentStore` already persists as it happens and `resumeActiveIncidentIfNeeded` (§6.2) already announces on the host page's next `viewDidAppear`; the only missing piece was the page reopening, which restoration supplies. The suite asserts the two meet (a restored page carries its `hostIdentity` and resolves the real persisted incident) and deliberately stops short of calling `viewDidAppear` on a page with an ssh tab.
  - Saved on quit, on every navigation (`AppShellController.onSessionStateChanged`, the choke point every navigation path already funnels through) and on `applicationDidResignActive` - the last two are what make it survive a crash or force-quit. `saveSessionState` writes only when the encoded state actually changed, which is why `captureSessionState` sorts `hostConsoles.keys` (`Dictionary.keys` has no defined order, so without that it would write on every navigation regardless).
  - **Two launch-path robustness fixes worth keeping, both found by re-reading the finished code rather than by a failing test.** `Dictionary(uniqueKeysWithValues:)` *traps* on a duplicate key, and the host lookup runs at launch against a hand-editable `hosts.json` - `uniquingKeysWith` keeps the first instead, because a crash at launch is a far worse answer to a duplicated id than quietly ignoring it.
