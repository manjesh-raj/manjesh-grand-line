## Full-app audit #2, section 1 ("UI")

**`fm/grandline-audit2-ui-fixes` closed §1 of `data/grandline-full-app-audit-2/report.md`** - the second audit's two confirmed UI defects, both missed-adoption gaps left by #333's own sweeps. What is worth carrying forward:

- **`HelmDomainHue.fallbackTint` now has zero production callers, and a new one is a red flag.** §1.1: `RecentDestinationsPopover.makeRow` was the last, and it is exactly the shape `identityHex` was written to fix - `RailDestination.domainHue` maps Tasks/Dictation to `.rose` (fallback `.critical`) and Postmortems/Sticky Board/the four Setup pages to `.amber` (`.warn`), so "you were recently on Tasks" painted a red alert bar and badge on all twelve legacy palettes, and on Daylight replaced the real §2.2 hue with a semantic slot (`fallbackTint` resolves unconditionally). Fixed by passing `domainHue:` and leaving `tint:` as the value it overrides - Dictation's history row is the precedent. `fallbackTint` itself stays: it is still right for a surface the caller wants *coloured* (a gradient tile, a ribbon, a primary button), which is what its own doc comment distinguishes.
- **The audit was factually wrong about one of its six §1.2 sites, and the brief's own "re-verify every file:line" instruction is what caught it.** It claimed `LogRawPaneView`'s rows render `HelmType.code()`; they render raw `.monospacedSystemFont(ofSize: 9.5 / 10.5)` literals. The `HelmType.code()` call it cited (`LogAnalyzerViews.swift:487`) belongs to `LogErrorGroupListView`'s *sample* cell, a different class further down the same file. Consequence: that pane cannot clip at "Larger" today, because nothing in it grows - it is unscaled sub-11pt GL-32 debt, which was explicitly out of that task's scope. Its row height is scaled anyway, so the height is already right when that debt is paid instead of the fix for it landing as a clipping bug. **Do not "fix" the discrepancy by reverting the scaling.**
- **Chrome scale owns the Log Analyzer's row heights, not `FontSizeManager`** - the §1.2 decision that site was left to make. `FontSizeManager` has exactly three observers (Console, Tools, Code Preview); nothing in the Log Analyzer touches it, and every `HelmType` role in that file is chrome-scale driven, so wiring the terminal size in would be a new capability rather than adopting an existing mechanism.
- **Eight tables were migrated, not the audit's six.** The other two are `LogErrorGroupListView`'s `sampleRowHeight` (a sibling height returned by the *same* `heightOfRow`, whose cell is a scaled `HelmType.code()` - scaling only the group height would leave the same table clipping its other half) and `LogAccentRowListView`, a seventh instance of the identical shape in the same file backing three real lists. Empty-state heights stay unscaled, per `FleetLogListView`'s precedent. Three views had their inline `heightConstraint.constant` extracted into a `recomputeHeight()` so `applyTheme` can re-derive it.
- **A measured, pre-existing defect this surfaced and deliberately did NOT fix - it needs a captain decision.** `LogErrorGroupListView` (58pt) and `LogCorrelationListView` (56pt) render the maximal accent-row shape (kicker + title + **meta** + chip) that the 78pt Shift/Dictation lists carry, and they are undersized at **every** scale including Default. Measured with this codebase's own instrument: a group row needs **76pt**, and a geometry probe showed its kicker occupying y 50-64 in a 58pt row - 6pt genuinely outside the bounds. The already-fixed 60/64pt lists are not comparable: they render **no meta line**. The correlation row is the harder half - `titleWraps = true` in a fixed-height table needs 76-108pt depending on width, so **no constant fixes it**; it wants either no wrapping or `usesAutomaticRowHeights`, which is a design call. Scaling narrows the group row's shortfall (18pt -> 12.6pt at Larger) and never widens it, which is what `TextScaleRowHeightSelfTest` asserts and prints rather than failing on a defect this pass neither caused nor fixed.
- **Coverage** extends the two suites that already own these areas rather than adding a third. `TextScaleRowHeightSelfTest` gained the eight tables in its arithmetic table, a re-derivation check (built at 1.0, asserted *stale* before the theme re-fire - without that step the assertion would pass against a table that never re-derived), and a fit check split by shape. `RecentDestinationsSelfTest` gained a case reading the **actually painted** `debugPaint().accentBar` across all 14 themes, comparing colours **component-wise** (`HelmContrast.ratio` is a luminance comparison - two different hues of similar brightness pass it, a trap this codebase has hit twice). **Confirmed to catch real regressions by scripted revert**: the 1.1 fix (failed by name on the first theme), one scaling site (failed both the arithmetic *and* the fit half - "a HelmType.code() line needs 18.0pt but KubeLogListView gives it 17.0pt", the audit's own worst case reproduced), and one `applyTheme` re-read.
- **Verified** by `swift build` (clean debug and release, zero warnings in this app's sources), the release binary carrying no `FM_RUN_*` strings or the new test accessors, and the full suite (118 passed / 0 failed / 1 documented skip, `fm.themeID` unchanged) - **without launching the app**, per the README's worktree rule.

## Full-app audit #2, section 4 ("Bugs")

**`fm/grandline-audit2-bugs-fixes` closed the three confirmed findings in §4 of `data/grandline-full-app-audit-2/report.md`** (4.1, 4.2, 4.3), each with its own recommended fix and each confirmed to catch its regression by scripted revert. 4.4 is filed under that report's §5.1 (a lock bypass) and is a **separate, not-yet-approved** fix - it shares 4.1's code path (`restoreConsoleTabs` / `resumeActiveIncidentIfNeeded` / `viewDidAppear`) but no lock-awareness was added here, deliberately.

- **4.1's real lesson is not the guard, it is that a self-test harness which differs from production on one constructor argument can keep a whole feature's dead code reporting PASS.** `restoreConsoleTabs` opened with `guard tabs.isEmpty`, and the shared Firstmate console is an **eager** mount (`DestinationRegistry`'s `mountsEagerly` set) whose `loadView` calls `openFirstmateHost(focus: false)` unconditionally - which runs when `window.contentViewController = appShell` is assigned, long before `restoreSessionIfNeeded` at the end of `applicationDidFinishLaunching`. So `tabs` was **never** empty in production, F2's console-tab restore was dead on every real launch (saved names silently dropped; only Tools' tabs came back, Tools being lazy and opening nothing in `loadView`), and `SessionRestoreSelfTest.makeConsole` passed `isFirstmateConsole: false` - skipping the auto-open and testing a state no launch ever reaches. **Both harness constructors now pass `true`**, which is the fix that keeps this closed; the guard change alone would have left the blind spot.
  - **`soleAutoOpenedShellTab` is the widened match**: exactly one tab, a plain interactive `.shell`, not a one-shot command, and still carrying a name this app derived. That one tab is **reused** as the first restored tab, never closed - its shell process may already be running (`hasAppeared`), and `closeTab` on the shared console's *last* tab deliberately opens a fresh Shell to keep the window non-empty, so closing first lands straight back at the start.
  - **Do not reach for `renameTab` on the restore path.** It ends by moving first responder to the current tab's terminal, and this runs at launch behind the lock screen, whose password field owns first responder at that moment. Set `name`/`hasUserChosenName`/`chip.setName` directly and call `styleChips()` only when no `addTab` followed (i.e. exactly one restored tab), since `addTab` refreshes the strip itself.
  - Consequence worth knowing: the auto-opened Shell **is** recorded by `restorableConsoleTabs()` like any other interactive shell tab (it always was), which is why `onlyShellTabsAreRecorded` now expects 3 rather than 2. Restore reusing it is what stops that becoming a duplicate on the way back in.
- **4.2: "the namespace list is unknown" and "this cluster will not list namespaces" are different states, and only a *completed* kubectl run can establish the second.** `sweepCommands()` issues `get namespaces` only while `knownNamespaces == nil`, so anything setting it non-nil latches for the session - and `applySweep` latched `[]` on **any** `.failure`, including a `.busy` refusal (captain typing in the feed tab, sibling-bridge contention, `queueDeadline` expiry) or a `.timeout`. One transient refusal on the first sweep blamed RBAC for the rest of the session on a cluster that lists fine, and nothing ever reset it.
  - The fix is the general form of the audit's suggestion: **a bridge-level `.failure` leaves it `nil`** (the command never ran, so nothing was established), while a bridge-level *success* whose output parses `.empty`/`.failed` still latches - which is exactly the RBAC case (`Error from server (Forbidden)` arrives as real output between real markers), so the anti-retry protection is untouched. `KubeBridgeError.countsAsGenuineFailure` is deliberately **not** the predicate here: it puts `.timeout` in the "genuine" bucket, correctly for the give-up threshold and wrongly for "did this settle the RBAC question".
  - **Plus the second half**, because the in-code comment promised "the manual Refresh is the way to ask again" and `sweepCommands()` made that impossible: `refreshTapped` clears the latch - in the `.cluster` branch only, since a Refresh on the Log Tail runs `pollTail()` and issues no `get namespaces`, so clearing there would strand the picker on "Checking…". This is the rule `DependencyCheckCache` already follows (every explicit Check/Refresh bypasses the cache it would otherwise read).
  - **Its self-test is pinned in both directions, and the over-broad fix is the one worth guarding**: never latching at all makes the page re-type a command it already knows the answer to into the captain's own bastion session every 30s, and `aRealForbiddenReplyStillLatchesNotListable` fails on it. A transient-refusal case must be built on `Harness(offerTabs: false)` (no feed adopted, so no real sweep runs and the list starts genuinely unasked) - a live harness cannot stand in for it, because the fake answers *every* injected command and **an unscripted answer is still a completed command**, which legitimately latches. That distinction is the finding.
- **4.3: a terminate-time flush belongs on the shared serial git queue, with a bound, and must cancel the pending debounce first.** `StickyBoardController.shutdown()` called `commitAndPushNow()` directly from `applicationWillTerminate` - on the main thread and **off** `queue`, the one queue every other invocation in this app serializes on (`ShiftGitSync.sharedQueue`, shared with Shift's, Docs' and Code Preview's own commits against the *same* working tree). So a flush could run `git` concurrently with a sibling's (`.git/index.lock`), quitting could block on a real network push (the `Subprocess` bound there is 600s), and the still-pending debounced `pendingCommit` was never cancelled, so it could fire during or after the flush and commit the same work twice.
  - `StickyBoardGitSync.flushForTerminationNow()` dispatches onto `queue` and waits at most `terminateFlushBudget` (3s). **The short bound is the right answer because what it abandons is already recoverable**: the local YAML write completed synchronously before this is ever called, and `ensureReadyNow()` re-reports a dirty tree on the next launch and calls `markDirty()` itself. The self-test asserts that recovery, not just the happy path.
  - **The cancel goes *inside* the queue block, not before it** - `pendingCommit` is only ever touched on `queue` (see `markDirty`), and a serial queue guarantees the pending item is not running concurrently, so the cancel takes if it has not started and is moot if it has. Doing it on the caller's thread is worse than useless: `markDirty`'s own `queue.async` may not have run yet, so the cancel can land *before* the item is even assigned - which the self-test catches.
  - **The "did it really run on the queue?" assertion is the interesting one**: occupy the queue with a blocked work item, then call the flush. On-queue, it cannot get on and must give up on its own budget; run inline, it succeeds immediately. A property check of the implementation could not tell those apart.
  - Wiring is a **source guard** (`shutdown()` names `flushForTerminationNow` and not `commitAndPushNow`), because both commit the same work when the queue happens to be free - nothing observable distinguishes them. It strips whole-line comments before grepping, since this file's own fix note names `commitAndPushNow()` in order to explain why it is no longer called.
  - `CodePreviewController.shutdown()` carries the identical direct-call shape and was deliberately left alone: the audit records it as pre-existing and, separately, that it has **zero callers**, so it is unreachable today. Fixing it is a separately-scoped task, not a free ride on this one.
- **Verified** by `swift build` (clean debug and release, zero warnings in this app's sources), the release binary confirmed to carry no `FM_RUN_*` strings and neither new `#if FM_SELFTESTS` probe, and two full `./Scripts/run-all-tests.sh` runs (118 passed / 0 failed / 1 documented skip) - **without launching the app**, per the README's worktree rule. **Six injected regressions each reproduced by name**: 4.1's original `tabs.isEmpty` guard (which failed the aligned harness with the exact production symptom, "the saved shared-console tabs were dropped on the launch path"), 4.2's latch-on-any-failure and its Refresh-cannot-re-ask half separately, 4.2's over-broad never-latch, and 4.3's off-queue inline flush, missing cancel, and reverted `shutdown()` wiring.

## Full-app audit #2, section 7 ("End-to-End Testing")

**`fm/grandline-audit2-e2e-fixes` closed §7 of `data/grandline-full-app-audit-2/report.md`** - 7.1 (local test runs could reach the captain's real `manjesh-config` clone), 7.3 (the same class, four stores wide) and 7.2 (the 36%-of-windowed-CI-runs flake that was the sole blocker to promoting the windowed job to blocking). What is worth carrying forward:

- **`DocsRunbookStore` honours `FM_SHIFT_DIR` now, and it was the one store in the `GrandLineDocs/` family that never did.** With neither override set, its `init()` calls `DocsRunbookGitSync.shared.start()` -> `ShiftGitSync.shared.ensureWorkingTreeNow()` - the real clone/fetch/pull machinery. Two windowed suites reached it on **every local run** (`AppShellDrillHeaderTitleSelfTest` through a real `AppShellController`'s eager `RunbooksController`/`PostmortemsController`/canvas store; `DaylightDrillPageSelfTest` through `ShiftController` -> `CommandLibraryPageView`'s own store) - both of which correctly set `FM_SHIFT_DIR` and were silently getting nothing for it. CI was safe only because `ci.yml`'s env block happens to set `FM_DOCS_RUNBOOKS_DIR` directly.
- **Reproduced and proved, not reasoned about, and safely.** The real clone genuinely exists on this machine, so the pre-fix path was demonstrated against a *disposable* local bare repo (`FM_SHIFT_GIT_CLONE_PATH`/`FM_SHIFT_REMOTE_URL`, the convention `ShiftGitSyncSelfTest` already uses): the reverted build resolved the store to `<clone>/GrandLineDocs/runbooks` and **created the clone directory** - the machinery genuinely ran - while the fixed build, same invocation, never touched it. The real clone's `HEAD`, `git status` and `.git/FETCH_HEAD` mtime were captured before and confirmed unchanged after running both affected suites.
- **The fix is the store, not the redirect block, and the distinction matters.** `main.swift`'s block *also* sets `FM_DOCS_RUNBOOKS_DIR` now (belt to the store's brace), but the store-side fallback is what makes the contract that block's own comment - and this file - already claimed actually true, and it is the half that covers a single suite run by hand with just `FM_SHIFT_DIR` set. The git branch deliberately keeps its old behaviour of *not* creating directories eagerly: `ensureReadyNow()` makes them after the clone-into-temp-and-swap lands, and pre-creating them would put the store into `salvageRacedLocalWrites`' path for no benefit.
- **`E2ETestingPolicySelfTest.checkEveryGrandLineDocsStoreHonoursShiftDir` is the guard, and it is the point.** The audit's real finding was not "one store is missing a line" - it was that the existing hermeticity check **cannot see this class**: it asserts the overrides the block sets, and says nothing about whether a store *honours* the one they fall back to. The new check names the seven family members and requires each to actually read `environment["FM_SHIFT_DIR"]` - the read, not a mention, because every one of those files also discusses the variable in a doc comment. Source rather than behavioural, because proving it behaviourally means constructing the store with no override, i.e. performing the hazard. **Confirmed to catch the regression by name** (scripted revert, never `git stash` - see this file's own warning about the shared stash stack).
- **7.3's four variables (`FM_KEYS_FILE`/`FM_SNIPPETS_FILE`/`FM_HOSTS_FILE`/`FM_DICTATION_DIR`) plus `FM_DOCS_DIR` joined the block** for the reason the block's own rule already implied. ~10 windowed suites construct a bare `SSHKeyStore()`/`SnippetStore()` purely to satisfy `ConsoleController`'s parameter list, so locally each *read* the captain's real `keys.json`/`snippets.json`. Read-only today (GL-01 backs up rather than overwrites) - the point is that the next suite to reach one is the one that writes.

### 7.2: the settle wait, and why "two consecutive equal reads" was never a settle

- **Both documented failure modes are one bug: a 50ms window cannot tell *settled* from *has not begun*.** `waitUntil` polls every 50ms, so the two sequential "two consecutive equal reads" loops asserted 50ms of stability each. The geometry failure (`80x25 -> 115x36`) is the loop declaring victory at SwiftTerm's **untouched default** before AppKit's first layout; the content failures (three runs, an identical `19093 -> 19191`) are the ssh child not having exited yet. **The audit's own suggested fix - "assert geometry stability across two consecutive reads" - is what the code already did**, which is why the fix had to go further.
- **The +98 characters are not "a shell that might emit anything": they are `processTerminated`'s own `[process ended (exit N) - ...]` notice**, one buffer line wide (`ConsoleController+Tabs.swift`). Identifying it is what makes this deterministically fixable rather than a flake to be tolerated.
- **So the settle waits for a positive signal of completion, not an absence of change**: `[process ended` present in the buffer - which is the *last* write anything makes to that terminal (child gone, auto-reconnect off, SRE Lead writes to its own chat view) - **and** both length and geometry unchanged across 10 consecutive polls of one combined loop, so settling one cannot perturb the other. Waiting for the child also buys ~a second of pumped runloop, by which point the first layout has certainly landed. A timeout now fails with the measured state (`processEnded=`, size, length, `stableReads`) instead of proceeding on a bad baseline.
- **A vacuity guard, in the style of the seeded-content one below it**: a baseline still at 80x25 means no layout ever happened, which makes the no-resize assertions meaningless rather than merely fragile - so that fails loudly rather than passing.
- **Measured A/B under real load, locally rather than by spamming CI** (45 busy loops on 15 cores, three-times oversubscribed, matching a shared runner's contention; the two builds differ only in this file): **original 10 failures in 20 runs, hardened 0 in 20.** The original's failures reproduce the CI signature with the *same 19093 baseline* the three CI failures show (`19093 -> 19220` nine times, `-> 19152` once). Unloaded both pass 5/5, which is why re-running it locally never reproduced anything.
- **Honest limit on that evidence:** the load harness reproduced the **content** mode only - the geometry mode (1 of the 4 CI failures) did not recur locally in 40 runs, because this machine's first layout lands well before the child exits. It is addressed structurally rather than by reproduction: the 80x25 vacuity guard fails loudly instead of measuring a default, and the combined loop means geometry must hold still for ~0.5s *after* the child has exited, which is strictly later than the point the old loop sampled.
- **`processEndedMarker` is a wire contract with `ConsoleController.processTerminated`.** If that string changes, the settle times out with a message naming it rather than silently reverting to guessing.

**Verified** by `swift build` (clean debug and release, zero warnings in this app's sources), the release binary confirmed to carry no `FM_RUN_*` strings, and the full `./Scripts/run-all-tests.sh` run - **without launching the app**, per the README's worktree rule (the captain's real packaged instance shares this bundle identity).

## Full-app audit #2, section 5 ("Security Enhancements")

**`fm/grandline-audit2-security-fixes` closed §5 of `data/grandline-full-app-audit-2/report.md`** - two lock-screen bypasses (5.1, 5.2) and two smaller ones (5.3, 5.4). This is the follow-through on the deferral the §4 entry above records: that task deliberately added no lock-awareness to the `viewDidAppear` / `resumeActiveIncidentIfNeeded` path it was already editing, because the lock bypass was a separate, separately-approved finding - this is it. Coverage is the split the first audit's security work established: `FM_RUN_AUDIT2_SECURITY_FIXES_TESTS` is pure logic plus source guards and runs in CI, `FM_RUN_AUDIT2_SECURITY_LOCK_TESTS` mounts real `ConsoleController`s and drives real lock transitions and is in `run-all-tests.sh`'s `NEEDS_SESSION` list. **Eleven injected regressions were each confirmed to reproduce by name** (scripted revert, never `git stash` - see this file's own warning about the shared stash stack).

- **The headline finding is what F2 turned `viewDidAppear` into: "the page appeared" and "the captain is here" stopped being the same statement.** `main.swift` locks and *then* restores, and the lock overlay is a subview of the main window - so a restored showing host page mounts under it, `viewDidAppear` fires, and the page forks its `ssh` (Touch ID prompt *above* the lock screen, private key written to a temp file), hands keyboard focus to a terminal nobody can see, and pops its incident card. `ConsoleController.runAppearanceWorkIfUnlocked()` is the one list of those three, called from `viewDidAppear` and again from `resumeAfterUnlock()` - both paths land on the same function rather than the unlock path re-implementing it, so a fourth side effect added to appearing is covered without anybody remembering the second call site.
- **`hasAppeared` is deferred too, not just the start loop it guards - and skipping that leaves the hole open.** `addTab` reads that flag, so a page that set it while locked would fork an `ssh` on the *next* `addTab` even with the appearance loop correctly gated. `Audit2SecurityLockSelfTest.test_addTabWhileLockedStillWaits` is the case that fails if it comes back.
- **`appearanceWorkDeferredByLock` is self-scoping, which is why replaying "every console the shell owns" on unlock is safe.** Only a page that genuinely appeared sets it, so F2's own guarantee - a *background* restored host page forks nothing until the captain opens it - is untouched. Pinned by its own case, because "nothing starts while locked" is otherwise satisfied by a console that never starts anything.
- **The unlock replay is a push from `AppShellController.hideLock` (`forEachConsole`), deliberately not an `AppLockGate.observe` registration in the console.** That API has no unregister and a per-host `ConsoleController` is deallocated when its host is deleted - the dead-closure leak this controller already keeps theme/font/activity *tokens* to avoid.
- **`ConsoleController.focusTerminal(of:)` is the one place this controller family hands focus to a live PTY**, and the gate lives there rather than at `viewDidAppear`. The harm is not "`viewDidAppear` stole focus", it is "a terminal nobody can see is first responder while the lock screen is asking for a password" - and `AppShellController.revealHostConsole` -> `focusCurrentTab()` reaches that state on the *same* launch sequence, so gating only `viewDidAppear` would have left §5.1(c) open. Seven call sites were routed through it; `Audit2SecurityFixesSelfTest.test_focusChokePoint` counts `makeFirstResponder` + `terminal` across the four files and requires exactly one.
- **An `NSPopover` cannot be dismissed by the gate's generic `orderOut` sweep, and doing it anyway breaks the card for the rest of the session.** A popover tracks its own shown state, so ordering its window out behind its back leaves `isShown` true and `showIncidentCard` then declines to re-`show()` it. `AppShellController.showLock` therefore calls `closeLockSensitiveSurfaces()` (a real `performClose`) **before** `setLocked(true)`, so the sweep finds nothing to do; the `registerSecondaryWindow` registration in `buildIncidentCard` stays as the backstop for any future path that opens one without coming through there. That provider guards on `isShown` **and** on the window not being this page's own - `contentViewController.view` is expected to be detached when a popover is closed, and the cost of that expectation being wrong is handing the gate the app's *main* window to `orderOut`.
- **§5.2's lesson generalises past this feature: a local `NSEvent` monitor bypasses `AppDelegate.setContentMenusEnabled(false)` entirely.** The Tab menu `TabKeyboardShortcuts` replaced was disabled while locked by that call; the monitor that replaced it inherited nothing. Today's protection was incidental - the lock screen's password field is an `NSText` responder, which the monitor already refuses to act under - and evaporates the moment anything else holds focus (a Full Keyboard Access user tabbing to the unlock *button*; §5.1(c)'s own race). **Any future keystroke handling moved off a menu item onto a monitor loses the lock gate the same way.**
- **Four new `AppLockedSurface` cases, not one shared one**, per that file's own header rule: `.terminalSession` (forking a tab's child process), `.terminalFocus` (first responder to a PTY), `.incidentCard`, `.tabShortcuts`. The first two are the pointed pair - they are different harms with different call sites (two versus eight), and a self-test asserting "no ssh starts while locked" passes just as happily with the focus gate deleted.
- **§5.3: a stored `risk` is a human vouching for text they read, so an AI rewrite cannot carry it.** `CommandRiskConfirmation.confirm` short-circuits on `.readOnly`, so a `readOnly` command whose template the model rewrote reached a terminal with *no* confirmation, silently, forever after - through the detail pane, ⌘K and F9's multi-host fan-out - while `confirmAIAuthored` never fired either, because by then it was an ordinary saved command. Fixed with both halves the audit offered: the save goes through `confirmAIAuthored` (new `AIAuthoredIntent.saveTemplate`; `.run` keeps byte-identical copy, so the two pre-existing callers are unchanged), and the level is re-derived as `existing.risk.raised(to: heuristicRisk(of: newTemplate))`. **`raised(to:)`, never a plain assignment**: `heuristicRisk` is coarse and deliberately never answers `.readOnly`, so taking the maximum both guarantees no stale-low level survives and guarantees a re-derivation can never talk a `destructive` command down. `CommandRiskLevel` is deliberately **not** `Comparable` - a free `<` would make "is this low enough to skip the confirmation" expressible, which is the decision `CommandRiskConfirmation` exists to keep in one place.
- **A modal cannot be answered from a headless suite, so `applySuggestedTemplate` (confirm) and `commitSuggestedTemplate` (write) are split** - behaviour asserted by driving the write, routing asserted by a source guard that the write has exactly one production caller and that caller confirms first. The same split this codebase already uses for the other two `confirmAIAuthored` sinks. `CommandLibraryAISelfTest.savingATemplateChangesOnlyTheTemplate` used to assert `saved.risk == .readOnly`, i.e. it **encoded §5.3 as expected behaviour**; it asserts the opposite now.
- **§5.4: the redaction lives in `CommandLibraryAI.prompt`, not at the popover's call site.** At the prompt, every caller of `prompt`/`run` inherits it and a second entry point added later cannot forget it; at the call site it covers exactly one caller. Explain and Improve needed no equivalent and that is asserted rather than assumed - both send the saved `{{token}}` template and never a filled-in instance, so no captain-supplied value reaches either prompt.
- **A trap this created for every future window-backed suite: `AppLockGate` starts *locked*** (the app does, and the gate's default says so), so a console page now defers everything privileged it does on appearing. A self-test process never runs the real unlock, so any suite driving a console's appearance, focus or incident card has to set the gate unlocked and put it back - `FleetActionsSelfTest`'s save/restore is the shape. **Five** existing suites needed it: `IncidentResumeSelfTest`, `TabKeyboardShortcutsSelfTest`, `FullAppAuditUISelfTest`'s S4a, `CommandLibraryAISelfTest` indirectly, and `SRELeadPerTabSelfTest` - and that last one is the instructive case. Its `makeStartedTestConsole` starts real `.ssh` children through the real `viewDidAppear` path, so an unstarted tab means its child never runs, never exits, and the `processEndedMarker` settle loop waits for a signal that can never arrive. It only failed at all because #339 had just hardened that case: the pre-hardening version measured a stable-because-empty buffer and **passed vacuously against a tab that never started**. A sixth suite that forgets will fail with something that reads like a real defect - or, worse, quietly stop testing anything.
- **Deliberately recorded rather than silently widened**: a page that appeared while *unlocked* keeps `hasAppeared` through a later lock, so `processTerminated`'s auto-reconnect timer would re-establish a dropped `ssh` - and re-prompt for Touch ID - behind the overlay. Every other route to `addTab` was traced and is already gated (the palette and notification actions by their own cases, the tab keystrokes by §5.2's, every menu item by `setContentMenusEnabled`, and `ScheduledActionKind` opens no tab). That one is the same harm class but not what §5.1 found, and gating it needs a resume story for the tab left dead afterwards - see `runAppearanceWorkIfUnlocked`'s own doc comment.

**`fm/grandline-audit2-feature-enhancements` closed §6 of `data/grandline-full-app-audit-2/report.md`** - and its first job was establishing that **six of its ten items were already closed** by #337/#338/#339/#340, because §6 is explicitly a list of the *enhancements that complete* findings filed in the earlier sections rather than a separate body of work. Three were genuinely open, and one of the three turned out to be two problems.

- **§6.2's structural lock-gate guard is the item with the most leverage, and the reason is what the *existing* coverage could not do.** #340 answered §5.1/§5.2 with targeted cases plus `Audit2SecurityFixesSelfTest.test_gateCallSites` - a hardcoded seven-entry list of the sites that had been *found*.   - **An exemption must name where the gate really is, and the guard resolves that claim** - it is not an allowlist. `DictationHotkey` forced this shape and is the honest case: its gate is real but lives at the *consumer* (`main.swift`'s `onDown` closure), because the monitor only reports a key transition.   - **The other two monitor exemptions are `AppLock` itself (gating it on the gate it feeds is circular - a locked app that stopped watching for activity could never re-arm its own idle timer) and `CockpitTerminalView`** (a keystroke timestamp for `lastUserActivity` plus drag-vs-selection inside one view under the overlay - and suppressing it while locked would make the SRE Lead/kube bridges *less* careful about injecting while the captain types, not more).
  - **`AppLockGate.registerLockDismissiblePopover` is the mechanism the guard made necessary, and it is deliberately not `registerSecondaryWindow`.** Building the guard found that `closeLockSensitiveSurfaces()` covered exactly one of the app's nine popovers - the incident card - so eight others left open when the lock fires stayed readable and interactive above the overlay. The idle lock implies nobody was at the keyboard; the **12h session-expiry lock fires mid-use**, which is the same reasoning that already put the ⌘K and Quick Capture panels on `registerSecondaryWindow`. Popovers get a real `performClose` **before** the window sweep, and `test_popoverClosePrecedesWindowSweep` asserts that ordering rather than leaving it to a comment: an `orderOut` behind a popover's back leaves `isShown` stuck `true` and its owner then declines to reopen it for the rest of the session. All nine self-register (weakly - there is no unregister, and a per-host `ConsoleController`'s popovers go away with its host); `popoverExemptions` is empty on purpose, so a future entry has to argue why a window above the lock overlay may stay there.

- **§6.3: the session strip's dishonesty was never that a restored page had a registry entry - it was what every surface read off it.** `HostSessionState` (`.connected` / `.restored`) is the fix, and **registering only started sessions (the audit's other option) is the wrong one**: switching *into* a restored page is correct and useful - revealing it is what connects it - so dropping it from the strip, the ⌘⌃ shortcuts and ⌘K would remove the affordance F2 exists to provide. What was wrong was the claim, not the entry.
  - **The registry stays a registry.** `ConsoleController.hasLiveSession` (`tabs.contains { $0.started }`) is the fact, reported through `onLiveSessionMayHaveChanged` from `startTab` - the one place `TabModel.started` is ever set - and from `closeTab`. Deliberately a "may have changed" ping rather than a transition event: the shell re-reads `hasLiveSession` itself, which costs one array scan and cannot get out of step with the tabs.
  - **`register` never downgrades a live entry to `.restored`, and that is load-bearing.** `connectHost` runs *before* the page appears, so it honestly reports `.restored` even for a host that is already connected - honouring that would flicker a live pill to "not connected" on every re-reveal. `setState` is the one path that moves an entry either way, and it restamps `startedAt` on `.restored` -> `.connected` so "Connected · 14m" measures the connection rather than however long the page sat unopened since launch.
  - **`isLive` and `isConnected` are different questions and both are needed.** `isLive` ("is there an entry at all") keeps the entry switchable and out of ⌘K's duplicate Hosts row; `isConnected` is what every "Connected" claim and every immediate-send decision reads.
  - **§4.5 came with it, and needed a second fix beyond the honesty.** `isHostConnected` was `hostConsoles[host.id] != nil`, so F9's picker reported a restored page connected and `sendCommandToHost` took its *immediate* branch, typing into a terminal with no process and reporting nothing. Narrowing it is uniformly correct precisely because no reader wants "the page exists"; `debugConnectedHostIDs()` resolves the real closure so the test cannot assert its own copy of the predicate.
  - **A pre-existing assertion encoded the bug as expected behaviour**, the same shape #340 found in `checkSettingsTwoColumnLayout`: `SessionRestoreSelfTest.hostPagesComeBackWithoutConnecting` asserted `isHostConnected(host)` was **true** for a restored page, two lines after proving that page had no started tab and no live child process. - **§6.8's Code Preview half could not be "just wire up the call".** `CodePreviewController.shutdown()` had zero callers for its whole life *and* carried the exact direct-`commitAndPushNow()` shape §4.3 had fixed one store over - so wiring it would have **activated** that bug here rather than fixing it. `CodePreviewGitSync.flushForTerminationNow()` is §4.3's fix applied to this store (shared serial queue, 3s bound, cancels the pending debounce inside the queue block for the reason the Sticky Board's own version records), and the two land together.
  - **The ordering inside `shutdown()` is the substance, not tidiness.** A pending edit lives only in the page's own 500ms JS debounce until `flush` posts it back over the bridge, and *that reply* is what runs `snippetChanged` -> `store.save` -> `markDirty()`. Two fire-and-forget calls would commit a working tree not yet containing the keystrokes the method exists to save. So the page flush is awaited first, bounded (`terminateEditFlushBudget`), and the git flush follows.
  - **The wait pumps the main run loop; it must not block it.** The bridge reply arrives as a `WKScriptMessageHandler` callback delivered *on the main queue*, so a `DispatchSemaphore.wait()` there would deadlock against the very thing it waits for. `applicationWillTerminate` is a synchronous last-chance hook, which is what makes `RunLoop.main.run(mode:before:)` right here - and this is the app's only production run-loop pump, so a second one wants the same justification.
  - Safe on a never-mounted page: this destination is lazily mounted but its controller and store are built eagerly, and `webView` is an eagerly-stored `let` whose `isReady` is `false` until the editor loads.
