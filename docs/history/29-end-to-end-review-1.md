## End-to-end review #1 (`fm/grandline-fix-high-severity`) - the three HIGH findings

**`data/grandline-e2e-review-fable/report.md` (firstmate-side) is the third full review of this app, and its three confirmed HIGH findings were all in the two newest features - the Poneglyph credential vault (#344) and the Straw Hat crew (#348-#361) - i.e. exactly the code no prior audit had reached.** The older, twice-audited surface, the vault crypto core, the MCP boundary and the AI write gate all came back clean. This entry is the fix; its MEDIUM findings are closed by the sibling section below, and the report's LOW/INFO findings (L1-L10) are deliberately still open.

- **H1's real lesson generalises past this feature: a transcript that is a pure function of its data cannot hold *decision* state in a view.** `StrawHatChatView.applyTheme` rebuilds every block from `messages` (correctly - styling is a pure function of the data, the same call `SRELeadChatView.applyTheme` makes), and the confirmed state lived only on the `StrawHatConfirmCard` *instance*. So a theme change or a chrome-font-scale change - both ordinary user actions, both firing `ThemeManager.reapplyCurrentTheme()`'s app-wide fan-out - replaced an already-pressed card with a fresh, fully-armed one whose own `guard !isConfirmed` passed because it was a new object, and the next press wrote a **duplicate record to the captain's stores**.
  - **`StrawHatProposal.id` (a `UUID`, minted by the parser) is the identity that makes resolution survive the rebuild**, and it is deliberately **excluded from `==`** via a hand-written `static func ==`: equality here is about content (what a suite asserts when it constructs an expected proposal) and a synthesised one would compare two fresh UUIDs and never match. Same call the vendored `Yaml` type makes for its own `quoted` field.
  - **Two guards, and they are two different guarantees rather than redundancy.** `StrawHatChatView.proposalResolutions` (keyed by that id) is the *render* half - a rebuilt card comes back in its done state; `StrawHatController.resolvedProposals` is the *write* half - a repeat confirm replays the recorded outcome and never reaches `StrawHatProposalExecutor.execute` again. Confirmed to fail independently: reverting only the render half fails four assertions about the card's state while no duplicate is written, and reverting only the write half writes a real second sticky note.
  - **`clearMessages()` and `rebuildTranscript()` had to become two methods.** The first is "New conversation" and drops the resolutions with the thread; the second is what `applyTheme` calls and must keep every one. Calling the former from `applyTheme` *is* the bug.
  - **`.failed` is deliberately not recorded** on either side: nothing was written, so re-arming the button on a rebuild is correct there (a retry is the useful next action). And a `.written` replay drops the `undo` closure rather than storing it - a replay shows no toast, so nothing would ever call it, and keeping it alive would hold a closure that removes a record the captain may have edited since.
- **H2: a `presentAsSheet` sheet is a child *window*, so it floats above the app's lock overlay - which is only a subview of the main window.** All three vault lock paths (`lockTapped`, `checkAutoLock`, `lockForAppLock`) cleared the key, dropped the reveal state and re-rendered, and left every presented sheet up; `CredentialVaultDetailController` captures the plaintext credential at construction and its Reveal button toggles masked/plaintext display of that already-in-memory value with **no reference to vault state at all**. So locking by any path left a floating sheet still holding - and still able to reveal - the decrypted secret. The self-test's revert run prints the literal secret as the failure message, which is the clearest statement of the defect there is.
  - **`dismiss(_:)`, never `orderOut`**, and this is why the gate registration is `AppLockGate.observe` rather than `registerSecondaryWindow`/`registerLockDismissiblePopover`: those two dismiss a window or an `NSPopover` *for* you, and ordering a sheet's window out behind AppKit's back leaves `presentedViewControllers` believing it is still up - the same stale-presentation class `registerLockDismissiblePopover`'s own header documents for `NSPopover.isShown`. A sheet needs its presenter's own `dismiss`, so the page registers the **action** with the gate instead. **Any future sheet-owning page that needs a lock gate wants this shape, not the window one.**
  - **`lockForAppLock`'s dismissal goes *before* its `guard store.isUnlocked` early return**, and that ordering is the whole point: the auto-lock timer or the Lock button can have locked the store while a detail sheet was up, so returning early on an already-locked store is precisely the case that leaves a plaintext secret over the lock screen. Its own self-test case asserts that sequence.
  - Defence in depth beside the dismissal: `detail.onReveal` refuses outright once `store.isUnlocked` is false. Both halves are needed - the guard alone leaves an already-revealed value on screen, the dismissal alone leaves any future non-dismissing path open.
  - **A real environment finding worth reusing: `presentAsSheet` works in a headless window-backed suite here** (the presenting controller's view is `window.contentView` on an ordered-front, far-off-screen window), so `presentedViewControllers` really populates and a sheet's own buttons can be driven. The case still prints a NOTE and skips rather than passing vacuously if a future environment cannot manage it - `WhiteboardViewSelfTest`'s convention.
- **H3: the caller must not be the one hopping to a background queue, and that is now stated in the store's own signature.** The Settings sheet ran the whole synchronous `store.changeMasterPassword` on `DispatchQueue.global`, but the method did its state mutation and its `onChange?()` inline on that thread - and `onChange` is `CredentialVaultController.render()`, **a full AppKit view rebuild off the main thread**. Compounding it, the auto-lock `Timer` runs in `.common` mode (so it fires even while the modal Settings sheet is up) and locks on **main**, mutating the same `vaultKey`/`file`/`auditLog` concurrently.
  - The fix is `unlock`/`finishUnlock`'s own split, applied one method over: `changeMasterPassword(currentPassword:newPassword:completion:)` derives both keys **and seals the new verifier** on a background queue (all three are pure functions of their inputs and touch none of the object's state), then hops to main for the verifier check, every mutation, `persist()`, the Keychain removal and `onChange?()`. `dispatchPrecondition(condition: .onQueue(.main))` on both the entry point and `finishPasswordChange` is what keeps it that way.
  - **`finishPasswordChange` re-reads `file` after the hop and checks its KDF salt, rather than carrying the pre-hop copy - and that guard is load-bearing, measured rather than argued.** Reverting just it (carrying the file across, which is what the old fully-synchronous method did by holding `onDisk` as a local) reproduces real corruption in the self-test: the vault gets re-keyed to a password the captain was never told applied, the credential is gone (the concurrent `lock()` had already cleared the in-memory arrays that `persist()` then wrote), and the original password no longer opens it. Salt is the right field to compare because an ordinary write re-persists the items and leaves the KDF header alone, so it is exactly the test for "is the key I derived still the key this file needs".
  - The outer `do`/`catch` is gone from the main-thread half because nothing there throws any more; `persist()` keeps its own inner one, since its failure is the one this method rolls back rather than merely reports.
  - **The threading assertion that works: capture `Thread.isMainThread` inside `onChange` and assert every fire.** `onChange` is fired from the same statement sequence as the mutation, so that one check covers both - and it is what fails (`got [false]`) the moment the pre-fix shape comes back. A test asserting only the completion's thread would pass against the defect.
- **Verified by `swift build` (clean debug and release, zero warnings in this app's sources), the release binary confirmed to carry no `FM_RUN_*` strings, and the full `./Scripts/run-all-tests.sh` run (131 passed / 0 failed / 1 documented skip, `fm.themeID` unchanged) - without launching the app**, per the README's worktree rule: the captain's real packaged instance was running throughout and shares this bundle identity. **Six injected regressions each reproduced by name** (scripted file copies, never `git stash` - see this file's own warning about the shared stash stack): H1's render half, H1's write half, H2's dismissal (which reported the plaintext secret itself), H2's reveal guard, H3's off-main `onChange`, and H3's stale-file re-check.

## End-to-end review #1 (`fm/grandline-fix-medium-severity`) - the five MEDIUM findings

**The sibling of the section above: same report (`data/grandline-e2e-review-fable/report.md` §4), the five confirmed MEDIUM findings.** Its LOW/INFO findings (L1-L10) are still open. Read that section before extending any of this - and note that four of the five were in the credential vault, i.e. the same never-before-audited feature the HIGH findings came from.

- **M1 is the one worth internalising, because the bug was a *correct* function that the wrong caller invoked - and a self-test that asserted the bug was right.** `CredentialVaultStore.lock` called `CredentialVaultClipboard.abandonPendingClear()`, which cancels the auto-clear timer and never touches the pasteboard, on the reasoning that "a locked vault has no business reaching into a pasteboard the captain may since have filled". That concern is real and was **already handled one level down, and better**: `clearIfUntouched` no-ops unless `NSPasteboard.changeCount` still reports this app's own copy, so it physically cannot clear somebody else's content. Abandoning instead inverted the outcome exactly - copy a secret, lock inside the clear window, and the pending clear was cancelled while the secret stayed on the pasteboard indefinitely. **Locking, the one action whose entire purpose is to stop disclosing secrets, made the clipboard less safe than not locking.** `lock` calls `clearNow()` now.
  - **`abandonPendingClear` is deleted, not left unused.** After the fix it had zero production callers, and leaving it would be a loaded gun aimed at this same regression - the whole failure mode was one call site reaching for the un-guarded variant.
  - **The suite had a case pinning the old behaviour** (`"abandonPendingClear should cancel the timer without touching the pasteboard"`), i.e. it encoded the finding as expected behaviour, which is why a suite this thorough shipped it. It is **inverted**, per this file's own repeated precedent (`SessionRestoreSelfTest`, `checkSettingsTwoColumnLayout`, `checkPersona`). A new case then drives the real store: copy → `lock()` → the pasteboard no longer holds the secret; and copy → someone else copies → `lock()` → the other value survives.
  - **Two guarantees, and a behavioural check only covers one.** "`clearNow` clears" and "`lock` calls it" are different failures - the shipped bug was the second - and "locked and cleared" is indistinguishable from "locked, and the pasteboard happened to be empty" to a test that looks a moment later. So a source guard asserts `lock` names `clearNow()` and that nothing reintroduces `abandonPendingClear`.
- **M2: `CredentialVaultClipboard.writeConcealed` is now the *only* place this app puts credential material on a pasteboard, and that is the fix rather than a tidy-up.** A bare `setString` makes a copied password an ordinary clipboard item, which Universal Clipboard syncs to other devices (contradicting the feature's deliberate `ThisDeviceOnly` Keychain posture) and clipboard-history managers archive (outliving the 20s auto-clear entirely). Two copy paths existed and **both** were unmarked - the secret copy and `CredentialVaultController.copyAccount`, which had hand-rolled its own `NSPasteboard.general.clearContents()`/`setString` pair. One shared writer is what stops the *next* copy path shipping unmarked, which is exactly how the account one did; a source guard asserts no vault file contains a bare `NSPasteboard.general.setString` and that exactly one `setString(` exists in the whole feature.
  - **The three markers buy different things and the doc comment says so rather than implying one guarantee.** `org.nspasteboard.ConcealedType` is the documented nspasteboard.org convention history managers honour - the load-bearing one. `org.nspasteboard.TransientType` covers a manager that honours transience but not concealment. `com.apple.is-sensitive` is the Apple-side marker aimed at the Universal Clipboard half and is recorded as **unverified best-effort**: not a public API constant, and a real two-device Handoff sync was not testable here. `org.nspasteboard.AutoGeneratedType` is deliberately omitted - it means "not produced by a user selection" and the captain pressed Copy, so writing it would be a false statement for no gain.
  - **An account is copied concealed too**, even though it is not the secret half: it is half a credential, and there is no upside to syncing production usernames to other devices.
  - **`changeCount` is read after every write, and the ordering is load-bearing.** `clearContents()` is what increments it, so the string and all three markers share one count - which is exactly the count this class's entire guard depends on having recorded. A test asserts that equality, because getting it wrong would silently disable the auto-clear.
  - **Only the pasteboard can show this.** The marker payload is empty `Data`, so a `setData` that silently did nothing looks identical in a diff and identical on screen; the suite reads `pasteboard.types` back.
- **M3: `SensitiveFile` (in `PersistenceFailureReporter.swift`, beside `AtomicWrite`) is the one definition of "only this account may read it", and `AtomicWrite.data(_:to:sensitive:)` is how a store opts in.** Every store wrote with no mode set, so files landed 0644 and directories 0755. `hosts.json` (addresses, usernames, ports, jump hosts, port forwards) and `keys.json` (public keys, SHA256 fingerprints, certificates) are **plaintext**, and the vault's KDF salt and round count sit in cleartext beside its ciphertext.
  - **The threat model is narrow and is stated rather than oversold.** Measured on the captain's own machine: `~/Library` and `~/Library/Application Support` are already `drwx------`, so another local account cannot traverse to the stores kept there whatever their mode. What this buys is defence in depth where the cost of being wrong is highest, plus real protection for the copies **outside** that umbrella - `VaultRecipeGit`'s secret-name inventory lands in the dotfiles repo under a `drwxr-xr-x` home directory and was genuinely world-readable, making it the most exposed of the lot and the one the report did not name.
  - **Seven sites, not the three the report listed**, found by sweeping every production write: the vault file + its own directory, `keys.json`, `hosts.json`, `snippets.json` (shell text that in practice carries hosts and pasted tokens), `VaultRecipeGit`'s recipe, `BackupUI`'s `.glbackup` export (it aggregates hosts + snippets + all key metadata into one file), and the `.corrupt-` backups.
  - **Directory first, then write, then file** - the ordering is the only subtle thing here. `.atomic` lands the bytes via a rename, so the final file cannot be *created* with the mode already set, only tightened after, which leaves a readable window. Narrowing the directory to 0700 first closes that window for every other account regardless of what the file wears for those microseconds, and repairs a directory an earlier build already made 0755.
  - **Two directories are deliberately left alone, and both would have been wrong to touch**: `BackupUI`'s (the captain's own Downloads/Documents, chosen in an `NSSavePanel` - not this app's to narrow) and `VaultRecipeGit`'s folder (a tracked directory inside the captain's config repo that `rebuild.sh` and git reach into; the filename is not the secret). Likewise the vault's `withIntermediateDirectories` **parents** - on the git-synced path those are the config clone itself.
  - **`.corrupt-` backups needed their own fix and their own case.** `copyItem` carries the source's mode across, so once a store writes 0600 its backups follow for free - but a file written by a pre-fix build is 0644, and **nothing ever rewrites a `.corrupt-` file**, so it would keep that mode forever. The case seeds a genuinely 0644 original, or it proves nothing. **It also caught a real gap in the fix itself: there are two backup paths**, `StoreLoadFailure.backUp` (shared) and `HostStore`'s own older inline copy, and only the shared one had been patched.
  - **The scope half is asserted too.** A benign store (`schedules.json`) is checked to *keep* its default mode - M3 is about credential and connection material, and quietly tightening every store would be churn presented as security.
  - **`SensitiveFile.restrict` is best-effort and non-throwing on purpose**: the bytes are already safely on disk by the time it runs, so failing a write over a mode change would turn hardening into a data-loss risk. It logs (GL-11) and deliberately does *not* go through `PersistenceFailureReporter` - the captain's data is not at risk, so it is not that surface's "your save failed" alarm.
  - **What it cannot do, recorded rather than half-done:** a `git checkout`/`pull` that updates the vault file recreates it honouring the umask, so a copy arriving from another machine is 0644 until this app next writes it. Git tracks only the executable bit, which is also why tightening a tracked file is safe and never shows as modified. Closing that gap means chmod-ing on read as well, which is broader than this finding.
- **M4: `ci.yml`'s `generated` job runs the `--check` of every generator whose inputs live in this repository.** Drift in a generated Swift file **compiles cleanly** - it is a valid file either way - so nothing but a human remembering stood between a hand-edit (or a forgotten regen) and shipping a stale artifact. Three are in scope: `build-card-shortcut-icons.py`, `build-rail-icons-batch2.py`, and `build-whisper-metal-shader.py`, which **gained a `--check` in this task** (it had none, needs no Pillow, and reads only vendored in-repo sources, making it the cheapest of the four).
  - **Two are deliberately excluded, with reasons in the job's own comment**: `build-straw-hat-flag.py`/`build-straw-hat-portraits.py` read source images from firstmate's `data/` outside this repo, so `--check` would fail for the environment rather than for drift (the report's own L1 finding - closing it needs a decision about committing those images, not a CI step); and the Monaco/Excalidraw bundle rebuilds need a full npm install of an unpinned transitive tree, where a "drift" failure would as often mean "npm resolved a different patch today".
  - **Every `--check` was verified in both directions** - clean exit 0, and exit 1 with a named file after appending one comment line to a committed artifact. A `--check` that only ever passes is worth nothing.
  - **Pillow is pinned in that job, and the job's own first run is why - this is the lesson worth carrying.** A byte-for-byte `--check` on an icon *re-encodes* a PNG, and PNG compression output depends on the Pillow build, so an unpinned install makes the guard non-deterministic. Measured rather than guessed: the committed icons match under **11.3.0**, and **12.3.0 changes exactly one** of the 19 rail icons (`PostmortemsIcon.swift`) from an identical source PNG with identical pixels. Unpinned, the job failed on its first real run for that reason alone - which is the same "a drift failure would as often mean the toolchain moved" flakiness the job's own comment rejects the npm bundle rebuilds for, shipped by accident one library over. **Regenerating an icon with a newer Pillow means bumping that pin in the same commit.** A local run can hide this: this machine's `python3` is 3.9, which caps at Pillow 11.3.0, while `setup-python` on CI resolves 12.x - so "it passes locally" says nothing about which library the artifact was built with.
- **M5 (the version frozen at `0.1.0` for 130 commits) is a captain action by his own decision, not a code change.** He chose `0.2.0` and chose to push the tag himself after this merges, because pushing a `v*` tag **triggers `release.yml` to build and publish a real GitHub Release** - outward-facing, and not a crewmate's call. The exact command is in this task's PR description. `build_native_app.sh` needs no change: it already derives `CFBundleShortVersionString` from `git describe`'s leading dotted number (GL-18), so the tag alone moves the shipped version and gives the F3 self-update check something newer to see.
- **Verified by `swift build` (clean, zero warnings in this app's sources), both affected suites, the full `./Scripts/run-all-tests.sh` run, and each `--check` driven in both directions - without launching the app**, per the README's worktree rule (the captain's real packaged instance shares this bundle identity). **Six injected regressions each reproduced by name** (scripted file copies, never `git stash` - see this file's own warning about the shared stash stack): `lock` no longer running the guarded clear (3 named failures, including the source guard), the concealment markers dropped (all 4 marker assertions), the account copy reverted to its bare `setString` pair, the sensitive file mode dropped (5 failures), the sensitive directory mode dropped, and the vault's own root hardening removed.
  - **A seventh injection initially reproduced NOTHING, and the suite was strengthened rather than the finding dropped.** Removing `CredentialVaultStore.createVaultRoot`'s hardening changed no assertion, because `AtomicWrite`'s own directory pass re-hardens the same directory the moment the vault file is written - two mechanisms overlapping, so the store's own was untested. The added case asserts the mode **at construction, before anything is written**, which is the only window where the store's own hardening is the only thing doing the work. That shape of overlap is worth looking for whenever a fix lands in two places.

## End-to-end review #1 (`fm/grandline-fix-low-info`) - the LOW/INFO findings

**The last of `data/grandline-e2e-review-fable/report.md` - §6's L1-L10 plus both INFO items** (its HIGH findings shipped in #366, four of five MEDIUM in #367, and M5's version tag is the captain's own action). What is worth carrying forward:

- **L6 was a false positive, and the mechanism it missed is worth knowing before re-filing it: `ConsoleController.isConsolePageOnScreenForPeriodicWork()` IS the idle gate.** Its third clause is `!AppActivityState.shared.isBackgrounded` - so the herdr poll it guards stops entirely after the app has been inactive for `backgroundThreshold`, rather than merely slowing the way `BackgroundSignalsPoller`/`FleetNotifier`/`ShiftGitSync` do with a `BackgroundedPollGate`. Verified against the reviewed commit itself (`git show d5215ad:...`), not just HEAD. `ConsoleController+Herdr.startHerdrStatusPolling`'s doc comment now spells that out, because the call site reads as visibility-only and a second `AppActivityState` check beside it would be the same condition written twice. **The API is `isBackgrounded`, not `isActive`** - the report and several briefs name the latter, which does not exist.
- **L4 was answered by stating the scope rather than persisting the throttle, and the reasoning is on `CredentialVaultStore.attemptsBeforeThrottle` so nobody "completes" it by accident.** The only cleartext metadata this store keeps is the vault file's own header, and that file is **committed and pushed to `manjesh-config` on every change** - so persisting `failedAttempts`/`throttledUntil` there would publish a failed-attempt count and timestamp to a git host in cleartext (against the posture `CredentialVaultFile.settings`' own comment states) *and* produce a commit plus a push on every mistyped password. It cannot go in the encrypted `settings` blob either: sealing that needs the vault key, which a failed unlock by definition does not have. A local sidecar avoids both and is trivially deleted, so it would not make this a control while adding a file, its GL-01 handling, an `FM_*` override and a `main.swift` redirect entry. And an attacker with the file never touches this code path - they run PBKDF2 offline. **If it should ever become a real control, the honest version is a slower KDF (the rounds are already in the file and tunable), not a counter.**
- **L1 put `build-straw-hat-flag.py`'s reference image in the repo (`native/Scripts/assets/straw-hat-flag/`, the icon-batch convention) and wired its `--check` into CI's `generated` job** - that job's own comment had named L1 by name and said closing it "needs a decision about committing those images". Regenerating from the committed copy produced a **byte-identical payload** (Pillow 11.3.0, the pin CI already carries), so only the file's header comment moved. **`build-straw-hat-portraits.py` deliberately did NOT get the same treatment and stays out of CI**: its inputs are seven portraits embedded in a ~12MB plan-artifact HTML, which is a materially different decision from committing a 110KB PNG. Both `--check` modes are in-memory now and leave no temp file on a mismatch; both were driven in **both** directions (a `--check` that only ever passes is worth nothing).
- **The README's env-var table is guarded now, not just corrected** (`E2ETestingPolicySelfTest.checkTheReadmeEnvTableIsComplete`). It had gone stale in both directions at once - eight variables the app reads were missing (five of them the newest stores' overrides, i.e. the ones a future suite most needs to find) while `FM_MIRROR_TARGET`/`FM_BACKEND` promised overrides for a feature removed twice over. Neither direction is visible from anywhere else: a stale docs table compiles and passes every other suite. **Two traps in writing that guard:** it must strip whole-line `//` comments before scanning (the app's sources name `FM_MIRROR_TARGET` in order to explain that it is gone, and two reverted `FM_DEBUG_*` probes survive only in the comments recording what they measured - without stripping, the guard demands README rows for three variables nothing reads, one of which this batch deliberately deleted); and only a line beginning with a pipe-and-backticked `FM_` (i.e. a real table row) counts as documentation, or the prose explaining a removal reads as a row and the guard insists the dead variables come back.
- **L5's rollback forces `touchIDUnlockEnabled = false` rather than restoring a captured value, and its guard is a source check for a stated reason.** The forward path removes the stored Keychain key unconditionally (it held the *old* derived key), and the rollback has no key to write back - so `false` is the only value describing what is on the machine. Reaching the interesting case behaviourally (`hadStoredKey == true`) needs a **real login-Keychain write**, and `FM_RUN_CREDENTIAL_VAULT_TESTS` is pure logic that runs in CI where there is no unlocked keychain - the same rule `FM_RUN_CREDENTIAL_PATH_TESTS` states for itself. So the post-condition is asserted behaviourally and the *absence of `previousTouchID`* as source.
- **L2/L7/L9's fixes each needed their test written a particular way, and the first draft of two of them was wrong:** a second `debugRenderReply` inside `StrawHatViewSelfTest.checkContributingGlow` changes what "the most recent reply" means for every assertion after it (it broke three), so L9's caption check got its own mount; and L2's "an unreadable docs folder prints no count" is only half - the other half is that a **readable but empty** store still prints its real zero, or the fix is indistinguishable from "never print the count". L7 needed a `delay` knob on `writeFakeClaude`, because a turn already in flight is the only way to reach `startNewConversation`'s guard through the real path.
- **`StrawHatChatView.setComposerText` must fire `textDidChange`**, not just set `string`: Send's enablement and the placeholder's visibility are both driven from that notification, so a composer handed real text with a disabled Send beside it is the failure mode - and L7's whole promise is that recovery is one press.
- **The window title comes from `CFBundleDisplayName` now** (`AppDelegate.windowTitle()`), so the sanctioned probe app's own plist ("Grand Line Probe") makes a probe screenshot self-identifying - it used to hardcode the real app's name, which is a genuine review hazard in a repo with no process isolation between builds sharing a bundle identity. The fallback chain to `CFBundleName` then the literal exists because a plain `swift build` binary has no `Info.plist` at all.
- **The other INFO item (~1MB of base64 icon literals, ~38KB per new destination icon) was looked at and deliberately left alone**, per the report's own conclusion: it is a documented tradeoff (`actool` is absent from a CLT-only toolchain), decode is lazy and cached, and only the ~6 quick-access icons decode at launch. Worth watching as the icon set grows, not worth changing.
- **Inserting a Swift doc-comment block by anchoring on a `static func` declaration splits the *previous* declaration's own doc comment** - the helper landed between `defaultWindowFrame`'s comment and its `func`, silently re-parenting half that comment. Anchor on the first line of the preceding doc comment instead. And in a Python heredoc writing Swift, `"\n"` in a non-raw string becomes a real newline in the output - which is an unterminated Swift string literal, caught only at build time.
